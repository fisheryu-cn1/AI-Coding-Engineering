## 1. 背景与规模前提

- 当前语料实测：433 文件 / 约 290 篇可解析文档（103 PDF + 137 md + 25 txt 等）；按"不超过当前 3 倍"约束，上限约 **900 篇文档、2–5 万 chunk**。
- SQLite FTS5（trigram）在 GB 级文本上为毫秒响应；该规模下不存在需要 ANN 向量索引解决的召回性能问题。
- 架构解耦事实（目标态可恢复性的依据）：`Chunk.embedding_id` 为可空 join key（05 §2.2）；图库只用标准 Cypher 子集、不用内置向量（05 §11-3）；向量库不存正文（05 §2.2）；`embedding.backend` 本为分层配置（05 §4.1）。

## 2. 无向量 MVP 检索架构（03 §5.1 的 M3 实施口径）

```
查询 → 查询理解（LLM 可选：改写 + 提取主题词 + 同义/中英扩展，§2.3）
     ├─ 全文路：FTS5 trigram（chunk 级召回 → 聚合到 section，§2.2）
     └─ 图路：结构导航（topic/标题命中 → section 列表，§2.1）
     → RRF 融合（两路统一为 section 粒度排名列表，rrf_k=60 沿用 retrieve 配置）
     → LLM 重排（可选，§2.4）
     → 输出 [{doc, section_path, 摘要层, 锚点, 得分}]（FR-3.5）
```

### 2.1 图路（结构导航）的确切语义

**回答的问题**：主题/结构约束型查询——"X 主题下有哪些资料"、"标题/章节名里带 X 的内容在哪"。它不是独立的相关性召回器，而是**主题命中驱动的结构下钻 + FTS 结果的主题分组信号**。

- **输入与主题词匹配**（三轮评审 #5，离线归一化补全）：
  - **统一归一化** `norm(s)`（查询串与 `topics.name` 双向应用）：小写化 → CamelCase 拆词（`ContextEngineering`→`context engineering`）→ 连字符/下划线/多余空白归一为单空格 → trim；
  - **匹配规则**（离线档唯一入口、在线档复用）：`norm(topic)` 作为词序列出现于 `norm(query)` 中——ASCII 片段要求词边界（防 `AI` 误中 `contain` 类），CJK 片段允许子串；
  - **LLM 在线档**：查询理解提取的主题词候选同样过 `norm()` 后与 `topics.name` 精确匹配，不命中则图路空；
  - 无主题词命中时图路**输出空列表**（RRF 自然零贡献，不报错）。
  - **norm 碰撞处理**（四轮 #3）：多个主题归一化后同名（现状 `core_topics` 即含 `ContextEngineering` 与 `context-engineering`）时，图路**激活全部 norm 等价主题并取文档并集**（去重）——这与 03 §4"同名主题跨语料归并"的语义一致，碰撞组本就指同一主题域；同时 `kb topics`/`kb status` 输出对 norm 碰撞组给出提示，引导人工 `set-topic` 归并（长期约定：主题名规范化唯一，归并入 M3 收尾运维项）。
- **产出与排序**（粒度 = section）：
  1. 命中 topic → `files.topic = ?` 的文档集（`status NOT IN ('deleted','duplicate')`）；
  2. 文档序：`summary_source`（curated > auto > none）→ `files.updated_at` 新到旧；
  3. 每文档展开其 section（`fts_chunks` 按 `doc_id` 反查 distinct `section_path`，M2 无持久 chunks 表，JOIN 反查即够——见 §4.2）；
  4. 查询串命中 `title` 或 `section_path` 的 section 提前。
- **有界化与 RRF 权重**（二轮评审 #1：防"新鲜但无关"的 topic 成员淹没融合结果）：
  - **截断**：文档取 top-`search.graph.max_docs`（默认 20，按上述文档序）；展开 section 总条数上限 `search.graph.max_sections`（默认 40，标题命中者优先）——热 topic（几百篇）不会产出无界列表；
  - **加权 RRF**：`score = Σ w_i / (rrf_k + rank_i)`，`w_fts = 1.0`、`w_graph = 0.5`（可配 `search.graph.weight`）——图路定位是**主题分组/约束信号**而非相关性排序，其排序基准（摘要质量→新鲜度）不含查询相关性，必须降权参与；
  - **硬过滤例外**：`--topic T` 显式指定时图路转为**前置过滤**（FTS 仅在 T 的文档集内执行），不进 RRF——此时用户意图是约束范围而非融合排序。
- **topic 稀疏冷启动**（P3-12）：默认 `classify.topic_keywords={}` 下大量文档 `topic=NULL`、图路第一步即为空。此时图路退化为 **corpus/doc_type 导航**（按 `files.corpus`/`doc_type` 分组下钻，同样受 max_docs/max_sections 截断），并在响应中标注"主题未确认占比高，建议 `kb index set-topic` 改判"。空/短列表经 RRF 自然少贡献。
- **粒度统一的必要性与做法**：FTS 路返回 chunk 级、图路天然 doc/section 级，RRF 要求同粒度排名列表——**两路统一以 section 为粒度进 RRF**（全文路的聚合规则见 §2.2），否则融合在实现时必然返工。

### 2.2 全文路与章节级归并

- FTS5 查询：`MATCH` 于 `fts_chunks(title, text)`（§3.4 起含摘要伪 chunk）；长查询按 trigram 拆分 AND 组合（03 §5.1 原口径）。
- **chunk → section 聚合**（FR-3.5 最小定位单位为章节的前提）：同 `doc_id + section_path` 的多 chunk 命中**取 bm25 最高分**，该 chunk 即本节锚点；同 section 只输出一条。RRF 输入为聚合后的 section 排名列表。
- **排序口径**：FTS5 `bm25()` 辅助函数对 trigram 同样可用，但 trigram 把 3 字符 n-gram 当词元，tf 统计失真，排序质量弱于词级 tokenizer——**M3 接受此限制**（P1 目标态可评估 unicode61 + 自定义分词或双 FTS 表）。
- **短查询兜底**（P1-5 + 二轮 #3）：FTS5 trigram 对 **< 3 字符**的词元不命中（本域高频缩写 `AI`/`KG` 等 2 字符词会静默零召回）。按词种分两路：
  - **含 CJK 的短词**：`text LIKE '%词%'` 子串回退（中文无词边界问题），与其余词元的 FTS 结果取交集；
  - **ASCII 缩写**（`[A-Za-z0-9]{1,2}`）：**主路径走确定性缩写扩展**——扩展表 = 代码级常量 `BUILTIN_SYNONYMS`（内置本域高频缩写→全称/候选：`AI→artificial intelligence`、`KG→knowledge graph`、`RL→reinforcement learning` 等，随版本迭代）**与 config `search.synonyms` 查询期合并**（同名键用户配置覆盖内置；config 默认 `{}` 保持为空，只承载用户自定义，四轮 #2）；扩展为 ≥3 字符候选走 FTS，与原始查询结果取并集；**禁用裸 `LIKE '%AI%'` 子串**（SQLite LIKE 对 ASCII 默认大小写不敏感，`%AI%` 会命中 cont**ai**n/tr**ai**ning/br**ai**n，精度崩塌）。扩展表无命中时的兜底为空格包裹词边界匹配（`' ' || text || ' ' LIKE '% AI %'`，覆盖空格边界的独立词；标点粘连漏召回记为已知限制，P1 评估正则/词级 tokenizer 时一并解决）。

### 2.3 查询扩展与离线兜底（P1-7）

- LLM 可用：查询理解生成同义词/中英互译候选词，并入 FTS 查询（`search.query_expansion: true` 默认开）；失败静默回退原始查询。记账 `purpose='query_expand'`（§7）。
- **合成语义（v6 补，DoD 实测裁决）**：扩展词**并集增召回**——原查询按 §2.2 语义单独执行；扩展词（≥3 字符、引号消毒）另起独立 OR 组 MATCH，两结果按 `(doc_id, section_path)` 并集留最高分。扩展词**不进**原查询 AND 组（全合取会致 FTS 零命中），也不参与 LIKE 交集——扩展只加候选、绝不收缩原查询结果；排序仍由 bm25/RRF/重排负责。
- **token 预算（v6 补）**：推理模型（如 MiniMax-M3）的 think 开销计入 completion 预算，扩展/重排的小预算会被吃光导致静默零效果——`search.query_expansion_max_tokens`（默认 1024）、`search.rerank.max_tokens`（默认 1024）可配。
- LLM 不可用（未装 llm extra / 无 key）：查询扩展关闭，跨语言召回靠**确定性扩展表**兜底（代码级 `BUILTIN_SYNONYMS` + config `search.synonyms` 合并，口径见 §2.2；含本域高频词中英对）。容器型键的 `kb config set` 写入走 M2 已修的 YAML 解析口径（10 号 P3-5）。
- **口径声明**：离线档（无 LLM 且 synonyms 未配）跨语言召回显著受限——FR-3.1 已加注，这是无向量 MVP 的已知取舍，§8 ② 的恢复条件以此监测。

### 2.4 LLM 重排

- 对 RRF 后 top-K（`search.rerank.top_k`，默认 20）候选，用 09 §9 的 LLM client 打相关性分重排；失败**静默回退 RRF 原序**。`max_tokens` 口径见 §2.3（默认 1024）。
- **输出清洗（v6 补）**：LLM client 统一剥 `<think>…</think>` 闭合块与 ```json 围栏（MiniMax-M3 等推理模型实测混入 content，json_mode 不能免）；截断未闭合的 think 块不剥，交调用方解析失败走降级。
- 记账 `purpose='rerank'`；输入为各候选的 L1 摘要（无摘要回退 title + text 前 200 字符），预算见 §7。
- `embedding.backend=none` 时 `--mode vector` **显式报错**并提示"P1 目标态"；§5 另有非 none 档的启动校验。

### 2.5 related / compare 的 M3 口径（P2-9 显式登记）

- `related`（M3）：同 Topic 文档 + FTS 共词扩展 + curated summary 一句话索引信号，文档级推荐。**04 §2.1 原语义 `related <doc|entity> --hops`（实体图遍历）登记为 M5 目标态**，M3 参数实体/`--hops` 不接受（显式报错）。
- `compare`（M3）：两/多文档的 L1–L3 摘要经 LLM 组装对比表。**04 原语义 `compare "<concept>"`（按概念收集观点）登记为 P1/M5 目标态**，M3 仅支持 `--docs a,b[,c]` 指定文档。

> **M5 已交付（15 §5.1）**：`kb related`/`kb compare` 已切换为图遍历语义（M3 文档级推荐/摘要对比 → M5 图遍历）；图库不可用（backend 缺失或 schema 版本不符）时**显式报错**并引导 `kb index reindex --full`，不静默回退 M3 文档级实现。

### 2.6 检索模式与参数语义（四轮 #4）

| `--mode` | M3 语义 | 与 `--topic T` 的交互 |
|---|---|---|
| `hybrid`（默认） | §2 两路 section 粒度加权 RRF + 可选 LLM 重排 | T 转为**前置硬过滤**（FTS 与图路均限定 T 文档集，不进 RRF，§2.1） |

## 3. 自动摘要子特性（P0-2；05 §2.6 ③ 的 M3 落地）

### 3.1 生成与 L1–L3 映射

- 触发（四轮 #1 修正）：`stage_classify` 成功后，（`summary_source='none'` **或** `summary_source='curated' 且 summary_stale=1`）且 LLM 可用 → 入队 `kind='summarize'` 任务（09 §10 串行 runner 同管线执行）。
- **runner 分派**（三轮评审 #2）：summarize 任务 payload 与 parse 同形 `{"doc_id": "Dxxxx"}`；`next_task` kind 过滤扩为 `('parse','summarize')`，`_run_one` 按 `task.kind` 分派——`parse` 走现有 parse→chunk→classify 三段，`summarize` 走单段 `stage_summarize(doc_id, ctx)`。失败/锁内语义与 parse 完全一致：LLM 调用失败抛 `LLMUnavailable`（继承 `RetryableError`）走标准退避、非 LLM 逻辑错误终态、Ctrl-C `immediate=True` 立即重排队、单写锁由 CLI 持有不变、`reset_stale_running` 崩溃恢复天然覆盖新 kind。**时序保证**：summarize 由 stage_classify 成功后入队，同 doc 的 parse 任务必已 done，无需跨任务依赖机制；LLM 不可用（`ctx.llm is None`）时在入队点控制**不入队**，不产生空转任务。
- **curated 命中跳过与 stale-curated 裁决**（四轮 #1，采 **(b)**，对齐 05 §2.6 ②"回退自动摘要并提示人工重生成"的原设计意图）：
  - `summary_source='curated'` 且非 stale 的文档**不入队**（05 §2.6 集成机制 ①③ 的建库收益由此兑现）；
  - **stale-curated 处理**：生成**临时**自动摘要写 `auto_summaries/<doc_id>.md`，但 `summary_source` **保持 `'curated'`**、`summary_path` 保持指语料侧策展文件、`summary_stale=1` 保持——**provenance 不丢**；L1–L3 读取与 `$summary` 伪 chunk 文本在"stale=1 且 auto 临时文件存在"时取 auto 文件（检索连续性），否则取 curated 文件；
  - `kb status` 与 `reports/run_*.md` 列出 stale curated 清单，提示人工再策展；人工再策展（manifest 重绑定、`summary_stale` 清 0）后**删除 auto 临时文件**并重建伪 chunk 为 curated 文本；
  - 否决 (a)（纯标记待人工：检索信号断档期无兜底）与 (c)（改写 `summary_source='auto'`：人工策展 provenance 静默丢失，违背 05 §2.6"策展摘要 ≥ 自动四段式"的定位）。
- 自动四段式（对齐 05 §2.6 五段裁剪为自动生成版）：`一句话索引`（L1，~100–200 token）/ `适用场景+主要观点`（L2）/ `要点细节`（L3）；原文 L4 经锚点下钻不变。LLM 输入 = 章节树 + 各章首段（预算 `llm.summary_input_budget`，默认 12k 字符）。
- LLM 不可用：不入队 summarize——`none` 文档保持 `summary_source='none'`，stale curated 文档保持原状（检索继续用旧策展文件，待 LLM 可用或人工再策展）；检索与组装时无摘要文档 L1 回退 `title`、L2 回退首节前 200 字符（分层供给不断链，仅信号降档）。

### 3.2 存储

- 产物文件 `auto_summaries/<doc_id>.md`（数据目录下**平级新目录**，三轮评审 #3：不与语料侧 `summaries/`（curated manifest）同名嵌套，规避命名混淆）；`paths.py` 增 `AUTO_SUMMARIES_DIR = "auto_summaries"` + `DataPaths.auto_summaries_dir` 并进 `ensure_dirs()`（03 §2 布局已回写）；`files.summary_source='auto'`、`summary_path` 指向该文件——**复用 05 §2.6 ① 既有字段口径，不建新表**。
- `kb index reindex`/重解析时按 sha256 缓存复用：sha256 未变则摘要保留，变了才重生（摘要属衍生数据，NFR-5 可重建）。

### 3.3 记账与预算

- `purpose='summarize'`（枚举已有）；`llm.summary_max_tokens`（默认 800）；成本记账沿用 09 §9（`cost` 仍 NULL 待价格表）。

### 3.4 摘要进 FTS

- 决策：**摘要经伪 chunk 进 `fts_chunks`**——每文档一条 `chunk_id='<doc_id>#summary'`、`section_path='$summary'`、`title=<doc title>`、`text=<L1+L2 文本>`。重解析/重生摘要时按 `chunk_id` 幂等覆盖（先删后插，同 09 §6）。
- 由此 §2 全文路的"标题/摘要/章节文本"三信号落在同一张 FTS 表，无 Schema 变更；章节级归并时 `$summary` 伪 section 与正常 section 同规处理（锚点即文档级）。
- 持久 `chunks` 表 M3 仍不建（M2 登记口径不变）；M5 实体挂载章节时再评估。
- **`$summary` 锚点渲染**（三轮评审 #4）：检索结果中 `$summary` 命中显示为**文档级命中**（锚点 `<doc_id>#$summary`，标注"摘要"），下钻提示 `kb show <doc_id>`；`kb read <doc> '$summary'` 输出摘要产物文件全文（经 `files.summary_path` 取文件，auto/curated 同口径）；`kb show` 的章节树**不列** `$summary` 伪 section，摘要在文档摘要区单独展示——FR-3.5 锚点下钻语义由此闭合。
