## 2. MCP 服务落地

### 2.1 模块与接线

```
src/kbapp/mcp_server.py     # FastMCP 声明 + 四工具实现（薄封装 retrieve）
src/kbapp/cli/serve.py      # mcp_cmd 替换占位：ImportError 显式报错，否则启动 stdio
```

- 工具函数只做参数校验 → 调 `kbapp.retrieve`（`search` / `assembler.read_summary` / `section_tree` / `read_section` / `assemble_for_task` / `topic_panorama`）→ 装配 JSON 返回；**不含业务逻辑**。
- **doc 解析提升为 retrieve 层**：现 `_resolve_doc`（cli/search.py:72）提升为 `retrieve.resolve_doc(registry, ref)` 供 CLI/MCP 共用（MCP 不反向依赖 cli 层，CLI 改为调用它）。优先级明确为：**doc_id 精确 → path 精确 → path 后缀 / title 子串（须唯一）**；多文档歧义命中不返回"首个"，回 `DOC_NOT_FOUND`（message 列出候选路径，`suggestion` 引导 `kb_search` 或补全路径消歧）。
- **`kb_search` mode 分派**（`hybrid.search()` 只处理 hybrid/graph，hybrid.py:374 注释口径不变）：`topic-global` → 分派 `topic_panorama`（返回主题分组清单，shape 同 11 §2.6）；`vector` → `MODE_NOT_READY`；**非法 mode（非枚举值）→ `MODE_NOT_READY`**（message 列出合法枚举 `hybrid|graph|topic-global`），不走 CLI 的"未知 mode"裸退出。
- LLM 接线与 CLI 一致：`get_llm_or_none(cfg)`，有 key 即启用查询扩展/重排（`purpose` 记账沿用 11 §7）；`kb_assemble_context` 例外——走确定性路径（决策 7、§4）。
- 客户端配置（03 §7.3 回写后）：

```json
{ "mcpServers": { "graphit-kb": { "command": "kb", "args": ["serve", "mcp"] } } }
```

### 2.2 四工具契约（05 §6 的 M4 收窄口径）

| 工具 | 参数 | 返回 |
|---|---|---|
| `kb_search` | `query:str, mode:enum[hybrid,graph,topic-global]="hybrid", topic:str?, limit:int=10` | `{hits:[{doc_id, section_path, title, score, snippet, topic}], note:str}`（FTS 路 `title` 为复合标签 `{stem} \| {章节标题}`——检索展示保留 stem 有助于辨认来源文档；`note` 承载图路退化提示等诊断；`vector`/非法 mode 显式 `MODE_NOT_READY`） |
| `kb_show` | `doc:str`（doc_id 或路径/标题片段，走 `retrieve.resolve_doc`，§2.1） | `{doc_id, path, title, corpus, doc_type, topic, status, summary_source, summary:str?, sections:[{section_path,title}]}`（**`sections[].title` 为纯章节标题**——R-1 复合标签在 `section_tree` 出口剥离 stem，见 §3） |
| `kb_read` | `doc:str, section:str`（含 `$summary` 哨兵，渲染口径同 CLI，11 §3.4） | `{doc_id, section_path, text:str}` |
| `kb_assemble_context` | `task:str, budget:int=8000, topics:list[str]?` | `{context_block:str, budget:int, used:int, sources:[{doc_id, section_path}]}`（sources 仅含实际纳入的文档，§4） |

> `kb_search` 的 `mode=topic-global` 分派 `topic_panorama`，返回 `{topics:[{name, doc_count, docs:[…]}], note:str}`（非 `hits` 形状，同 11 §2.6）；`CONFIG_INVALID` 由 `load_config` 的 `ConfigError` 产出（wrapper 单独捕获，不并入 `INTERNAL`）。

```json
{ "error": { "code": "DOC_NOT_FOUND", "message": "…", "suggestion": "call kb_search to resolve title to doc_id" } }
```

M4 错误码子集：`DOC_NOT_FOUND`（含歧义命中）/ `SECTION_NOT_FOUND` / `MODE_NOT_READY`（vector 与非法 mode）/ `CONFIG_INVALID` / `INTERNAL`（兜底，message 不含堆栈；**只读路径的 SQLite busy 归此码**，message 提示稍后重试）。`LOCK_HELD` 是应用级写锁（05 §7.1），只读进程永不取，M4 不产出此码，留 P1 写工具；`EMBED_NOT_READY`/`WRITE_TOOL_DISABLED` 等随 P1 完整集引入。

## 3. 检索排序改进（DoD-7 裁决回收，12 报告 misses 归因对应）

三项均为**确定性**改进，目标是召回抽检在线档**连续两轮 ≥80%**（消除 70–80% 波动）。

- **R-1 文档标识进 FTS**（对应 `context rot` miss）：`stage_chunk` 写 fts_chunks 的 `title` 列改为 `f"{文件名 stem} | {章节标题}"`。动机：文件名 stem 携带章节文本中缺失的强信号（如 `06-Hong-Context_Rot`）；`files.title` 虽经 `_derive_title` 占位符清洗（剥离"全文/第 N 页/(无标题)"），抽取质量仍不稳（可能只剩 `Introduction` 类弱标题），不作检索标识。`$summary` 伪 chunk 维持不动（其 title 用 `files.title` 是 M3 既有口径，本次不改）。**展示/匹配出口剥离 stem**（决策 8）：`section_tree`（→ `kb_show.sections[].title`）、图路 `_enrich` 的命中标题、图路 `_sections_for_doc` 的 `query in title` 排序匹配，一律用 `title.partition(" | ")[-1]` 取纯章节标题——避免复合标签污染 `kb_show` 契约、避免 stem 造成图路"全章节恒真匹配"的虚假排序信号；FTS 路 `kb_search.hits[].title` 保留复合（§2.2）。生效需 `kb index reindex --full`（stage_chunk 从缓存重算，`--no-cache` 不必需）。
- **R-2 精确命中保护**（对应 `LLMLingua` 扩展稀释 miss）：`_fts_chunk_hits` 中**原查询语义命中**的 chunk 得分 ×`search.exact_boost`（默认 1.3，可配）再与扩展路并集——扩展只增召回、不压精确命中。实现要点：现状合并按 (doc_id, section) max 并集会丢来源（hybrid.py:115-120），须保留 provenance——**先对原查询路（`_fts_rows` 返回行）得分乘 boost，再与扩展路 max 并集**（等价于 provenance 标记、不改动合并结构与返回 shape）。`search.exact_boost` 需补入 `core/config.py` DEFAULTS["search"]（现状无此键，§5）。
- **R-3 LIKE 路分档排序**（对应 `图谱` miss）：纯 LIKE 兜底路不再一律 score=0——`title LIKE` 命中记 1.0、`text LIKE` 命中记 0.5，按 (score desc, doc_id asc) 确定性排序。

回归约束：R-2/R-3 不得改变无扩展词时的既有相对序（`test_hybrid.py` 既有断言兜底）；三项各配单测。

## 4. `kb_assemble_context` 编排设计（FR-3.2/FR-3.3）

现有 `assembler.assemble_context(registry, cfg, doc_ids, budget)` 是 doc_ids 驱动的低层装配（M3），保留不动；M4 新增 task 驱动编排层：

```
assemble_for_task(registry, cfg, task, budget, topics=None):   # 不接 llm 参数
  1. search(task, mode="hybrid", topic 逐 topics 过滤合并, limit=10)   # 不传 llm：确定性路径，无扩展/重排
  2. 按命中序取文档（去重），逐文档取摘要（read_summary；无摘要回退首节前 200 字符，沿用 M3 口径）
  3. 分层拼装 context_block（Markdown）：## 标题(doc_id) + 摘要块；char_budget = budget * _CHARS_PER_TOKEN，
     超预算即截断（先砍尾部文档，不内联原文——L4 原文以 sources 锚点供 kb_read 下钻，FR-3.3 分层供给）
  4. used = len(context_block) // _CHARS_PER_TOKEN（复用 assembler.py:23 常量，两处口径同源）；
     返回 {context_block, budget, used, sources}
```

- **确定性路径**：step 1 调 `search()` 不传 `llm`——不触发查询扩展/重排，Agent 侧延迟可预期，NFR-4 余量充足（决策 7；MCP 调用方若需 LLM 路可自行先调 `kb_search`）。
- **sources 口径**：`sources` 只含**实际拼入 context_block** 的文档（与截断严格一致——被砍掉的尾部文档不出现在 sources），不给 Agent 悬空锚点。
- `topics` 非空时对每个 topic 各跑一次 `--topic` 硬过滤检索合并去重；空则全库一次。
- NFR-4 口径：端到端 < 10s（确定性路径，实测随 DoD 记录）。

1. `kb serve mcp` stdio 握手 e2e：initialize → tools/list 恰含四工具 → tools/call 全通（集成测试用 MCP client 会话，非 mock 函数级）。

8. 全量门禁：`uv run pytest` 全绿 + `ruff check` / `ruff format --check` 全过。
9. 文档同步：milestone-log 新增 M4 节（含补充设计登记）、design README 索引、§8 回写清单执行。
