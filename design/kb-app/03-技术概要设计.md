## 2. 存储布局

数据目录（默认 `~/.graphit-kb/`，可配置）：

```
graphit-kb/
├── config.yaml            # 全局配置：资料根目录、LLM 后端、预算、主题清单、评分配置
├── sources.yaml           # 自动收集来源（FR-6.1）
├── scoring_modules/       # 用户/第三方评分插件（P1 起；MVP 仅内置 default）
│   └── default.py         # MVP 默认评分模块（embedding vs 主题质心）
├── registry.sqlite        # 注册库：文件指纹、任务、Inbox、收集台账
├── graph/                 # LadybugDB 数据库文件
├── vectors/               # LanceDB 表
├── cache/
│   └── extracted/         # 解析产物缓存：<sha256>.json（文本+章节树）
├── inbox/                 # 待审核新资料（含 metadata.json）
└── reports/               # 自动产出：文献扫描、缺口分析、任务报告
```

### SQLite 表（核心）

- `files(path, sha256, mtime, doc_id, topic, doc_type, extract_status, version, status, updated_at)` —— 指纹与登记（FR-1.5、FR-4.1）。
- `tasks(id, kind, payload_json, status, attempts, created_at, finished_at)` —— 流水线任务队列（§6）。
- `inbox(id, source, url, title, arxiv_id, sha256, relevance_score, verdict, created_at)` —— 待审核收集（FR-6.3）。
- `collect_log(...)` —— 收集台账，字段沿用 `references/arxiv_2026-07_manifest.md` 规范。

## 3. 知识图谱 Schema（LadybugDB，Cypher；经 GraphStore 适配层访问）

> **GraphStore 适配层**：全部图库访问经薄 `GraphStore` 接口（`init/add_nodes/add_edges/query/close` 等），内部实现为 LadybugDB；Schema 与查询只用 Cypher 通用特性，不依赖 LadybugDB 特有扩展。降级后端（归档 Kùzu 0.11.3、Neo4j）实现同一接口，CI 中同 Schema 双后端跑通测试（对应 02 D2 对策，接口定义见 05-详细设计方案 §4.1）。

章节级颗粒度（FR-5）的核心：实体挂载到 Section，检索最小单位为 Section。

### 3.1 节点

| 节点 | 关键属性 | 说明 |
|---|---|---|
| `Document` | `doc_id, title, path, sha256, doc_type, corpus, arxiv_id, version, authors, published, valid_from, valid_to` | 资料条目；`corpus ∈ {references, research, design}` 区分语料来源；`valid_to` 非空即墓碑（FR-4.4） |
| `Section` | `section_id, doc_id, section_path, level, title, summary, page_range, order` | 章节，携带摘要与定位信息 |
| `Chunk` | `chunk_id, section_id, text_ref, embedding_id` | 检索单元，桥接向量索引 |
| `Entity` | `entity_id, name, type, aliases, description` | type ∈ Concept / Method / Tool / Dataset / Person / Organization |
| `Topic` | `name, description` | 主题域，扁平映射目录叶子；同名主题跨语料归并（规则见下） |

### 3.2 边

```
(:Document)-[:CONTAINS_SECTION {order}]->(:Section)
(:Section)-[:CONTAINS_CHUNK]->(:Chunk)
(:Chunk)-[:MENTIONS_ENTITY]->(:Entity)          -- 词汇图与实体图桥接
(:Section)-[:MENTIONS]->(:Entity)               -- 章节级聚合（由 Chunk 归并）
(:Document)-[:ABOUT_TOPIC {confidence}]->(:Topic)
(:Section)-[:ABOUT_TOPIC]->(:Topic)
(:Entity)-[:RELATES_TO {kind, weight, evidence_section_id}]->(:Entity)
(:Document)-[:CITES]->(:Document)
(:Document)-[:SUPERSEDES]->(:Document)          -- 版本演进（arXiv v1→v2）
(:Entity)-[:SAME_AS]->(:Entity)                 -- 实体融合记录（可追溯）
```

设计要点：

- **Topic 扁平映射规则**：主题不分层，映射目录叶子名；大小写/连字符归一后归并（`references/ContextEngineering/` 与 `research/context-engineering/` 为同一 Topic），语料来源由 `Document.corpus` 区分。主题数超过 ~30 个时再引入 `SUBTOPIC_OF` 边，Schema 已留扩展位。
- **双索引同步**：`Chunk.embedding_id` 映射 LanceDB 行，`chunk_id` 映射图库节点，两侧以 `chunk_id` 为 join key（溯源 GraphIt 方案 §4.2）。
- **Chunk 文本不存图库**：`text_ref` 指向解析缓存文件 + 偏移，图库保持轻量。
- **软删除（Document 级）**：仅 `Document` 带 `valid_from/valid_to`，删除即置 `valid_to`，保留历史与时间点查询能力（溯源 API 专题）；`Section/Chunk` 经父 `Document` 级联过滤，`Entity/Topic` 为共享节点不置墓碑（详见 05 §2.2）。

## 4. 处理流水线

每阶段输入输出显式、可独立重跑；LLM 调用分层（NFR-6）。

### P1 解析（零 LLM）

输入：文件路径。流程：指纹（SHA-256）→ 命中缓存则跳过 → 按格式选解析器（D5）→ 产出 `{全文文本, 章节树[{section_path, level, title, page_range, text_span}]}` → 写 `cache/extracted/<sha256>.json`。

PDF 解析双路径，三级判定：先试 **PyMuPDF4LLM 快速路径**（毫秒级/页）——a) 文本覆盖率 < 85%（无文本层/损坏）→ 降级 **Docling** 版面分析；b) 覆盖率正常且识别出 ≥3 个标题（任意层级）→ 采用快速路径；c) 覆盖率正常但标题识别失败 → 仍采用快速路径，章节树标记 `structure=flat`（按页/段落切分），在 P3 摘要阶段由 LLM 补章节归属，不触发 Docling。Docling 也失败的标记 `extract_status=failed`，扫描版标记 `no_text` 进人工清单。注：PyMuPDF4LLM 本身内置自动 OCR（无文本层页面自动触发，依赖本机 Tesseract），OCR 能力**已具备但刻意延后启用**——属成本/复杂度取舍而非能力缺口，后续启用时无需新引入 OCR 库。

分块（在 P5 前执行）：先按章节边界，超 2048 字符再按句子切分、重叠 200 字符，Chunk 携带 `section_path`（溯源 GraphIt 分层混合分块）。

### P2 分类（Embedding 为主，LLM 仲裁）

1. 用文档首章 + 摘要段生成 embedding，与各**主题质心**（该主题已有文档的均值向量）算余弦相似度，取 top-1 且差距 > 阈值则直接定类。
2. 差距不足（新主题迹象）时，LLM 对候选主题仲裁或建议新主题名。
3. 文档类型用规则优先（manifest/路径/文件名模式）+ LLM 兜底。
4. 结果写入 `files.topic` 与 `ABOUT_TOPIC {confidence}` 边。`confidence < 0.7` 的进人工确认队列（CLI/Web 可改判）。
5. 改判与质心防震荡：改判即时生效（该文档归属立改、写审计表），但**主题质心不实时更新**——冻结至下次批量 `index run` 或月度重建时统一重算，避免"边界文档改判 → 质心漂移 → 邻居分错"的循环；同一文档改判后 90 天内不参与质心计算。

### P3 摘要（LLM）

- 章节摘要：逐 Section 生成 1-3 句；超长章节先块级摘要再归并。
- 文档摘要：由章节摘要分层合并生成，固定四段式：研究问题 / 方法 / 结论 / 与 GraphIt 的相关性（对齐 `reading-report.md` 的既有体例）。
- 摘要带 `model`、`generated_at` 元数据，供换模型后局部重生成。
- **Curated Summary 复用**：`references/<topic>/summaries/` 的预生成论文摘要（含"一句话索引/适用场景/主要观点/效果 + §锚点"）作为文档级摘要的高质量替代，命中即跳过 LLM 生成；全文/向量索引仍保留。摘要的**构建规范（五段结构 + 头部字段 + 质量要求）与命名规范（`NN[-letter]-中文短标题.md`，序号与源 PDF 一致、不带版本号）**见 05 §2.6。

### P4 实体抽取（LLM + Schema 先验，限核心域）

- 触发范围：**核心域主题内的**论文/设计方案 + 被单独标记的文档，控制总量在 15–25%（FR-2.7）。注意必须为主题与文档类型的**交集**而非并集——本库论文占比约八成，按并集会击穿 15–25% 约束。
- 核心域清单：config.yaml 中 `core_topics` 配置，默认值 `["ContextEngineering", "context-engineering", "ai-coding", "CodeGraph"]`（当前活跃研究主线）；月度报告（§8.4）将"实体密度低于均值"的主题列为待标记候选，人工确认后加入；Inbox 审核时可对单篇单独标记。
- Schema 先验：Prompt 中限定实体类型（§3.1）与关系类型（`RELATES_TO.kind` ∈ {extends, contradicts, applies, evaluates, improves-on, part-of, ...}），要求 JSON 输出并附 `evidence`（章节定位）。
- 实体融合：候选实体先与库内实体算名称 embedding 相似度，> 0.9 自动归并（记 `SAME_AS`），0.75–0.9 由 LLM 确认，< 0.75 新建（溯源详设方案两阶段法）。
- 关系冲突：同对实体同 kind 关系取证据频次高者，保留备选于边属性。

### P5 索引（零 LLM）

事务式写入：图库写入 Document/Section/Chunk/Entity 节点与边 → LanceDB 写入 chunk 向量（bge-m3）→ SQLite `files` 置 `status=indexed`。任一失败则任务标记失败可重放（§6）。

## 5. 检索引擎

### 5.1 混合检索流程

```
查询 → 查询理解（LLM 可选：改写 + 提取实体/主题词）
     ├─ 向量路：bge-m3 查询向量 → LanceDB top-k Chunk
     ├─ 图路：查询实体 → LadybugDB 子图遍历（1–2 跳）→ 关联 Section/Document
     └─ 全文路：SQLite FTS5 关键词匹配（标题/摘要/章节文本，trigram 分词）
     → 融合排序（RRF，倒数排名融合）
     → 章节级去重归并（同 Section 多 Chunk 合并）
     → 输出：命中列表 [{doc, section_path, 摘要, 锚点, 得分}]
```

全文路分词决策：FTS5 表以 `tokenize='trigram'` 建索引（D8），保证中英混合语料的召回；查询侧对 ≤3 字符的中文查询词原样匹配，长查询按 trigram 拆分后以 AND 组合。

四种模式（FR-3.1）：`vector` / `graph` / `hybrid`（默认）/ `topic-global`（主题全局：返回该主题下的文档级摘要与社区结构，用于"这个领域都讲了什么"类问题）。

### 5.2 上下文组装器（FR-3.2）

输入：任务描述 + token 预算（默认 8k）+ 可选主题/文档约束。输出：一个可直接嵌入提示词的 Markdown 块：

```markdown
## 知识库上下文（预算 8000 tokens，实际 ~6200）
### 结构化要点（来自图谱）
- [概念] Context Rot：……（来源: doc#sec 锚点）
### 相关资料摘要（按相关性降序，关系越远粒度越粗）
1. 【直接相关】标题 — 文档摘要（锚点）
2. 【间接相关】标题 — 一句话（锚点）
### 可下钻条目
- kb_read_section(doc_id, section_path) → 获取原文
```

组装规则（溯源 `design/AI代码生成上下文控制_设计分析框架.md` 四维框架与 Wiki 笔记三段式模板）：

- 按 MECW 而非标称窗口定预算；默认 8k，超预算时先砍"间接相关"层。
- 关键约束性内容（全局不变量）放块首与块尾锚定。
- 分层供给：L1/L2 摘要内联（每条 50–100 token），L3/L4 原文以"可下钻条目"形式列出工具调用方式，不内联（FR-3.3）。
- 每条信息必带锚点（FR-3.5）。

## 6. 索引更新机制（FR-4）

### 6.1 变更检测

`kb scan`（或目录监听触发）对比 `files` 表与实际目录：

| 情形 | 判定 | 动作 |
|---|---|---|
| 新增 | 路径不在表中 | 入队完整流水线 |
| 修改 | sha256 变化 | 旧节点置墓碑 → 入队完整流水线 |
| 移动/重命名 | sha256 相同、路径不同 | 仅更新 path，零重抽取 |
| 删除 | 表中路径不存在于磁盘 | 置墓碑（`valid_to`），向量标记过滤 |

### 6.2 一致性与可重放

所有流水线执行以 SQLite `tasks` 表驱动：扫描器只负责入队任务；执行器取任务、执行、更新状态；崩溃后重启自动续跑未完成任务。三存储组件不设跨库事务，靠"任务重放 + 写入幂等（以 doc_id/chunk_id 为键 upsert）"达到最终一致。

### 6.3 全量重建（FR-4.3）

`kb reindex --full [--no-cache]`：清空图库/LanceDB/FTS（可选保留墓碑历史到归档表）→ 按 `files` 表重跑 P1（命中缓存则秒过）→ P5。`--no-cache` 连解析缓存一起清除，彻底重跑。

### 6.4 嵌入式单写者并发约定

LadybugDB 与 LanceDB 嵌入式模式均为单写者。系统有三个进程入口（CLI、MCP stdio 子进程、Web UI），约定如下：

- **写互斥**：任何执行写入的命令（`index run`、`reindex`、`collect`、Inbox `accept` 等）启动时获取数据目录下的锁文件（`graphit-kb/.write.lock`，O_EXCL 创建）；已持有则报错退出并提示持锁进程 PID。`--wait` 可选阻塞等待。
- **只读入口**：检索类命令（`search`、`show`、`read`）与 MCP 服务、Web UI 以只读模式打开图库与向量库，不取锁、可与一个写进程共存。
- **Web UI 钉死**：`kb viz` 进程永远不持有写锁、永远不直接写图库/向量库。Web UI 的全部写操作（Inbox accept、实体合并/拆分、摘要重写、主题改判）统一落 SQLite 意图/任务表，由任务执行器（持锁进程）异步落图，Web UI 轮询任务状态呈现结果。
- **Inbox `accept` 的折衷**：审核操作只写 SQLite（多写者由 SQLite 自身 WAL 保证）并入队任务，不直接写图库/向量库，因此不取图库写锁；实际索引由随后的 `index run` 完成。

### 6.5 存储维护（`kb maintenance`）

LanceDB 为追加式格式，每次写产生新 table version，长期积累导致元数据膨胀、版本链遍历变慢、磁盘占用上升。`kb maintenance` 命令统一处理：

- `cleanup_old_versions(older_than=...)` 清理过期版本；
- 碎片 compaction（可选 `--compact`，合并小 fragment）；
- 报告 SQLite 注册库体积、LadybugDB 文件体积、LanceDB version 数，供容量预警。

触发方式：手动 `kb maintenance`，或并入月度 `kb report monthly`（§8.4）。默认只清理不做激进 compaction（compaction 需短暂写锁）。

## 7. MCP 服务设计（FR-3.4）

> **SDK 版本**：采用官方 `mcp` Python SDK **v1 稳定线（`mcp>=1.29,<2`）**，`uv.lock` 钉版本；v2（2026-07-28，`FastMCP`→`MCPServer` 破坏性变更）留待 P1 迁移。工具定义用 v1 `FastMCP` API，与 PrefectHQ 的独立 `fastmcp` 框架无关（对应 02 D7）。

### 7.1 工具清单

| 工具 | 参数 | 返回 | 说明 |
|---|---|---|---|
| `kb_search` | `query, mode=hybrid, topic?, limit=10` | 章节级命中列表（摘要+锚点+得分） | 主检索入口 |
| `kb_get_document` | `doc_id` | 元数据 + 章节树 + 文档摘要 | 了解一篇资料的结构 |
| `kb_read_section` | `doc_id, section_path` | 章节原文（带页码） | 下钻取原文 |
| `kb_related` | `doc_id 或 entity_id, hops=1, limit=10` | 关联资料/实体及关联原因 | 关联阅读（FR-2.4） |
| `kb_compare` | `concept, doc_ids?, limit=5` | 多篇资料对该概念的观点段落并排 | 比较分析（FR-2.5） |
| `kb_assemble_context` | `task, budget=8000, topics?` | 组装好的提示词上下文块（§5.2） | 方案编写主入口 |
| `kb_topics` | — | 主题清单及各自资料数 | 发现入口 |
| `kb_status` | — | 库规模、索引时间、队列状态 | 健康检查 |
| `kb_ingest`（写） | `paths[]` | 入队结果 | 默认关闭，`--enable-write-tools` 开启 |
| `kb_reindex`（写） | `scope, full=false` | 任务 ID | 同上 |

### 7.2 资源与提示词

- Resources：`kb://documents/{doc_id}`（元数据+摘要）、`kb://topics/{name}`（主题全景）、`kb://reports/{name}`（定期报告）。
- Prompts：`research-brief`（研究简报模板）、`compare-viewpoints`（观点比较模板），内部调用 `kb_assemble_context` 后拼接任务指令。

### 7.3 部署

stdio 为主，客户端配置示例（Kimi Code / Claude Code 通用形态）：

```json
{ "mcpServers": { "graphit-kb": { "command": "kb", "args": ["mcp", "serve"] } } }
```

HTTP 模式（可选，默认关闭）：仅供 Web UI 或远程调试，默认绑定 `127.0.0.1`，可选本地 token 校验；绑定非回环地址超出本系统设计范围（NFR-1 纯本地运行）。

输出纪律（溯源 `design/Claude-Code-context-management.md` 的紧凑化实践）：工具返回默认紧凑（摘要级），原文须显式下钻；列表结果折叠为表格而非长文本。

## 8. 自动收集子系统（FR-6，P2）

### 8.1 来源配置（`sources.yaml`）

```yaml
arxiv:
  - query: 'cat:cs.SE AND (context OR "knowledge graph")'
    topic_hint: ContextEngineering
    max_per_run: 20
  - author: "Hong, J."
web:
  - url: "https://example.com/blog-feed"
    topic_hint: industry
```

### 8.2 收集流程

```
调度触发（openclaw cron / kb collect run）
 → 查询各来源（arXiv API / 网页抓取，降级链 Trafilatura→readability→Playwright）
 → 去重：arXiv ID 去版本号 + SHA-256（对照 files 与 inbox 与拒绝名单）
 → 选择评分模块（§8.2.2）：按 (source, topic_hint) 查 config.binding
 → 相关性初评（§8.2.1）：输入 = 标题 + 摘要（无摘要降级仅标题），调用评分模块得 score
 → 三档处置：score ≥ accept_threshold → inbox(status=pending)；
                borderline ≤ score < accept_threshold → inbox(status=watchlist)；
                score < reject_threshold → 仅入 collect_log，不入 inbox
 → 下载/存档至 inbox/，写 inbox 表（含 score、scoring_module、scoring_version）
 → 生成运行报告（reports/collect_<date>.md，沿用 literature_scan 体例）
```

### 8.2.1 相关性初评打分规则（FR-6.2 落地）

**MVP 内置实现**（`scoring_modules/default.py`，即当前文档描述的方案）：

1. **输入**：候选文档的标题 + 摘要（来自 arXiv API 或网页抓取）。摘要为空时降级为仅标题，并在 `inbox.scoring_notes` 字段记 `no_abstract=true`。
2. **候选向量**：`v_c = bge_m3_embed(title + " " + abstract)`；摘要为空时 `v_c = bge_m3_embed(title)`。
3. **主题相似度**：对每个主题 t，算 `sim_t = cosine(v_c, centroid_t)`。质心是该主题已有文档 embedding 的均值（样本 < 5 篇时不参与打分，详见冷启动）。
4. **综合 score**：
   - `sources.yaml` 指定了 `topic_hint`：`score = sim_topic_hint`（单一目标主题，避免被其他主题高分稀释）
   - 未指定 `topic_hint`：`score = max_t sim_t`（取最强匹配主题的分数）
   - **多主题强相关加成**：top-2 主题 `sim` 均 ≥ 0.7 时，`score = min(score + 0.05, 1.0)`——反映跨主题论文价值
5. **降权**（04 §6 落地）：
   - 同 `(source, topic_hint)` 组合 90 天内被拒绝 ≥ 3 次：该组合下次候选 `score × 0.8`（最多一次乘，不叠加）
   - 单篇 SHA-256 入拒绝名单：永久跳过（不重复推荐）
6. **冷启动**：某主题样本 < 5 篇时，回退到"标题关键词命中主题白名单"粗排（白名单在 config.yaml 中 `topic_keywords` 配置）；样本 ≥ 5 篇后切回 embedding 打分并自动建质心。

**阈值默认值**（可在 config.yaml 中调整，§8.2.3）：

| 阈值 | 默认值 | 含义 |
|---|---|---|
| `accept_threshold` | 0.70 | ≥ 此值入 inbox(status=pending)，UI 主区显示 |
| `reject_threshold` | 0.50 | < 此值仅入 collect_log，不入 inbox |
| `watchlist_threshold` | （= reject_threshold） | < accept_threshold 且 ≥ reject_threshold 时入 inbox(status=watchlist)，UI 折叠显示 |
| `cross_topic_bonus` | 0.05 | top-2 sim 均 ≥ 0.7 时加成 |
| `min_centroid_samples` | 5 | 主题样本数 < 此值走冷启动路径 |
| `rejection_damp_factor` | 0.8 | 同 (source, topic) 高拒后 score 乘数 |
| `rejection_damp_window_days` | 90 | 降权统计窗口 |
| `rejection_damp_min_count` | 3 | 窗口内拒绝次数阈值 |

**输出到 inbox 表的字段**（§2 SQLite 表扩展）：

```sql
ALTER TABLE inbox ADD COLUMN scoring_module TEXT DEFAULT 'default';
ALTER TABLE inbox ADD COLUMN scoring_version TEXT;             -- 模块声明式版本
ALTER TABLE inbox ADD COLUMN scoring_notes TEXT;               -- 自由文本，如 "no_abstract=true" 或 "cross_topic_bonus=true"
ALTER TABLE inbox ADD COLUMN suggested_topic TEXT;             -- 评分模块推荐的归属主题（可能与 topic_hint 不同）
```

### 8.2.2 评分模块插件架构

**目标**：让相关性初评不再绑死单一算法，不同研究主题可绑定不同评分模块（如 ontology 主题用"本体关键词召回"、context-engineering 用"embedding + 引用图"），未来引入新模块不需改主代码。

**MVP 与 P1 分期**：

| 阶段 | 内容 |
|---|---|
| MVP | 仅内置一个 `default` 模块（§8.2.1）；配置接口就位但只支持调阈值；插件目录 `scoring_modules/` 预留但不加载第三方 |
| P1 | 引入插件发现（注册表）+ config 驱动的主题绑定；用户可在 `~/.graphit-kb/scoring_modules/` 放 `.py` 文件自动加载；Web 设置页可视化绑定 |

**接口契约**（Python `Protocol`，P1 落地）：

```python
class ScoringModule(Protocol):
    name: str                # 唯一标识，如 "default" / "ontology-keywords"
    version: str             # 声明式版本，如 "1.0.0"

    def score(
        self,
        candidate: CandidateDoc,        # 含 title / abstract / source / topic_hint
        context: ScoringContext,        # 含 centroids / rejection_log / topic_keywords
    ) -> ScoringResult:

@dataclass
class ScoringResult:
    score: float                                # 0.0–1.0，主分数
    suggested_topic: str | None                 # 推荐归属主题
    notes: dict[str, Any]                       # 自由元数据，进 inbox.scoring_notes
    debug: dict[str, Any] | None = None         # 可选，写入运行报告供调参
```

**注册与发现**（P1）：

- 系统启动时扫描 `~/.graphit-kb/scoring_modules/*.py`，每个文件必须暴露 `module: ScoringModule` 单例
- 内置 `default` 模块随包提供，路径 `kbapp.scoring.default`，始终可用、不可禁用
- 加载失败的模块：写 `reports/scoring_module_load_error_<date>.md`，不阻塞流水线——降级回 `default`
- 安全：插件以受限子进程或 importlib 隔离加载；禁止 `os.system` / 网络外联（仅可访问 ScoringContext 内的数据与 bge-m3 embedding）；MVP 不引入沙箱，P1 评估

**配置绑定**（`config.yaml` 示例，P1）：

```yaml
scoring:
  default_module: default
  thresholds:
    accept: 0.70
    reject: 0.50
    cross_topic_bonus: 0.05
    min_centroid_samples: 5
    rejection_damp:
      factor: 0.8
      window_days: 90
      min_count: 3

  topic_bindings:                # P1：主题级模块绑定
    - topic: ontology
      module: ontology-keywords  # 用户自定义插件
    - topic: CodeGraph
      module: default            # 仍用默认
    # 未列出者用 default_module
```

**MVP 简化**：MVP 阶段只支持调阈值（§8.2.3）+ 默认模块；插件发现/主题绑定 P1 再实现。`scoring_modules/` 目录在 MVP 中仅放 `default.py`，其他文件被忽略。

### 8.2.3 配置入口（FR-6.6）

由于当前设计**没有交互式配置界面**（NFR-1 纯本地 + 终端优先，02 D9 CLI 优先于 Web），配置入口采取"配置文件 + CLI 子命令"双轨：

- **配置文件**：`~/.graphit-kb/config.yaml` 中的 `scoring:` 段（§8.2.2 示例）。`kb init` 生成默认值；用户编辑后下一次 `kb collect run` 即生效（无需重启）。
- **CLI 子命令**：`kb config show` / `kb config set scoring.thresholds.accept 0.75` / `kb config get scoring.default_module`。CLI 内部读写同一 `config.yaml`（原子写、临时文件 + rename），保留人类可读格式。
- **Web 设置页**（P1）：只读展示当前配置 + 引导跳到配置文件路径；不做可视化编辑器（避免 YAML 边界条件在前端复刻）。MVP 不实现 Web 设置页。
- **运行时生效**：`kb collect run` 启动时读一次 config；不热更新（与 NFR-1"无独立服务进程"一致）。
- **审计**：`config set` 命令写 SQLite 审计表 `config_audit(timestamp, key, old_value, new_value, source=cli|file_edit)`，便于追溯阈值漂移。

### 8.3 审核入库（人在回路，FR-6.3）

`kb inbox list/accept/reject`（CLI）或 Web Inbox 页操作。`accept` → 移动到目标主题目录（按项目收录规范命名：`序号-作者-短标题_vN.pdf`）→ 入队流水线；`reject` → 删除文件并记录，避免下次重复推荐。

### 8.4 定期整理（FR-6.4）

月度任务 `kb report monthly`：汇总当月新增、按主题统计、生成阅读路线建议、图谱缺口分析（各主题文档数/实体密度低于均值的标出），输出到 `reports/`。

## 10. 可观测性

- 每次流水线/收集运行写 `reports/run_<id>.md`：处理清单、成功/失败、token 消耗、耗时。
- `kb status`：库规模（文档/章节/实体数）、最近索引时间、失败任务、Inbox 待审数。
- LLM 调用统一记账（模型、token、用途），支持月度成本回顾。
- 依赖漂移检查：`kb status` 附带关键依赖版本与"距最新发布版次"提示；月度报告列出需评估升级的组件（对应 02 风险表"破坏性更新"对策）。

### 10.2 首次建库成本量级估算（NFR-6 验证依据）

- 语料量：69 篇 PDF 按均 20 页 ≈ 1,400 页，约 80–100 万 token；research/design 的 Markdown 约 35 万 token；全库正文合计约 **120–150 万 token**。
- 首次全量：P3 摘要输入 ≈ 全量一遍 + 归并二遍（~165 万输入 / ~10 万输出）；P4 抽取限核心域 15–25%（~30 万输入）；P2 分类以 embedding 为主。合计约 **200 万输入 / 15 万输出 token 的一次性成本**。
- 折算：mini 级 API 模型约 ¥10–30 一次性；旗舰级 API 模型约 ¥200–600 一次性；本地 14B 级模型约 3–6 GPU·小时。embedding（bge-m3）本地推理，CPU 约 1 小时、GPU 分钟级。月度增量 < 首次的 5%。
- 结论：首次建库为一次性小额成本，月度增量可忽略，NFR-6 成立。
