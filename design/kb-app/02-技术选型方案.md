## 2. 逐项决策

### D1 实现语言：Python 3.11+

- **理由**：核心依赖（Docling、Trafilatura、LadybugDB、LanceDB、MCP SDK、LiteLLM）均以 Python 为一等公民；数据处理流水线代码量小，开发效率优先。
- **备选**：TypeScript（前端可视化部分不可避免会用，但主体不采用）。

### D2 图数据库：LadybugDB（嵌入式，Kùzu 社区继任 fork）

- **背景**：Kùzu Inc. 于 2025 年 10 月被 Apple 收购，GitHub 仓库 `kuzudb/kuzu` 于 2025-10-10 归档只读，原项目停止维护，维护转移至社区 fork。LadybugDB（"DuckDB for Graphs"，明确定位为 Kùzu 继任者）是当前最活跃的继承者：MIT 协议、嵌入式、Cypher 兼容，内置 FTS(BM25) + 向量(HNSW) + ACID。
- **理由**：
  1. 嵌入式、零独立服务，符合 NFR-1"纯本地运行"；Neo4j Community 需常驻 JVM 服务，对单机个人知识库过重。
  2. Cypher 兼容，03 文档的 Schema 与查询设计可整体平移，迁移成本接近零。
  3. 沿用 `design/Wiki与图数据库混合架构策略笔记.md` 的 MVP 选型方向（其推荐 Kùzu 的理由全部适用于 LadybugDB）。
- **风险**：项目年轻（2025-11 首个版本）、社区规模小、bus factor（核心维护者集中）。对策：Schema 只用 Cypher 通用特性，不用 LadybugDB 特有扩展（包括其内置 FTS/向量——向量检索仍由 LanceDB 承担，避免检索索引与知识关系绑死在同一个年轻项目上）；保留两个降级路径——归档版 Kùzu（API 兼容、短期可用）与 Neo4j（规模升级路径）。
- **分歧裁决**：`design/GraphIt_软件设计方案.md` 选 Neo4j（生态优先），Wiki 笔记选嵌入式（本地化优先）。本项目场景是**单机个人资料库**，规模（百级文档、万级节点）远在嵌入式图库能力内，故裁决胜嵌入式，具体产品选 LadybugDB。
- **备选**：FalkorDBLite（嵌入式 RedisGraph，生态较窄）；SQLite + 递归 CTE（图遍历表达力弱，放弃）。

### D3 向量数据库：LanceDB（嵌入式）

- **理由**：嵌入式、列式存储、与 Pandas/Arrow 生态友好；GraphIt 方案已选定，直接继承。
- **备选**：Chroma（API 简单但存储格式锁定较强）；sqlite-vec（可与注册库合一，但大规模向量性能弱）。

### D4 Embedding：bge-m3（本地）

- **理由**：中英文混合语料（中文报告 + 英文论文）表现好；支持 dense + sparse 混合检索；可本地推理（符合 NFR-2）；GraphIt 方案与详设方案的选型在此收敛。
- **备选**：bge-large-zh（中文强但英文论文偏弱）；OpenAI text-embedding-3（需联网，作可选配置）。

### D5 文档解析

- **PDF：双路径**。快速路径 **PyMuPDF4LLM** 优先——本库 PDF 绝大多数为 arXiv 原生数字版（自带文本层），直接提取为毫秒级/页，保障 NFR-4 的"30 页 < 2 分钟"；仅当文本覆盖率不足（无文本层/损坏的扫描版）时降级 **Docling** 做版面分析（其标题层级与页码输出是章节级颗粒度 FR-5 的前提，GraphIt 方案已选定）。标题结构识别不全**不**触发降级，按扁平章节处理（三级判定细则见 03 文档 §4 P1）。
- **DOCX：Docling**（仅 2 篇，成本可忽略）。
- **HTML：Trafilatura**。GraphIt 方案引用其 F1=0.958；降级链 Trafilatura → readability-lxml →（收集场景）Playwright（溯源 `design/API文档知识图谱构建专题设计.md` §1.2）。
- **Markdown：markdown-it-py** 自建标题树解析，天然有 `section_path`。
- **TXT**：直接读取。

### D6 LLM 调用层：LiteLLM

- **理由**：统一 OpenAI 兼容接口，一行配置切换 API（Claude/GPT/DeepSeek 等）与本地 Ollama，支撑 NFR-6 的成本-质量权衡；带结构化输出（JSON mode）能力，满足实体抽取。
- **不采用** LangChain 全家桶：只需要模型调用与 JSON 输出，不引入重型抽象（溯源：详设方案与 GraphIt 均主张自建流水线）。
- **使用纪律**：结构化源（arXiv API、Markdown 标题、manifest）直接解析零 LLM 调用；LLM 仅用于摘要、分类仲裁、实体抽取与确认——这是三份设计文档独立得出的共识。

### D7 MCP 服务：官方 Python SDK（FastMCP）

- **理由**：官方 SDK 跟进协议演进；FastMCP 声明式定义工具，几十行即可暴露一个工具；stdio 传输被 Kimi Code / Claude Code 等客户端原生支持。
- **传输**：stdio 为主（本地子进程，零网络面）；streamable HTTP 作为可选模式（供 Web UI 或远程调试）。
- **HTTP 模式安全姿态**：默认关闭；开启时默认绑定 `127.0.0.1`，可选本地 token 校验；绑定非回环地址超出本系统设计范围（NFR-1 纯本地运行）。

### D8 元数据注册库：SQLite

- **理由**：文件指纹表、任务状态、来源管理、Inbox 队列都是关系型数据，SQLite 零服务、事务可靠；与图库职责分离——SQLite 管"处理状态"，LadybugDB 管"知识关系"，避免把流水线状态塞进图里污染知识模型。
- **全文检索补充决策**：03 §5.1 的全文路基于 SQLite FTS5，但语料为中英混合（中文研究报告 + 英文论文），FTS5 默认分词器对中文无效。建表时显式使用 `tokenize='trigram'`（SQLite ≥ 3.34，中英兼顾：英文按子串匹配略笨但可召回，中文三gram 切分有效）；不使用默认 `unicode61`。
- **备选**：全部入图（否决，理由同上）。

### D9 CLI：Typer + Rich

- **理由**：Typer 类型注解声明命令、自动生成帮助；Rich 输出表格/树/进度条，适合章节树与检索结果的终端呈现。

### D10 Web 可视化：FastAPI 只读 API + Cytoscape.js

- **理由**：FastAPI 复用 Python 栈，与 MCP 服务共享检索层代码；Cytoscape.js 图交互成熟（布局、着色、下钻、框选比较），静态前端无需构建链。
- **离线约束**：Cytoscape.js 等前端静态资源**随包内置（vendored）**，不依赖 CDN——NFR-1 要求纯本地运行，前端资源不能成为联网例外。
- **备选**：pyvis（交互弱）；Sigma.js（大图性能更好但 API 较底层）；Neo4j Bloom（绑定 Neo4j，与 D2 冲突）。
- **规模预案**：万级节点内 Cytoscape.js 足够；若未来超限，后端做子图裁剪（按主题/跳数），不在浏览器渲染全图。

### D11 调度：openclaw cron + CLI 手动触发

- **理由**：用户明确要求依赖本地 openclaw 定时任务；不引入常驻调度进程（APScheduler），定时触发实际等价于"openclaw 定时执行 CLI 命令"，调度与执行解耦，任务幂等由 CLI 侧保证。
- **手动入口**：同一 CLI 命令（如 `kb collect run`），保证两种触发路径行为一致。

### D12 流程框架：自建轻量流水线

- **不采用 Microsoft GraphRAG**：不支持增量更新（GraphIt 方案已论证）。
- **不直接采用 LightRAG**：借鉴其双层检索与增量算法思路，但其存储抽象与本项目的"SQLite + LadybugDB + LanceDB 三件套"不匹配，自建更省。
- **自建范围**：五个流水线阶段（解析→分类→摘要→抽取→索引），每阶段单一职责、可独立重跑，代码量预估 < 3k 行。

## 3. 部署形态

```
单机本地，无常驻服务（除可选的 Web UI / MCP HTTP 模式）
├── CLI（Typer）：全部功能的入口，含索引、检索、收集、审核
├── MCP 服务（stdio 子进程）：由 Agent 客户端按需拉起
├── Web UI（uvicorn 按需启动）：可视化与审核界面
└── openclaw cron：定时调用 CLI（收集、增量更新、报告）
```

数据目录默认 `~/.graphit-kb/`（可通过配置指向项目内），原始资料目录只读引用，不做拷贝（遵循项目"canonical PDF 只存一份"的收录规范）。

## 4. 风险与对策

| 风险 | 对策 |
|---|---|
| LadybugDB 项目年轻、bus factor，或 Kùzu 系 fork 社区进一步分裂 | Schema 只用 Cypher 通用特性，不用特有扩展；降级路径：归档版 Kùzu（短期）→ Neo4j（规模升级）；图数据可由原文+缓存全量重建 |
| 本地 Embedding 首次下载模型（~2 GB） | `kb init` 时引导下载；支持 API Embedding 兜底 |
| LLM 摘要/抽取成本随库增长 | 分层策略：结构化零 LLM；摘要仅对新增/变更；抽取限核心域 15–25% |
| 多组件（SQLite/LadybugDB/LanceDB）写入一致性 | 以 SQLite 任务表为准的 WAL 式流水线：先记任务、后执行、失败可重放（见概要设计 §6） |
| 嵌入式存储单写者冲突（CLI/MCP/Web UI 并发打开） | 进程级互斥锁文件 + 只读打开模式（见概要设计 §6.4） |
| 解析器对扫描版 PDF 无文本层 | 快速路径校验失败后降级 Docling；仍无文本则标记 `extract_status=no_text`，列入人工清单，不阻塞流水线（OCR 列为可选增强，不进 MVP） |
