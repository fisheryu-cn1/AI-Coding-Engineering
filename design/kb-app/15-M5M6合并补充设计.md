## §1 合并可行性分析

### 1.1 结论

可以合并。推荐**方案 B：合并为一次里程碑，内部四阶段**。

### 1.2 论证

1. **前端契约与图 schema 强耦合**。M6 图谱页的节点/边模型（04 §3.3：Document/Section/Entity/Topic 四类节点——Chunk 为存储层节点、不上图谱页渲染）直接是 M5 图 schema 的投影；`kb related`/`kb compare` 与图谱页的路径高亮共用同一套 Cypher 查询。分开做，M6 图谱页只能对假数据空转，M5 抽取质量则失去唯一的人审回路——实体归并、关系冲突的验收本来就要靠图谱页"看出来"。
2. **依赖落地与只读服务可以共享**。ladybug（图库）、FastAPI（只读服务）、G6 vendor 三件事在同一次环境变更中落地，一次评审覆盖，避免两次依赖评审。
3. **可并行的工作面足够大**。检索/文档/状态三页只依赖 M1–M4 已落地的 SQLite+FTS，与 M5 图流水线天然并行；合并后不是简单的工作量相加。
4. **均为 P1、均不阻塞 M7**。M7（Inbox）依赖的任务表机制在 M3 已就绪，合并不挤压关键路径。

### 1.3 备选方案比较

| 方案 | 描述 | 评价 |
|------|------|------|
| A. 顺序执行 M5→M6 | 先完成图谱底座与抽取，再启动可视化 | 两次评审、两次依赖落地；M5 验收缺可视化回路，只能看 Cypher 结果文本，实体归并质量难以人审 |
| **B. 合并，四阶段（推荐）** | 一次里程碑，P-A 图谱底座 / P-B 流水线+CLI+MCP / P-C Web 三页 / P-D 图谱页 | 一次评审闭环；P-C 可与 P-B 并行；图谱页落在最后，其前端契约以已稳定的图 schema 为准 |
| C. 先 M6 结构图谱版再 M5 | 先做只含 Document/Section/Topic 的骨架图谱页 | 图谱页契约要做两轮（结构版→实体版），返工量大于其带来的早期可视化收益 |

### 1.4 合并的主要风险与对策

- **范围膨胀**：两个里程碑合并后表面工作量翻倍。对策：§2 收窄（砍 Inbox/设置/写交互），§8 四阶段各带独立 DoD，任一阶段不过即不进入下一阶段。
- **抽取质量拖累图谱页**：实体抽取是 M5 最大的不确定项。对策：P-D 启动条件只要求 P-A 图结构稳定，抽取以种子语料先行（§8 阶段顺序保证图谱页开发时已有真实实体数据可用）。
- **G6 v5 UMD 可用性**：02 D10 已预留退路（UMD 不可行退 esbuild 产物 vendored）。对策：P-C 首个任务即做 vendor 可行性 spike，结论写入 DoD。

## §3 图库底座

### 3.1 GraphStore 协议（维持 05 §3.1）

维持 05 §3.1 的接口面不变：

```
open(path, mode: "rw" | "ro") / close()
upsert_nodes(label, rows) / upsert_edges(label, rows)
query(cypher, params)          # Cypher 通用子集，禁用厂商专有语法
shortest_path(src, dst, max_hops=3)
make_graph_store(backend, cfg) # 工厂；仅接受 "ladybug"（单一选型 D15-10，无第二后端）
```

约束：只使用 Cypher 通用子集（02 D2 薄适配层原则）；调用方不得拼接字符串构造查询，一律参数绑定。

### 3.2 Schema 落图范围（MVP 简化，对 03 §3.2 / 05 §2.2 的收敛）

落图节点四类：**Document**（含 corpus/valid_from/valid_to 软删、summary 三字段）、**Section**、**Entity**（Concept/Method/Tool/Dataset/Person/Organization）、**Topic**。

落图边四类：**CONTAINS_SECTION{order}**、**MENTIONS{weight}**（Section→Entity，weight = 实体名在该 Section 文本中的出现次数）、**ABOUT_TOPIC{confidence}**（Document→Topic）、**RELATES_TO{kind, weight, evidence_section_id}**（kind 受控词表：extends/contradicts/applies/evaluates/improves-on/part-of/instance-of/uses/compares）。

**砍除项与理由（D15-2，MVP 简单直接）：**

| 砍除 | 理由 |
|------|------|
| Chunk 节点 + CONTAINS_CHUNK + MENTIONS_ENTITY | Chunk 为存储层节点、不上图谱页渲染、`related`/`compare` 不消费；实体抽取本就按 Section 归属（evidence_section_id），Section→Entity 直接落 MENTIONS 即可，无需 chunk 级桥接再归并。`embedding_id`/`text_ref` 是 P1 向量/细粒度检索预留，图库为衍生数据、届时删 graph/ 重建再补 |
| CITES / SUPERSEDES | 引用抽取（参考文献解析）复杂、本里程碑无实现任务，且非 MVP 图价值（related/compare/图谱页均不依赖）；版本链 SUPERSEDES 同理后置 |
| SAME_AS | 实体消歧改 entity_id 碰撞（D15-13），同名同型 MERGE 到同节点，无"两节点归并"场景，无需 SAME_AS 记录边 |
| Section→Topic | 同 v2.1：主题归类是文档级，Section 主题经父 Document 的 ABOUT_TOPIC 反查推导 |

索引策略维持 03 §3.2 S8：无属性二级索引，热路径走主键定位 + 关系遍历（Entity 按 `entity_id=type:norm(name)` 主键定位，无需名称二级索引）。

### 3.3 重建与钉版（单一后端）

- 唯一后端 LadybugDB（Python 包 `ladybug`），**无降级后端**（D15-10，覆盖 02 D2）。
- 契约测试集：同一套 schema DDL + 一组固定查询（建点建边/2 跳遍历/最短路径/软删过滤）在 LadybugDB 单后端跑通，作为 schema 与查询层的回归基线纳入 CI。
- 图库是衍生数据：任何时刻可由 SQLite + 正文文件全量重建（§4.4），允许在破坏性 schema 变更时直接删 `graph/` 重建，不提供图内迁移工具。
- uv.lock 钉版，升级 ladybug 为独立变更；若 ladybug 上游出现不可逆问题，换库路径是重写一个 GraphStore 实现 + 全量重建，不预留第二后端代码。

## §4 流水线扩展

### 4.1 任务分派

不新增 task kind 枚举值（03 §4 的枚举已含 extract/index/tombstone，无需 DDL 变更），runner 分派扩展为：

| kind | 处理 |
|------|------|
| index | 既有的 chunk+FTS 之上，追加**结构同步**：Document/Section/Topic 节点与 CONTAINS_SECTION、ABOUT_TOPIC 边入图（无 Chunk/CITES/SUPERSEDES，D15-2） |
| extract | **实体抽取**：Entity 节点与 MENTIONS、RELATES_TO 边入图（无独立 stage_relate；无 MENTIONS_ENTITY/SAME_AS，D15-2/D15-13） |
| tombstone | 既有文件清理之上，追加图侧 Document 置 `valid_to` 软删（不物理删边，查询层过滤） |

is_core 门控（03 §4 "交集而非并集"，FR-2.7）：`topic 命中 core_topics（norm 匹配）∩ doc_type ∈ {paper, design}`，或命中 `extract.extra_docs`（单独标记，D15-12，恢复 03 §4 P4 的"被单独标记文档"入口）时才为该文档入队 extract 任务；目标结构化覆盖率维持全库 15–25%。

**时序约束**：extract 产出 MENTIONS（挂到 Section）与 RELATES_TO 边，依赖结构同步（index）已把 Section 节点落图；同一文档的 index 任务须先于 extract 任务执行（runner 串行保证，09 §10；reindex --full 按 §4.4 先结构同步后抽取入队）。

### 4.2 实体抽取与归并

- 抽取：stage_extract 单次 LLM 调用同时产出实体清单与实体间关系（带 evidence_section_id），输出 JSON 契约同 05 §4.4。
- 消歧：**entity_id 碰撞**（D15-13）——`entity_id = type:norm(name)`（小写 + 连字符/空白归一），同名同型实体 MERGE 到同一节点；无 embedding、无 SAME_AS、无归并/重指向逻辑。LLM 输出的 `aliases` 落 Entity 字段仅作记录，MVP 不用于消歧。
- MENTIONS：实体名在 Section 文本中出现（`str.count`）即落 `Section→Entity`，`weight` = 出现次数；实体按 `evidence_section_id` 定位，未给则全文档 Section 扫描。
- 关系冲突：同一对实体同一 kind 的多条关系取证据频次高者，其余降 weight 保留。

> 记账：无 embedding 调用；仅 LLM 抽取 `purpose=extract`。

### 4.3 质量门

种子语料（取 core_topics 命中的 paper/design 各 ≥10 篇；现存语料足以产出 >100 实体，保证抽检样本量）抽取结果须满足：

- 实体类型准确率（人工抽检 100 个实体）≥ 85%；
- 实体名一致性（同名同型应归并为一、不同实体不误并）经图谱页人审无错并；
- RELATES_TO 的 kind 分布中 `uses`/`part-of` 等高频类不出现单一类占比 >70% 的坍缩。

### 4.4 reindex 扩展

`kb index reindex --full` 扩展为：清空 `graph/` 目录 → 全量重新入队 index（含结构同步）→ 对满足 is_core 的文档重新入队 extract。部分重建（单文档级）复用既有 index/tombstone 路径，不新增命令。

## §5 CLI / MCP 扩展

### 5.1 CLI

| 命令 | 语义 |
|------|------|
| `kb related <doc\|entity> [--hops N] [--limit N]` | N 跳邻域（默认 1，上限 3；limit 默认 10，对齐 05 §6 kb_related），输出实体/文档清单及路径上的关系 kind |
| `kb compare "<concept>" [--docs a,b,c]` | 概念在两个及以上文档/实体间的 RELATES_TO 对照表（kind × 证据 section）；`--docs` 可选，对应 05 §6 kb_compare 的 `doc_ids` |

两命令在图库不可用（backend 缺失或 schema 版本不符）时给出明确报错，不静默降级为 FTS 检索，报错信息引导 `kb index reindex --full`。

> **行为回归提示**：M5 落地后 `related`/`compare` 从 M3 的"文档级推荐/摘要对比"降级（11 §2.5）转为图遍历语义，无图库时不再回退 M3 文档级实现而是显式报错——这是对 M3 已交付命令的刻意行为变更，回写 11 §2.5 时标注。

### 5.2 MCP

新增三个只读工具，薄封装 retrieve/graph 层，参数与返回 schema 直接复用 05 §6 登记的目标态：

- `kb_related(target, type, hops, limit)`、`kb_compare(concept, doc_ids?, limit)`、`kb_topics()`。
- 写工具、HTTP 模式、kb_status、LOCK_HELD 维持 13 §1 边界，本里程碑不动。

## §6 Web 可视化

### 6.1 服务与约束

- `kb serve viz [--port 8371]` 启动 FastAPI 只读服务，**绑定 127.0.0.1**（03 §7.4），无鉴权（仅本机），HTTP 默认关闭的开关语义不变。
- 全部端点只读；任何变更操作在 API 层即不存在（D15-4）。

### 6.2 只读 API 端点

对照原型 `data.js` 的全局 KB 对象 schema，端点集：

| 端点 | 用途 | 数据来源 |
|------|------|----------|
| `GET /api/search?q=` | 检索页 | SQLite FTS（M2 既有） |
| `GET /api/docs/{id}` | 文档页（元数据+summary+section 树+正文引用） | SQLite + 正文文件 |
| `GET /api/topics` | 图谱页主题清单 | SQLite topics |
| `GET /api/graph/subgraph?topic=&hops=` | 主题 2 跳子图（默认裁剪上限 500 节点） | GraphStore |
| `GET /api/graph/path?src=&dst=` | 路径高亮（max_hops=3） | GraphStore shortest_path |
| `GET /api/status` | 状态页（任务队列、库统计、图统计） | SQLite + GraphStore |

### 6.3 页面

- **检索页 / 文档页 / 状态页**：vanilla JS + `body[data-page]` 分派（沿用原型范式）。核心检索/摘要/章节树/状态只依赖 SQLite，可在 P-B 之前先行（P-C）；但 04 §3.1 检索页"命中实体词云"与 04 §3.2 文档页"关联侧栏（关联资料/提及实体）"依赖图谱（MENTIONS/RELATES_TO），随 P-D 图谱数据就绪后回填——P-C 先出无实体侧栏的版本，P-D 补齐。
- **图谱页**：G6 v5 vendored，支持选中主题下钻、节点折叠、框选、路径高亮（02 D10 的内置交互清单）；规模保护按 D15-9。
- 原型中的 Cytoscape vendor 为原型选型，正式实现以 G6 v5 为准（02 D10），原型代码仅作交互参考。

### 6.4 工程化

- G6 v5 为 ESM/TypeScript 优先（02 D10），UMD 可用性**待 P-C spike 裁决**：

> **Spike 结论（v2.4 落地实测，2026-08-16）**：G6 v5 官方提供 UMD 单一产物 `dist/g6.min.js`（约 1.38MB），通过 `!function(t,e){...e((t="undefined"!=typeof globalThis?globalThis:t||self).G6={})}(this, ...)` 在浏览器侧挂 `globalThis.G6`。Node CJS 验证：`module.exports` 含 `Graph` / `ExtensionCategory` / `AntVDagreLayout` 等 200+ key。
>
> 决策：直接 vendored `g6.min.js` 落 `src/kbapp/web/static/vendor/`，Task 18 图谱页用 `<script src="vendor/g6.min.js">` 加载即可。仓库不引入 esbuild 持续构建链。15 §6.4 兜底序列保留（esbuild 产物、Cytoscape.js UMD）作为后续维护选项。
- 兜底序列为 G6 UMD → esbuild 产物 → **Cytoscape.js UMD**（02 D10 明示的零构建最终退路："若坚持零构建纯静态，则退选 Cytoscape.js"）；仅当 G6 两条路径均不可行时启用，启用即触发 02 D10 回写与图谱页交互清单重估（下钻/框选等需自建）。
