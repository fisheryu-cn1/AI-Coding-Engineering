「上下文的纪律」系列 · 第 1 篇

我们在给编码智能体喂什么，它们消化得怎么样

▍AI搬砖工平凡一周的开始

周日晚上8点，你刚把团队的新项目仓库 clone 下来，准备接入编码智能体。按官方文档的指引，第一步不是写代码，而是跑一句 /init——于是仓库根目录多了一个 CLAUDE.md（或者 AGENTS.md）。你往里面填：目录结构说明、构建命令、测试怎么跑、"提交前务必跑 lint"……12个小时后，一份像模像样的"仓库说明书"诞生了。组长点点头："好，以后 AI 就懂咱们项目了。"

这一幕正在全世界上演。AGENTS.md 官网报告：已有超过 60,000 个开源仓库放进了这样的文件；几乎所有主流 agent 框架都支持它，各家厂商的文档也在推荐你写。

但"大家都在写"和"写了真有用"之间，隔着一堵证据的墙——从来没有人为这件事做过严格实验。直到 ETH 苏黎世的一组研究者把它当成一次临床试验来做：三种设置对照、四个编码智能体、438 个真实任务。结论有点扎心：成功率纹丝不动，账单稳定上涨 20%。

大家刚学会“没有AGENTS.md的项目是不专业的”也没多久，この世界のコンティニュイティは、既に崩壊してしまったのだろうか？？！！ Ne vous emportez pas습니다，还是耐心看一下到底发生了什么吧。

本期论文

Evaluating AGENTS.md: Are Repository-Level Context Files Helpful for Coding Agents?
《评测 AGENTS.md：仓库级上下文文件对编码智能体有帮助吗？》
作者：Thibaud Gloaguen, Niels Mündler, Mark Müller, Veselin Raychev, Martin Vechev
ETH Zürich & LogicStar ｜ arXiv:2602.11988（2026-02 首发，v2 更新于 2026-06）

简要结论：仓库级上下文文件不显著提升任务成功率（p=0.87 / 0.37），却把推理成本平均抬高 20% 以上（p<0.001）。

名词速查

▸ 上下文文件（context file）：AGENTS.md、CLAUDE.md 这类放在仓库根目录、专门写给 AI 编码助手看的说明文件，内容通常包括仓库概览、构建与测试命令、代码约定等。

▸ SWE-bench：从真实 GitHub issue 构建的编码任务基准，任务是修复 issue 并通过测试；"Lite" 子集 300 题，是行业最常用的Agent编码能力测试集之一。

▸ p 值：粗略地说，p 越小，越不像是巧合。惯例 p<0.05 算"显著"；p=0.87 意味着"与噪声无法区分"。

一、把"感觉有用"变成可测量的东西

研究者要回答的问题只有一个：给编码智能体一份仓库说明书，它修 bug 的成功率和花销会变吗？实验设计成一个标准的"临床试验"：同一个仓库、同一个任务，只改变一个变量——上下文文件的有无与来源，共三种设置：

① DEV：仓库里开发者亲手写的文件保持原样（真实写作场景）

② None：把文件拿掉（对照组）

③ LLM：删掉原文件，按厂商推荐的方式用智能体自己生成（/init 一键生成那类）

任务来自两个互补的基准。一边是行业标尺 SWE-bench Lite（300 题，11 个热门 Python 仓库）——但热门仓库大多没有开发者手写的上下文文件，只能测"LLM 生成"这一格。为补上"真人手写"这个实验设置，作者自建了 CTXBENCH：从 GitHub 上筛出根目录带 AGENTS.md/CLAUDE.md、以 Python 为主语言、有测试套件、PR 数不少于 400 的小众仓库，从 5,694 个 PR 中经双重过滤，再由智能体自动搭建环境（通过率 87%）、LLM 重写任务描述防止泄漏解法、LLM 生成回归测试并人工排查过拟合，最终得到 12 个仓库、138 个实例。被测的是四个主流组合：Claude Code + Sonnet-4.5、Codex + GPT-5.2、Codex + GPT-5.1 Mini、Qwen Code + Qwen3-30B-Coder（本地部署）。

图 1｜评测流水线：同一仓库派生三种设置（①保留开发者文件 ②不放上下文文件 ③智能体自动生成），交由编码智能体解题，再对补丁与行为轨迹做双重分析（原论文 Figure 1）

双基准的选择本身是经过深思熟虑的：SWE-bench 的仓库太热门，可能早就被模型"背过"；CTXBENCH 专挑小众仓库，还按模型知识截止日期做了切分检验（训练截止前的任务占比最高 40%，结论不变）。一热一冷互为印证。

二、结果一：成功率，纹丝不动

先看主指标——任务解决率。LLM 生成的上下文文件，在 8 个"智能体 × 基准"设置中有 5 个不升反降：SWE-bench 上平均 −0.5 个百分点（p=0.87），CTXBENCH 上平均 −2 个百分点（p=0.37）——统计上与零无法区分，翻译过来就是：加了等于没加，还可能略有反作用。

图 2｜四组智能体的解决率：左为 SWE-bench Lite（None vs LLM），右为 CTXBENCH（None / LLM / DEV）。柱子高度的差别始终在误差范围内（原论文 Figure 3）

逐个智能体看（下表，单位 %，± 后为标准误），涨跌互现、幅度全在噪声量级：

表里藏着一个真正显著的差别：开发者手写的文件显著优于 LLM 生成的文件（p=0.038，平均领先约 7 个百分点），对除 Claude Code 之外的智能体都有提升——但手写相对"完全不放文件"也只平均 +2.4 个百分点（p=0.21，不显著）。这组数字很有意思："写不写"不重要，写对内容才有价值；如果让AI替你写，那连这点价值也会写没了。顺带一提，CTXBENCH 上提升最明显的是最小的模型 Qwen3-30B（45.7 → 53.6），越弱的模型越吃手写说明——这个梯度后面还会用到。

三、结果二：账单，稳定上涨

成功率不动，成本却动得很坚决：每一个设置、每一个智能体，成本都在涨。SWE-bench 平均 +20%、CTXBENCH 平均 +23%（置换检验 p<0.001），步数平均多出 2.45 / 3.92 步。

注意一个不太直觉的细节：成本上涨不只是"文件本身占 token"那点钱——文件最多几百 token，涨的却是两三成的总开销。多出来的钱花在了后面：智能体遵循说明书里的指示，跑了更多测试、grep 和读写了更多文件、翻来覆去重读已经注入的上下文文件。说明书被"念"了，而且是被认真地念了。

四、追问：指令明明被执行了，为什么没用？

面对"不涨点"，第一个自然的怀疑是：智能体根本没理会说明书。作者用行为轨迹分析否证了这一点。把工具按"说明书是否提及"分组，差距是一到两个数量级：被提及的 uv 工具平均被调用 1.6 次/实例，未被提及的工具不足 0.01 次；仓库自有工具 repo_tool 是 2.5 次对不足 0.05 次。指令不仅被读了，还被执行了。

图 3｜工具平均调用次数：实心 = 说明书提及，斜纹 = 未提及。提及与否，差出一到两个数量级（原论文 Figure 9）

说明书还让智能体整体"更忙"：带上下文文件时，pytest、python、grep、read/write 等工具的调用量普遍上升（图 4）。对具备自适应推理的模型还能看到一笔隐性开销——GPT-5.2 的推理 token（reasoning tokens）平均多花了 22%（SWE-bench，GPT-5.1 Mini 为 +10%）。用论文的话说：遵循额外指令，本身就更"费脑子"。

图 4｜引入上下文文件（LLM 生成 / 开发者手写）后各工具平均调用量的变化，普遍右移即增加（原论文 Figure 5）

那无效的是哪部分内容？作者逐一检查了文件的组成。最受厂商青睐的"仓库概览（repository overview）"并不能减少智能体找到关键文件所需的步数；而删除概览、工具说明、测试说明等类别的消融实验，也没有任何一类删掉后成功率显著变化。测试与工具类的指令倒是显著推高了成本（删掉 Testing 类，GPT-5.2 的成本从 $0.47 降到 $0.37）。被认真执行的指令，没有换来任何收益。

五、最有意思的反转：删光文档，它就有用了

实验做到这里，作者提出了一个漂亮的假说：LLM 生成的上下文文件，本质上是仓库既有文档的冗余复读。验证方法简单粗暴——把仓库里所有文档（*.md、docs/、示例）全部删掉，让上下文文件成为唯一的信息来源，再跑一遍。

图 5｜删光仓库文档后，LLM 生成的文件（绿）平均 +2.7%，并反超开发者手写版本（原论文 Figure 12，CTXBENCH）

结果：LLM 生成的文件平均提升 2.7%，而且反超了开发者手写的版本。这个反转同时解释了两件事：其一，为什么它在正常仓库里没用——它讲的东西，模型翻翻 README 和文档本来就能知道；其二，为什么坊间一直有"加了文件确实变好"的传言——很多小众仓库本来就没有文档，此时说明书是雪中送炭。作者的措辞很克制，但意思很清楚：在文档健全的仓库里，让 AI 生成的 AGENTS.md 大概率是在为冗余信息付费。

六、论文的启示

① 暂缓把"LLM 一键生成上下文文件"当默认动作——这与当前多数厂商的推荐正好相反；

② 手写文件只写 README 之外的非标准约定：易错的构建陷阱、非常规的项目结构、必须遵守的非功能性要求；

③ 对上下文文件进行改动的效果，是值得用可度量方法进行记录和总结的。

▍那么到底还要不要AGENTS.md？

Pro rerum natura：AI应用的本质是上下文管理，有用的上下文就有用，没用的上下文是纯负担。往上下文中添加的每一个字，都应该考虑这是不是必要的信息。"手写的上下文说明比AI自动生成的结果好7个点、却只比完全不写高2.4个不显著的点"，这组数字说明：不是所有的附加信息都有价值。需要的是 README 里查不到的非标准约定，而把文档里已有的东西换个格式再写一遍，只是付两遍钱。

事实上，大部分转型中团队面对的现状是：文档不全的祖传屎山代码库，能力不一的组员（有些还是刚从其他项目上调过来的），和还没来得及问明白的需求。这种情况下，由核心成员整理出一份共享的基础说明/规约自然是很有必要的。但是，切不可“因为组长说了要写AGENTS.md”而写，或者无脑让AI照着标准模板自动生成一份。

这篇论文中还有一个值得思考的现象：指令明明被执行了，测试多跑了，推理 token 多花了 22%，成功率却分毫不动。多提供的信息，多做的工作，为什么没有效果？虽然主流模型的上下文窗口普遍达到了百万级——大部分情况下，整个仓库都放得下——但显然，并不是只要窗口装得下，就能随便塞进去的。
