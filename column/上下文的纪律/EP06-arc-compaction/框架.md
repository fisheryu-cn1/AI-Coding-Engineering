## 1. 系列衔接

- EP05 结尾落点原文："材料已经进了窗口、想压掉又怕丢，是再下一道工序。"EP06 正面回答这道工序：压缩的通病是不可逆丢信息，ARC 给出"指针+按址取回"的解法。
- 与 EP05 的机制呼应（一句带过）：ContextSniper 的门控把原件存在记忆层、窗口里留截断标记和恢复提示；ARC 把同一个思想做到压缩上并给出严格化版本（内容寻址 id+按址取回+系统级保证）。两者一个管"进窗口之前"，一个管"进了窗口之后"。
- 第2期容量纪律的硬失败版：满上下文不是性能下降而是下一次调用直接失败（Full_context 在两个基准上 0% 全因溢出）。
- EP07（ACM 自治）伏笔：ARC 的 _recall 是工程约定的工具，"什么时候压、什么时候取回"仍靠外部规则触发；让模型自己学会这套动作是下一篇。藏在结尾一句，不预告。

## 2. 论文→建议映射（advice-first）

**主建议：压缩策略先问一句话——被压掉的内容还能原样找回吗？按"可恢复性"给压缩方法分类，比按"压得多省"分类更要紧；能用指针+原样外存，就不要用摘要覆盖原文。**

- 操作点 1（分类轴）：五种主流做法按可恢复性排（全文保留→溢出即失败／滑窗→永久丢／LLM摘要→改写丢细节／结构化状态→未建模即丢／RAG→存了但只能相似度召回）；选型先看丢什么，再看省多少。
- 操作点 2（解耦两个决定）："系统保留什么"与"窗口展示什么"分开决定——全量原文入只增存储，窗口只留引用+近期原文。
- 操作点 3（确定性压缩）：压缩例程零 LLM 调用（截老思考/短观测内联/长观测换引用/近期轮次原文保留），不重新摘要、不改名，保证地址稳定可寻。
- 操作点 4（取回要有地址）：_recall §id 按址取回原文而非相似度搜索；引用本身有小额固定 token 开销（论文自列量化为待办）。

- HBM（对成功提交任务，vs Sliding_window=0 基准）：LongBench ARC 省 38.8%（8B）/73.5%（32B）；NIAH 省 80.3%（8B）/59.3%（32B）；总时间 LongBench 3.99s vs 6.53s（8B）/8.11s vs 30.57s（32B）；RAG_memory 在 LongBench 上带宽开销 −124.9%/−151.9%（更贵）

- 机制细节：id=SHA1(sig(A)||O) 前 8 hex（碰撞按 4 hex 延展）；引用=头/尾预览+元信息+recall 提示；有界视图五段=任务前缀/确定性摘要/近期后缀/一页引用目录/已召回正文，K≤L；_recall 每轮限 r 次（默认 2），超总预算时 LRU 回退为裸 §id；_recall_meta 轻量恢复元信息；压缩例程确定性零 LLM 调用；主动（预估超限前）/被动（溢出报错后）双触发同一例程
- 定理1 四条件：i 注入式定宽 id；ii 任何压缩前原文已 verbatim 入库；iii 外部目录完整+prompt 内目录有界一页；iv K≤L ⇒ 按 id 严格可恢复（条件在有效地址，不在 agent 决策）；附录下界：任意精确恢复历史的系统外部存储至少线性增长，ARC 只增存储一阶匹配
- 开放问题（论文自列）：引用 overhead 未量化；单一模型族（Qwen3）泛化未验；模型/窗口/max-token 网格其余点未测；LongBench 对话历史类子任务上隐式检索仍赢——"显式与隐式召回互补而非竞争"

## 5. 去AI味自查（本文高发点）

- "指针/按址取回"是论文自身机制（pointer/addressable recall），直陈机制即可；"地址"用存储地址的通行含义首现拆解（内容寻址=用内容哈希当存储地址）。
- 主对比句"不是压得更省，而是丢得可逆"——避免口号化：写成机制差异（摘要覆盖原文后细节不可恢复；ARC 原文永在库中，窗口内换成短引用，需要时按 id 取回原样）。
- 数字口径三处高危：①99.40%/88.12%/29.97%/28.25% 全是"两模型均值"，正文表格给分模型值时须标明；②Full_context 只在 LongBench 全零，NIAH 上 8B 36.80%/32B 2.93%（溢出早晚不同），不可写成"全线零分"；③+1.64/+1.80 是对"各模型最优基线"的分模型差值。
