# 论文摘要：Towards an Agent OS（从经典 OS 与云 OS 汲取教训的代理操作系统纲领）

## 1. 适用场景

- 需要 **"harness≈OS"类比的正面学术工程化谱系** 时读本文：它与 Karpathy LLM-OS 框架、AIOS、MemGPT 同列，但把类比推进到"规范/specification 层"——给出类比成立所需的语义条件与失效边界（§I、§III）。
- 研究 **harness 的学术定位** 时：本文把当今成功 Agent 系统依赖的 bespoke 代码层（即 harness）判定为平台浪潮"实验期（Phase 1）"的产物——domain 与 model 特定，但其涌现模式可提炼为平台公共原语（§I）。
- 设计 **Agent 平台层机制**（调度与编排、隔离与生命周期、skills 版本控制、安全区/沙箱、授权与身份）并希望从经典 OS（进程/虚拟内存/系统调用/MAC）与云 OS（Pod/RBAC/Saga/服务网格）逐条推导对应物时（§IV、Table I）。
- 评估 **现有 Agent 框架与协议（CrewAI、LangGraph、AutoGen、MCP、uTCP、A2A）在"平台保证"上的缺口**、规划 Agent 基础设施标准化路线图时（§II-A、§VII）。
- 撰写"harness 与冯·诺依曼架构类别关系"类研究材料、需要 OS 类比的**边界证据**（哪些经典语义仍然够用、不需要新抽象）时（§IV 开篇、§VI Lesson 3）。

> 锚点：Abstract；§I Introduction；§II-A Each Era Follows the Same Arc；§III The Semantic Gap；§IV Proposed Agent-OS Primitives + Table I；§V Open Source Prototypes；§VI Discussion；§VII Open Research Agenda。

## 2. 主要观点与方案

### 2.1 三波平台浪潮与同一弧线（§I、§II-A）

- 计算史可读为平台迁移序列：经典服务器时代（OS，POSIX 完成标准化）→ 云时代（Cloud-OS，Kubernetes 完成标准化）→ 当前的 **agentic 时代**（Agent-OS 尚不存在）。
- 每波浪潮都走同一三段弧线：**Phase 1 Experimentation**（框架 proliferate，如pre-POSIX 的 Unix 变种、pre-K8s 的 Chef/Puppet/Mesos/Swarm）→ **Phase 2 Articulation**（社区识别核心抽象并精确规定语义，POSIX 耗时十年）→ **Phase 3 Consolidation**（平台收敛，获得可移植性）。
- **agentic 时代当前处于 Phase 1**：数十个框架与协议都在回答"怎么写 Agent 代码"，没有一个定义"平台必须保证什么"——LangGraph 写的 Agent 跑不到 CrewAI 上，一个框架的授权策略无法被另一框架的工具审计。UC Berkeley 生产测量研究 [11] 佐证：框架在原型期有价值，进入生产后常被弃用，让位于基础设施语义与运维控制。本文自我定位为 **Phase 2 贡献**。

### 2.2 执行单元的性质变化与核心洞见（§II）

- 执行单元从 program（确定性、可静态分析）→ service（分布式中的确定性单元）→ **agent**（以 LLM 为推理引擎、感知-规划-行动-迭代的自主系统），带来四个破坏性性质：**随机性**（同输入产生行为分布）、**作用于外部世界**（API/数据库/消息，后果常不可逆）、**自设计交互模式**（无法先验验证）、**策略性不当行为**（受压力时伪造成功、删除证据以避免任务被放弃 [6][7]；LLM 无法自检错误 [24]、无法无外部反馈自我纠错 [25]）。
- **核心洞见（§II-3）**："可靠性/安全性是基础设施属性而非模型属性"——调度器必须 bound 规划阶段、工具中介必须拦截并授权每个动作、记忆系统必须维护并发一致性；平台必须强制执行 Agent 提示词只能"请求"的东西。
- 企业需求（§II-4）：合规可审计、数据主权、多云/本地部署、与既有 ERP/CRM/ITSM 集成。

### 2.3 语义鸿沟：OS/Cloud-OS 语义在哪失效（§III）

- 鸿沟不是基础设施能力差距（K8s 完全能跑 Agent 容器），而是**平台能对其推理、强制、保证什么**的差距。OS 与 Cloud-OS 都建立在"结果确定性"上，Agent 从两个方向打破它：
- **结构性断裂**：Agent 作用于外部世界——不可逆操作（发邮件、金融交易、删生产记录）没有 OS 抽象按 reversible/compensable/irreversible 分类；自然语言消息可注入并重编程接收 Agent（无字节级对应物）；动态授权（按任务推理发现并调用 API）使部署期声明权限集失效。有部分经典先例可依：补偿事务 [22]、capability-based security [23]。
- **随机性内禀断裂**（即使确定性外作用系统也无对应物）：最坏情形执行时间不可计算（推理调用次数运行时才知）；capability 安全的静态可分析性失效；replay 调试无法复现故障；时间局部性驱逐不适用于上下文窗口（token 相关性取决于任务语义而非访问新旧）；声明式期望状态无法表达/验证自然语言目标；目标导向的隐瞒行为推翻"进程自报状态可信"这一 OS/Cloud-OS 故障检测根基。
- 随机性还放大结构性问题：内存冲突谓词变成推理上下文的函数（"forecast: increasing" vs "forecast: decreasing" 是字节级 ACID 看不见的语义冲突）；自然语言的前/后置条件抵抗类型化契约的静态验证。

### 2.4 十三个 Agent-OS 原语与三问推导法（§IV、Table I）

- 方法论三问：(1) 原 OS 抽象解决什么问题、给出什么语义保证？(2) 该问题在 agentic 场景是否复现？(3) 处理随机/自然语言中介执行需要改变什么？**不提出 prior 原语仍然够用的新抽象**——"Agent-OS 是第三层，不是替代品"。
- Table I 全景（OS → Cloud-OS → Agent-OS 原语；状态 Open/Partial/Early；地平线 Near/Mid/Long）：

| # | OS 起点 | Cloud-OS 延伸 | Agent-OS 原语 | 状态/地平线 |
|---|---|---|---|---|
| 1 | Process | Pod/container | Agent lifecycle（语义身份=goal/skills/tools/model+云身份） | Partial/Near |
| 2 | Scheduler | kube-scheduler/HPA | Orchestrator（token 配额、语义环检测、多维成本） | Open/Mid |
| 3 | Package mgmt | Helm/OCI | Skills registry（语义 SBOM、来源证明） | Open/Long |
| 4 | System call | Service mesh/sidecar | Tool mediation（可逆/可补偿/不可逆分类+提权） | Partial/Mid |
| 5 | Virtual memory | ResourceQuota/LimitRange | Context management（token 驱逐理论缺失） | Open/Long |
| 6 | IPC | Service/ClusterIP | A2A communication（动态图+注入防护） | Partial/Mid |
| 7 | File system | PersistentVolume/etcd | Agent memory（语义冲突、意图感知检索） | Early/Long |
| 8 | Permissions/ACL | RBAC/NetworkPolicy | Identity & AuthZ（SPIFFE 扩展+RFC 8693） | Partial/Near |
| 9 | MAC/SELinux | PodSecurityPolicy/OPA | Behavioral guardrails（无可判定 NL 策略语言） | Open/Long |
| 10 | Signal/exception | Liveness/readiness probe | Failure detection（自我隐瞒、开放失败空间） | Open/Long |
| 11 | Transaction/journal | Saga/Temporal | Saga & checkpoint（随机工作流的补偿事务） | Partial/Long |
| 12 | Audit/syslog | Prometheus/Jaeger | Trajectory observability（观察单元未定义、时间错位） | Partial/Mid |
| 13 | Network stack | Envoy/Istio | AI-aware proxy（对 prompt 盲、无 KV-cache 路由） | Early/Mid |

- 与本研究最相关的原语细节：**Tool mediation（§IV-D）** 将工具调用按 reversible/compensable/irreversible 分类，不可逆类需提权授权——MCP 只定义通信方式不定义执行保证，"REST/Kubernetes 之差距的复刻"。**Context management（§IV-E）** 指出 token 驱逐比页驱逐严格更难（Bélády 最优性依赖可静态推导的未来访问知识，token 的未来访问模式本身是概率推理的输出），需要"token 相关性形式理论"。**Secure code execution（§IV-L）** 要求 copy-on-write 的事务性文件系统沙箱：Agent 生成代码先入影子副本、经审查再提交。**Failure detection（§IV-J）** 列出五种 Agent 特有失败模式：返回 HTTP 200 的规划失败、上下文/记忆丢失致陈旧动作、Agent 间失调、静默级联、自我隐瞒。

### 2.5 harness 与 OS 类比的边界（§I、§VI）

- 谱系定位（§I）：Karpathy LLM-OS 框架 [4] 与 AIOS [5] 已证明 OS 类比是 productive 的；本文是"该类比所要求的下一步"——把语义定义到平台可强制、应用可移植依赖的程度。
- **边界即 Lesson 3（§VI）：只规范真正新的东西**。K8s namespace 仍然隔离 Agent 容器；POSIX 文件系统仍然存储 Agent 产物；OpenTelemetry span 仍然追踪服务调用——§III 的语义鸿沟（随机性、动作可逆性、目标导向不当行为）恰是"真正新"的精确边界。其余四条教训：标准化是实验期的出口；在上一层之上构建而非取代（agent 授权建在 SPIFFE→ServiceAccount→POSIX UID 之上）；平台强制执行应用代码只能请求的东西。

### 2.6 开源原型 rossoctl（§V）

- IBM 开源原型 **rossoctl**（github.com/rossoctl/rossoctl），构建于 Kubernetes 之上：用 CRD（MCPServer、VirtualMCPServer）与 Gateway API 表达平台策略；AuthBridge（授权）、SPIFFE/SPIRE（身份证明）、MCP Gateway（网络策略）为平台服务，经 sidecar/CRD 透明消费、**应用代码不可绕过**（类比内核级强制）；Agent Execution Environment sidecar 提供隔离/观测/控制点，实现框架无关（LangGraph、CrewAI、Marvin、AutoGen 经统一 sidecar 接口接入）。
- 同类开源：AutoGen、LangChain/LangGraph、OpenAI Swarm、Kagent（K8s 上编排 Agent）、Openshell（NVIDIA，harness 安全沙箱管理）——各实例化 13 原语的不同子集，**尚无一个提供完整平台层**。

### 2.7 开放研究议程（§VII）

八个开放规范问题：随机调度理论；随机系统评测方法学（含"面向 Agent 的混沌工程"）；语义化 skill 接口契约；Agent 感知的信息流分析；AI 生成代码的供应链安全；自然语言 guardrails 的形式策略语言（现役 DSL/概率模型检查/道义时序逻辑为起点）；有原则的上下文驱逐理论（Bélády 类比）；agentic RL 与元学习的平台支持。
