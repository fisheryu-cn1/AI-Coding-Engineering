# 论文摘要：规约驱动开发——AI 编码助手时代的从代码到契约（实践指南）

## 1. 适用场景

- 当你需要 **spec-driven development（SDD）的分级概念框架**（spec-first / spec-anchored / spec-as-source 三级严格度及其适用决策树）来定位自己的实践或设计工具时，读这篇。
- 当你要论证"**代码成为派生工件**"的可行性边界（哪个领域已成立、哪个还在愿景期）并需要案例证据时，读其 §VI 三个案例与 §VIII 决策框架。
- 当你要预判 SDD 的失败模式（过度规格化、规格腐烂、虚假信心）时，读其 §IX。

> 锚点：Abstract; §II The Specification Spectrum; §III The SDD Workflow; §IV How SDD Boosts AI Coding Agents; §V Tools; §VI Case Studies; §VIII When to Use SDD; §IX Common Pitfalls; §X SDD vs Traditional Design Documents

## 2. 主要观点与方案

- **三级严格度谱系**（§II; Fig.1）：①**spec-first**——spec 仅指导初始实现，之后可弃（低维护负担，适合 AI 辅助初版/原型）；②**spec-anchored**——spec 与代码全程共同维护，测试强制同步（多数生产系统的甜点区；BDD/OpenAPI+契约测试即此级）；③**spec-as-source**——spec 是人唯一直接编辑的工件，代码完全生成、永不手改，drift 由构造消除——仅当生成工具成熟可信时可行（OpenAPI 桩代码、Simulink→认证 C 代码已是既有实践；Tessl 是通用软件的愿景尝试）。
- **AI 催化论证**（§I-A; §IV）："AI 擅长模式补全、不擅读心"——松散 prompt（vibe coding）迫使 AI 猜测数十个未言明假设；spec 充当"super-prompts"，按上下文窗口粒度分解复杂度；引转述级实证称人工精炼 spec 使 LLM 代码错误至多降 50%（§IV，转引 InfoQ/Red Hat 文章，非受控研究）；spec 还支持并行 agent 分区执行。
- **四阶段工作流**（§III; Fig.2）：Specify（What）→Plan（How 约束）→Implement→Validate，每阶段产物约束下一阶段、均设人审检查点；验证失败时"改代码或改 spec"二选一，spec 恒为权威。
- **与传统设计文档的本质区别**（§X）：不在写什么，在**advisory vs enforced**——可执行（BDD 场景/契约测试/模型仿真）、CI 逐提交强制、面向 AI 消费三件套；自认"SDD 不是革命，是 BDD 换品牌"（引 Finster）。
- **案例**（§VI）：金融微服务 API-first（Specmatic，集成周期 −75%）；企业 BDD（Gherkin 作共享权威语言）；汽车引擎控制（Simulink 模型级验证+认证代码生成满足 ISO 26262——spec-as-source 在安全关键域已是数十年既成事实）。
- **陷阱**（§IX）：过度规格化（spec 退化为伪代码即过界）；规格腐烂（无自动强制则必然漂移）；**虚假信心**（spec 测试通过只保证"符合 spec"而非"正确"——spec 错则代码忠实实现错误；spec 需要与代码同级的评审）。黄金法则：用消除歧义所需的最小严格度（§VIII）。
