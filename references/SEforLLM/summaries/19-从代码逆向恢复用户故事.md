# 论文摘要：从代码逆向恢复用户故事——LLM 反向文档化生成侧的首个实证

## 1. 适用场景

- 当你需要 **"从源代码直接生成用户故事"的可行性证据与量化基线**（首个该方向研究；F1 随代码复杂度的衰减曲线与三档忠实度阈值）时，读这篇。
- 当你要为反向文档化/意图恢复任务 **选模型（参数规模×成本×微调）或选 prompt 策略（one-shot / few-shot / 结构化思维链）** 时，读其 §III-B、§III-C 与 §IV。
- 当你需要为"生成文本 vs 参照文本"的语义忠实度 **挑选自动度量并设定判读阈值**（为何弃用 BLEU/ROUGE、为何选 bert-base-uncased）时，读其 §III-D 与 Table II。
- 当你要论证 **"用户故事（why）≠ 代码摘要（how）"** 的定位区分，或评估"LLM 能否从实现反推人的意图"的能力边界时，读其 §I、§II。

> 锚点：Abstract; §I Introduction; §II Related Work; §III Methodology（A 数据 / B 模型 / C Prompt / D 度量 / E 实验设置）; §IV Findings（RQ1 / RQ2）; Fig.1–3; Table I–IV; §V Threats to Validity; §VI Conclusion and Future Work

## 2. 主要观点与方案

### 2.1 问题定位与贡献（§I; §II）

- **首个直接从源码恢复用户故事的研究**：既有用户故事生成工作全部依赖既有文本规格——需求文档（Rahman & Zhu 的 GeneUS/GPT-4）、issue 记录、干系人访谈、设计规格（§I; §II）——而源码是最持久、最普遍存在的工件，常比设计笔记/会议记录活得更久（遗留系统、团队更替后尤其如此）。
- **与代码摘要的本质区分**：摘要回答"代码怎么做"（面向技术读者），用户故事回答"代码为何存在"——用户角色+目标+收益（"As a [role], I want [goal] so that [benefit]"），非技术干系人（产品经理、客户、新人）可读，可用于回顾会对照"预期 vs 已实现"、改善 onboarding 与 OSS 新人留存（§I）。
- 贡献三条（§I）：首个研究；发布 1,750 对 C++ 代码-故事数据集；对模型规模与 prompt 设计（SCoT、k-shot）的实证分析。RQ1：LLM 能否从代码生成用户故事？复杂度与架构如何影响？RQ2：SCoT / k-shot 提升到什么程度？

### 2.2 数据集与真值构建（§III-A）

- 语料：IBM CodeNet 的 Project_CodeNet_C++1400 子集（约 42 万个 C++ 受理解答、1,400 个竞赛编程任务）。选 C++ 因其 GitHub 语言排名第 6、约 10% 公共贡献（§III-A 正文口径；其引文 [30] 注记为 8%，原文内部略有出入）、2024 全年居 TIOBE 前 3。
- **用真实仓库标定尺寸带**：克隆 star 数 top 200 的 GitHub C++ 仓库（2025-03），测 950 个类、15,400 个函数的 NLOC——函数均值 55，类集中于 100–200；据此设 35 个等长分层（1–10, 11–20, …, 341–350 NLOC）× 每层随机 50 个 CodeNet 文件 = **1,750 片段**；100–200 NLOC 被标为"实践中功能复杂度"的兴趣区间（图表中灰显）。
- prompt 长度从 350 输入 tokens（zero-shot, 1–10 NLOC）到 3,500 tokens（few-shot+SCoT, 341–350 NLOC），同时考验逻辑复杂度与 LLM 对"lost in the middle"的鲁棒性。
- **真值**：3 名 C++ 熟练研究者独立为每段代码撰写用户故事再调和分歧，Cohen's κ = 0.86（almost perfect agreement）。数据集与全部 prompt 模板见补充材料（Zenodo，§III-A; §III-C; [36]）。

### 2.3 模型选择与成本（§III-B; Table I）

- **5 个 LLM**：LLaMA 3.1 指令微调三档 8B/70B/405B（同架构同训练数据、规模差两个数量级——干净隔离"参数更多⇒更好"假设）；DeepSeek-R1（推理控制器+内置结构化思维链的推理架构）；GPT-4o-mini（原样 + 轻量微调版，微调用 70 个上下文示例）。
- 每 1M tokens 价格（输入/输出, USD, Table I）：LLaMA-8B $0.05/$0.25；LLaMA-70B $0.65/$2.75；LLaMA-405B $9.50/$9.50；DeepSeek-R1 $0.55/$2.19；GPT-4o-mini $0.80/$3.20；O1 $10.00/$40.00（O1 输入约为前者的 ~200×、输出 ~160×；标准 GPT-4o 比 DeepSeek-R1 贵 3–5×，§III-B）。
- 推理模型的冗长代价：DeepSeek-R1 平均 620 输出 tokens（偶超 2,500），约为 LLaMA-70B / GPT-4o-mini（100–130 tokens）的 5×（§III-B）。

### 2.4 Prompt 设计（§III-C）

- 6 个模板 = {zero-shot, one-shot, few-shot} × {有/无 SCoT}。**SCoT（Structured CoT）**不同于自由形式 CoT，用顺序/分支/循环三类程序原语分解推理——与代码控制流结构对齐，故适合反向工程场景（§III-C; [41]）。
- 抗"lost in the middle"：把指令（如"以 'As a...' 格式输出用户故事"）放在长 prompt **开头**，试点测试中指令遵循度 +22%（§III-C）。

### 2.5 度量学：BERTScore(bert-base-uncased) 的选型论证（§III-D; Table II）

- 构造 60 对用户故事对（3 类 × 20）：Twin-Minimal（仅微小词汇变化、语义同）、Paraphrase-50（约 50% 词汇变异、语义等价）、Different-Meaning（根本性语义偏离），对比 3 个 BERTScore 变体 + ROUGE + BLEU。
- **BLEU/ROUGE 判废**：Paraphrase-50 与 Different-Meaning 得分几乎无差（BLEU 65 vs 56；ROUGE-L 55 vs 50），无法区分"保义改写"与"变义"；roberta-large / deberta-large 对变义对区分度不足（81/84）。
- 唯 **bert-base-uncased** 呈现良好梯度：97 / 85 / 60 → 采纳，并定义三档判读阈值：**忠实 ≥0.9；充分改写 0.66–0.9；变义 ≤0.65**（§III-D）。

### 2.6 实验设置（§III-E）

- 三个维度：① 5 模型架构对比；② 全模型成对测 SCoT 有/无；③ 对最小模型 LLaMA-8B 做 6 变体集中 prompt 工程（知识注入 vs 结构化推理两个来源分离）。全部经 Replicate 平台运行保证环境一致；解码参数统一 temperature=0、最小输出 50 tokens、重复惩罚 0.2；按 35 个复杂度带分层评估。

### 2.7 发现（§IV; Fig.2–3; Table III–IV）

**RQ1——能力与规模（§IV-A）**：
- 总体可行，但 F1 随 NLOC 单调下降（Fig.2; Table III）。<100 NLOC：每个模型 F1 ≥0.78，区段均值无一低于 0.83；100–200 NLOC（实践复杂度区间）：F1 0.77–0.84，保持"充分改写"档；>200 NLOC：无一低于 0.74、无一跌破变义线 0.65——衰减可归因于 lost-in-the-middle（§IV-A1）。
- 规模收益递减：8B 最弱（≤255 NLOC 全程最低）；**255 NLOC 之后 405B 反而落到 8B 之下**；70B 在复杂度上升时持续压过 405B，且价格远低——70B 是最具性价比的开源选项（§IV-A2）。
- 推理架构无红利：DeepSeek-R1 全程仅与 8B 相当——其推理能力主要训练于代码/数学，而用户故事生成需要同时捕捉功能与背后的人类目标/意图（§IV-A2）。
- 轻量微调有效：GPT-4o-mini 微调版在中小 NLOC 区间提升，且输出 token −80%（§IV-A2）。

**RQ2——prompt 技术（§IV-B）**：
- **SCoT 增益取决于模型规模**：大模型（70B/405B）在 101–200 与 201–350 带最多 +4%（Table III：70B 0.80→0.83、0.78→0.80）；小模型（8B、4o-mini、微调版）无显著变化或反降——可能缺乏整合额外推理指令的表征容量（§IV-B）。
- **one-shot > few-shot**：zero→one-shot 使 8B 在 101–200 与 201–350 带 F1 +4%（0.77→0.81；0.75→0.79，Table IV；1–100 带无增益甚至略降 0.83→0.81）；few-shot 在 one-shot 之上仅再 +1%——8B 能从单个示例有效抽取隐式规则（§IV-B; Table IV）。
- **小模型逆袭**：极简 prompt 下 8B 全复杂度最高 F1 仅 0.73；加示例后 8B 在 **>120 NLOC 持续超过 LLaMA-70B**；SCoT 与示例组合仅 ±1%（§IV-B; Fig.3）。

### 2.8 效度威胁与未来工作（§V; §VI）

- 威胁：CodeNet 竞赛代码 ≠ 大型生产系统（自包含功能单元，定位为概念验证）；≤350 NLOC 简化问题空间（与热门 GitHub 仓库典型类/函数尺寸对齐；更大系统可靠分层抽取+分块）；仅 C++（流行度论证、方法可迁移）；真值主观性由三人独立撰写+调和+κ=0.86 缓解（§V）。
- 未来：分层抽取把函数级故事聚合为类/模块级叙事（>200 NLOC 分块）；**把用户故事恢复用作 AI 编码助手的验证机制**——检测实现与用户意图的偏离、自动幻觉检测与自校正（§VI，展望、未实施）。

## 6. 与本仓库研究的相关性注记

- **与 C-2 的对应（生成侧直接实证）**：研究备忘 §13.4-C2 确立拓展课题"反向文档化的可信度验证"——设想敏捷多轮迭代后由 LLM 从产物反向整理过程文档（用户故事/需求级），替代前期重文档。本论文正是该设想**生成侧**的直接实证：反向整理的落点是用户故事层，比 Reversa 线（2605.18684，操作规格层）更靠近业务语义，覆盖了 C-2 设想中"反向整理到需求层"这一档；其 §VI 展望"故事恢复作为 AI 编码助手的验证机制（意图偏离检测/自动幻觉检测/自校正）"与 C-2 的验证动机同源——但该展望在论文中仅是 future work，验证层完全未实施。
- **对本仓库反向文档化课题的输入价值（prompt 工程发现）**：①**one-shot 即饱和**（few-shot 仅再 +1%）：反向文档化只需一个高质量"代码→用户故事"示例，不必堆 few-shot；②**SCoT 只对大模型有效、对 8B 级本地模型无效或负效**：若本仓库用本地小模型批量反向整理，应投资示例而非结构化推理；③**指令前置抗 lost-in-the-middle**（指令遵循 +22%），长上下文反向整理的 prompt 布局可直接借用；④**度量学结论可复用**：bert-base-uncased 三档阈值（≥0.9 / 0.66–0.9 / ≤0.65）可直接作为"反向生成物 vs 参照文本"的自动初筛标尺，BLEU/ROUGE 不可用。对照本仓库 04/05 轮"从代码提取 UML/OpenAPI"的双通道方法（AST 确定性通道 + LLM 语义通道、diff 对账）：本论文是**纯 LLM 单通道、无确定性通道、无对账环节**——双通道经验恰好可作为其方法缺口的补法。
- **论文未覆盖的验证层空白（C-2 的差异化空间）**：论文的"忠实"仅指与三位标注者手写真值的 BERTScore 语义相似度，且自认局限——竞赛代码自包含（§V）、真值有主观性、仅 C++、≤350 NLOC。它**没有回答"恢复出的用户故事对原需求的忠实性如何检验"**：真实敏捷场景中不存在手写 ground truth 可对照，论文"与真值比相似度"的评估范式在 C-2 场景下不可用；且 0.66–0.9 的"充分改写"档对需求语义而言仍可能丢失关键约束（论文对变义的识别也只到 ≤0.65 一刀切）。这正是研究备忘 §13.4-C2 指出的空白——"反向生成物如何证明忠实？"，本仓库的检查器体系（闭包/一致性/diff 应用于"反向生成物↔代码/历史"）正是该空白的差异化答案（研究备忘 §13.4-C2）。
