# 论文摘要：协议驱动的多智能体 LLM 工程（SEMAP：行为契约 + 结构化消息 + 生命周期验证）

## 1. 适用场景

- 当你要为多 agent LLM 系统设计协议层/中间件（在 A2A 等通用互操作协议之上叠加领域约束），而不是继续堆松散 prompt 与角色扮演时，读这篇作参考架构。
- 当你用 MAST 失败分类（under-specification、inter-agent misalignment、inappropriate verification）诊断多 agent 系统失败、并寻找架构级（而非 prompt 级）缓解手段时。
- 当你要在代码生成/漏洞检测等多 agent 工作流中引入 Design by Contract 式行为契约、schema 化消息、FSM 生命周期验证门控，需要现成的形式化定义（元组表示）与评估方法时。
- 当你需要对照"MetaGPT 式角色编排 baseline"量化协议约束对失败总数与轮次稳定性的影响、或复现该类实验（HumanEval/ProgramDev/devign100/vudenc100 + LLM-as-a-Judge 失败计数）时。
- 当你在 A2A/MCP 等协议生态中判断"通用互操作 vs 领域专用协议"的分层取舍时（本文是 domain-specialized 协议的代表工作）。

> 锚点：§I. INTRODUCTION; §II. BACKGROUND; §III. METHODOLOGY; §IV. PRELIMINARY EVALUATION; §V. CONCLUSION AND FUTURE WORKS。

## 2. 主要观点与方案

### 2.1 研究问题与动机（§I. INTRODUCTION）

- 背景：2025 年全球开发者约 4,700 万仍供不应求；AutoGen/MetaGPT/ChatDev 等端到端框架按 Agile/Waterfall 等流程模型把开发角色编排成多 agent 系统，但实践失败率高。
- 核心论断：MAST 识别的三类反复失败只是症状，根因是三类经典 SE 结构缺陷——(1) 组件设计不足（agent 职责与角色边界不清）→ under-specification；(2) 接口规约不足（agent 间通信缺语义结构与类型化格式）→ coordination misalignment；(3) 转换逻辑不当（阶段推进无形式化门控/校验）→ inappropriate verification。
- 主张：经典 SE 的解法（组件带显式契约、接口形式化、状态机协调 + 验证保证正确性）在现有多 agent LLM 框架中基本缺位；SEMAP 首次把三条 SE 原则统一进一个 SE 领域专用的协议层，实现为 Google A2A 之上的轻量协议中间件，同时支持 centralized 与 decentralized 工作流。

### 2.2 背景与协议生态（§II. BACKGROUND）

- §II.A Multi-Agent LLMs for SE：多 agent LLM 按角色分工模拟人类协作，覆盖需求工程（模拟用户交互做需求引导/分析/确认）、代码生成（planner/implementer/reviewer 协作并守编码规范）、质量保障（测试生成/执行/分析）、漏洞检测（识别与缓解安全缺陷）、维护（运行时监控、故障诊断、补丁生成）。
- §II.B Multi-Agent Protocols：协议按两维分类——context-oriented vs inter-agent、general-purpose vs domain-specific；Google A2A 是通用互操作代表：结构化 HTTP API + JSON-RPC 2.0 消息、每个 agent 暴露 run() 函数并发布机器可读 Agent Card（身份、端点、输入输出模态如文本/图像/文件、认证要求、能力），支持跨环境动态发现与集成。

### 2.3 SEMAP 方法三组件（§III. METHODOLOGY）

- §III.A Methodology Overview：可靠的多 agent 协作需要经典 SE 的三大抽象——components、interfaces、transition logic，分别落到三条原则；Fig. 1 给出总览。
- §III.B Explicit Behavioral Contract Modeling（借 Design by Contract）：每个 agent 建模为可验证 schema 的行为契约 C = (name, IC, OC)——IC 为必需输入 artifacts 集合（前置条件：任务计划、同伴反馈、先前输出），OC 为预期输出 artifacts 集合（后置条件：Coder 产出的代码、Reviewer 产出的 review log）；显式形式化职责与角色边界，缓解设计期与运行期的 under-specification。
- §III.C Structured Messaging（借类型化接口设计/schema 驱动通信）：每条消息 M = (sender, receiver, CM)，CM 是 schema 指定的对象列表（code、review log、reviewer comment 等）；保证 agent 间信息交换语义清晰完整，缓解 coordination misalignment。
- §III.D Lifecycle-Guided Execution with Verification（借状态机工作流建模 + 阶段化测试）：任务生命周期建模为有限状态机 L = (S, Σ, δ, s0, F)——S 为阶段集（initialized、implementing、reviewing、completed、failed），Σ 为验证结果（pass、fail），δ: S×Σ→S 按验证结果驱动转移，s0 为初始阶段、F 为终态集；任务推进被验证门控，失败可触发恢复或重派，防止过早/无效终止，保证全局任务完成与输出有效性（契约与消息只保证局部正确）。

### 2.4 实验设置（§IV.A Experiment Settings）

- 两类任务、四个数据集：function-level 开发用 HumanEval（按文字规约写简洁函数）；deployment-level 开发用 ProgramDev（出自 MAST 论文，从一句话用户需求开发完整部署）；C/C++ 漏洞检测用 devign100（Devign 随机抽 50 脆弱 + 50 安全函数，片段通常 <30 行，聚焦指针误用/不安全内存操作等局部模式）；Python 漏洞检测用 vudenc100（按 CVEFixes 行级标注随机抽 50+50，片段更长更复杂、含真实 CVE 补丁与嵌套逻辑）。
- Baseline 与架构：baseline 用 MetaGPT 实现。开发任务为 centralized 五 agent（CEO、Planner、Coder、Reviewer、Tester），每任务最多 5 轮协作；漏洞检测任务 baseline 与 SEMAP 均为 decentralized 三 agent（Auditor、Critic、Tester），执行单轮分析 + 投票。
- 模型与失败判定：agent 底座模型为 DeepSeek-V3-0324 与 gpt-4.1-nano-2025-04-14；失败分类沿用 MAST 的 LLM-as-a-Judge 流水线（judge 模型 gpt-4o-2024-08-06），把每个实例归入 specification issues、inter-agent misalignment、task verification failures 一类或多类。
- 研究问题：RQ1 问相对 baseline 三大类失败总数的降幅；RQ2 问失败随协作轮次变化是否稳定、是否减少复发。

### 2.5 主要发现（§IV.B Experiment Results; Table I; Table II; Fig. 2）

- RQ1：所有数据集 × 模型组合下 SEMAP 均降低失败数。开发任务中 under-specification 降幅最大（HumanEval：GPT-4.1-nano 137→39 即 −71.5%、DeepSeek 63→17 即 −73.0%）；inter-agent misalignment 可清零（ProgramDev DeepSeek 8→0，−100%）。漏洞检测的降幅在三类失败间更均衡，对应并行协作的去中心化工作流。
- RQ2（轮次稳定性）：SEMAP 失败数随轮次单调稳定下降，baseline 常在暂时下降后复发——HumanEval under-specification 到第 5 轮：GPT-4.1-nano-SEMAP 20→2、DeepSeek-SEMAP 14→0，而两个 baseline 分别收于 9 和 2；ProgramDev：GPT-4.1-nano-SEMAP 16→3、DeepSeek-SEMAP 14→0，两个 baseline 均收于 3。misalignment 与 task verification 呈类似模式。

### 2.6 结论与未来工作（§V. CONCLUSION AND FUTURE WORKS）

- 结论：SEMAP 三原则（行为契约、结构化消息、生命周期验证）显著提升多 agent LLM 在 SE 任务上的稳健性，对 centralized/decentralized 工作流均有效。
- 自述局限与未来工作：当前为 preliminary 评估——将扩展到更大数据集、更大 agent 群、更长工作流；增加 baseline（单 agent LLM、领域专用检测器）；做消融以分离契约/消息/生命周期各自贡献；测量资源开销；支持跨 agent 工具使用；协议正确性的形式化验证；发布 artifacts 以便复现（当前未开源）。
