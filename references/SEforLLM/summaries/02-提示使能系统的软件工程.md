# 论文摘要：Promptware 工程——prompt 作为软件制品的软件工程议程

## 1. 适用场景

- 当你要为团队/组织**建立 prompt 的工程化开发流程**（需求→设计→实现→测试→调试→演化→部署→监控），摆脱逐条试错的 ad hoc 方式时，读这篇。
- 当你要**论证 prompt 与传统代码/软件制品的本质差异**（自然语言 + LLM 运行时的 10 项特征 C1–C10），为 prompt 专用工具或方法找理论基础时，读这篇。
- 当你在做 **prompt 测试/调试方向的研究选题**（flaky test、test oracle、test adequacy、prompt 调试会话）或** prompt 语言/编译/IDE 方向**的设计时，读这篇——27 项研究机会（O1–O27）可直接当选题清单。
- 当你需要引用**"prompt 开发现状堪忧"的实证证据**（试错为主、仅 21.9% 的 prompt 变更有文档记录）来支撑 prompt 治理/平台建设的立项时，读这篇。

## 2. 主要观点与方案

### 2.1 问题与动机：promptware crisis（Abstract; §1 Introduction）

- 背景：LLM（GPT / LLaMA / DeepSeek）大规模进入软件产品，形成 **prompt-enabled systems**——prompt 成为塑造系统行为的"编程"接口；从业者已有 Liquid / LangChain 等模板方案，**promptware** 范式把自然语言 prompt 当作一等软件制品（first-class software artifacts）。
- 双重本质差异：**语言侧**是歧义、非结构、上下文相关的自然语言；**运行时侧**是以概率性、非确定性 LLM 为运行环境（引发类人行为、能力边界不清、错误处理未定义、执行控制不确定）。OpenAI / Meta 的官方 prompt engineering 指南是 output-centric 的，缺乏系统性开发方法；实证研究（Mailach、Parnin、Dolata、Liang、Nahar）一致表明 prompt 开发是耗时试错——作者称之为 **promptware crisis**。
- 两大立论依据：(1) prompt 已成为关键软件构件、prompt 开发是一种新形态的编程，应纳入 SE；(2) 数十年 SE 积累证明系统化方法能管理复杂度、保障质量，可把 prompt 开发从实验性实践改造为结构化规程。

### 2.2 概念与相关工作定位（§2 Preliminaries; §2.1; §2.2）

- 术语链（§2.1）：prompt-enabled systems（以 prompt 为主要接口的 LLM 应用）→ promptware（prompt 为核心制品的软件范式）→ **promptware engineering**（把 SE 原则系统应用于 prompt 开发）；定位是 SE 在 LLM 时代的**自然演化**而非替代——需求、设计、测试、部署等活动仍在，但须针对自然语言接口与非确定性执行重新诠释。
- 相关工作两分（§2.2）：**prompt engineering for SE** 已较充分（如 LLM4测试综述中约三分之二研究采用 prompt engineering；Hou 等识别出 8 种技术）；**SE for prompt engineering** 不足——现有实证只识别挑战（实验性质、上下文长度、成本、prompt 不可预测变化、自由职业者的试错循环），Liang 把 prompt 概念化为新型程序；Hassan 等的 FMware 挑战目录提出 prompt-aware IDE、prompt transpiler，但把 prompt 开发当**单步**问题。本文差异点：**全生命周期、工程中心**的视角。

### 2.3 与传统软件范式的系统对比：C1–C10（§3; Fig. 1; Table 1; Table 2）

- 语言侧（§3.1; Table 1）：C1 Structure and Formalism（严格语法 vs 无结构开放文本）；C2 Explicitness and Determinism（显式确定、可做数据流/控制流分析 vs 歧义、上下文依赖、概率行为）；C3 Correctness and Quality（形式规约定义正确性、语法错误即失败 vs 无普适正确性标准，错别字可能不报错但悄然改变语义）。
- 运行时侧（§3.2; Table 2）：C4 Determinism（同输入同输出 vs 同 prompt 不同输出）；C5 Human-Like Characteristics（机械执行 vs 上下文推理、情绪对齐、社会智能，受偏见影响）；C6 Capability Boundaries（边界清晰可预测 vs 边界不清且演化、黑盒）；C7 Error Handling（确定性错误信息/栈回溯 vs 隐式容错、可能幻觉而无错误信号）；C8 Execution Control（可单步、查变量、用调试器 vs 只能启发式改 prompt 间接影响）；C9 Access Control（权限/内存保护/沙箱 vs 缺乏细粒度控制，易受 prompt injection 与敏感信息泄漏）；C10 Memory Management（显式分配回收 vs 无持久记忆，跨交互需外部记忆机制）。

### 2.4 路线图：6 大活动 × 27 项研究机会（§4; Fig. 2，每项机会标注关联的 C 特征）

- **Prompt Requirements Engineering（§4.1，O1–O4）**：O1 LLM 驱动的需求工程——需求须对齐 LLM 能力/约束，并计入人格、偏见、情绪对齐等类人特性（建议 CS+语言学+心理学跨学科）；O2 功能/非功能 prompt 需求（清晰性、抗偏见、时延与 token 效率）；O3 多目标权衡（role-play 提升相关性但放大偏见；细化指令提质但增加 token 成本，需依赖实证测试而非形式验证）；O4 抗歧义规约——半形式/形式化 prompt 规约语言（结构模板 + 自然语言注释，支持自动校验）。
- **Prompt Design（§4.2，O5–O8）**：O5 形式化 **prompt 设计模式**（意图、适用条件、构成组件——角色/指令/示例/约束、预期效果、失败模式与权衡；借鉴 agentic design patterns，催生 recursive prompting、failure-resilient 等新模式）；O6 prompt 设计工具（类比 UML）；O7 prompt 设计度量（cohesion / coupling / complexity + 记忆保持度量、概率确定性得分、错误处理度量）；O8 prompt 模式仓库（能力感知、对抗鲁棒性专区、长程依赖模式）。
- **Prompt Implementation（§4.3，O9–O15）**：O9 **prompt 中心编程语言**（prompt 为一等程序实体：模块化 prompt 单元、显式上下文作用域、类型化/约束式输出契约，采用 soft/refinement 类型与置信感知契约；声明式为主、命令式编排为辅；衔接 CNL-P）；O10 **prompt 编译**（词法/语法分析 → prompt 中间表示 → 语义优化 → token 压缩 → 安全增强五阶段）；O11 prompt 中心 IDE（实时性能反馈、变体生成、概率一致性评估、歧义检查）；O12 prompt 优化（search-based SE / 遗传算法 / 多目标优化）；O13 在线 prompt 实现（实时适应性与上下文一致性平衡）；O14 prompt 中的 role-play（角色过刚限制输出、过泛丢失上下文；刻板印象偏见及缓解）；O15 prompt 库与 API（版权与许可如 PRSA prompt 窃取问题、依赖追踪、访问控制）。
- **Prompt Testing and Debugging（§4.4，O16–O22）**：O16 **flaky test**（超越二元 pass/fail，如"≥80% 测试轮次输出高度相似"才判通过；temperature=0 减小但不消除变异性，且不代表真实场景）；O17 测试输入生成（prompt 变量来源含 LLM 输出与其他组件，覆盖难保证）；O18 **test oracle**（人工评估慢且有偏、LLM-as-a-judge 可能放大共同偏见、metamorphic testing——改写任务描述应保持响应一致）；O19 测试充分性（对任务描述/上下文/示例/格式要求做组件级覆盖）；O20 单元与集成测试（prompt 链场景，需更可观测的执行控制工具）；O21 非功能测试（公平性 / 安全性——prompt injection / 隐私泄漏）；O22 **prompt 调试**（复现：捕获并重放可观测执行状态——prompt 制品、运行时配置、交互上下文，构成版本化可重放边界；定位：分解与消融，引入 "prompt debugging session" 抽象以统计方式区分真故障与随机波动；修复：基于失败模式的建议与验证；期望 LLM 主动标记歧义）。
- **Prompt Evolution（§4.5，O23–O24）**：O23 由代码变更、LLM 更新、用户反馈驱动的演化（上下文感知 prompt 管理系统）；O24 版本管理与可追溯（changelog、语义化版本类比、自动 diff 检查 prompt 变更对响应的影响、访问控制与回滚）。
- **Prompt Deployment and Monitoring（§4.6，O25–O27）**：O25 部署流水线与自动化（类 CI/CD、金丝雀发布、分阶段上线、安全回滚）；O26 运行时监控与可观测（guardrails 与策略检查、RBAC、审计日志、沙箱、自动化红队，应对 prompt injection / 数据泄漏 / 越狱）；O27 带反馈回路的自适应监控（结合用户反馈半自动精化 prompt，外部记忆机制支持长期追踪）。

### 2.5 局限与未来工作（§5 Limitations and Future Work）

- 自认局限：vision paper，框架**未经实现与实证验证**（有效性/可扩展性/可用性待真实系统检验）；落地需要 prompt 工程 + 传统 SE 的复合能力，小团队可能难以负担（未来可做自动化工具、引导式开发环境、跨学科培训降门槛）。
- 提供一个贯穿全生命周期的示例 vignette：LLM 客服系统（退款/物流咨询）——需求期定功能目标（准确且礼貌）、非功能约束（时延、单查询成本）与可信性要求；设计期拆分系统指令/任务描述/上下文输入的结构化模板并定义与检索知识、后端工具的交互；实现期 prompt 与代码并列实例化、参数化、版本化；测试期自动生成用例（含边界与对抗输入）+ 评估正确性/鲁棒性/公平性的 oracle；部署后监控输出质量、稳定性与策略合规并告警；随需求演化迭代精化再部署。
- 结论（§6 Conclusion）：promptware 与传统软件的 10 项特征差异使试错式开发难以为继；promptware engineering 以 27 项研究机会覆盖 8 个生命周期环节，本质上是 SE 与 AI 的交叉学科议题。
