# 论文摘要：Lost in the Middle（长上下文中的信息丢失）

> **原论文标题**：Lost in the Middle: How Language Models Use Long Contexts
> **完整 PDF 文件名**：`02-Liu-Lost_in_the_Middle.pdf`
> 作者 / 年份：Nelson F. Liu et al.（Stanford / Berkeley / Samaya AI），2023，arXiv:2307.03172
> 摘要类型：Agent 设计参考 + 内容索引
> 生成日期：2026-08-12

## 1. 适用场景

- 设计或评估 **RAG / 长上下文阅读器** 时：当检索器返回多份文档拼入 prompt，需要确认模型能否稳定利用其中的关键信息。
- 设计 **文档排序 / 重排（rerank）/ 截断** 策略时：评估"把相关文档放到 prompt 的哪个位置"对答案质量的实际影响。
- 评估 **长上下文窗口模型** 的实际利用能力，而不仅是窗口大小。
- Agent 上下文供给策略（如分块供给、首尾锚定）的事实依据——本文是"少即是多 + 首尾锚定"的最早系统化实证之一。

> 锚点：摘要（Abstract）；§1 Introduction。

## 2. 主要观点与方案

### 2.1 核心发现（"U 形性能曲线"）

- 模型对长上下文中信息的利用 **强烈依赖位置**：相关文档位于开头（primacy bias）或结尾（recency bias）时效果最好，位于中间时性能显著下降。
- GPT-3.5-Turbo 的多文档 QA 准确率在 20 / 30 篇文档设置下，**最差可低于 closed-book 基线**（即"给文档反而比不给更差"）。
- 扩展上下文窗口的版本（GPT-3.5-16K、Claude-100K）相比原版 **并未带来利用能力的提升**——窗口大不等于用得好。

### 2.2 实验方法

- **任务 1：多文档问答**（§2）—— 在输入中插入 10 / 20 / 30 篇文档，被测模型需从中定位并回答问题；控制相关文档在 prompt 中的位置。
- **任务 2：键值检索**（§3）—— 合成 JSON 键值对，控制目标键的位置；剥离语义干扰，单纯衡量"取回"能力。
- **讨论维度**（§4）：① 模型架构（decoder-only vs encoder-decoder）；② 查询感知上下文（query-aware contextualization）；③ 指令微调的影响；④ closed-book vs oracle 对照。
- **案例研究**（§5）：开放域 QA 中检索器召回率饱和远早于阅读器性能饱和。

> 锚点：§2.1 实验设置；§2.3 主要结果；§3 键值检索；§4.1–§4.3 影响因素讨论；§5 开放域案例。

## 5. 一句话索引（给 Agent 用）

> 设计 RAG / 长上下文阅读器时，**不要假设模型能用好整个上下文窗口**：相关文档放首尾、把多文档 QA 视为"放首位"的优化问题、检索召回率 ≠ 阅读器利用能力——这是本文给 Agent 上下文供给策略的核心教训。
