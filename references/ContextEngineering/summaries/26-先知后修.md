# 论文摘要：ACQUIRE（修代码前先问代码——QA 驱动的仓库知识获取）

> **原论文标题**：Know Before Fix: QA-Driven Repository Knowledge Acquisition for Software Issue Resolution
> **完整 PDF 文件名**：`26-Lin-Know_Before_Fix_v1.pdf`
> 作者 / 年份 / 出版：Haotian Lin, Silin Chen, Xiaodong Gu, Yuling Shi, Chengxi Pan, Jiaqi Ge, Mengfan Li, Jianghong Huang, Mengchieh Chuang, Beijun Shen, Haibing Guan（Shanghai Jiao Tong University; U. Pittsburgh; GTIIT），2026，arXiv:2607.11111v1
> 摘要类型：Agent 设计参考 + 内容索引

## 1. 适用场景

- 设计**仓库级 SWE 修复流水线**时，在 patch generation 之前先显式做一次"知识缺口探测 + 补足"，而不是仅靠 issue 关键字搜索/排序。
- 当现有 pre-repair 探索方法以**fix-driven 角度**（suspicious location / 结构摘要）为主、却常给出**不精确上下文**时；ACQUIRE 提出分类引导的 QA 问句来更精准补足知识缺口。
- 当需要解决**背景知识缺乏导致的事实性错误**——跨模块依赖、隐式 API 契约、数据流——failure type 比 reasoning capacity 更频繁。
- 想用 oracle-style 探测先量化"通过该修复有多少原本失败的 case 能复活"再自动化推广时。
- 评估 / 比较 pre-repair 策略：LocAgent / CoSIL / LingmaAgent / SWE-Debate 是直接 baseline。

> 锚点：Abstract；§I Introduction；§II Motivation（Oracle QA experiment）；Figure 1 Overview。

## 2. 主要观点与方案

### 2.1 核心主张（"补知识缺口 vs 找修复地点"）

- 现有 pre-repair 方法（LocAgent、CoSIL、LingmaAgent、SWE-Debate）多为 fix-driven：要么产可疑位置列表，要么补结构摘要，都没有**先识别 agent 缺什么知识**。
- ACQUIRE 把"知识获取"和"修复"显式拆成两阶段，模仿工程师先代码理解再修 bug 的工作流。
- 关键贡献是引入**4 类知识维度**作为 Questioner 的结构化模板，让生成的问句既覆盖又 non-redundant / self-contained。

### 2.2 框架（§III Methodology）

- **阶段 I：QA 驱动的知识获取**
  - **Questioner**：4 个 Category 模板——
    1. **Mechanism & Behavior**：问功能性逻辑流 / 状态管理 / 数据处理（占 70.7%）。
    2. **Design & Usage**：问 API 定义 / class 层级 / 错误规约 / 设计惯例（18.1%）。
    3. **Locating & Structure**：问代码库布局 / 模块组织 / 依赖关系（7.8%）。
    4. **Ecosystem & Standards**：问外部库行为 / 协议约束 / 语言层语义（3.4%）。
    每个问题可自由选最相关类别而不强制 round-robin。
  - **Answerer**：与 Mini-SWE-Agent 同 shell 环境，**只读模式**，要求引用具体 file path / function name / code behavior；找不到就显式说"gap"而不是 fabricate。
  - **并行执行**：N 个 Answerer 实例隔离探索（避免相互污染），wall-clock 等于最慢的那个。

- **阶段 II：知识引导的修复（Resolver）**
  - N 个 QA pair 序列化成结构化文本块，**先一次性静态注入**（不用 streaming dynamic interleaving）以保留模块化 + 第一步就看到全貌。
  - 注入信息用于补足定位 + 编辑决策，对 reproduction / verification 阶段影响较小（这部分主要靠可执行反馈）。

### 2.3 Oracle QA 探测作为定量证据（§II Motivation）

- 给定 golden test patch，oracle Questioner 提出"最重要一个问题"，oracle Answerer 只准用 golden 涉及的文件。
- 在 DeepSeek-V3.2 + Mini-SWE-Agent 上失败的 **116 个 SWE-bench Lite 实例**中，oracle QA 注入了 **26 / 116 直接成功修复**（recovery rate）。
- 这个 22.4% 恢复率设定了 QA 范式能带来的潜在上限，是后续自动化设计的理论驱动。

## 5. 一句话索引（给 Agent 用）

> 设计 SWE 修复流水线时，**别只做"给定位、给摘要"这种 fix-driven pre-repair**——先用结构化 4 类模板（Mechanism & Behavior / Design & Usage / Locating & Structure / Ecosystem & Standards）让 Questioner 抛出针对知识缺口的问句，让并行只读 Answerer 给证据答案，最后把 QA 一次性注入 Resolver：在 SWE-bench Verified 上让 GPT-5-mini 从 58.4 → 62.2、DeepSeek-V3.2 从 66.4 → 70.8，oracle-style 实验表明 116 个原本失败 case 可复苏 26 个，验证了该范式的有效空间。
