## 1. 适用场景

- 设计 **编码 Agent 评测 / Benchmark 报告** 时：本文提出"评测 = 评测 harness + 模型"，应在报告中显式声明 harness 条件。
- 构建 **长周期、仓库级** 的编码智能体时：明确需要把哪些能力下沉到 harness（控制平面）。
- 做 **Agent 安全治理** 决策时：本文论证威胁面已从模型本身迁移到 harness 接口（工具、协议、沙箱、权限）。
- 给团队做 **Agent 落地治理** 时：理解 AGENTS.md、CLAUDE.md、skills、custom agent 等"仓库可见制品"成为可版本化的策略载体。
- 写 **Agent 综述 / 比较报告** 时参考：把"上下文工程 / Repo-native agency / Harness-native SE"区分清楚。

> 锚点：Abstract；§1 Introduction；§2.8 Missing lens；§10.1 与相邻术语的关系。

## 2. 主要观点与方案

### 2.1 核心框架：Harness-Native Software Engineering

- 定义编码智能体系统为 `A = ⟨M, H, E⟩`：M 为基础模型（或路由模型集），H 为 harness（控制平面），E 为执行环境。
- **主张**：在长周期、仓库级软件任务中，决定智能体成败、安全、成本、连续性的关键变量已经转移到 harness 层，而不再仅仅是模型本身。
- **术语区分**（§10.1）：Harness-Native SE ≠ "上下文工程"（仅是控制平面的一个子集）；≠ "Repo-native agency"（仓库在场但缺少 harness 抽象）；≠ "AI-native SE / SE 3.0"（覆盖更宽泛的人机协作风貌）。

### 2.2 Agent Harness Control Plane（八功能分解，§4）

H = ⟨C, A, X, S, V, R, D, G⟩，八项功能分别处理：

1. **Context ingress（C）**——任务描述、检索结果、AGENTS.md / CLAUDE.md、skills、memory、issue/PR 状态。决定"模型能看到什么"。
2. **Action mediation（A）**——工具 schema、权限模型、协议绑定（MCP / ACP）、审批门、策略过滤器。决定"模型能做什么"。
3. **Execution substrate（X）**——本地终端、editor 沙箱、容器、worktree、CI runner、云任务环境。决定"在哪执行"。
4. **State persistence（S）**——进度文件、checkpoint、git 历史、恢复的线程、记忆文件。决定"跨窗口/跨会话的连续性"。
5. **Verification & review（V）**——测试、lint、自审、PR review、安全扫描、CI gating。决定"如何独立校验产物"。
6. **Recovery & debugging（R）**——回滚、checkpoint 恢复、debug subagent、AgentStepper 等。决定"出错后如何恢复连贯性"。
7. **Delegation & coordination（D）**——subagent、specialist 工具、人审路由、跨 harness 调度（如 ACP）。决定"工作如何分配与协同"。
8. **Governance & audit（G）**——分支保护、沙箱规则、repo trust、审批策略、审计日志、provenance。决定"信任边界落点"。

### 2.3 五个主张（Propositions 1–5，§6）

- **P1 Harness sensitivity**：固定模型下，不同 harness 条件 `ΔH` 常常不弱于更换一个更强模型带来的收益——Debug2Fix 显示加一个 debug subagent 即可让弱模型追平强模型（§6.2）。
- **P2 Recovery dominance**：在长周期任务中，一旦具备基础仓库能力，**可恢复性**成为 verified success 的主要决定因素（Anthropic long-running harness、Debug2Fix、AgentStepper、FeatureBench 11.0%、Terminal-Bench、SWE-EVO 21% vs 65% 等数据支持，§6.3）。
- **P3 Artifact externalization**：团队越来越多地把 Agent 行为外部化到版本控制制品（context files / skills / custom agents / memories），而不是藏在 prompt 里（配置研究 + AIDev / Agentic Much 的采用数据，§6.4）。
- **P4 Boundary displacement**：实际可被攻击/防御的边界已经从模型输出层迁移到 harness 接口（protocol / tool / shell / network）。证据：prompt-injection SoK（自适应攻击成功率 >85%）、Breaking the Protocol（MCP 攻击放大 23–41%）、AIShellJack（恶意命令执行成功率高达 84%），§6.5。
- **P5 Evaluation inversion**：不显式固定 harness 条件的 Benchmark 会系统性高估/低估真实能力；排行结论在 harness 改变时可能反转（Agentic Benchmark Checklist、Saving SWE-Bench、FeatureBench、Terminal-Bench、SWE-EVO），§6.6。

### 2.4 方法学与可交付物

- **方法学（§5）**：四类证据——系统表面证据（官方文档）+ 基准证据 + 制品/工作流证据 + 安全证据；区分"实证观察 / 跨源综合 / 理论诠释 / 推测"四类断言。
- **Harness Condition Sheet（§7, Table 5）**：12 字段的 benchmark 报告模板（基模型、接口形态、context 制品、工具与协议、审批策略、网络策略、执行底座、持久化、验证栈、恢复机制、委托拓扑、预算）。
- **Threat Mapping（§8, Table 4）**：把攻击向量映射到控制平面功能——issue 投毒→Context ingress；恶意 shell→Action mediation + governance；MCP 冒充→Action mediation；过度网络权限→Governance + execution substrate；弱 CI 审查→Verification + governance；持久化记忆投毒→State persistence。
- **建议度量（§7, Table 6）**：VTS / RR / UAR / HIB / CE / Review friction / Verification depth。

### 2.5 应力测试（§6.8）

- 框架在四类任务上仍可解释：Feature development（FeatureBench）、long-running bug fixing（Anthropic 长周期案例）、security remediation（SEC-bench + prompt injection）、parallel agent workflows（GitHub mission control / multi-agent failures）。
