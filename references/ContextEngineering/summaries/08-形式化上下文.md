## 1. 适用场景

- **设计大型 / 多模块项目的 Agent 上下文架构** 时：把"单个 AGENTS.md/CLAUDE.md"扩展为三层基础设施（hot constitution / specialist agents / cold knowledge base）。
- **构建多 Agent 协作 / orchestrator 工作流** 时：把 trigger table + suggest_agent + MCP retrieval server 当作路由模板。
- **做 Agent 上下文基础设施的可观测性** 时：参考本文对 agent invocations、turns、人类 prompt 数的统计方法。
- **处理跨 session 持久知识** 时：参考 hot/cold memory 分离 + on-demand retrieval + specialist agent 嵌入 domain knowledge 的做法。
- **做 Agent 工程经验报告 / 系统论文** 时参考：本文的 case study 写法 + 威胁有效性讨论。

> 锚点：Abstract；§1 Introduction；§2 Related Work；§3 Architecture；§4 Evaluation；§5 Discussion。

## 2. 主要观点与方案

### 2.1 问题定位（§1）

- AI coding agent 没有 **persistent memory**——跨 session 失忆、忘约定、重复踩坑。
- 单文件 manifest（.cursorrules / CLAUDE.md / AGENTS.md）只能 cover **小型原型**，对 100k+ 行复杂系统不可扩展。
- 类比：把"文档当基础设施"（load-bearing artifacts），让 agent 把规范当作一等公民来消费。

### 2.2 三层架构（§3 + Figure 1）

| Tier | 名称 | 加载策略 | 体量 | 内容 |
|---|---|---|---|---|
| T1 | **Constitution（hot memory）** | 每 session 自动加载 | 1 文件，~660 行 | code quality 约定、naming、build 命令、架构摘要 + Tier 3 链接、checklists、known failure modes、**orchestration trigger table** |
| T2 | **Specialist Agents**（domain experts） | per task 触发 | 19 agents，~9,300 行 | 8 个 high-capability（~711 行/个）+ 11 个 standard-capability（~327 行/个）；每个含 domain scope、工具/权限、相关 T3 文档、output format、**known mistakes 表** |
| T3 | **Knowledge Base**（cold memory） | on-demand via MCP | 34 docs，~16,250 行（含 ~1,600 行 retrieval service） | 每个子系统一个 Markdown，规范为 machine consumption 写（明确 code patterns + 文件路径 + 参数 + 期望行为） |

- 总基础设施：~26,200 行，占代码总量 24.2%。
- 关键设计原则：**Constitution 要短（fit 整 session）**，详细文档放 T3 链接；T2 agent 把 domain knowledge **内嵌超过一半内容**（避免每次 retrieve 4–5 次）。

### 2.3 Orchestration 协议（§3.1.1 + Table 1）

- Trigger table 编码"哪个文件改动 → 哪个 specialist agent"。
- 例：网络 / sync 相关改动 → `network-protocol-designer`；坐标 / camera 改动 → `coordinate-wizard`；架构 / design 改动 → `systems-designer`；ECS / network review → `code-reviewer-game-dev`。
- 通过 MCP retrieval server 的 `suggest_agent(task)` API 做 routing。
- **redundant encoding**：constitution 同时要求"必须查 trigger table"和"使用 suggest_agent"——增强依从性。

### 2.4 Specialist Agent 设计原则（§3.2）

- **知识嵌入**：>50% 内容是 project-domain knowledge（codebase facts、formulas、patterns、failure modes），不是行为指令。
- **Symptom-Cause-Fix tables**：从 debug session 蒸馏，固化"踩坑"经验。
- **Emergence pattern**：agent 是 **失败驱动**——当某类任务反复需要重新解释知识时，codify 成新 agent（"if debugging X consumed an extended session without resolution, faster to create a specialized agent and restart"）。本文首批 agent：`network-protocol-designer` + `coordinate-wizard`（debug 失败率最高）。

### 2.5 Knowledge Retrieval Service（§3.3.1）

- 通过 **Model Context Protocol (MCP)** server（~1,600 行 Python）暴露 5 个工具：
  - `list_subsystems()`
  - `get_files_for_subsystem(key)`
  - `find_relevant_context(task)`
  - `search_context_documents(query)`
  - `suggest_agent(task)`
- 当前实现：keyword substring matching；语义检索列为 future work。

### 2.6 规模与交互（§4.2 / §4.3 / Tables 3）

- 108,000 行 C#（MonoGame + Arch ECS 分布式系统），405 个源文件，45+ ECS systems，55+ components，35+ 网络消息类型。
- 70 天 part-time，148 commits，283 development sessions，2,801 human prompts，1,197 agent invocations，16,522 agent turns（~9.9 prompts/session）。
- Agent invocations：757 可分类中 432（57%）为 project-specific specialist，325 为 built-in tool agent。
- 最常被 invoke：code-reviewer（154 次）、network-protocol-designer（85 次）。
- 两种 session 模式：structured plan-execute-review（~13%）/ ad-hoc（~87%）。
- 每个 human prompt 平均产生 ~6 autonomous agent turns（chain：file exploration、tool calls、plan review、SME consult）。
- 三阶段增长（Figure 2）：Phase 1（day 1–10）仅 100-line constitution；Phase 2（11–30）spec 涌现 + 初批 agent；Phase 3（31–57）整合 MCP retrieval + 扩 agent 池。

### 2.7 4 个 Case Study（§4.4）

- **Case 1**：preventing determinism regression via network protocol spec.
- **Case 2**：shop open/close UI 状态机经多次手动 debug 后写入 `ui-sync-patterns.md`（126 行），后续 radial selection dial 一次性套用"双 delivery 模式"成功。
- **Case 3**：drop system 重构触发 knowledge gap detection——agent 通过 `find_relevant_context` 找不到对应 spec，提示作者补文档。
- **Case 4**：autonomous debugging 跨 session 复用。

### 2.8 关键发现（§5 Discussion）

- 知识/代码比 24.2% 不是目标，反映 project 复杂度；**可操作信号**："agent 行为犹豫/不一致 ⇒ 对应 spec 可能缺失或过期"。
- 维护成本：spec 必须 **living document**，否则静默漂移。
- 与 ACE（Agentic Context Engineering）"evolving playbooks" 呼应；与 AutoGen/ChatDev/MetaGPT 互补——本文聚焦 "知识" 而非 "通信协议"。
- 与 Google Conductor 并发独立工作，区别：本文架构 **portable across tools**（不绑定 Gemini CLI）。

## 5. 一句话索引（给 Agent 用）

> **复杂代码库的 Agent 上下文不能只有一个 manifest**——把它做成 3 层基础设施：常驻的短 constitution（hot memory）+ 19 个 specialist agent（内嵌 domain knowledge >50%）+ 34 篇 on-demand spec 通过 MCP retrieval 服务检索，总投入可达代码量 ~24%；按"反复 debug 失败 → codify 为新 agent" 的失败驱动策略逐步生长。
