## 2. 主要观点与方案

### 2.1 定位与结构

阿里巴巴 2026-09 发布的 Agentic 研发范式实践手册，68 页纯图形排版（无文本层）。叙事起点：2024 年中行业主流为 Copilot（IDE 内嵌补全）；2024-11 Anthropic 发布 MCP、2025 年初 Claude Code 与 OpenAI Codex CLI 相继发布后，行业转向自主交付的 Agent 形态；SWE-bench 得分一年内从约 30% 升至约 80%（p2 ✅，数字无口径说明）。全书结构：

1. **三个业务案例**：AIDC 数字投手智能营销助手、千问用增 Agent、万有无界平台（第一章）；
2. **五个共性挑战**：范式导入、平台能力升级、提效度量、数字员工、组织与人才配套（第二章）；
3. **企业级基础设施全景**：Harness 框架、企业知识库、MCP/Skill/CLI 工具体系、Sandbox 与编码环境、身份与权限、生产安全 Guardrail、可观测性（第三章）。

### 2.2 核心诊断：瓶颈转移论（p2 ✅）

代码生成本身不再是瓶颈，瓶颈转移到"需求理解、环境构建、测试验证、发布运维"等占研发生命周期 70%~80% 的环节；企业竞争力取决于是否成体系地面向 Agent 重新设计基础设施（p3 ✅ 原句："我们成体系地面向 Agent 重新设计基础设施"）。组织侧配套表述：打破岗位与团队边界、知识透明流动、"超级个体"涌现（p3 ✅）。

### 2.3 需求侧实践：四问门 + 结构化 PRD（p22 ✅）

- **需求四问门**：业务方每次提需求必须回答四个问题——Who（目标用户是谁）/What（解决什么问题、达到什么目标）/Why（为什么现在做、业务价值）/How（方案与验收标准）；"回答不清楚的需求不该被做"。注：该页标题原文用词视觉转录存疑（"四心"或"四问"），四个问题本身核验无误。
- **结构化 PRD**：需求阶段产出结构化需求文档，包含上述四要素，机器可读，下游 Agent 可直接消费。
- **变更影响分析**：需求变更触发影响分析，自动更新关联文档（设计/API/测试用例）——文档级关联更新，未提及锚点级或可判定的回归机制（本库注：此空缺即确定性检查体系的增量空间）。

### 2.4 验证侧实践：验证前置 + 80/20（p23 ✅）

- "验证前置且贯穿全程——这是 Agentic 范式与传统流程最大的分野之一"：验证从研发末端环节变为前置门禁（CI 门禁不通过不能进主干）。
- 多级验证：静态检查 → 单元测试 → 集成测试 → 端到端验证。
- 80/20 分工：自动化验证覆盖约 80% 常规场景，人工评审聚焦约 20% 高风险场景（边界、安全、资损）。
- 失败自动归因：测试失败自动定位到需求/设计/代码层并分发给对应角色（运行时数据驱动的统计归因）。
- 需求级回归：需求变更后自动触发全链路回归。

### 2.5 可观测性：失败归因四分类与需求质量反哺（p59 ✅）

- 四个核心指标：任务成功率、Token 消耗、工具调用成功率、**人工介入率**（自动化程度的核心反向指标）。
- **失败归因四类（按占比排序）：需求模糊（第一）> 上下文不当 > 工具缺陷 > 模型能力不足**；页面原句："需求模糊是 Agent 失败的第一归因——这个结论反复出现在三个案例中"。
- 反哺机制：失败归因数据按周汇总，反哺需求模板（增加必填字段、澄清字段），"让需求质量成为可管理的工程对象"。

### 2.6 证据驱动修复（p21 ✅）

- Auto Bug Fix：测试失败后 Agent 自动收集证据（日志、trace、复现步骤、diff），自动生成修复方案并提交 PR，修复成功率约 89%。
- 证据链强制：每个自动修复 PR 必须附带完整证据链（失败日志 → 定位 → 修复理由 → 验证结果），人工抽检 10%。
- 原话："没有证据，就没有修复。"

### 2.7 角色分工变化与考核迁移（p19 ✅）

范式导入一年后的复盘表：

| 角色 | 原职责 | 现职责 |
|---|---|---|
| 产品经理 | 需求编写、优先级 | 对需求质量负责（需求模板、验收标准） |
| 架构师 | 系统设计 | 系统设计审核（AI 生成设计，人审边界） |
| 开发 | 编码 | 编排：拆解任务、管理 Agent 并发、验收产出 |
| 测试 | 测试用例编写与执行 | 测试策略制定 + 高风险场景人工测试 |

考核变化原话："过去考核'写了多少'，现在考核'验得怎么样'——验收能力成为核心考核项。"（本库注：架构师"审设计"用什么审，手册未给出可核验的审据——形式化锚点缺位。）

### 2.8 其余要点（多数经组图阅读，标 ◇ 者未单页复核）

- **数字员工**（p20 ✅）：有岗位、职责、目标、记忆、可成长的 Agent；与传统自动化的区别=目标导向对结果负责 vs 流程编排按既定流程执行；"数字员工不是工具，是 teammates"，纳入虚拟团队编制管理（含岗位职责说明书、绩效评估、任务交接协议 ◇）。
- **提效度量**（p62 ✅）：核心矛盾="管理层要总账，工程师要个案"；三层框架=宏观（组织级 ROI：提效工时×人力成本−工具投入）/中观（团队级交付周期与吞吐量）/微观（任务级耗时打点）；反虚荣指标原则（不用代码行数、提交数、AI 采纳率单指标论英雄）；"用真实交付数据说话"。
- **基础设施组件**（◇ 组图阅读，与简介页总览交叉一致）：企业知识库=文档向量化+结构化知识图谱双通道（知识质量评分与淘汰机制）；工具体系=MCP（连接协议）+Skill（能力复用）+CLI（执行），工具上架需质量门禁；Sandbox 三级隔离（开发/测试/生产）+环境镜像标准化；Agent 身份=独立 Agent ID+权限最小化+审计留痕；Guardrail 三层（输入侧 prompt 注入检测/输出侧代码扫描合规/执行侧权限拦截）；落地顺序建议=知识库 → Sandbox → 工具体系 → Guardrail → 可观测（按投入产出比）。
- **范式导入经验**（◇）："没有验证的产出等于没有产出"；失败模式三条（把 Agent 当高级补全工具未改流程/缺少验证闭环直接上线/组织未配套）；落地三阶段=工具引入→流程改造→组织变革，不可跳步。
- **组织侧**（p3 ✅ + ◇）：组织三原则=打破岗位边界、知识透明流动、让有价值观判断的工程师自主决策；人才结构="按判断力分工"取代"按技能分工"。

## 6. 与本仓库研究的相关性注记

- **对立项的佐证**：简介页瓶颈转移论与 requirement-to-spec 的立论同源；失败归因"需求模糊第一"是产业侧用自己的失败数据独立得出的同款诊断。引用注意：佐证的是问题，不是解法。
- **C-1 对照组设定（备忘 §13.4-C/§14.3）**：手册的需求侧对策停留在模板级（必填字段/澄清字段）+机器可读 PRD 原则（无格式、无校验、无一致性机制的细节），是"轻规格化"路线的产业真实形态。其业务构成（营销投放、用户增长，容错率高、生命周期短）恰好落在轻方案够用的场景端——与 loan-system（信贷，资损敏感、规则密集）构成两模式边界对照实验的两端设定。
- **§12.3 最终界面提议的产业印证**：角色分工变化表与"概要设计为界、之后人转审核"的提议几乎逐条对应；但架构师"审设计"无可核验审据（无形式化锚点）——把"审边界"变成"审差异"（UML/OWL/锚点比对）是本仓库相对产业实践的明确增量。
- **机制借鉴候选**：①人工介入率 → R3 实验可定义对称的"人工决策负载"指标（每轮人工决策条数/耗时）；②失败归因四分类 → 检查失败的归因分类可对齐（模型能力/工具缺陷/上下文不当/需求模糊 ↔ 本库两层归因的扩展维度）；③证据链强制 → E30 修正执行的证据链强制化（每条"已修正"须附定位锚+回归验证结果，否则视为未执行——针对第 35 场续六揭出的静默失败）。
- **可选小实验**：intelli-metric 三份原始需求按四问模板做模糊度预检，与 E30 审计 15 项发现对照，度量模板法与建模法的检出能力差异（成本低）。
