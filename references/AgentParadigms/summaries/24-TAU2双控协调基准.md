# 论文摘要：τ²-bench——双控环境下的协调能力测量

## 1. 适用场景

- 当你要评测**人机各持工具**（dual-control，如技术支持中用户须自己重启手机/关飞行模式）场景下 agent"引导用户行动"的能力时读这篇——现有单控基准（用户只是信息提供者）测不出这类短板。
- 当你要**程序化生成大批可验证任务**（原子子任务 init/solution/assert 三函数组合 + 自动正确性校验）而避免手工命题的脆弱性时，照抄其 §3.2 Stage 3 的组合式任务生成器设计。
- 当你的 **LLM 用户模拟器不可靠**（幻觉、提前终止、漏约束）时，读其"用环境与工具约束用户行为"的方案（§1、§4.3）：用户工具只输出人类可读结果、限制为被动响应式调用，可把模拟器总错误率从 40%+ 压到 16%。
- 当你要把 agent 失败**分解归因为推理 vs 沟通/协调**时，用其 Default / No-User / Oracle Plan 三模式消融（§4.2）。
- 当你要为新域搭建"agent 数据库 + 用户设备数据库 + 域政策 + persona"的多阶段构建流程时，参照 §3.2 的 5 阶段法。

> 锚点：Abstract; §1 Introduction; §3.1 The Dec-POMDP Formalism; §3.2 Domain and task creation; §4.2 Results; §4.3 How does dual-control impact benchmark reliability?; §5 Conclusion。

## 2. 主要观点与方案

### 2.1 研究问题与动机（§1 Introduction）

- 既有会话 agent 基准（含前作 τ-bench 的 retail/airline）本质是**单控环境**：只有 agent 能用工具改变世界，用户仅提供偏好与目标；真实场景（技术客服）中用户须主动执行诊断/修复动作（§1）。
- 引入 **dual-control**：LLM 模拟的用户除交流外还能调用工具作用于共享动态环境，由此带来选择性信息隐藏、非语言的环境操作、结构化任务指定等好处（§1）。
- 核心设计挑战是保持 agent 与用户模拟器之间的**复杂度不对称**（complexity asymmetry）：给用户"有意义的能动性"但确保其仍需 agent 支持才能解决问题；做法是用户工具只产出人类可读输出、把用户规划限制为响应 agent 请求的被动工具使用、用环境紧约束用户行为（§1）。
- 四大贡献：Telecom 双控域（Dec-POMDP 形式化）、组合式任务生成器、高可靠用户模拟器、推理 vs 沟通/协调的细粒度失败归因（§1、Abstract）。

### 2.2 Dec-POMDP 形式化（§3.1）

- 环境建模为 Decentralized POMDP，元组 (S, {Ai}, {Oi}, T, R, U, M)：消息空间 M（双方自然语言）；状态 S = Sworld ⊗ Shistory，其中 Sworld = Sdb,agent ⊗ Sdb,user（agent 侧 CRM + 用户侧手机状态）；动作 = 工具调用或消息，**每回合只允许一方行动、一方观察**；转移 T 由确定性工具执行 + 消息传递构成；奖励 R ∈ [0,1] 依全局状态判成败；指令空间 U 同时定义用户场景与 agent 须遵守的域政策（§3.1）。
- 该形式化使 agent 工具可影响用户数据库（如 agent 侧开通漫游后用户手机才能漫游），并让用户行为被工具与可观测状态约束、少依赖大段自然语言提示（§3.1、Figure 2）。

### 2.3 域与任务构建（§3.2、Table 1、Appendix A）

- 五阶段构建：Stage 1 用 LLM 生成 PRD 再生成 agent 数据库 schema/工具/单测，人工精修至测试全过；Stage 2 同法构建**用户侧数据库与工具**（telecom 中是带信号强度等状态的 mock 手机 + toggle_airplane_mode 等 15 写/15 读工具）；Stage 3 程序化任务生成；Stage 4 由任务与解反向生成域政策；Stage 5 联合人工精修并给每任务随机挂 persona（None/Easy/Hard）（§3.2）。
- 组合式任务生成器：每个原子子任务 t = ({f_init}, {f_sol}, {f_assert})——初始化函数造障、解函数限定为 agent/用户工具、断言函数校验终态；互斥/可替选子任务同组，组合任务每组至多选一个拼接；自动验证"终态满足全部断言且未应用全部解前不可解"，任务正确性由构造保证（§3.2）。
- Telecom 域：15 个原子子任务组 × 3 个用户意图（service_issue / mobile_data_issue / mms_issue，难度天然递增）组合出 **2285 个任务**，再按意图与子任务数平衡抽样 **114 个**；子任务数即难度代理（§3.2、Appendix A Table 3/4）。
- 规模对比（Table 1）：retail 500 users/50 products/1000 orders、agent 7 写+6 读工具、无用户工具、115 任务；airline 500 users/300 flights/2000 reservations、6 写+6 读、50 任务；telecom 5 plans/9 lines/4 customers、agent 6 写+7 读 + **用户 15 写+15 读**、114 任务（全集 2285）。

### 2.4 任务评估（§3.3）

- 五类成败判据：DB check、状态断言（终态 Sworld 的断言函数）、自然语言断言（对 Shistory 的 NL 条件）、communication info check（继承自 τ-bench）、动作匹配（解函数是否出现在轨迹中）；telecom 仅用断言函数判分（§3.3）。

### 2.5 实验设置（§4.1）

- 4 个被评模型：gpt-4.1-2025-04-14、gpt-4.1-mini-2025-04-14、o4-mini-2025-04-16、claude-3-7-sonnet-20250219；用户模拟器固定 gpt-4.1；每任务跑 4 次、温度 0；Litellm 实现、OpenAI tools 格式；agent 与用户均为 function-calling agent，政策与提示见 Appendix C/D（§4.1）。
- 成本：gpt-4.1×gpt-4.1 时 agent/用户模拟器每任务 $0.086/$0.059；全域跑 1 trial 约 $40（§4.1）。

### 2.6 主要发现（§4.2）

- **Telecom 双控域显著更难**：gpt-4.1 pass^1 从 retail 74% / airline 56% 跌到 telecom 34%；gpt-4.1-mini、o4-mini、claude-3.7-sonnet 在 telecom 约 50%（Abstract 给 34%/42%/49%）；claude-3.7-sonnet telecom pass^1 49% 与 airline 相当，但 pass^k 随 k 衰减比 airline 快，说明一致性更差（§4.2、Abstract、Figure 3）。
- **三模式消融**（Default 双控 / No-User 给工单且 agent 控全部工具 / Oracle Plan 给真值动作序列）：No-User→Default 使 gpt-4.1 pass^1 掉 18 个百分点（0.52→0.34）、o4-mini 掉 25 个百分点（0.67→0.42）（original policy），证明**协调与沟通是独立于推理的瓶颈**；Oracle Plan 增益 o4-mini（0.42→0.96）大于 gpt-4.1（0.34→0.73），说明 o4-mini 更会用真值（§4.2、Figure 4）。
- **政策文档形式的影响**：换成更具体的 workflow 版政策（Appendix D.2.2/D.2.3）后 Default/No-User 略升（gpt-4.1 Default 0.34→0.52、o4-mini 0.42→0.59），但在 Oracle Plan 反而**伤害**两模型（gpt-4.1 0.73→0.57、o4-mini 0.96→0.88）——已有真值动作序列时 workflow 制造混淆（§4.2、Figure 4）。
- **动作数与子任务数**：动作数 >7 时 Default 模式 pass^1 接近 0；No-User 与 Default 差距随动作数从 0.3–0.4 缩到 <0.2，说明长程可靠性在两种模式下都是挑战、沟通并非唯一瓶颈；No-User 下 gpt-4.1 在尾部（≥10 动作）优于 o4-mini（§4.2、Figure 5）。
- **意图类型**：失败集中在更复杂的 mobile_data_issue 与 mms_issue（多阶段推理 + 条件逻辑）；claude-3.7-sonnet 在 mobile_data_issue 上优于 o4-mini 但 service_issue 更差（§4.2、Figure 6、Appendix A Table 4：平均动作数 2.31/4.31/6.00）。
- **用户 persona**：Easy persona 成绩最好，Hard 最差；**None（不给 persona）与 Hard 相当甚至更低**——上线前必须用明确定义的 persona 测试（§4.2、Figure 7）。

### 2.7 基准自身可靠性（§4.3、Appendix B/E）

- 先排除三类不确定性中的前两类——实现错误（统一工具形式、域数据模型、mock 域单测）与任务规约错误（结构化任务元数据、分类评估判据、基于模拟结果的迭代审查、程序化生成）——再单独评估用户模拟器（§4.3、Appendix B）。
- 用户模拟器质量协议：gpt-4.1 扮演双方生成轨迹，每条对话 2 名标注员按 4 项标准（守指南/守指令/正确用工具/自然延续）审用户每个回合，错误分 task-critical（阻断完成）与 task-benign（§4.3）。
- 结果（Table 2）：airline 100 对话错误率 47%（critical 13%）、retail 50 对话 40%（critical 12%）、**telecom 仅 16%（critical 6%）**——结构化接口与清晰动作空间"天然引导"用户模拟器，替代大段自然语言约束（§4.3）。
- 错误模式（Appendix E）：retail 20 错中 conversation-structure 11、missing constraint 4、premature termination 3、ungrounded reference 2；airline 47 错中 conversation-structure 19、ungrounded reference 15、missing constraint 11、premature termination 2；telecom 8 错**全部**是 premature termination（用户在 agent 调 transfer 工具前就输出 ###TRANSFER###）。

### 2.8 结论、局限与未来工作（§5 Conclusion、Broader Impact）

- 结论：从自主到"引导用户"造成大幅性能下降，协调与沟通是当前 agent 相对纯推理的关键瓶颈；τ²-bench 为"既要会推理又要会带人"的 agent 提供受控测试台（§5）。
- 局限与未来：工具约束法尚未回迁到 retail/airline 的用户模拟器；域扩展仍重依赖人类专家，须研究自动化域策划；**未显式建模专家-新手差距**（expert-novice gap，即理解用户心智模型并适配解释）是明确局限与方向（§5）。

## 5. 一句话索引（给 Agent 用）

> τ²-bench（Sierra，2025）把会话 agent 评测从单控推广到**双控（dual-control）**：环境形式化为 Dec-POMDP，LLM 用户也持有工具（telecom 域 15 写/15 读）作用于共享世界，agent 须引导用户操作。配套贡献：组合式任务生成器（15 原子子任务组→2285 任务、断言函数自动验证）、被工具与环境约束的高可靠用户模拟器（错误率 16%/致命 6%，vs τ-bench retail 的 40%/12%）。实测：gpt-4.1 telecom pass^1 仅 34%（retail 74%）；No-User→Default 掉 18–25 个百分点，证明协调/沟通是独立于推理的瓶颈；动作数 >7 时接近全败；不给 persona 的成绩与 Hard 用户相当或更差。
