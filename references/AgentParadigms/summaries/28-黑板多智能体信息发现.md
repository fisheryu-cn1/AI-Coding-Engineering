# 论文摘要：LLM 多智能体黑板系统用于数据科学信息发现（Blackboard MAS for Information Discovery）

## 1. 适用场景

- 在"**消息传递 / 主从式 MAS 之外为多智能体系统选通信范式**"时读这篇：Google Cloud AI Research 提出的黑板范式变体——主 agent 不派活、只往黑板广播"请求"，从 agent 按自身能力**自愿应答**；在数据科学"数据发现"任务上端到端较最佳基线相对提升 13%–57%（Abstract; §4.2）。
- 设计**中心 agent 无法知晓全部子 agent 能力**的大规模系统（数据湖分片、能力部分可观测、专长重叠）时：本文论证主从式三缺陷——限制从 agent 自主性（被迫执行信息不足/过时的指令）、控制器须精确建模每个子 agent 能力、能力重叠引发指派歧义（§1）；黑板广播 + 自选参与消除这些假设。
- 做**数据科学 agent / 数据发现（data discovery）评测**时：KramaBench + 改造版 DSBench/DA-Code（去掉题目-文件映射、聚成统一数据湖）协议、recall/precision/F1 文件发现指标、LLM-as-judge（DSBench 用 Gemini-2.5-Pro 二值判分）可直接复用（§4.1; Appendix A）。
- 对本研究（`research/agent-software-design/materials/harness与冯诺依曼架构类别关系.md` 的"黑板架构替代路线"一节）：提供**黑板 vs 消息传递式 MAS 的最干净受控对照**——同款 ReAct 主 agent、同款 file agent/search agent，唯一差异是 request_help 广播 vs 按名指派；其"请求/响应写入独立响应板防止子 agent 互相影响""子 agent 并行处理请求"是对"黑板=共享结构化状态对象"的操作化细节，与本研究"文档传递式协同"（请求与响应即结构化文档）可直接类比；Fig 20 的"数据湖越大、黑板相对主从式增益越大"是黑板路线可扩展性的核心证据。
- 评估**黑板架构的精度-成本权衡**时：运行时与基线相当（132.0–145.2 秒/题）但每题成本约 2.3× RAG、1.8× Master-Slave（§4.2; Figure 2(D,E)）。

> 锚点：Abstract; §1 Introduction; §3; §4.1 Experimental Setup; §4.2 Empirical Findings; Appendix B。

## 2. 主要观点与方案

### 2.1 问题与动机（§1; §2）

- 真实数据科学的前置瓶颈是**数据发现**：在数千个松散组织的异构文件（数据湖）中定位相关数据，此前工作普遍假设数据已备好（§1）；单 agent 方案三缺陷——不可扩展（塞不进上下文窗口）、异构性挑战（单一 agent 难以整合多样信息）、噪声鲁棒性差（无关文件淹没模型）；RAG 检索器在表格/领域数据上表现差（§1）。
- 主从式（master-slave）MAS 三缺陷（§1）：从 agent 被迫执行协调者指令即使其信息不足或过时/有误；中心控制器须维护每个 agent 能力的精确模型（大规模 + 部分可观测 + 知识演化下不现实）；能力重叠导致指派歧义、路由困难。
- **与"共享内存"范式的关键区分**（§1）：共享内存范式中 agent 仍按中央协调者的指派基于共享内存执行任务；黑板范式中**没有任务指派**——请求广播到黑板，每个 agent 全权自主决定是否参与。
- 问题形式化（§2）：数据湖 D={d_i}，查询 q，系统生成 Python 程序 P 检索/加载/处理数据并作答；两类评估——端到端答案评分 + 文件发现（retrieval）评分。

### 2.2 系统设计（§3; Figure 1; §3.1; §3.2）

- **离线阶段**：数据湖分簇（默认 Gemini-2.5-Pro 仅按**文件名**聚类，输出簇名/文件列表/描述/理由的 JSON，图 4 提示词；替代方案 E5-large 内容嵌入 + KMeans，Appendix F），每簇指派一个 **file agent**；另设一个 web 检索的 **search agent**。
- **在线阶段**：main agent 按 ReAct 循环（≤T=10 步），五动作选一——Planning（内部规划）、Reasoning（内部推理）、Executing Code（Python 解释器执行）、**Requesting Help**（把请求发布到黑板 B、不指名任何子 agent；子 agent 响应收集后作为该动作的 observation 返回）、Answering（生成最终 Python 程序并终止）（§3.1; Figure 5）。
- **响应板 B'**（脚注 2）：子 agent 响应**不写回黑板 B** 而写入 B'——防止子 agent 互相影响、保证独立运作，B' 仅主 agent 可访问。
- **File agent**（§3.2; Figure 6）：离线两步——先选择性抽验部分文件内容（文件名表明同型不同期的可抽样推断），再分析结构/预处理/加工方式；在线监听黑板请求，基于离线分析判断能否贡献（can_help），若能则输出结构化响应：相关文件、加载代码、数据解释、数据样例、必要步骤、依赖库。
- **Search agent**（§3.2; Figure 7）：仅响应 web 信息类请求（明确拒答本地文件类请求）；迭代搜索 ≤3 步、每步一组 query、每 query 取 3 个网页（Google Custom Search + beautifulsoup 抽取），评估信息充分性决定停止或续搜。
- 主 agent 拿到 B' 上的响应后**自行决定采用或忽略**（§3）。

### 2.3 实验设置（§4.1; Appendix A; Appendix D）

- **基准**（Appendix A; Table 3）：KramaBench（104 任务、数据湖共 1,746 文件、Gemini 聚 27 簇；六域：Archeology 12/Astronomy 12/Biomedical 9/Environment 20/Legal 30/Wildfire 21，其中 Astronomy 1,556 文件最大）；改造 DSBench（253 任务/48 文件/12 簇）与 DA-Code（91 任务/145 文件/26 簇）——手工滤除无需数据文件或缺乏发现线索的题，所有文件聚成统一数据湖，模型只拿题目 + 数据湖（保留实例 ID 见 Appendix G）。
- **评估**（§4.1）：KramaBench/DA-Code 用各自官方脚本；DSBench 沿用 LLM-as-judge（Gemini-2.5-Pro，二值判分，图 3 提示词）。
- **推理设置**（§4.1; Appendix D）：temperature 0.1 核采样、每步 ≤8,192 token、主 agent ≤10 动作；模型 Gemini 2.5 Pro/Flash、Claude 4 Opus（Vertex AI）+ Qwen3-Coder-30B-A3B-Instruct（vLLM，2×A100 80GB）。
- **基线**（§4.1）：(1) DS-GRU——全部文件直塞 prompt + 自纠错循环（唯一已有数据发现基线，Lai et al. 2025）；(2) RAG——E5-large 检索 top-5 文件直塞 prompt + 同款 ReAct（帮助动作仅限 search agent），隔离"文件发现机制换成 RAG"的效应；(3) Master-Slave——同款主 agent 与子 agent，差异仅为按名直接调用子 agent 并指派任务（图 8 提示词）。

### 2.4 主要发现（§4.2; Table 1; Table 2; Figure 2; Appendix F）

- **端到端**（Table 1）：四个 LLM 下 Blackboard 宏观平均全部第一——Qwen3-Coder 7.90%（vs Master-Slave 5.03%，约 +57%）、Gemini 2.5 Flash 16.54%（vs RAG 14.52%，约 +14%）、Gemini 2.5 Pro 28.53%（vs Master-Slave 24.01%，约 +19%）、Claude 4 Opus 31.43%（vs Master-Slave 27.63%，约 +14%）——即摘要口径的 13%–57% 相对提升，且跨专有/开源 LLM 一致（Abstract; §4.2）。
- **文件发现**（Table 2, Gemini 2.5 Pro）：Blackboard 平均 recall 0.533 / precision 0.699 / F1 0.561 全面最高（Master-Slave F1 0.513、RAG 0.247）；KramaBench 6 域中 4 域 F1 最高——归因于 file agent 基于自身数据 holdings 自判贡献、而非被中心指派（§4.2）。
- **对高级数据科学基线**（Appendix F; Table 4, KramaBench, Gemini 2.5 Pro）：Blackboard 平均 37.53% > Data Interpreter 30.34% > AutoGen 19.30%，6 域中 5 域领先（§4.2）。
- **可扩展性**（§4.2; Figure 20）：数据湖规模与相对增益正相关；两个最大数据湖上增益最大——DA-Code（145 文件）+70%、KramaBench Astronomy（1,556 文件）+211%（注：按 Table 1 Pro 值 17.95% vs 8.47% 计算为 +112%，正文 211% 与表值不一致，引用时建议注明并附表值）。
- **动作预算**（§4.2; Figure 2(B)）：主 agent 上限 2→10 性能单调提升（更充分探索与更优解）。
- **搜索组件**（§4.2; Figure 2(C)）：去掉 search agent 平均性能下降——遇陌生概念时主 agent 请求 web 知识支撑续解（案例 Figure 12/13）。
- **运行时与成本**（§4.2; Figure 2(D,E); Appendix F）：50 题 KramaBench（Gemini 2.5 Pro）上三系统运行时均在 132.0–145.2 秒窄带内（黑板**并行**处理子 agent 请求，RAG/Master-Slave 串行）；黑板每题成本约 2.3× RAG、1.8× Master-Slave（token 增多），换来 +54.1%（vs RAG）/ +18.8%（vs Master-Slave）性能。
- **聚类策略与簇数**（§4.2; Figure 2(F,G); Appendix F）：内容嵌入聚类（E5-large + KMeans）> Gemini 文件名聚类 > 随机聚类；簇数 2→16 增多性能上升（每 agent 子集更小更专注）——框架不绑定特定聚类方法。
- **案例**（§4.2; Appendix E）：一次请求 8 个 helper 中 3 个应答、合起来覆盖全部 ground-truth 文件（Figure 14）；Blackboard 选对文件（mmc1/mmc7）得正确答案 60、Master-Slave 误选列（mmc2 的 APP_log2_abundance）得错误答案 74（Figure 15）；无人应答时主 agent 多次改写请求、退化为 run_code 自行列目录搜文件（Figure 16）；Master-Slave 路由失败——被点名 agent 连续拒答、最终只拿到泛化搜索结果（Figure 17）。

### 2.5 与 Han & Zhang (2025)（本目录文献 27）的谱系区分（Appendix B）

- 并行工作 Han & Zhang（arXiv 2507.01701）面向数学/推理任务（无需数据发现）：其主 agent 仍通过决定"下一个该谁行动"来分配任务，黑板主要作信息交换的**共享内存**、决策权集中于主 agent；本文则**全员自主、无显式任务指派**——且其设计不适合本文场景，因为不可能把所有相关信息放进 LLM 的 prompt（Appendix B）。

### 2.6 结论与未来工作（§6）

- 黑板范式以灵活的去中心化协作替代刚性集中式任务指派；未来方向：推广到数据科学之外的通用 MAS、研究自适应数据划分策略以应对动态演化的数据环境。

## 5. 一句话索引（给 Agent 用）

> Google Cloud AI Research 的黑板范式 MAS（arXiv 2510.01285, v2 2026-01）：主 agent 以 ReAct（≤10 步）解题、只把数据/知识需求广播到黑板，按簇分片数据湖的 file agent（离线预分析文件）与 search agent 自愿应答到独立响应板，主 agent 整合响应生成 Python 程序；在 KramaBench + 改造 DSBench/DA-Code 上端到端较最佳基线（RAG/Master-Slave）相对提升 13%–57%（Qwen3-Coder 7.90% vs 5.03%）、文件发现 F1 0.561 vs 0.513（+9%），数据湖越大增益越大（DA-Code +70%、Astronomy +211%），运行时与基线相当而成本约 1.8–2.3 倍——是"黑板广播自组织 vs 主从式指派"最干净的受控对照证据。
