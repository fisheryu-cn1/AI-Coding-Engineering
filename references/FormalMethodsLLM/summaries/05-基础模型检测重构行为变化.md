# 论文摘要：基础模型检测 Python 重构行为变化（SafeRefactorPy 扩展，UFCG/UFAL/PUC-Rio）

## 1. 适用场景

- 当你要为**代码变换工具设计"foundation model as oracle"语义等价检查器**（diff-scoped、零样本、可机器解析的受限输出格式）时，读这篇——§3.3 给出完整 prompt 文本、严格假设集与用辅助模型当 prompt critic 的迭代精炼方法。
- 当你需要检测**动态语言（Python）重构"表面成功但 observable behavior 已变"**的静默行为变化，并把失败实例归并成可提交的最小复现 bug 报告时，读 §3.4 与 §4.3.2 的五类 Python 特有失败根因。
- 当你要建立**模型 oracle vs 人类专家基线**的评测协议（precision/recall/F1 + tar@k/cons@k/pass@k/accuracy spread 稳定性度量），或比较大模型与开源模型 oracle 的推理范围（diff-scoped vs project-aware）差异时，读 §4.2 与 §4.4.6。
- 当你评估 **FM oracle 在验证流水线中的定位**（测试/静态分析/项目级语义检查之外的补充层而非替代品）及其威胁效度时，读 §1 末段的定位声明与 §5。

> 锚点：Abstract; §1 Introduction; §3.3 Detecting Behavioral Changes; §4.2 Methodology; §4.4.6 GPT-5.2 Thinking; §5 Threats to Validity

## 2. 主要观点与方案

- **问题与动机**：Python 的 dynamic typing、runtime name resolution、dynamic dispatch 使重构难以静态验证——工具视角"成功"的变换仍可能改变 observable behavior（如 Rope Inline Method 删除被覆盖的 `WordList.extend` 后调用静默落到继承的 `list.extend`，元素从 `Word` 变 `str`，无任何报错，Rope issue #828）；已有行为变化检测技术面向 Java 等静态类型语言，不覆盖 Python 机制（§1; §2）。
- **流水线设计**：扩展 SafeRefactorPy 为四步——(1) 在输入程序上应用被测重构（唯一工具相关步骤）；(2) 计算原/新程序的 git-style diff；(3) foundation-model oracle 仅凭 diff 判定是否保持 observable behavior；(4) categorizer 聚合结果、按"重构类型+失败症状+最小复现"归并出 bug 候选，并用 delta-debugging 式缩减得到最小重现程序（§3.1; §3.4; Figure 1）。
- **diff 作为 oracle 输入的理由与代价**：diff 紧凑（规避上下文窗口与推理成本）、聚焦变换本身（贴近人工 code review）、格式工具无关；代价是可能漏掉 diff 之外的 project context（外部调用者、子类交互、import 期依赖）——这是明确的方法学 trade-off（§3.2）。
- **FM oracle 检测机制（核心）**：零样本 prompting，模型扮演"refactoring-aware coding assistant"，仅凭 diff + 语言语义判定 BEHAVIOR 条件（输出/异常/外部可见状态/时序同步是否一致）；prompt 内嵌严格假设（diff 外代码视为未改、一致重命名视为已同步更新、忽略纯注释/空白变更、把新增 logging、异常类型变更、常量值变更、求值顺序变更视为潜在行为变化、禁止虚构符号）与分析步骤清单；输出格式强制为恰好一行 `YES`/`NO` + 1–3 句证据（纯文本、禁 JSON/工具调用），供 categorizer 关键词解析；oracle 模型无关，主评测用 gpt-oss-20b（Ollama 本地，64 GB RAM + RTX 4060 8 GB VRAM 混合 CPU–GPU）。prompt 经迭代 meta-prompting 精炼：辅助 FM 作 prompt critic 在代表性 diff + 真值标签上找歧义与边界情况，循环修订直至稳定（§3.3; §4.2.3）。
- **评测方法**：被测对象 Rope 1.3.0 的 7 种常用重构（Rename Field/Method、Inline Method、Extract Method、Move Field/Method、Use Function）；复用先前研究（SBES'25 静态检测故障 Python 重构）1,152 次重构尝试中留下的 217 个"成功且无已知问题"变换对，逐一生成 diff；ground truth 为单名 10 年经验 Python 专家以**同样 diff-scoped 输入**给出的保持/改变标签（附书面理由）；指标为二分类 precision/recall/F1/accuracy（行为变化为正类）+ 重复运行稳定性（mean accuracy、accuracy spread、pass@k、tar@k、cons@k），k=3 取众数响应（§4.1; §4.2）。
- **RQ1 发现**：高 recall、可接受 precision——oracle 能暴露行为变化型变换但存在假阳性；假阳性/假阴性的一大来源是 Python 缩进定义作用域，模型需语义化解析 diff 中的空白而非只看词法 token（§4.3.1; §4.4.3）。
- **RQ2 失败分类**：64 个专家判定的行为变化实例归并为 13 个独立 bug，落在五类 Python 特有根因：(i) 名称/import 处理错误的运行时失败；(ii) 表达式/调用点变换错误；(iii) 违反 Python data model 约束（dunder/富比较方法）；(iv) 继承/契约违规（删除被覆盖或抽象方法）；(v) 结构性依赖破坏（循环依赖）（§4.3.2; Table 2）。
- **RQ3 外部效度**：13 个 bug 全部提交 Rope，12 个被接受；唯一未接受的 #750（内联 `__new__`）被维护者改判 enhancement——"不支持"而非"有 bug"；其中 10 个为本技术独有发现（§4.3.3）。
- **GPT-5.2 Thinking 探索性分析（k=1，网页手动）**：判 197 个 NO、20 个 YES；20 个 YES 全部与专家一致，专家标记的 64 个行为变化零漏报，且不存在 gpt-oss-20b 报警而 GPT-5.2 判保持的情形；但 133 个 NO 超出 diff 范围（project-aware 风险声明：外部调用/子类覆盖/dynamic dispatch/introspection/公开 API 增删/import 期效应），暴露 diff-scoped 基线无法确认此类真实风险的范围错配——作者留 project-aware 基线为未来工作（§4.4.6）。
- **定位声明**：SafeRefactorPy 是 bug 发现与验证辅助，不替代测试套件、静态分析或项目级语义检查；FM oracle 适合作为附加验证层（§1; §7 Conclusions）。
