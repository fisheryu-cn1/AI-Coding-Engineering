# 论文摘要：VERISPECGEN 意图对齐形式规格合成（UC Berkeley / AWS / Harvard）

## 1. 适用场景

- 当你要设计**"自然语言 → 形式规格（precondition/postcondition）"的 LLM 合成与精化流水线**，且需要把验证失败**定位到具体需求**（而非只拿到 type error / proof failure 这类粗粒度信号）时，读这篇——它的 traceability map + clause 级局部修复是需求级失败归因的直接模板。
- 当你在评估**"LLM 自判式精化（self-judgment refinement）是否可靠"**——尤其是弱模型上自反馈是否会反噬——时，读其 §5.2 消融：direct refinement 在 Qwen3-Coder-30B 上不升反降（−2.3），带归因的完整流水线才稳定有效。
- 当你要为**形式化/定理证明任务构造过程级（process-level）训练数据**——从 agent 精化轨迹蒸馏 SFT 数据集并迁移到域外推理能力——时，读其 §3.4 + §4：343K 轨迹蒸馏样本使规格合成提升 62–106%（相对）。

## 2. 主要观点与方案

- **问题定位**：形式验证的保证强度被规格质量封顶——过弱的规格放行 buggy 实现、错误的规格拒绝正确实现；且真实代码库几乎不含形式规格，训练数据稀缺，SOTA 模型在 VERINA SpecGen 上依然挣扎（§1）。
- **范式定位（intent-anchored）**：与从程序行为挖掘规格（Daikon 类动态分析、LLM 从代码反推规格）的 program-behavior-based 路线相对，VERISPECGEN 坚持规格内容只来自自然语言意图；先前 intent-anchored 系统（nl2spec、Clover 等）既无法判断规格是否覆盖全部需求，又依赖无法定位失败来源的粗粒度精化信号（§2）。
- **Traceable refinement 机制（核心贡献，§3）**：三阶段把"精化步骤"与"需求证据"显式绑定——
  1. **Atomic Requirement Decomposition（§3.1）**：LLM 把问题描述 P 分解为 atomic requirements R={rᵢ}，每条表达**单个可测行为性质**（含边界条件、tie-breaking 等边缘需求），另用 LLM judge 复核改进；R 是后续可追溯性的归因单元。
  2. **Requirement-Targeted Tests + Traceability Map（§3.2）**：对每条需求生成三类测试——positive（应被规格接受）、negative-input（应被 precondition 拒绝）、negative-output（应被 postcondition 拒绝）；输出标注用**黑盒执行 oracle**（题目自带或 LLM 生成的参考实现，只用来给输入标输出，不从实现抽取规格内容，保持 intent-anchored）。每个测试经 **traceability map π: T→2^R** 标注它验证哪些需求——这就是"测试证据 ↔ 需求"的绑定。验证时把每个测试实例化为 Lean 命题（ϕ⁺/ϕᵢₙ⁻/ϕₒᵤₜ⁻）交 proof automation（grind tactic）证明/证伪，仅对不确定的测试回退 LLM judge；失败测试集 F(S) 经 π 提升为被牵连需求集 **R_FAIL(S)=∪_{t∈F(S)} π(t)**。
  3. **Requirement-Localized Repair + Adversarial Testing（§3.3）**：初始规格 S₀ 按"一条需求对应一个子句"的结构生成；修复 prompt 只含当前规格 + 被牵连需求 + 代表性失败测试，LLM 做**只改动受影响子句**的局部修复（如图 1 中 tie-breaking 失败只改 postcondition），保留已正确部分；全部测试通过后再做 adversarial testing 生成专门打破当前规格的测试以暴露缺失约束，新失败测试同样经 π 归因并触发新一轮局部修复。全程记录轨迹 τ=(P,σ,R,T,π,S₀,F₀,Δ₀,…,S_K) 作为过程级监督（§3.4）。
- **与 direct refinement 基线的关键差异（§5.2 消融）**：direct refinement = 纯 LLM 自判（生成→自评是否满足描述→修改，最多 25 轮，无测试验证）——在 Opus 4.5 上 +13.2 但在 Qwen3-Coder-30B 上 **−2.3（29.3→27.0）**，自反馈对弱模型反噬；test-driven refinement（有需求定向测试但无分解/归因）在 30B 上崩到 **20.9（低于基线 8.4 分）**——有测试无归因会把弱模型绕晕。完整流水线（分解+π 归因+局部修复+adversarial）86.6/50.3，比 test-driven 变体高 12.8/29.4 分：**grounded validation 与 requirement-level attribution 缺一不可**。
- **轨迹蒸馏训练数据（§4）**：用 Claude Sonnet 4.5 作 teacher 在 TACO-Verified（MIT 许可）上跑流水线，源数据与 VERINA 零 10-gram 重叠（防泄漏）：12,901 题去污染 → 11,981 题译成 Lean → 成功合成 6,842 个规格；轨迹按流水线模块拆成 11 类任务，蒸馏出 SFT Full 343,827 / SFT No-Test 121,531（只留 5 类核心规格任务，refinement 相关占 80.3%）/ SFT Spec-Only 6,842（纯端到端对）三种变体。
- **实验设置（§5）**：Lean v4.24.0 + grind（120s 超时），T=0.3、单次生成上限 10K token；VERINA 官方 harness，基线为 2-shot pass@1（5 次平均）；VERISPECGEN 每题最多 25 轮精化、60 个测试，oracle 用 LLM 生成的参考程序。
