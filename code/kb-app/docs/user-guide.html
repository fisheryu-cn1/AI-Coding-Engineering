一、软件概述：设计目标与主要功能

1.1 这是什么

GraphIt-KB（命令行工具名 kb，Python 包名 kbapp）是一个纯本地运行的个人知识库应用。它把你积累的研究资料（论文 PDF、网页存档、Markdown 报告、DOCX、TXT）自动完成分类、索引、章节级结构化与多粒度摘要，并提供检索、原文查阅、关联阅读、比较分析能力；同时它可以作为本地 MCP 服务被 AI Agent（如 Kimi Code、Claude Code）调用，为知识检索与方案编写提供按 token 预算组装、带溯源锚点的上下文。

1.2 设计目标

  • 本地优先：全部数据（索引、缓存、配置、摘要产物）保存在本地数据目录，无云端同步、无多用户权限体系；原文资料只读，所有产物单独存储。
  • 章节级颗粒度：知识管理的最小单位不是"一篇文档"，而是文档内的章节（Section）。检索命中、上下文组装、原文定位均精确到章节。
  • 面向 Agent 的上下文供给：内置 MCP 服务，Agent 可按"检索 → 查看结构 → 读取章节 → 组装上下文"的固定路径自助取用知识，替代人工翻找、复制、拼接。
  • 可维护的索引：基于 SHA-256 指纹的增量更新（新增/修改/移动/重复/删除五种情形自动判定），同时支持一键全量重建。
  • 离线可降级：不配置 LLM 时，分类、检索等核心功能仍可用（纯规则降级）；配置 LLM 后自动获得自动摘要、查询扩展、重排等增强能力。

1.4 总体架构

系统由两个入口（人用的 kb 命令行、Agent 用的 MCP 服务）、三组核心能力（索引流水线、检索引擎、上下文组装）和一个本地数据目录构成。LLM API 是可选增强项，不配置时系统按纯规则降级运行。

二、术语与特殊概念

以下概念贯穿全部命令的输出与配置，阅读后续章节前请先了解。

概念含义
doc_id每篇资料的全局唯一编号，格式 D0001、D0002……由系统顺序分配，永不复用。检索、查看、改判等操作都以它为主键。
语料（corpus）资料的来源分区：references（参考论文/存档）、research（研究报告）、design（设计文档）、external（库外登记文件）、inbox（自动收集待审区，M7）。每个 corpus 对应配置里的一个根目录。
主题（topic）资料归属的研究主题域（如 ContextEngineering、ai-coding）。主题清单存于 topics 表，初始由配置 core_topics 播种；set-topic 可创建新主题。
文档类型（doc_type）paper（论文）/ design（设计文档）/ other。按规则链判定：有策展摘要 → paper；文件名含 arXiv 号 → paper；位于 design 语料 → design；PDF → paper；其余 → other（有 LLM 时可仲裁）。
文档状态（status）new 待解析；active 已解析且分类确定；needs_confirm 分类不确定或解析失败，需要人工处理；duplicate 内容重复（不入索引）；deleted 墓碑（源文件已删除，保留身份字段）。
抽取状态（extract_status）ok 解析出标题树；flat 只有纯文本无结构；no_text PDF 无文本层（扫描件）；failed 解析失败；pending 待解析。
章节（Section）与 section_path文档内按标题层级划分的结构单元；section_path 是章节的路径式标识（如 §2.1 总体架构），用于精确定位与原文读取。
Chunk章节内按长度（默认 2048 字符、重叠 200 字符）切分的检索单元，写入 FTS5 全文索引。chunk 编号形如 D0001#c003。
$summary 伪章节特殊的 section_path 哨兵值。每篇文档的摘要会作为一个"伪 chunk"写入索引，kb read D0001 '$summary' 可读取摘要全文。
摘要来源（summary_source）curated：人工策展摘要（语料目录下 summaries/*.md，质量最高，优先使用）；auto：LLM 自动生成（存于数据目录 auto_summaries/）；none：无摘要。源 PDF 修改后，curated 摘要会标记 summary_stale（过期）。
锚点（anchor）指向原文具体位置的引用，形如 D0001#§2.1（doc_id + section_path）。检索结果和上下文组装都带锚点，供随时下钻原文。
FTS5 / trigramSQLite 的全文检索扩展；trigram（3 字符滑动窗口）分词使中英文都能检索，无需额外分词器。
RRF 融合倒数排名融合（Reciprocal Rank Fusion）：把全文路和图路两路结果按排名加权合并（权重 1.0 / 0.5，k=60），产出统一排序。
写锁数据目录级互斥锁（.write.lock），保证同一时刻只有一个写进程。写命令遇锁占用默认立即失败（退出码 2），部分命令支持 --wait 阻塞等待。
任务队列索引工作以任务形式排队（tasks 表），kb index run 串行执行。失败任务按 30 秒 → 1 分钟 → 5 分钟退避重试，最多 4 次；进程崩溃后启动时自动恢复超时任务。

三、安装、初始化与配置

3.1 环境要求

项目要求
Python≥ 3.11 且 < 3.13；推荐 3.12（3.11.0 自带的 SQLite 3.38 对中文 LIKE 查询有缺陷，会导致中文短查询零命中）
包管理uv（仓库已含 uv.lock 与 .python-version）
操作系统Linux / macOS 全功能；Windows 上写锁不可用（写命令可能失败），只读命令（config get / status / search 等）可运行但未做端到端验证
磁盘数据目录所在盘建议 ≥ 2 GB 剩余空间；不要放网络盘（NFS/SMB 上 SQLite WAL 不可靠）
Tesseract可选，仅 PDF OCR 用；OCR 默认关闭，缺失只警告

3.2 安装

cd code/kb-app
uv sync                                # 基础依赖（CLI + 配置 + 注册库）
uv sync --extra parse                  # 文档解析器（PDF/DOCX/HTML/MD），检索前必须
uv sync --extra llm                    # 可选：LLM 能力（自动摘要、查询扩展、重排、分类兜底）
uv sync --extra mcp                    # 可选：MCP 服务（Agent 集成必须）
uv sync --extra parse --extra dev      # 开发：跑测试

安装后命令名为 kb，通过 uv run kb … 调用（下文示例均省略 uv run 前缀）。

3.3 指定数据目录

所有数据（配置、注册库、缓存、摘要、报告）保存在一个数据目录中，定位优先级：

  1. 命令行全局选项 --data-dir <路径>（放在子命令之前，如 kb --data-dir D:\kb-data status）；
  2. 环境变量 GRAPHIT_KB_DATA_DIR；
  3. 默认值 ~/.graphit-kb。
多项目/多语料场景可为每个库设一个数据目录，用环境变量区分；MCP 服务进程通过 GRAPHIT_KB_DATA_DIR 注入数据目录（见 5.3）。

3.4 初始化：kb init

kb init            # 幂等：可重复执行，不覆盖既有文件
kb init --force    # 强制重写 config.yaml 为默认值（其余文件不动）

init 完成四件事：创建数据目录树；写入默认 config.yaml 与 sources.yaml 注释模板；初始化注册库 registry.sqlite；从 core_topics 播种主题清单。同时做环境检查（Python 版本、磁盘空间、Tesseract）。若 config.yaml 已存在，会打印你相对默认值的改动清单。

初始化后的数据目录布局：

~/.graphit-kb/
├── config.yaml            # 全局配置
├── sources.yaml           # 自动收集来源模板（M7 起生效，当前仅占位）
├── registry.sqlite        # SQLite 注册库（元数据 + 任务 + FTS5 全文索引）
├── cache/extracted/       # 解析产物缓存（<sha256>.json，避免重复解析）
├── auto_summaries/        # LLM 自动摘要产物（<doc_id>.md）
├── reports/               # 运行报告（如策展摘要绑定不匹配报告）
├── inbox/                 # 待审核新资料（M7 预留）
├── graph/  vectors/       # 图谱 / 向量库（M5 / M3+ 预留）
└── .write.lock            # 写锁文件（运行时出现）

3.5 配置详解（config.yaml）

配置采用"默认值 + 用户覆盖"合并机制：只写你要改的键即可。用命令读写，不要手改时跳过审计：

kb config show                 # 查看当前生效配置（默认值合并后）
kb config show --defaults      # 只看默认值
kb config get corpus_roots     # 按点路径读单个键
kb config set classify.min_keyword_score 3        # 写单个键（交互确认）
kb config set classify.min_keyword_score 3 --yes  # 跳过确认
kb config diff                 # 你改过哪些键（与默认值对比）

每次 config set 都会写入审计表（config_audit），可回溯"何时把什么从什么改成了什么"。写 list/dict 类型的键时，值按 YAML 语法传入，例如：

kb config set classify.topic_keywords '{ContextEngineering: [context engineering, 上下文工程, context rot], ai-coding: [agentic coding, ai coding]}' --yes

关键配置键

四、标准应用流程（功能与用法全览）

本章按"从零建库 → 日常检索阅读 → 维护"的正常顺序，逐一说明每个功能的用法。整体流程见下图。

4.1 准备语料目录

  • 把资料放入 corpus_roots 配置的三个目录（references / research / design）中，可按主题建子目录。
  • 支持的格式白名单：.pdf、.html、.htm、.md、.docx、.txt，其余扩展名直接跳过。
  • 扫描时自动跳过：隐藏文件/目录、名为 summaries/ 的目录（它是策展摘要存放区，不作为语料）、符号链接，并遵循语料根下 .gitignore 的规则。
  • 策展摘要约定（可选，强烈推荐）：在 <语料根>/<主题>/summaries/ 下放人工编写的高质量摘要 Markdown，文件名形如 NN-短标题.md。文件头支持两种格式——YAML frontmatter（含 source_pdf 字段）或引用块头（含 > **完整 PDF 文件名**：xx.pdf 行）。扫描时按 source_pdf 的文件名自动绑定到对应 PDF，绑定后该文档的摘要标记为 curated，跳过 LLM 摘要生成。

4.2 扫描入队：kb index scan

kb index scan                    # 扫描全部 corpus_roots
kb index scan --corpus research  # 只扫指定分区

扫描对每个文件计算 SHA-256 指纹，按决策表判定五种情形：

情形判定条件动作
new（新增）路径与内容都未见过分配 doc_id，登记 files 表，入队 parse 任务
modified（修改）路径已登记但内容变了保留 doc_id，重新入队；若绑定了策展摘要则标记摘要过期
moved（移动/改名）内容相同但路径变了只更新路径，零重抽取（不入队）
duplicate（重复）内容与库内另一文件相同分配 doc_id 登记为 duplicate，不入队、不入全文索引
deleted（删除）已登记文件在磁盘上消失标记墓碑（保留身份字段；文件回归时自动复活复用原 doc_id）

扫描结束打印变更报告。若策展摘要的 source_pdf 找不到对应文件，会在报告中提示并写 reports/manifest_mismatch_<时间戳>.json 供排查。扫描是幂等的，无变更时输出"无变更，无需入队"。

4.3 执行流水线：kb index run

kb index run                 # 取写锁，串行跑完任务队列
kb index run --wait          # 写锁被占用时阻塞等待（最多 30 秒）
kb index run --max-tasks 10  # 最多处理 10 个任务就退出（调试用）

每个 parse 任务串行经过四个阶段：

  1. parse：按格式解析全文与标题结构（PDF 走 PyMuPDF 快路径；扫描件无文本层标记 no_text）；结果缓存到 cache/extracted/<sha256>.json，同内容文件再次解析直接命中缓存。
  2. chunk：结构感知分块——章节是原子单位，超长章节按段落边界切分并保留 200 字符重叠；分块写入 FTS5 全文索引（先删后插，幂等）。
  3. classify：关键词计分定主题（标题命中 ×3 + 正文命中 ×1，默认 top1 ≥ 2 分且 ≥ top2 的 1.5 倍），规则链定 doc_type；不确定的文档进入 needs_confirm 待确认队列。doc_type 规则全部落空且有 LLM 时，用 LLM 仲裁一次。
  4. summarize（有 LLM 且摘要非 curated 时自动入队执行）：生成 L1–L3 摘要，写 auto_summaries/<doc_id>.md 并作为 $summary 伪 chunk 进索引。已绑定策展摘要的文档跳过；策展摘要过期时生成临时 auto 摘要但不覆盖原绑定。
run 是可中断的：Ctrl-C 会把正在执行的任务立即放回队列（退出码 130），下次 run 继续。失败任务按 30s→1m→5m 退避自动重试（最多 4 次），LLM 不可用等临时故障不会丢任务。进程崩溃后，下次 run 或 status 会自动把卡在 running 超 30 分钟的任务重置回 pending。

4.4 查看库状态：kb status

kb status

输出五组信息：总览（版本、schema 版本、任务队列计数、FTS chunk 总数）、files 分状态统计、extract_status 统计、topics 清单（含文档数）、needs_confirm 待确认队列（前 20 条，附改判命令提示）。这是日常巡检的主入口。

4.5 人工改判：kb index set-topic

kb index set-topic D0007 ContextEngineering   # 改判到指定主题（主题不存在会自动创建）
kb index set-topic D0007 -                    # 清空主题，留待以后处理

改判即时生效（状态变为 active），并自动维护各主题的文档计数。改判不需要重新解析。

4.6 检索：kb search

kb search "context rot"                        # 默认 hybrid 混合检索，返回 10 条
kb search "上下文工程" --topic ContextEngineering  # 限定主题（硬过滤）
kb search "知识图谱" --mode graph               # 仅结构导航（图路）
kb search "" --mode topic-global               # 主题全景：按主题分组列出文档 + 一句话摘要
kb search "..." --mode vector                  # 当前显式报错（P1 目标态）
kb search " Petri net " --limit 20             # 调整返回条数

hybrid 模式的工作原理（见图 3）：查询先经查询理解（归一化、主题词匹配、内置+用户同义词表扩展，有 LLM 时再做一次查询扩展），然后两路召回——全文路用 FTS5 trigram 做 BM25 检索并聚合到章节粒度（短查询自动走 LIKE 兜底，标题命中排正文命中之前）；图路按主题匹配做结构导航（主题缺失过半时退化为按语料/类型浏览并给出提示）；两路经加权 RRF 融合，有 LLM 时再对前 20 条做相关性重排（重排失败自动回退融合原序）。

每条命中包含：得分、文档路径、section_path、摘要片段。输出末尾提示下钻命令。

4.7 查看与阅读：kb show / kb read / kb related / kb compare / kb topics

kb show D0001                    # 元数据 + 章节树 + 摘要
kb show "context rot"            # 也可用路径/标题片段；歧义时列出候选
kb read D0001 '§2 方法'          # 读某章节原文（章节名从 kb show 的章节树复制）
kb read D0001 '$summary'         # 读摘要全文（$summary 哨兵）
kb related D0001 --limit 10      # 同主题关联阅读（无主题时退化为全库最近更新）
kb compare --docs D0001,D0002,D0003   # 多文档对比表（需 LLM；无 LLM 回退并排摘要）
kb topics                        # 主题清单与规模；主题名归一化碰撞会给出归并建议
文档引用（show / read / related 的 doc 参数）按以下优先级解析：doc_id 精确 → 路径精确 → 路径后缀 / 标题子串（须唯一命中）。多文档歧义时不猜，报错并列出候选路径。

4.8 登记库外文件：kb index add

kb index add /abs/path/to/paper.pdf

把不在三个语料目录里的文件登记进库（corpus=external），只登记不拷贝，请确保原文件路径长期有效。路径已登记会报错（退出码 1）；内容与库内文件重复时按 duplicate 登记，不入队。

4.9 全量重建：kb index reindex --full

kb index reindex --full              # 清空全文索引，重新入队全部有效文档
kb index reindex --full --no-cache   # 连带清空解析缓存（解析器升级后用）

适用场景：修改了分块参数（chunk_size 等）、分类关键词大改、怀疑索引损坏。重建只影响索引与产物，不触碰原文与人工改判记录之外的元数据；doc_id 全部保留。重建后执行一次 kb index run 完成重处理。

五、MCP 服务与 AI Agent 集成

5.1 启动服务

uv sync --extra mcp        # 首次需安装 mcp 依赖（未安装时启动会明确报错提示）
kb serve mcp               # 以 stdio 传输启动（前台进程，由 Agent 客户端拉起）

MCP 服务是只读的：它只打开注册库读取，不取写锁，与正在运行的 kb index run 互不阻塞（SQLite WAL 支持并发读）。服务进程内缓存配置与连接，修改 config.yaml 后需重启服务生效。

5.2 四个工具

工具参数返回用途
kb_searchquery；mode=hybrid|graph|topic-global；topic；limit=10hits[doc_id, section_path, title, score, snippet, topic] + note章节级检索，拿锚点
kb_showdoc（doc_id / 路径 / 标题片段）元数据 + summary + sections[section_path, title]了解一篇文档的结构与摘要
kb_readdoc；section章节原文（$summary 读摘要全文）下钻读取原文
kb_assemble_contexttask；budget=8000；topics（可选列表）{context_block, budget, used, sources[doc_id, section_path]}按任务描述一步到位组装提示词上下文

所有工具出错时不抛协议层异常，统一返回 {error: {code, message, suggestion}}。错误码：DOC_NOT_FOUND（含歧义，附候选与"先 kb_search 消歧"建议）、SECTION_NOT_FOUND（建议先 kb_show 列章节）、MODE_NOT_READY（vector 模式未就绪或非法 mode）、CONFIG_INVALID、INTERNAL。

kb_assemble_context 走确定性路径：内部检索不做 LLM 扩展与重排，延迟可预期；预算按约 4 字符 ≈ 1 token 折算截断；sources 只包含真正拼入 context_block 的文档，每个都带可回读的锚点。

5.3 在 Agent 客户端中注册

以 MCP stdio 方式注册（以 Claude Code 的 .mcp.json 为例，Kimi Code 等客户端同理，字段名以各客户端文档为准）：

{
  "mcpServers": {
    "graphit-kb": {
      "command": "uv",
      "args": ["run", "kb", "serve", "mcp"],
      "cwd": "D:/Users/Yu/Documents/Coding/AI-Coding-Engineering/code/kb-app",
      "env": { "GRAPHIT_KB_DATA_DIR": "D:/kb-data" }
    }
  }
}

要点：cwd 指向 kb-app 仓库（保证 uv run 找到环境）；GRAPHIT_KB_DATA_DIR 指向你的数据目录（不设则用 ~/.graphit-kb）。

5.4 典型调用时序

六、目标应用场景示例

场景 A：论文研究 —— 新增一批论文并快速进入阅读

目标：新下载了 10 篇 arXiv 论文 PDF，希望自动完成解析、分类、摘要，随后按主题浏览并精读。

  1. 把 PDF 放入 references/<主题>/ 目录；如已有配套人工摘要，放入该主题下的 summaries/ 并确保头部 source_pdf 与 PDF 文件名一致。
  2. 确认 classify.topic_keywords 覆盖这批论文的主题词（不配置关键词时所有文档都会进待确认队列）。
  3. 执行： 
    kb index scan          # 看到"新增 D0042–D0051，入队 10 个 parse"
kb index run           # 解析 + 分块 + 分类 +（有 LLM 时）摘要
kb status              # 检查 needs_confirm 队列
  4. 处理待确认：kb status 列出的条目，用 kb index set-topic D0044 CodeGraph 逐一改判；解析失败（no_text）的扫描件 PDF 当前版本无法检索全文，需人工 OCR 后重新放入。
  5. 进入阅读： 
    kb search "" --mode topic-global     # 主题全景：哪个主题有哪些论文
kb show D0042                        # 看章节树和摘要
kb read D0042 '$summary'             # 读摘要全文
kb read D0042 '§3 Method'            # 精读某章原文
kb related D0042                     # 找同主题关联论文
kb compare --docs D0042,D0043        # 两篇对比（需 LLM）
文件名含 arXiv 号（如 2607.03691v2.pdf）会被自动识别为 paper 类型；策展摘要文件名序号应与源 PDF 一致、不带版本号。扫描件 PDF（无文本层）会进入 needs_confirm 且 extract_status=no_text，这是预期行为而非故障。

场景 B：参考知识库编写设计方案

目标：写一份"XX 系统上下文管理"的设计方案，需要回顾库中相关论文与既有研究报告的观点。

  1. 广撒网：先用主题全景和粗检索圈定范围： 
    kb topics                                  # 看主题分布与规模
kb search "" --mode topic-global           # 每个主题下的文档与一句话索引
kb search "上下文工程 上下文预算"            # hybrid 检索定位章节
  2. 定点精读：对命中文档 kb show 看章节树，kb read 取关键章节原文；对短缩写查询（如 "RAG"）依赖内置同义词表自动扩展全称与中译。
  3. 横向比较：对观点相近的若干篇用 kb compare --docs D0005,D0011,D0019 生成对比表（一句话结论 / 适用场景 / 主要观点 / 关键差异）；无 LLM 时回退为并排摘要，人工比对。
  4. 沉淀：写出的设计文档放入 design/ 语料目录，再 kb index scan && kb index run 入库——它会因 corpus=design 自动判为 design 类型，成为后续检索的语料。
检索到的章节引用进设计方案时，直接记录锚点（doc_id + section_path，如 D0005#§2.1），日后可用 kb read 精确回读原文核对。

场景 C：AI Agent 自动参考知识库

目标：让编码/写作 Agent 在执行任务时自动查询知识库，获得带溯源的上下文，而不是人工粘贴资料。

  1. 按 5.3 在 Agent 客户端注册 MCP 服务，确认 uv sync --extra mcp --extra parse 已安装、数据目录已完成索引（scan + run 已跑过）。
  2. 在 Agent 的任务指令中引导使用模式，例如： 
    先用 kb_assemble_context(task="为知识库设计上下文预算分配策略", budget=8000)
获取参考资料上下文；对其中的关键文档用 kb_read 下钻章节原文核实；
引用结论时注明 sources 中的 doc_id 锚点。
  3. Agent 的典型自助路径（见图 4）：kb_search 粗查 → kb_show 看结构与摘要 → kb_read 精读 → 需要成段背景时直接 kb_assemble_context。
  4. 消费返回：context_block 直接拼入提示词；sources 中的锚点用于生成引用说明或后续回读。
注意四点：① kb_assemble_context 的 budget 是约 token 数（按 4 字符 ≈ 1 token 折算），按你的模型上下文窗口合理设置；② 工具返回 error 结构时按 suggestion 字段行动（如先 kb_search 消歧），不要重试相同参数；③ MCP 服务进程缓存配置，改完 config.yaml 要重启服务；④ 服务只读，索引进度（如 scan 后未 run）不会经 MCP 反映出来——先确认 kb status 队列已清空再让 Agent 使用。

场景 D：日常维护与故障处理

  • 资料变动：移动/重命名/删除文件后，跑一次 kb index scan（移动零重抽取、删除留墓碑），有新增或修改再 kb index run。
  • 索引重建：调整分块或分类参数后 kb index reindex --full && kb index run；解析器升级后加 --no-cache。
  • 写锁占用（退出码 2）：确认没有其他 kb index run 在跑；崩溃残留的锁会被自动回收（进程探测 + 1 小时 mtime 兜底），稍候重试或加 --wait。
  • 任务失败：kb status 看 failed 计数；可重试失败（如 LLM 超时）会自动退避重试，终态失败（如文件损坏）需人工处理源文件后重新 scan。
  • 策展摘要不匹配：查 reports/manifest_mismatch_*.json，修正摘要头部的 source_pdf 为库内实际文件名后再 scan。

七、注意事项与常见问题

主题说明
平台支持Linux / macOS 全功能。Windows 上写锁（依赖 POSIX PID 语义）不可用：index run、config set、set-topic 等写命令可能失败；只读命令可用但未完整验证。
网络盘数据目录不要放在 NFS/SMB 上，SQLite WAL 在网络盘上有损坏风险。
退出码0 成功；1 参数/校验错误（如未知配置键、文档不存在）；2 锁冲突或 IO 错误；130 用户 Ctrl-C（任务已安全回队）。脚本中可按退出码分支处理。
离线运行不装 llm extra 或不配 API key 时：分类走纯规则、无自动摘要（检索回退标题/首节）、无查询扩展与重排；其余功能不受影响。
LLM 费用每次 LLM 调用记入 llm_usage 表（模型、用途、token 数）；摘要批量生成是主要开销，可用 llm.summary_* 预算键控制。
Python 3.113.11.0 捆绑的 SQLite 3.38 对非 ASCII LIKE 查询静默返回空集，中文短查询会零命中——请用 3.12（仓库 .python-version 已钉 3.12）。
未落地功能--mode vector、kb collect、kb serve viz、kb maintenance 当前为显式报错或占位；知识图谱（实体/关系）与 Web UI 属后续里程碑。相关目录（graph/、vectors/、inbox/、sources.yaml）为预留。
原文只读系统永不修改语料文件；所有产物（缓存、摘要、索引、报告）都在数据目录。语料目录本身请用 git 等手段另行管理。
测试验证仓库含 242 项自动化测试（uv run pytest）；检索召回率实测约 70–80%（在线档），短查询与缩写建议配合 search.synonyms 配置优化。
