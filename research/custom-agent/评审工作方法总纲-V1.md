# AI 代码评审的总体工作方法（人在回路）V1

> 版本：V1.0（2026-08-20；可用交付版——先可用，再随研究迭代）
> 来源：本研究 P2/P3 阶段 22 个工作场次的方法沉淀，全部条款经真实实验验证（关键实证以〔实证〕注记，明细见研究仓库 `research/` 各记录）。
> 读者：准备在真实项目中采用"多轮 AI 评审 + 人工把关 + AI 修复 + AI 复审"流程的工程团队。本文自足，不需要了解研究背景。

## 0. 总体结构

```
① 多轮评审（并行，同模型或分档模型）──► ② 归并与仲裁（主题并集 + 置信分层 + 冲突标记）
        │                                        │
        ▼                                        ▼
③ 人工决策（少量关键介入点，决策文档内联比对）──► ④ 修复（编码代理执行）
        │                                        │
        ▼                                        ▼
⑥ 人工合并收口（生产仓库合并权在人）◄── ⑤ 独立复审（评审代理 + 规则指引，四档结论）
```

核心立场（全部来自实验）：AI 单轮评审是**对缺陷空间的一次采样**，不是判定；人负责大尺度判断与最终裁定；各环节产物必须是**结构化、可审计、可跨轮比对**的文档。

## 1. 评审执行

### 1.1 工具与角色分工（阶段-工具配适）

| 阶段 | 建议执行者 | 理由 |
|---|---|---|
| 全量评审（多轮） | 评审代理 + 规则指引（skill）；可用便宜模型跑量 | 需要覆盖面与格式一致 |
| 修复 | 编码代理（带集成编辑/测试工具者） | 修复需要工具链 |
| 独立复审 | 评审代理 + 规则指引，**与修复者不同工具/模型** | 独立性 |

〔实证〕本方法首次真实运行即采用"编码代理修复 × 评审代理复审"的跨工具分工：修复者当日两次低级失误（代码块错位、真值守卫），第一次被自身冒烟拦截、第二次被独立复审拦截——三段流程缺一不可。

### 1.2 单轮评审规程

1. **锚点隔离**（评审历史状态时）：被评审内容一律经 `git show <锚点>:<路径>` 读取；定位变更范围用 `git diff <fix>^ <fix> --stat`（**不得用会输出提交信息的命令查看修复提交**）。〔实证〕实验中先后发现五条信息渗漏通道：既往评审产物、工作区当前文件、锚点内既有评审报告、修复提交主题行（经 `--stat` 携带）、对被隔离材料的越界断言——前四条造成过实际污染，最后一条催生下述禁令。
2. **越界断言禁令**：对禁止读取的材料（如既有评审报告）不得做任何内容断言（如"设计文档未登记"），只能写"未核查"。
3. **意见卡契约**：统一模板（标题＝对象前缀＋缺陷一句话；单行字段：类型/溯源/证据/维度/建议；溯源列出涉及的全部文件）——使产出可解析、可跨轮比对。
4. **立项纪律**：检查清单中出现"缺/冲突/违规"判断的条目必须立项为意见（级别可低不可无）或写明豁免理由——禁止"标注即可"式降格。〔实证〕无此纪律时，评审者会把已发现的事实降格为备注（实测一例：把页面缺陷写成"设计选择、缺注释"）。

### 1.3 多轮策略

- **默认并行多轮再归并**，而非优化单轮提示。〔实证〕同一基线 5 份独立报告：单轮召回 31–46%（分母为逐条复核确认的问题主题）；稳定复现的仅高显著度主题（约 4–5 个），约半数发现是单轮独有；严重度可漂移两级；甚至出现"无误"与"缺陷"对立。
- **轮数投向按方差分配**：低方差域（通用工程缺陷，如超时/重试——裸模型三轮全中）一轮即可；高方差域（领域契约类）多轮。〔实证〕同规则版本在领域契约类锚点上命中波动 4–11/11。
- **规则指引的价值在覆盖面而非深度**：带指引两轮 ≈ 不带指引三轮的覆盖率（22/35 主题，"约白送一轮"）；指引稳定命中的是非直觉类别（用户输入硬上限：带 2/2、不带 0/3）与契约/登记口径类；深度发现两组都是单次采样运气。

## 2. 归并与仲裁

1. **主题归并**：跨轮意见按问题主题（非措辞）归并——并集取发现、交集定置信（出现在 ≥2 轮的意见优先复核）、独有项标"待核"。
2. **严重度仲裁**：每条意见须附分级依据陈述；最高级（P0）须有事故/资损级证据背书。〔实证〕无依据陈述的对照组给出 4 个 P0，人工复核全部偏高；带陈述的实验组唯一 P0 有真实事故背书，成立。
3. **跨轮纠错**：任何单卡的"未发现问题"清单不可直接采信——错误背书（把真缺陷标为"已核对无误"）只在对照中暴露。〔实证〕对照组两处错误背书之一，背书的正是后续被修复提交证实的真缺陷。

## 3. 人工决策（少量关键介入点）

使用本方法时需要人介入的三个时刻：①评审意见与已知事实矛盾（填"待确认问题卡"归类）；②修复应答中被驳回且复审仍持异议（人工裁定，不得默认放行）；③复审"部分修复/新发现"项的接受与再修复。研究/评估场景另有口径裁定类决策（用带固定字段的待办清单管理）。

**决策文档两条硬规范**（让人工处理可行）：①**内联摘录**——需比对的内容（双方判断、证据原文+行号）必须摘录进决策文档，不得只给路径让人跳转；②**自足表述**——每个待决策事项配自足背景段（做了什么/为何需要人来定/选项含义），内部编号附白话说明。

## 4. 修复与复审（A-B 闭环）

五步：评审 → 应答（修复方逐条"接受/部分/驳回"，**驳回必须给反证**，禁止未核对就驳回）→ 修复（每条承诺可追溯）→ 独立复审（四档结论：已修复/部分/未修复/驳回成立；**逐条内联原意见与应答结论**，单一文档完成三方比对；对修复 diff 本身做回归检查）→ 人工合并收口。

〔实证〕复审的价值两度现场证明：历史修复复审发现"12 项应答承诺未兑现"（无复审则漏检）；真实应用轮复审抓出修复引入的守卫回归（P3）并当场按处方修正。修复完成后按项目文档惯例出**修复报告**（逐项修复 + 复审结论 + 回归修正 + 验证与已知限制 + 合并建议）。

## 5. 错判复核清单（人工终审用）

AI 评审的五类典型错因与对应核查动作〔实证：85 条意见逐条复核得出〕：

| 错因 | 典型形态 | 核查动作 |
|---|---|---|
| 运行时行为臆测 | 凭代码形状联想已知缺陷模式（如"子类没调 super 会崩"——实际子类没定义 `__init__`） | 对崩溃/异常类断言要求最小验证或给出继承链证据 |
| 逻辑极性反转 | 否定式条件方向读反 | 对含 NOT/排除条件的意见重读原句 |
| 机制推演失真 | 代码观察对、影响量化夸大数倍 | 抽算量化依据（次数×时长等） |
| 越界断言 | 对未读材料下"未登记"类结论 | 只采信"未核查"表述 |
| 计数粗疏 | 次数/条目数与实际不符 | 抽算计数 |

复核优先级：**错误背书 > 深度发现 > 长尾意见**（错误背书传递虚假安全感，危害最大）。

## 6. 停止条件与工具价值边界

1. **规则迭代停止**：当修订开始针对单一案例具体形态、复测通过率不再显著提升、修订理由变成"更全"而非根因、或投入将超过一次新项目冷启动成本时——停止在当前项目微迭代，转入新项目检验。〔实证〕源项目上第二轮规则修订被叫停时的裁定记录。
2. **工具价值边界**：规则指引的增量取决于缺陷类型是否在裸模型能力圈内——通用工程缺陷（超时/重试/异常处理）裸模型即稳定发现，规则近乎零增量；领域契约与口径类缺陷才有明确增量。部署前先在本项目测一轮裸模型基线，把规则预算投给裸模型的盲区。
