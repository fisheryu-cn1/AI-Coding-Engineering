# 场景画像问卷 v1（D1-S2 定稿）

> 日期：2026-08-17（P1 产出）
> 话题标签：[D1]（问项 1–6 引用 [D1+D2] 范式决策树；问项 7–9 引用团队实践调研）
> 依据：notes/02 v0.2 §3（9 问框架）、`agent-software-design/范式选型决策树.md`（判据）、两因素模型（组件配比原理）
> 用法：对候选场景逐问作答，产出**场景画像卡**（第 3 节模板）→ 直接驱动范式决策树走查与组件选配。本问卷的首个应用即场景一选型（第 4 节已给出三个候选的速画像供 P1 阶段评审评审）。

---

## 1. 问卷原理

问卷回答两个问题：**用什么范式**（问 1–6 → 范式决策树）与**配什么组件**（问 1–9 → 组件目录选配规则）。原理是两因素模型：问 1–5 界定"模式匹配"的难度（任务形态），问 6–9 界定"外部信息供给"与"质量门禁"的需求强度——**L2 上下文构建组件的厚度由前者决定，L5 观测验证组件的厚度由后者决定**。

## 2. 九问（每问含问法、判据、影响）

| # | 问法 | 判据/选项 | 影响 |
|---|---|---|---|
| 1 | 任务需要与外部环境/工具交互吗？交互密度多高？ | 无 / 低（读为主）/ 高（读写混合） | 无→纯提示工程；高→决策树 Q1 走是 |
| 2 | 存在可验证的成败信号吗？允许重试吗？ | 单元测试/环境判定/人工评审/无 | 有→Reflexion 外循环；无→护栏全靠 L5 |
| 3 | 是组合搜索/规划型任务吗？中间状态可自评吗？ | 是/否 | 是→ToT 候选（token 预算警示 5–10×） |
| 4 | 流程可预先静态分解吗？子任务独立吗？ | 确定 SOP / 半确定 / 高度动态 | 确定→代码编排（LLM 节点内）；动态→replan；独立多工具→DAG |
| 5 | 任务时间跨度与状态性？ | 分钟级无状态 / 小时级有状态 / 长时程连续性 | 后两者→外部化状态+检查点；连续性→记忆组件（L2 记忆行） |
| 6 | 输出错误的代价与可回滚性？ | 可回滚低代价 / 需人审 / 不可逆高代价 | 决定验证深度分级（P0–P3）与人在环位置（契约指南 §1 错误成本判据） |
| 7 | 团队用什么考核口径？交付稳定性有要求吗？ | DORA 型指标 / 无正式口径 | 有→L5 门禁+审计组件必配；评审耗时纳入预算 |
| 8 | 使用者画像：资历与代码库熟悉度？规范载体成熟度？ | 资深+熟悉 / 混合；有 AGENTS.md/spec / 无 | 资深+熟悉场景强调验证与解释组件（METR 教训）；有规范载体→消费而非另造 |
| 9 | 该场景在团队多工具分层中的位置？互操作面是什么？ | 规模化兜底 / 高自主专业位 / 独立工具 | 决定与既有工具（Copilot/Claude Code 等）的分工与 AGENTS.md 公分母 |

**附加问（需求阶段深度，来自笔记 03 交叉）**：该场景的需求产物需要多深的建模？（单文档级 / 多视角建模+一致性检查）——决定是否引入需求模板集 v0 的 R1–R5 规则与澄清循环。

## 4. P1 阶段评审准备：三个候选场景速画像（2026-08-17，供选型评审）

> 评审标准（规划 §6）：与 kb-app/文档链衔接且有真实使用者 > 任务可验证 > 非编码场景（检验通用性）。

| 问 | A 代码评审 agent | B API 文档问答 agent | C 文献调研 agent |
|---|---|---|---|
| 1 交互 | 高（读仓库/PR，写评审意见） | 低（读图谱，答询） | 高（检索/下载/写文档） |
| 2 可验证 | 强（评审意见可对照 R-条目人工抽检；规则可机检） | 中（答案可溯源锚点验证） | 中（产物可机检：manifest/红线，本会话已实战） |
| 3 组合搜索 | 否 | 否 | 否（可 best-of-N） |
| 4 静态分解 | 是（SOP：读 diff→对照规范→分级意见） | 是（检索→组装→答） | 半确定（台账驱动流程已验证） |
| 5 时间跨度 | 分钟级 | 分钟级 | 小时级有状态（会话续跑已验证） |
| 6 错误代价 | 中（误报漏报可被人工评审拦） | 低（有锚点可查） | 中（错误入库污染库，需门禁） |
| 7 团队口径 | 直接对接 D3-B（AI 先审门禁的真实试验场） | 弱相关 | 弱相关 |
| 8 使用者/规范 | 团队开发者；AGENTS.md+评审报告惯例成熟 | 研究者本人 | 研究者本人（真实用户 ✓） |
| 9 分层位置 | 高自主专业位 | 独立工具 | 高自主专业位 |
| **范式** | 代码编排（LLM 节点内）+ HITL | 代码编排（检索管道）+ MCP 服务 | ReAct+Reflexion 外循环（子代理分工已实战） |
| **衔接** | design/kb-app 评审报告体系 | context-engineering + kb-app MCP | 本仓库 research 流程（已半自动化） |
| **短板** | 评审质量基线难建（需标注集） | 场景较窄，范式单一 | 过程已部分存在，"构建方法"验证增量偏小 |

**初步建议（供 P1 阶段评审决策）**：**A 代码评审 agent** 综合最优——三向协同最强（D1 装配实验 + D2 规约-验证对实例 + D3-B 的 AI 先审门禁试验场），与 kb-app 评审报告体系直接衔接，任务可验证性最好；其短板（评审质量基线）恰是 D2-S4 规约-验证对的用武之地。次选 C（真实用户与既有流程衔接最好，但方法验证增量小）。**待定决策：首发框架（pi 或 DSH）与 A 的评测集规模。**

## 5. 使用边界

- 问卷是判据组织器而非充分条件：九问回答后仍需范式决策树走查 + 组件目录核对两步落地；
- 问项依据 2024–2026 证据，模型代际变化后问 2/5 的阈值需重校准（时间地平线）；
- v2 预期：场景一画像实测后修订问项表述与附加问的必要性。
