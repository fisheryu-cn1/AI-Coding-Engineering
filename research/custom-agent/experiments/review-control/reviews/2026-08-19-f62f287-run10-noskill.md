### [P0] Tombstone 任务会**静默抹空** Document 全部业务属性

类型 / 数据损坏
溯源 / code/kb-app/src/kbapp/graph/ladybug_store.py:96-109（upsert_nodes SET 全字段）；code/kb-app/src/kbapp/pipeline/graph_stages.py:56-66（stage_tombstone_graph 入参只有 doc_id + valid_to）

### [P0] `topic_subgraph` 的"hops=2 扩展"是 no-op：永远不会发现新 Entity

类型 / 功能失效
溯源 / code/kb-app/src/kbapp/graph/queries.py:60-70（"跳数扩展"段）
证据 / 注释自陈"hops=2 时一并拉 Entity 之间的 RELATES_TO 邻居"，但实际 Cypher 是 `MATCH (a:Entity)-[:RELATES_TO]-(b:Entity) WHERE a.entity_id IN [$ents_csv] AND b.entity_id IN [$ents_csv] RETURN DISTINCT b.entity_id AS eid`——`a` 与 `b` 必须**都已经在集合内**。结果集合只能确认已有成员，不会增长，hops=2 子图与 hops=1 子图结果完全一致。`_seed_full_graph` 测试不覆盖"已知集合 → 发现新邻居"路径，且 `test_topic_subgraph_truncates` 用 `if len(result["nodes"]) >= 500: assert ...` 的写法把断言条件化，长不出来就跳过——bug 静默通过测试。

### [P0] 图节点 PK 命名空间冲突：Document/Section/Entity/Topic 共享同一字符串池

类型 / 设计缺陷 / 用户可见
溯源 / code/kb-app/src/kbapp/graph/schema.py:60-110（四类节点 PK 都是 STRING）；queries.py / graph_search.py 用 `coalesce(n.entity_id, n.doc_id, n.section_id, n.name)` 反查
证据 / Topic PK = `name`、Document PK = `doc_id`、Entity PK = `entity_id`、Section PK = `section_id`，全部 STRING 类型且无前缀。Topic 命名走 classify 关键词打分收敛，但 LLM classify 可能产出与 doc_id 同名（如标题包含 "AI" 的论文 doc_id "D001"，主题也可能是 "AI"）。`coalesce` 只看首非空 PK，丢失类型信息；graph_search 的 `seen = set()` 仅按 id 去重，UI 看到两个不同类型节点共 id。Topic 节点的"id"和 Section 节点的"section_id"完全可能在同一字符串池碰撞。
维度 / 数据模型 / 正确性
建议 / (a) Topic PK 改为独立字段 `topic_id`（如 `sha256(name)` 或 `T:` 前缀）；或 (b) 所有节点 ID 加类型前缀（如 `T:`、`D:`、`S:`、`E:`）使命名空间隔离；并把 `coalesce(...)` 替换为显式按节点标签取对应 PK。

### [P0] stage_tombstone_graph 在文档不存在时**凭空创建** Document 节点

## P1 — 缺陷（非阻塞但影响功能/可维护性）

### [P1] Cypher 通过 `repr()` 字符串拼接构造 IN 列表：与"参数化绑定"契约自相矛盾

类型 / 安全/正确性风险
溯源 / code/kb-app/src/kbapp/graph/queries.py:39-43, 49-56, 62-70, 92-100；code/kb-app/src/kbapp/web/api.py:_aggregate_entities:53-69
证据 / ladybug_store.py docstring 明确"Parameter binding is mandatory — callers never concatenate strings"，但 queries.py 和 `_aggregate_entities` 在 4 处用 `",".join(repr(d) for d in ids)` 拼出 `IN [...]`，再用 `params={}` 空字典调用。doc_id 走数据库/搜索结果时一般是受控的 `D\d+`，但 LLM 抽取产生的 entity_id / topic name 都可能含特殊字符（如 `D'1`、`foo"bar`），Python `repr` 用双引号绕过单引号但仍与 Cypher 字符串字面量规则不完全等价——一旦 id 里出现反斜杠、控制字符、unicode 引号，查询就 syntax error 或语义偏移。
维度 / 一致性 / 健壮性
建议 / LadybugDB 参数支持列表绑定，把 `IN [...]` 改成 `IN $ids`、params 用 `{"ids": [...]}`. 同时把 queries.py 的 4 处、`_aggregate_entities` 的 1 处一并改掉，与 store docstring 契约对齐。

### [P1] `kb_compare` MCP 工具接受 `doc_ids` 参数却**完全不使用**

类型 / API 契约偏差
溯源 / code/kb-app/src/kbapp/mcp_server.py:181-209（_kb_compare）；code/kb-app/src/kbapp/retrieve/graph_search.py:69-94（graph_compare）
证据 / `graph_compare` 注释自陈"lbug 暂不支持 EXISTS 子查询 + 多 MATCH 联合；先按 concept 宽查，前端按 doc_ids 过滤显示"，因此 doc_ids 参数原样收下但完全不传给 Cypher。客户端调用方传 doc_ids 期待服务端按文档集合过滤，结果却拿到全图所有相关关系。新增 MCP 工具 (`kb_compare`) 误导调用方，且未在文档/错误信息里说明。
维度 / API 正确性
建议 / 在 docstring + tool description 显式声明"doc_ids 当前为预留参数，服务端忽略；过滤由调用方负责"；或者真正实现 doc_ids 过滤（即便拆成两步 Cypher：先按 concept 查所有相关 entity，再校验是否在指定 doc_ids 提及范围内）。

### [P1] MENTIONS weight 是字面子串计数 + 大小写敏感：严重失真

类型 / 语义错误
溯源 / code/kb-app/src/kbapp/graph/extract.py:148（`cnt = text.count(name)`）；tests/unit/test_extract.py:191-194 验证 `weights["Method:rag"] == 2`
证据 / 文本 `RAG uses Vector DB. RAG uses Vector DB again.` 用 `text.count("RAG")` 得 2，但同文本用 `text.count("rag")` 得 0——LLM 返回 "RAG" 而文本里出现 "rag" 的章节就会 0 weight。子串匹配还会把 "Transformer" 计入 "Transformer-based"、"RAG" 计入 "RAGged" 或 "DRAG"。"RAG" 和 "rag" 也算两个不同 entity_id，导致一个概念被拆成两个节点。
维度 / 数据语义
建议 / 用大小写不敏感 + 词边界正则：`re.findall(rf"\b{re.escape(name)}\b", text, flags=re.IGNORECASE)`；并把 norm 函数扩展到 entity name 路径前的预归一化，避免 "RAG"/"rag" 拆成不同 entity_id。

### [P1] `_doc_mentions` / 词云与 `_doc_related_docs` 不感知 Topic 关联

类型 / 功能缺失

### [P1] `web/api.py` 路由函数把 `request: Request = None` 作为占位：FastAPI 注入语义被绕开

类型 / 类型契约偏差
溯源 / code/kb-app/src/kbapp/web/api.py:18, 200-203, 240-243 等

建议 / 改为 `request: Request`（不带默认值），FastAPI 自动注入；或者把 helper `_state(request: Request)` 的 callers 重构成 dependency injection。
