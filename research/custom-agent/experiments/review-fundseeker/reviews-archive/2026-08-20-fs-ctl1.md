## 意见卡

### [P0] 重试循环对 HTTP 4xx 客户端错误一视同仁，导致永久失败反复重试并放大挂起风险
- 类型：缺陷-可靠性/重试策略
- 溯源：src/fundseeker/utils/http.py:127-132、149-154
- 证据：`except requests.RequestException as exc: ... if attempt < self.max_retries: backoff = ...; time.sleep(backoff); continue` —— `requests.RequestException` 同时覆盖 `ConnectionError`、`Timeout` 与 `raise_for_status()` 抛出的 `HTTPError`（含 4xx/5xx）。当目标返回 403/404 等永久性客户端错误时，4 次重试 + 累计 ~7-10s 退避 + 4 次请求间隔延迟（默认 5-10s）将单产品耗时人为放大到数分钟；若 4xx 期间服务器又因负载问题出现间歇性 5xx，长尾会被反复叠加。
- 维度：可靠性、健壮性
- 建议：将 HTTPError 单独识别，仅对 5xx 与网络类异常（`ConnectionError`、`Timeout`）启用退避重试；4xx 直接抛出。Eastmoney F10 接口的历史数据缺失/产品下线本就以 4xx 表达，盲目重试只会拉长 `run_holdings` 主循环。

### [P0] `run_holdings` 在产品循环内裸 `except Exception` 静默吞错，故障不可观测、无法回退重试
- 类型：缺陷-错误处理
- 溯源：src/fundseeker/runner.py:487-496
- 证据：
  ```python
  for product in products:
      try:
          result = collector.collect_holdings(...)
      except Exception:
          skipped_products += 1
          continue
  ```
  异常细节（traceback、`Timeout`、`ConnectionError`、解析错等）全部丢失，仅以 `skipped_products += 1` 计数；当 socket 异常而 `collect_holdings` 抛出而非永久阻塞时，整个批次的失败原因在 `CollectionLog.error_message` 中亦无记录（写入只发生在 `try` 顶层 `except`），排查时只能看到 “失败 N 个” 但无上下文。
- 维度：可观测性、可维护性
- 建议：将异常捕获窄化为 `(requests.RequestException, socket.timeout)` 等网络类异常并在 `collection_log` 中写入错误明细（含 `product_code` 与异常类型）；同时对非致命异常做有限重试（如 1 次），将真正失败的产品标记为 `skipped_with_error` 以便后续人工补采。

### [P1] `timeout` 仅作为单 float 透传，未区分 connect 与 read，无法抵御 “半开 socket 长期挂起” 场景
- 类型：缺陷-超时配置
- 溯源：src/fundseeker/utils/http.py:118、140
- 证据：`kwargs.setdefault("timeout", self.timeout)` —— `self.timeout` 是 `float`（默认 30.0），对 `requests` 而言同时约束 TCP 连接与读取两个阶段。当 Eastmoney 在握手阶段（SYN/ACK 后）出现慢响应、或 NAT 中途丢包但连接未关闭时，30s 单一值无法为 connect 提供更短的硬上限（如 10s），从而导致整个产品循环在连接阶段就耗尽窗口；亦不能给 read 留更长预算以容忍大 HTML 响应。
- 维度：可靠性
- 建议：使用 `(connect_timeout, read_timeout)` 元组分别配置（`urllib3` 支持）；建议 connect=10s、read=60s 或可由 `request_cfg` 注入。

### [P1] `requests.Session` 未配置 TCP keepalive 与空闲连接回收，半开连接长期残留导致 socket 池耗尽
- 类型：缺陷-连接管理
- 溯源：src/fundseeker/utils/http.py:60-62
- 证据：`self._session = requests.Session(); if ssl_legacy: self._session.mount("https://", _LegacyRenegotiationAdapter())` —— 默认 adapter 未设置 `socket_options`（`SO_KEEPALIVE`/`TCP_KEEPIDLE`/`TCP_KEEPINTVL`/`TCP_KEEPCNT`），亦未挂载 `HTTPAdapter(pool_block=True)`。在 NAT/防火墙静默丢包或服务端崩溃未发 FIN 的场景下，连接在 `ESTABLISHED` 状态永久残留，最终触发 “connection pool exhausted”，新请求排队直至 read timeout，整体 `run_holdings` 表现为 “卡死”。
- 维度：可靠性、网络
- 建议：为 `https://` 与 `http://` 显式挂载带 `socket_options` 的 `HTTPAdapter`，至少开启 `SO_KEEPALIVE` + `TCP_KEEPIDLE=60, TCP_KEEPINTVL=10, TCP_KEEPCNT=3`，并设置 `pool_block=False` 防止线程池阻塞；同时为 `urllib3.PoolManager` 设定 `maxsize` 与过期回收。

### [P1] `run_holdings` 主循环缺少单产品/单批次硬性截止时间，socket 阻塞时无可救生索
- 类型：缺陷-健壮性
- 溯源：src/fundseeker/runner.py:487-619（尤其 489-493 `collector.collect_holdings` 调用）
- 证据：`collector.collect_holdings(...)` 内部分别调用 `self.http.get(API_URL, params=...)`（eastmoney_holding.py:139），若 HTTP 客户端本身未在 socket 层 raise（已观察到 `_enforce_delay` 会先 sleep），单次调用最坏耗时 ≈ 4×(delay+timeout+backoff)；若上游服务器永久不关闭 TCP 连接且 `urllib3` 的 read 超时未触发（例如某些 keep-alive + 大响应 head-of-line 阻塞情形），整个 `for product in products` 循环将无限挂起，cron 任务无 watchdog 终止。
- 维度：可靠性、可观测性
- 建议：引入 `concurrent.futures.ThreadPoolExecutor` + `future.result(timeout=...)` 或 `signal.alarm`/`threading.Timer` 守护，对单产品 `collect_holdings` 设置硬性超时（如 180s），超时后标记产品失败并继续；并将 `product_code` 与耗时纳入 `CollectionLog.error_message` 与摘要指标。

### [P1] `PoliteHttpClient` 未对外暴露 `ConnectionError`/`ChunkedEncodingError` 等“可重试网络错误”的细分能力，所有 `RequestException` 一刀切退避
- 类型：缺陷-重试策略
- 溯源：src/fundseeker/utils/http.py:121-134、143-156
- 证据：循环仅按 `attempt < self.max_retries` 做指数退避，未对 `urllib3.exceptions.ProtocolError`、`requests.exceptions.ChunkedEncodingError`、`NewConnectionError` 等典型 “TCP 连接被服务端重置/截断” 场景做更激进的短退避；在 Eastmoney 反爬节奏切换、CDN 边缘节点抖动期间，此场景发生频率高，沿用 2^n 长退避会显著拉长每产品耗时。
- 维度：可靠性、性能
- 建议：按异常子类分级：`ConnectionError`/`ProtocolError` 用短退避（≤1s）；`Timeout`/`ChunkedEncodingError` 用原退避；`HTTPError` 按状态码分流（5xx 重试、4xx 即停）。同时为 `urllib3.Retry` 显式指定 `status_forcelist` 而非依赖 `raise_for_status` 之后再决策。

### [P2] `_LegacyRenegotiationAdapter` 默认虽关闭，但属已知 TLS 漏洞利用面，缺文档警告与日志
- 类型：缺陷-安全
- 溯源：src/fundseeker/utils/http.py:22-34
- 证据：`ctx.options |= getattr(ssl, "OP_LEGACY_SERVER_CONNECT", 0)` —— `OP_LEGACY_SERVER_CONNECT` 对应 CVE-2009-3555（TLS Renegotiation Attack），目前 `ssl` 模块该常量仍存在但已无安全实现。当前 `__init__` 仅以 `ssl_legacy: bool = False` 静默暴露，无 docstring 警示，亦无运行时拒绝在 HTTPS-only 站点启用。
- 维度：安全
- 建议：在 docstring 中标注 “仅用于兼容已知不安全的旧采集源，启用前需评估目标站点证书策略”；或直接移除该 adapter 并由业务方在调用方自行挂载。

### [P2] `_can_fetch` 的 robots.txt 缓存进程内永不过期，且解析失败一律返回 `True`
- 类型：缺陷-资源策略
- 溯源：src/fundseeker/utils/http.py:89-109
- 证据：`if base_url not in self._robots_cache: rp = RobotFileParser(); rp.set_url(robots_url); rp.read(); self._robots_cache[base_url] = rp` —— 同一 `PoliteHttpClient` 实例下所有后续请求均复用首次解析结果，长跑任务（如 cron 守护进程）永远看不到 robots.txt 更新；且 `except Exception: return True` 会在 DNS 失败/超时/TLS 异常时把 “未知” 当作 “允许”，与常见 “保守拒绝” 的 robots 策略相反。
- 维度：合规、可靠性
- 建议：缓存加 TTL（如 24h）或在每次 `_can_fetch` 时 `If-Modified-Since` 校验；解析异常改为 “上一次已知结果”，若尚未有结果则按 “保守拒绝” 返回 `False`，并写 WARN 日志。

### [P2] `CollectionSummary` dataclass 未声明 `institution_rows` 与 `recent_failures` 字段，运行时动态挂属性

### [P2] `run_holdings` 顶层 `except Exception` 仅回滚但未关闭数据库连接外的游离 HTTP 资源，失败时残留 socket 池
- 类型：缺陷-资源释放
- 溯源：src/fundseeker/runner.py:643-660
- 证据：`except Exception as exc: session.rollback(); ... session.commit()` 与 `finally: session.close()` —— 若 `collect_holdings` 内部已部分建立 keep-alive 连接且响应解析中触发异常，`PoliteHttpClient` 实例由 `EastmoneyFundHoldingCollector` 持有，session 关闭不会清理 HTTP 连接池；当 `run_holdings` 整体失败返回 `failed` 时，下次复用同一 Python 进程的 cron 仍可能命中陈旧连接。
- 维度：可靠性
- 建议：在 `finally` 中显式调用 `self.http._session.close()`（或在 `run_holdings` 末尾增加 context-manager 包装 `EastmoneyFundHoldingCollector`）。

### [P3] `post()` 未调用 `_can_fetch`，与 `get()` 行为不一致，robots 策略对 POST 不生效

### [P3] `_parse_market_date` 未处理空字符串与异常，CLI 误传 `--market-date ""` 会 500 崩溃
- 类型：缺陷-健壮性
- 溯源：src/fundseeker/runner.py:668-674
- 证据：`return datetime.strptime(str(value), "%Y-%m-%d").date()` —— 若 `value==""`，`str(value)==""`，`strptime` 抛 `ValueError` 无捕获。
- 维度：健壮性

### [P3] `build_summary` 的 `market_quote_symbol_count` 与 `recent_failures` 查询使用 PostgreSQL 专属 `INTERVAL '... days'`
- 类型：缺陷-可移植性
- 溯源：src/fundseeker/runner.py:828、900
- 证据：`WHERE quote_date >= CURRENT_DATE - INTERVAL '2 days'`、`created_at > NOW() - INTERVAL '7 days'` —— 标准 SQL 的 `INTERVAL` 字面量需 `- INTERVAL '7' DAY` 等写法，SQLite/MySQL 表现不同；当前 `fundseeker/models/database.py` 默认绑定 PostgreSQL，但 summary 函数不显式声明方言依赖。
- 维度：可移植性
- 建议：改用 Python 端 `datetime.now(timezone.utc) - timedelta(days=N)` 透传给绑定参数，或在模块文档中明确 “summary 仅支持 PostgreSQL”。

### [P3] `_enforce_delay` 在重试循环中累积，4 次重试叠加 4 段延迟，显著拉长挂起感知时间
- 类型：缺陷-性能
- 溯源：src/fundseeker/utils/http.py:80-87、121-122、143-144
- 证据：`for attempt in range(self.max_retries + 1): self._enforce_delay()` —— 每个 attempt 均重新计算 `time.monotonic() - self._last_request_time`，但在 4 次重试期间每次都强制等 5-10s（默认），“礼貌延迟” 与 “失败后快速重试” 语义被混叠，单产品失败链总耗时 ≈ 4×delay + 3×backoff + 4×timeout。
- 维度：性能
- 建议：区分两种延迟模式：`min_delay/max_delay` 仅在 “上次请求成功” 时生效，重试期间使用单一 `retry_delay_seconds` 或直接交给 `backoff`；`EastmoneyFundHoldingCollector` 改 `min_delay=0.5` 后此问题被放大更明显。

### [P3] `run_holdings` 顶层 `except Exception` 中 `session.rollback()` 后再次 `session.commit()`，rollback 之后 commit 行为依赖 SQLAlchemy 状态机
- 类型：缺陷-健壮性
- 溯源：src/fundseeker/runner.py:643-660
- 证据：`except Exception as exc: session.rollback(); ... session.commit()` —— 在 SQLAlchemy 2.x 中，rollback 后立即 commit 通常 OK，但若底层连接已被 `pool` 标记为 invalid（典型情况：数据库会话因网络中断被 invalidate），`session.commit()` 会抛 `InvalidRequestError`，掩盖原始异常；同样 `finally: session.close()` 不会回收该连接。
- 维度：健壮性
- 建议：将 `log.status="failed"` 等元数据写到一个新 `Session` 或直接 `session.add(log); session.commit()` 前判断 `session.is_valid`，或在 `except` 分支中 `session.close()` 后重新打开 session 写日志。
