### [P0] `get/post` 对 4xx 与 5xx 一律重试，永久性客户端错误无短路
- 类型：可靠性 / 错误处理
- 溯源：src/fundseeker/utils/http.py:117-145（`get`）与 147-174（`post`）
- 证据：循环内 `response.raise_for_status()` 将 HTTPError 一并纳入 `except requests.RequestException` 分支，无差别走 `max_retries + 1` 次；末尾 `raise last_exception`。在 `max_retries=3`、`timeout=30` 默认下，对 404/410/403 等永久错误会消耗 4 次请求 + 指数退避（2^attempt+rand），单次最坏耗时约为 4x30s 加退避，达数分钟。
- 维度：错误分类、重试退避策略、可观测性
- 建议：在 `raise_for_status()` 后显式拆分 `response.status_code`：`if 400 <= status < 500: 立即 raise`；仅 5xx、连接级 `ConnectionError`/`Timeout` 进入重试池；同时把 `raise_for_status()` 之外的 `RequestException` 与 `HTTPError` 区分对待。

### [P0] 单次 `get/post` 缺少请求级总超时上限，stuck socket 下累积远超一次 timeout
- 类型：可靠性 / 资源耗尽
- 溯源：src/fundseeker/utils/http.py:131-134、160-163（重试循环）；配置入口 src/fundseeker/collectors/base.py:51（`request_cfg.get("timeout", 30)`）
- 证据：每次 attempt 仅传入单次 `timeout`；4 次 attempt × 30s + 节流 5-10s + 退避 `2**attempt + random.uniform(0,1)` 累加；未提供整个请求级的 deadline。若服务端只建立连接从不响应（部分响应头后挂起、复位窗口打不开），`max_retries=3` + 大延迟放大效果会达到分钟级。
- 维度：超时预算、cron 可调度性、可观测性
- 建议：增加 `deadline`（墙钟）参数；维护 `deadline - elapsed` 传给每个 retry 的 `timeout`；当剩余时间不足一次重试所需最小时直接放弃并抛出可识别的 `TimeoutError`。

### [P1] `_LegacyRenegotiationAdapter` 跳过 `super().__init__()`，触发路径会 `AttributeError`
- 类型：可用性 / 接口契约
- 溯源：src/fundseeker/utils/http.py:22-34；调用方 src/fundseeker/collectors/citicwm.py:21-31、src/fundseeker/collectors/spdbwm.py:17-27
- 证据：子类只实现 `init_poolmanager`，未定义 `__init__`，更未 `super().__init__(...)` 初始化 `self._pool_connections`/`self._pool_maxsize`/`self.max_retries` 等。`requests.adapters.HTTPAdapter.send()` 第一次执行时按 `if self.poolmanager is None: self.init_poolmanager(self._pool_connections, self._pool_maxsize, ...)` 读取这些属性，实例上未设置将抛 AttributeError。CITIC、SPD 两个 collector 均显式 `ssl_legacy=True`，会在生产 cron 第一次 send 时崩溃。
- 维度：异常路径、单元可测试性、与 requests 版本耦合
- 建议：补 `def __init__(self, *a, **kw): super().__init__(*a, **kw)`，或直接 `super().__init__()` 后再覆盖默认参数；并为该路径补一个针对 https 端点的最小烟雾测试。


### [P1] `run_holdings` 用 `except Exception` 吞掉所有 collector 错误，无任何日志
- 类型：可观测性 / 错误处理
- 溯源：src/fundseeker/runner.py:约 203-209 行（`try/except` 包住 `collector.collect_holdings`）
- 证据：`try: result = collector.collect_holdings(...) ... except Exception: skipped_products += 1; continue`。所有 collector 抛出的异常（含网络层 5xx、解析 bug、KeyError、连接 reset）一律计数为"跳过产品"，连 `log.error_message` 都不写。`TaskResult.error_message` 也只在外层 `except` 填，下游 `print_summary` 看不到粒度。
- 维度：事故复盘、运维告警、SLO
- 建议：至少 `logging.warning("holdings skipped product=%s code=%s err=%r", product.product_code, product.product_name, exc)`；或将失败产品 ID 收集到一个独立集合，结束后写入 `CollectionLog` 之外的结构化日志（jsonl/数据库表），便于事后排查。

### [P1] `latest_report_date = MAX(report_date)` 是整库全局 max，`skip_existing` 会跨 institution 误过滤
- 类型：业务正确性
- 溯源：src/fundseeker/runner.py:约 151-163（skip_existing 分支的 SQL 拼装）
- 证据：query 内 `func.max(HoldingReport.report_date).scalar()` 不带 institution 过滤，然后 `reported_ids = {product_id ... filter(HoldingReport.report_date == latest_report_date)}` 仍以全局最新季度为准。当某机构先进入新季度（例如 YFD 已采到 2025Q2）而其他机构尚未同步，全局 max 即 2025Q2，未采机构的全部产品都会被 `~ProductInfo.id.in_(reported_ids)` 排除；下一轮同一季度其他机构再采时仍然无产品被选中（因为 reported_ids 已包含所有应该跳过的产品）。
- 维度：去重策略、cron 收敛性
- 建议：以 (`institution_code`, `max(report_date)`) 维度计算每个机构的最近季度并就机构粒度 skip；或仅在 `institution_code` 为 None（一次性全量）时用全局 max。当前实现导致发现新季度后其余机构因过滤而停摆。

### [P1] 重试循环未区分 `HTTPError`/网络异常/超时三大类的可重试性
- 类型：错误分类
- 溯源：src/fundseeker/utils/http.py:136-144、164-172
- 证据：`except requests.RequestException` 一并捕到所有异常：4xx（HTTPError）、5xx（HTTPError）、连接拒绝（ConnectionError）、读取超时（ReadTimeout）、DNS 失败等。当前实现对所有都走相同退避。DNS 失败、`SSLError`、`ProxyError` 这类相同网络错误重试无收益；`ChunkedEncodingError` 中断又恰好是 stuck-socket 的常见表征，需要在 retry 时换新连接而非复用。
- 维度：失败语义、退避针对性
- 建议：拆 `except requests.HTTPError` / `ConnectionError` / `Timeout` 三大类，对 DNS、Proxy 错误直接 raise 不重试；对 `ChunkedEncodingError`、`IncompleteRead` 等已建立连接后失败的错误，在新一次 retry 中强制 `self._session.get(...)` 不复用 keep-alive（发送 `Connection: close` 或新建 session）。


### [P2] `_can_fetch` 在 `RobotFileParser.read()` 失败时 fail-open 并把损坏实例写入缓存，永久绕过 robots
- 类型：合规 / 缓存语义
- 溯源：src/fundseeker/utils/http.py:91-115
- 证据：`try: rp = RobotFileParser(); rp.set_url(...); rp.read() ... except Exception: return True`，随后 `self._robots_cache[base_url] = rp`。`RobotFileParser()` 默认 `Allow_all` 行为等价放行所有，被缓存后该 host 永远命中 fail-open 分支，robots 配置无法生效。
- 维度：缓存失效模型、合规审计
- 建议：失败时不写入缓存（标记 `None` 或另存不可达），或者把未读取成功的 host 降级为禁用并显式日志；更稳妥的做法是分别缓存明确 Allow/Disallow 与未知，后者返回保守结果（disallow 拒绝）而不是 silently allow。

### [P2] `post` 跳过 `_can_fetch`，与 `get` 不对称，且没有任何文档说明

- 证据：`get` 入口调 `_can_fetch(url)` 检查 robots；`post` 完全不做该检查。如果 post 同样面向公网，会绕过 robots 设置；如果设计上是 API 调用，意图应在 docstring 中说明。

- 建议：要么也调 `_can_fetch`（统一策略），要么在 docstring/类注释中明确"post 不做 robots 检查，常用于机构内 API"并提供开关。

### [P2] `ProductHolding.on_conflict_do_nothing(index_elements=["report_id", "asset_code", "asset_name"])` 唯一键选取可疑
- 类型：数据正确性
- 溯源：src/fundseeker/runner.py:约 230-250 行（`insert(ProductHolding).on_conflict_do_nothing(...)`）
- 证据：资产名称受来源 HTML 字符串处理影响（前后空格、全/半角符、英文/中文括号、转义后空格），同一 asset_code + report_id 下微小名称差异会导致重复行插入；同时，同一 report_id + asset_code 但合法别名（如"中国平安A"/"中国平安H"）会被错误判冲突。`HoldingSecurityInfo` 的约束才是 `(asset_code, market)`，而此处 reporting 行唯一键却把 `asset_name` 拉进来，增加噪声。

### [P2] `run_holdings` 每产品内多次 commit，事务粒度过细
- 类型：性能 / 事务边界
- 溯源：src/fundseeker/runner.py:约 225 行（`session.commit()` after HoldingReport）、约 280 行（holding/alloc/summary 循环后 `session.commit()`）
- 证据：每个产品至少 3 次 commit（insert HoldingReport、asset security upsert 后、holding+alloc+summary 后），产品量 N 较大时事务数与 WAL fsync 成线性。
- 维度：吞吐、cron 时长
- 建议：每个产品结束后再 commit 一次（甚至每 K 个产品批 commit）；中途失败可被外层 `except` 统一 rollback。


### [P3] `_enforce_delay` 时间锚语义错位，`_last_request_time` 取的是"上次 `_enforce_delay` 时间"而非"上次响应完成时间"
- 类型：实现细节 / 节流精度
- 溯源：src/fundseeker/utils/http.py:86-89
- 证据：`_enforce_delay` 末尾 `self._last_request_time = time.monotonic()`，紧接实际 `self._session.get(...)` 才发出；若请求失败进入 `time.sleep(backoff)` 后下一次循环再调 `_enforce_delay`，elapsed 是基于前一次 `_enforce_delay` 时间，已涵盖请求耗时 + 退避，节流几乎白睡。
- 维度：精度 / 行为可预期性
- 建议：把 `_last_request_time` 改为响应完成时间（成功/失败分支都赋值），或直接基于 `response.elapsed.total_seconds()` 算 elapsed。

### [P3] `run_holdings` 异常分支 `session.rollback() ... session.commit()` 在 broken session 上再次写 `log`
- 类型：异常安全
- 溯源：src/fundseeker/runner.py:约 312-330 行（`except Exception as exc:`）
- 证据：rollback 之后立刻修改 `log.end_time`/`status`/`error_message` 并 `session.commit()`；若 rollback 后 session 实际仍处于不可继续操作状态（数据库连接断开、deferred constraint 失败等），commit 自身会再抛异常，掩盖原始 root cause。
- 维度：诊断可追溯性
- 建议：在 `rollback` 后用 `session.begin_nested()` 或新开 short-lived session 写 log；外层 `try/except` 把这两类异常分别捕获并都记录。

### [P3] `skip_existing` 把 `reported_ids` 一次性 select 到 Python set，大库下内存与全表扫描风险
- 类型：可扩展性
- 溯源：src/fundseeker/runner.py:约 156-163 行
- 证据：`{r[0] for r in session.query(HoldingReport.product_id).filter(...).distinct().all()}`，整库最大季度所有 product 全部载入；当 `HoldingReport` 行数 ≥ 10^5 时占用不小。
- 维度：内存 / 查询计划
- 建议：与 `query.filter(~ProductInfo.id.in_(reported_ids))` 等价的 SQL 是 `NOT EXISTS` 子查询，由 DB 评估；可改写为 `~session.query(HoldingReport).filter(...).exists()` 或者 `ProductInfo.id NOT IN (SELECT ...)` 让数据库处理。

### [P3] `HoldingReport.data_source` 默认值降级到 `collector.source_url`，兜底链两套值同义但来源不同
- 类型：可观测性 / 来源一致性
- 溯源：src/fundseeker/runner.py:`data_source=result.get("data_source", collector.source_url)`（约第 220 行）
- 证据：`EastmoneyFundHoldingCollector.collect_holdings` 总是返回 `data_source: self.API_URL`（具体 endpoint），而 `collector.source_url` 是主页（`https://fundf10.eastmoney.com`）。当 collector 升级到返回具体 page URL 时这里无副作用，但当某些子类未带 `data_source` 字段，兜底会写入主页 URL 与实际抓取 URL 不一致。
- 维度：来源可追溯性
- 建议：将 `data_source` 设为 collector 必填（或在 `HoldingCollector` 抽象协议中强制）；运行时若缺失则 Raise 而非静默降级。
