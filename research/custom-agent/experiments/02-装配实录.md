# 第 2 场：首次端到端运行（2026-08-17）

## 2.0 环境与校准

- 环境：pi 0.84.2（npm 全局）/ MiniMax-M3（thinking=high）/ Windows。
- **卡点 1（项目信任）**：`-p` 非交互模式无信任决策时**忽略项目 `.pi/` 资源**（skill 与扩展均未加载，冒烟测试守卫未拦截暴露此问题）。解法：命令加 `-a`（--approve）+ 写入 `~/.pi/agent/trust.json`（键为 realpath 规范路径）。**教训：print 模式装配必须显式处理信任，否则"静默降级为裸模型"——观测不到任何 skill/guard 生效痕迹就是信号**。
- **卡点 2（守卫 API 校准）**：v0 按调研材料推断的 `event.block()` 不正确；实版文档确认阻断用**返回值** `{ block: true, reason }`，事件字段为 `event.toolName` / `event.input`（可变）。已按实版重写并实测：拦截生效、理由回传给模型。**教训：文档调研→实测校准是 F-绑定组件的必经一步（这正是"因素 1/因素 2"边界在工具层的体现）**。

## 2.1 首跑设置

- 范围：M5M6 里程碑 `e7c9aa9..f62f287`（评审输入锚点 f62f287）；**防泄漏**：明令禁读 f62f287 之后的提交（否则 git log 会暴露修复信息）。
- 指令：按 code-review skill 五步 SOP；重点维度 RR-4/RR-1/RR-5/RR-7；意见卡写 `reviews/2026-08-17-f62f287.md`。

## 2.2 结果

- **产出**：19 条意见（P0=1 / P1=7 / P2=8 / P3=3），8/8 维度检查，"未发现问题的检查项"如实分维度列出，意见卡 11.5KB、每条带 file:line 溯源与证据片段。
- **P0 精确命中 17/R-1**：tombstone 经 `upsert_nodes` 缺失属性补空串 + MERGE…SET 整行覆盖，13 个非 PK 属性清空——机制、位置、建议与人工评审一致。
- 观测（首份轨迹报告见 `review-pi/traces/`）：65 轮 / 128,698 in + 20,828 out token / bash×58 read×4 write×2；守卫拦截 1 次（冒烟）。

## 2.3 评分与人工审计

| 口径 | 结果 | 说明 |
|---|---|---|
| 启发式（score_review v1，锚点过滤 11 案例） | **9/11 = 82%** | 上界：关键词命中即算 |
| 人工语义审计（严格） | **1/11 = 9%**（R-1） | 完整机制命中 |
| 人工语义审计（宽松，部分命中计 0.5） | **2/11 ≈ 18%**（+R-2 web 半面、R-10 coalesce 半面） | |
| 未命中 | R-3、R-4、R-5、R-7(CLI 面)、R-8、R-12、R-13 | 2 条前端类（R-5/R-13）+ 2 条**错误排除** + 3 条未显式表达 |

关键发现——**错误排除（false acquittal）**：R-3（RELATES_TO MERGE 不含 kind）与 R-4（sync 无条件写 valid_to）在意见卡"未发现问题的检查项"中被**主动排除**且理由有误（把 MERGE 行为当作与测试一致——而测试本身断言的就是缺陷行为）。这解释了启发式 82% 与语义 18% 的巨大差距：**关键词命中大量来自排除性表述**。教训双条：①评分器需区分"命中于意见"与"命中于排除"；②RR-4 的检查方法必须机械化（枚举 valid_to/MERGE 的全部写入点逐点核对，而非依赖阅读判断）。

评分器两处修正（v0→v1）：中文短语不可作关键词（整句成单 token 永不命中）；跨锚点案例须过滤（F/N 系列在 f62f287 已修复，计入分母是误罚）。

## 2.4 第 3 场迭代输入（错误分析 → skill 修订）

1. **RR-4 机械化**：检查方法改为程序式——grep 全部 `valid_to` 写入点与全部 `MERGE` 模式，逐点核对四项（属性保留/读过滤/合并键/复活），把核对清单写进意见卡（使"未发现"可验证）；
2. **前端维度补充**：R-5/R-13 类检查项（HTML 声明的交互是否实现、图表库配置完整性）进入 checklist（当前八维度偏后端）；
3. **"未发现"表述约束**：须列出实际核对过的写入点/查询点清单，而非概括性结论（R9 登记真实性在 skill 内的自应用）；
4. run2/run3 同锚点复跑 → pass^k；意见卡头补登记 session id（观测关联，本轮遗漏）。

## 2. 关键决策与卡点

1. **skill 即规范执行者**：评审维度 checklist 直接嵌入 R8/R9/R11/R13 与 kb-app 评审惯例（幂等/并发/防御性）——画像附加问的设计落地，"评审 agent = 中间产物规范的执行者"首次实例化。
2. **守卫扩展的诚实降级**：pi 扩展事件负载字段名按调研材料推断（toolCall/name/arguments 多候选），未找到阻止 API 时**告警而非静默**——v0 风险登记进工作区 README，首次运行校准（R11 精神：登记真实性）。
3. **评估集锚点选择**：案例锚定"修复提交的父状态"（缺陷尚在）；`git 历史`可重现。**舍弃记录**（evals/README）：M2–M4 及其修复被压缩进单个提交 `e7c9aa9`，10/12 号报告的缺陷状态在历史中不存在——**教训：里程碑提交应保留缺陷→修复的中间态（或 squash 前导出快照），否则回溯式评估语料不可重建**；非代码类（R-6）、未修复类（R-9/O 系）、不可从代码观察类（N-2）共舍弃若干。
4. **评分器 v0 定位**：关键词启发式（严格口径=全部关键词命中；溯源文件命中=半命中信号）——语义召回留待 judge（按可观测清单 §5 信度协议）。
5. **流程 v1 使用发现**：②能力清单与③组件选配在轻场景下界限模糊（能力即组件映射表）——v2 可合并为一步并保留"知识三段登记"子检查。
6. **变更登记（2026-08-17 修订，R9 自应用）**：初版 SKILL.md 的维度 checklist 以"规则来源"列引用项目内部路径（R8/R9/R11/R13、kb-app 评审惯例），导致 skill 与本项目强关联、脱离项目后规则不可访问、不具分发完整性。**修订**：按 Agent Skills 规范把规则内容摘录为自包含文档 `assets/review-rules.md`（RR-1~RR-7，含检查方法与反例信号，文件头仅保留一行来源追溯）、意见卡模板外移 `assets/opinion-card-template.md`；SKILL.md 改为相对引用（RR 编号 + assets 路径），并把仓库特定表述泛化（"任意仓库的 AGENTS.md/README"）。**教训**：面向分发的 skill 中，项目内知识必须摘录进 assets 而非引用路径——"引用完整性"应作为 skill 编写的默认红线（已体现为组件目录 F-通用档位的隐含要求，v2 补为显式判据）。
