# A-B 评审闭环工作流（工程实现 v1）

> 版本：v1（2026-08-19 第 9 场；修订随 review-pi README 与 skill CHANGELOG 登记）
> 定位：把三个案例项目已自发采用、并被实践证明有效的 A-B 交叉评审流程（模型 A 写代码 → 模型 B 评审 → A 复核应答 → 修复 → B 复审；过程事实见 `../../notes/07-案例项目的AB交叉评审工作流.md`）落地为本工作区的可执行工件——后续项目按本流程与配套提示模板直接运行，无需重新设计。
> 决策依据：P2 阶段评审 A1 决策——该流程不做效果验证实验（逻辑与历史实践已证明有效），深化重点是工程实现。

## 1. 角色与工件

| 角色 | 承担者 | 产出工件 | 载体 |
|---|---|---|---|
| A（实现方） | 写代码的 agent/人 | 代码提交、**复核应答卡** | `reviews/<日期>-<目标>-respond.md` |
| B（评审方） | 评审 agent（code-review skill） | **意见卡**、**复审卡** | `reviews/<日期>-<目标>.md`、`reviews/<日期>-<fix>-recheck.md` |
| 人工（裁决） | 研究者/维护者 | **待确认问题卡**（仅在触发时） | `evals/待确认问题卡-<日期>.md`（模板见 `evals/待确认问题卡-模板.md`） |

**模型路由**（pi 平台优势，notes/07 §5）：A 与 B 可配置为不同模型——pi 单平台按角色路由模型，工件格式、上下文、格式契约保持统一；各卡"评审者"字段必须带模型标识（provider/model），跨模型 run 独立成组，不与单模型 run 混算。

## 2. 流程五步（每步的运行方式）

```
① 评审      /prompt review-commit {{commit}}     → 意见卡（skill 五步 SOP）
② 复核应答  /prompt review-respond {{意见卡}}     → 应答卡（逐条 接受/部分/驳回+依据）
③ 修复      A 按接受项修复                        → 修复提交（每条意见的修复可追溯）
④ 复审      /prompt review-recheck {{fix}} …     → 复审卡（四档结论 + 回归检查）
⑤ 收口      全部"已修复"且无待确认项 → 闭环；
             有待确认项 → §4 待确认流程（人工裁决后回到 ③/④ 或改标注）
```

- ①④ 由 code-review skill 承担（同一 skill 版本内闭环才有可比性）；② 由实现方承担，**必须先核对锚点代码再应答**（禁止未核对驳回）；
- 守卫（`extensions/review-guard.ts`）全程生效：所有卡只写 `reviews/`；
- 清洁规程适用于①④的评估性运行（归档旧卡 + 指令双禁）；日常闭环运行不强制归档，但意见卡不得在评审前被对端读到（防跨 run 污染）。

## 3. 入口/出口判据

| 阶段 | 进入条件 | 完成判据 |
|---|---|---|
| ①→② | 意见卡含至少一条意见或完整"未发现"清单 | 应答卡逐条有应答（含驳回反证） |
| ②→③ | 应答摘要完整（接受/部分/驳回计数） | 修复提交逐条对应接受项 |
| ③→④ | 修复提交存在 | 复审卡四档结论齐全 + 回归检查完成 |
| ④→收口 | — | **已修复 = 接受项总数 且 待确认 = 0**；否则回 ③（残留）或进 §4（分歧） |

## 4. 待确认问题流程（B1 决策落地）

**三个触发点**：
1. 复审④中 B 对 A 的驳回仍持异议（review-recheck 规则 2）；
2. 评分器 `score` 的 **B1 待语义核定/未命中工作清单**（评估中发现"未复现期望缺陷、但同一问题域内有其他真实发现"——`score_review.py score` 自动输出）；
3. 复审新发现与既有意见/标注矛盾。

**流程**：触发 → 按模板填写待确认问题卡（双方判断并列）→ **人工归类四况之一** → 按处置路由执行 → 结论回填。四况与处置（P2 阶段评审 B1 决策原文）：

| 归类 | 处置路由 |
|---|---|
| ① 前一次缺陷标注识别错了（后发现的才是真缺陷） | 修正标注（改写 expected_finding，登记变更） |
| ② 前一次正确、本轮漏检（评审能力缺口） | 走规则修订工作单（`.pi/skills/code-review/assets/rule-revision-worksheet.md`，根因 R1–R4）或流程修补；修订后须复测 |
| ③ 两轮均为误检 | 清除标注并回溯标注来源；**执行误检原因分析**（见模板 §误检原因分析） |
| ④ 前一次正确、本轮既漏检又误检出新问题 | ②与③合并处理（分别立项） |

计分口径是人工裁定结论的下游：归类①改标注后按新标注重算；②③④维持未命中计数并记录原因。

## 5. 与评估工具的衔接

- `score_review.py score`：B1 清单输出 → 待确认问题卡输入；三口径（启发式/签名/语义终审）复算；
- `score_review.py pair` 与 `groups` 子命令：跨 run 意见配对与按文件分组核验清单（配对方法与三层定位见装配实录 §8.1/§8.5）；
- 闭环内各卡的格式契约以 `.pi/skills/code-review/assets/opinion-card-template.md`（v5）为准——标题带对象前缀、溯源列全涉及文件，配对与评分据此获得稳定信号。
