# 代码评审 SOP（code-review）

## 适用范围

- 评审对象：git diff（PR 或 commit）、指定文件快照。
- 输出：写入 `reviews/<日期>-<目标>.md` 的意见卡（唯一允许的写位置）。
- 不做：自动修复代码、阻塞合并（人工裁决）；不修改被评审代码。

## 评审流程（五步）

1. **读取变更**：`git show <commit>` / `git diff <base>..<head>` 获取 diff；先建立变更地图（文件 × 改动类型：新增/修改/删除/移动）。
2. **收集上下文**：读 AGENTS.md、相关设计文档（design/kb-app/ 对应编号）、被改文件的完整上下文（不只看 diff hunk）；判断该变更属于哪个里程碑/契约域。
3. **逐维度检查**（下表）；每发现一个问题，立即记录 file:line 与证据片段。
4. **生成意见卡**：按模板输出；每条意见必须含【溯源】【建议】【分级】。
5. **自检**：过一遍红线清单后再写文件。

## 评审维度 checklist

| 维度 | 检查问 | 规则来源 |
|---|---|---|
| 正确性 | 变更是否引入行为错误（边界条件、None/空集、异常路径）？ | 通用 |
| 状态生命周期 | 软删除/墓碑：属性是否保留？读路径是否过滤？合并键是否完整？是否可能复活？ | R13 |
| 契约一致性 | 实现与设计文档的 DDL/接口签名/错误结构是否同形？错误码三键 {code,message,suggestion} 完整？ | R7/R8 |
| 变更登记 | 实现是否塌缩/偏离了设计而未登记？依赖变更是否回写？ | R9 |
| 登记真实性 | 测试/DoD 声称的通过是否真实（断言形状而非仅 code；环境口径是否注明）？ | R11 |
| 幂等与重放 | 重跑/重放路径是否幂等（先删后插/merge 键完整）？ | kb-app 评审惯例 |
| 并发与锁 | 写路径持锁是否正确；读路径是否无需锁？ | kb-app 评审惯例 |
| 防御性 | 外部输入（LLM 输出/文件名/用户参数）是否有上界、消毒、兜底？ | 通用 + F-2/F-3 教训 |

## 意见卡模板

```markdown
# 评审意见卡：<目标（commit/PR）>
- 日期 / 评审者：review-pi / 基线：<review_base hash>
- 变更地图：<文件数 × 类型分布，一句话>

## 意见（按级别排序）
### [P0|P1|P2|P3] <一句话标题>
- 溯源：<file:line 或 设计文档 §x>
- 证据：<代码片段或事实，≤3 行>
- 维度：<上表维度名>
- 建议：<可操作的修正方向>

## 未发现问题的检查项
<列出检查过且未发现问题的维度——供人工复核聚焦>

## 评审元信息
检查文件数 / 耗时 / 置信度（高|中|低，低须说明缺口）
```

## 红线（违反任一条的意见卡无效）

1. 每条意见必须带 file:line 或文档 § 溯源——**禁止无证据泛泛而谈**；
2. 证据片段必须来自实际读取的代码/文档，不得凭变更主题推测；
3. 分级只依据"错误成本×确定性"：不可逆/数据损坏=P0，行为错误=P1，防御缺失=P2，风格/口径=P3；
4. 只写 `reviews/` 目录；不执行任何修改被评审代码的操作；
5. "未发现问题的检查项"必须如实列出（这是召回复核的依据，也是诚实性要求）。
