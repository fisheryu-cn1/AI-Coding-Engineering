### [P1] `topic_subgraph` 边查询 `coalesce` 把 Section PK 错配成 doc_id，UI 端 src/dst 全错
- 溯源：`code/kb-app/src/kbapp/graph/queries.py:100-108`（topic_subgraph 边查询 4 次 for-loop）+ `code/kb-app/src/kbapp/graph/ladybug_store.py:5-9`（"portable Cypher subset"声明）+ `code/kb-app/src/kbapp/graph/schema.py:71-86`（Section PK = section_id，doc_id 是普通属性）
- 证据：
  ```python

  f"WHERE coalesce(a.entity_id, a.doc_id, a.section_id, a.name) IN [{ids_csv}] "
  f"AND coalesce(b.entity_id, b.doc_id, b.section_id, b.name) IN [{ids_csv}] "
  f"RETURN coalesce(a.entity_id, a.doc_id, a.section_id, a.name) AS src, "
  f"       coalesce(b.entity_id, b.doc_id, b.section_id, b.name) AS dst"
  ```
  Section 节点的 `coalesce(entity_id, doc_id, section_id, name)` 实际返回 **doc_id**（因 `doc_id` 是 Section 的非 PK 属性且早于 `section_id` 命中）。后果：
  1. 过滤器用 doc_id（如 `"D1"`）匹配，命中 Section 节点，但 seen 集里 Section 用的是 section_id（`"D1#1"`）；
  2. 返回的 `src`/`dst` 用 coalesce 结果（即 doc_id），UI 拿到 `"D1"→"Method:rag"` 而非真实的 `"D1#1"→"Method:rag"`——**Section 节点身份被吞，MENTIONS 边在 UI 上画在 Document 上**。
- 维度：契约一致性 / **RR-1**；状态生命周期 / RR-7 防御性。
- 反例：测试 `test_topic_subgraph_collects_nodes` 只断 `types in nodes`，**未断言边 src/dst**；小种子图（1 doc 1 section 1 entity）掩盖了 Section PK 错配问题。`test_topic_subgraph_truncates` 只断 truncated 标志。
- 建议：(a) 在 Python 层维护 `{label: pk_field}` 表，遍历边时按端点 label 取 `entity_id`/`doc_id`/`section_id`/`name` 之一，不再依赖 `coalesce`；(b) 或对每个 rel 写 4 条专属 Cypher（MATCH scope 限定 label）；(c) `topic_subgraph` 端到端断言 `edges[].src in {section_ids}` 与 `edges[].dst in {entity_ids}`。
- run1 交叉：run1 列出 P1-4（同一处 `coalesce` 但归因到"portable subset 声明"，未点出 Section PK 错配这一更严重问题）；本条 run2 复验后升级为 PK 身份错配 P1。

### [P1-新增-复活] `stage_index_graph` 会在墓碑 Document 上 `valid_to = ""` 复活
- 溯源：`code/kb-app/src/kbapp/pipeline/graph_stages.py:32-44`（`stage_index_graph`）+ `code/kb-app/src/kbapp/graph/sync.py:62-65`（`"valid_to": ""` 写入）+ `code/kb-app/src/kbapp/core/files.py:118-126`（`apply_deleted` 仅置 `status='deleted'`，不动 valid_to）+ `cli/index.py:240-244`（tombstone 任务入队）
- 证据链：
  1. 用户运行 `kb index scan`：检测到磁盘文件消失 → `decide_action` 走 ACTION_DELETED 分支 → `apply_deleted(conn, doc_id)` 写 `files.status='deleted'` + `extract_status='failed'`，**保留 path/sha256/topic 等身份字段**（`files.py:128-150`）；
  2. 同事务内 `enqueue_task(kind="tombstone", payload={"doc_id": doc_id})` 入队图软删任务；
  3. runner 消费 tombstone 任务 → `stage_tombstone_graph(doc_id)` 走 P0-1 路径，把 Document 节点的 `valid_to` 设为 `now`、**其他 13 字段被覆盖空串**；
  4. **但**：`stage_index_graph`（路径 1-2）也会在 tombstone **之前**（同次 run）或**之后**（re-extract / re-scan）被同 doc_id 触发；`sync_document_structure` 调用 `upsert_nodes("Document", [...])` 走全行 SET，`"valid_to": ""` 把墓碑**覆写回空串**——Document 在图谱中被"复活"；
  5. 设计 15 §4.1 段落："tombstone | 既有文件清理之上，追加图侧 Document 置 valid_to 软删（**不物理删边，查询层过滤**）" —— 设计意图是 tombstone 后不可复活，需靠"查询层过滤"达成；当前实现既无"查询层过滤"（见 RR-4 #2 全栈失败），又**让 index 任务在 tombstone 后误改 valid_to**，双重失守。
- 维度：状态生命周期 / **RR-4 #4 不可复活**。
- 建议：与 P0-1 修复联动 —— `LadybugStore` 加 `_set_only(pk, field, value)` 单字段 SET 路径；`stage_index_graph` 在 sync 前先 `MATCH (d:Document {doc_id:$id}) WHERE d.valid_to = '' RETURN d.valid_to LIMIT 1`，墓碑存在则跳过 Document upsert（Section/Topic upsert 仍走，但应在 Cypher 端验证 Document 未墓碑）；或显式 `WHERE NOT EXISTS { MATCH (:Document {doc_id:$id, valid_to:<>'""}) }`。
