### [P2] `test_wait_mode_blocks_until_released` 不覆盖持锁进程在 wait 期间死亡场景（RR-3 测试覆盖率缺口）

  持锁方是同进程的 `a`（同 PID），子线程只调 `release_write_lock`。**`_is_lock_held` 在 wait 循环中只在每个轮询起点的 `FileExistsError` 分支被检查一次**（lock.py:103-110），但当前测试没有"持锁进程 PID 已死、文件未删"的中间状态——一旦死锁文件（mtime 过期 或 PID 死了）出现，下次轮询会走 `_try_reclaim` 分支（lock.py:108）回收。代码路径存在但测试未覆盖。

- 建议：新增
  ```python

      """持锁方锁文件 mtime 在 wait 期间被推过 stale_after → wait 应在下个轮询回收。"""
      lock_path = data_dir / ".write.lock"
      lock_path.write_text(f"{os.getpid()}\n", encoding="utf-8")
      old = time.time() - 7200  # 推过 60s stale_after 阈值
      os.utime(lock_path, (old, old))
      b = acquire_write_lock(data_dir, wait=True, timeout=5.0, stale_after=60.0)
      assert b is not None
      release_write_lock(b)
  ```

### [P3] `force_release` 不关闭被强夺方的 fd；头注 "已知限制" 未覆盖此路径（RR-6 + RR-7 防御性）
- 溯源：`code/kb-app/src/kbapp/core/lock.py:31-35`（"已知限制"只提 mtime 路径）+ `code/kb-app/src/kbapp/core/lock.py:140-149`（`force_release` 仅 unlink 不 close fd）+ `code/kb-app/tests/unit/test_lock.py:117-123`（测试自己手动 `os.close(a.fd)` 兜底）
- 证据：
  ```python
  # lock.py:31-35 —— 头注只提 mtime 兜底
  已知限制：mtime 兜底回收后，原持有进程恢复时调用 ``release_write_lock``
  会无条件 unlink，理论上可删掉新持有者的锁文件——单用户本地场景概率极
  低；M2+ 若引入多用户/网络盘需改为按 PID 校验后再删。
  ```
  ```python
  # lock.py:140-149 —— force_release 不关 fd
  def force_release(data_dir: Path) -> bool:
      """Forcibly remove the lock file regardless of holder.
      ...
      """
      lock_path = _lock_path(data_dir)
      try:
          lock_path.unlink()
          return True
      except FileNotFoundError:
          return False
  ```
  ```python
  # test_lock.py:117-123 —— 测试自己承认 fd 残留并手动关
  def test_force_release_removes_lock_even_when_held(data_dir: Path) -> None:
      a = _make_lock(data_dir)
      assert force_release(data_dir) is True
      assert not a.path.exists()
      # fd is closed; nothing more to do.
      try:
          os.close(a.fd)
      except OSError:
          pass
  ```
  注释 "fd is closed" 与随后 `os.close(a.fd)` 自相矛盾（既已 closed 为何再关？），实际语义是"原持有方 fd 已泄漏，测试兜底关"——这正是 **force_release 把责任甩给调用方** 的证据。
  触发链：`force_release` 仅 unlink → 原持有方 fd 泄漏（直到进程退出）→ 原持有方后续若调 `release_write_lock(a)` → `lock.path.unlink()` 会 unlink **当前** lock 路径（可能是新持有方的锁文件）→ 复用 mtime 路径的同一漏洞。
- 维度：并发与锁 / RR-6；外部输入防御性 / RR-7（`force_release` 是 `kb status` 等诊断命令的入口，未做"持有方校验"兜底）。
- 建议：(a) 头注 "已知限制" 段补一句"``force_release`` 同理——原持有方 fd 泄漏且 release_write_lock 会 unlink 新持有方锁文件"；(b) `force_release` 增加可选 `holder_pid: int | None` 参数，unlink 前校验 `lock_holder(data_dir) == holder_pid`，不匹配则 raise `LockHeld`；(c) 测试注释 "fd is closed; nothing more to do." 改为"force_release leaks the holder's fd; close it here to avoid ResourceWarning in long-lived test suites"。

- 溯源：`code/kb-app/src/kbapp/core/task.py:223-247`（`next_task` 动态 IN 子句）
- 证据：
  ```python
  # task.py:223-247 —— kinds 为空元组时 placeholders 为空字符串

          if kind is not None:

              placeholders = ",".join("?" for _ in kinds)
  ```
