### [P0] Tombstone 任务把所有 Document 属性清空为 ""
- 溯源：`code/kb-app/src/kbapp/pipeline/graph_stages.py:62-77`（`stage_tombstone_graph`）+ `code/kb-app/src/kbapp/graph/ladybug_store.py:103-115`（`upsert_nodes`）
- 证据：
  - `stage_tombstone_graph` 调用 `store.upsert_nodes("Document", [{"doc_id": doc_id, "valid_to": now}])`，只传两字段。
  - `LadybugStore.upsert_nodes`：`props = {k: row.get(k, "") for k in node.props}`，随后 `MERGE … SET n.title = $title, n.path = $path, … n.valid_to = $valid_to`——缺失键默认 `""`，MERGE…SET 走整行覆盖。
  - `Document.props` 含 `title/path/sha256/doc_type/corpus/arxiv_id/version/authors/published/summary_l1/summary_l2/summary_path/valid_from` 13 个非 PK 属性 → 全部被覆盖为 `""`。
- 维度：状态生命周期 / RR-4 属性保留；行为正确性。
- 建议：新增 `stamp_tombstone(store, doc_id, now)` 方法只 `MERGE (n:Document {doc_id:$pk}) SET n.valid_to = $v`；或在 `stage_tombstone_graph` 先 `store.query("MATCH (n:Document {doc_id:$i} RETURN …")` 取全行，再 upsert 回写（仍脏）；或扩展协议支持 partial upsert。

### [P1] `graph_compare.doc_ids` 参数被实现吞掉，契约 vs 行为脱节
- 溯源：`code/kb-app/src/kbapp/retrieve/graph_search.py:46-69`（`graph_compare`）+ `code/kb-app/src/kbapp/mcp_server.py:191-205`（`_kb_compare`）
- 证据：
  ```python
  # graph_compare.py:48-69
  params: dict[str, Any] = {"concept": concept, "limit": int(limit)}
  cypher = (
      "MATCH (a:Entity {entity_id: $concept})-[r:RELATES_TO]-(b:Entity) "
      "RETURN …"
  )
  rows = store.query(cypher, params)
  ```
  `doc_ids` 形参被接收但从未出现在 Cypher/params/后处理。
- 维度：契约一致性 / RR-1；行为正确性。
- 建议：在 Cypher 中加 `AND (a)-[:MENTIONS]-(:Section {doc_id: $did})` 过滤；或前端把 `doc_ids` 翻译成 entity 集合先 in-memory 收敛后再走 cypher。同时把 `params["doc_ids"]` 实际绑定到查询。

### [P1] Web 端点词云/侧栏不读路径过滤墓碑
- 溯源：`code/kb-app/src/kbapp/web/api.py:50-83`（`_aggregate_entities`）、`91-126`（`_doc_mentions`）、`128-156`（`_doc_related_docs`）
- 证据：三条查询均为 `MATCH (s:Section)-[:MENTIONS]->(e:Entity) …` / `MATCH (s:Section)-[:MENTIONS]->(e:Entity)<-[:MENTIONS]-(s2:Section)`，均无 `WHERE d.valid_to = ''`。`stage_tombstone_graph` 软删后 CONTAINS_SECTION / MENTIONS 边物理保留（见 `test_tombstone_soft_deletes_document`），结果墓碑文档的实体仍出现在词云与关联侧栏。
- 维度：状态生命周期 / RR-4 读路径过滤；RR-1（test_m5m6_e2e 仅断言图内 Document 集与 files 集相等，未覆盖这些 web 端点）。
- 建议：JOIN 到 Document 并 `WHERE d.valid_to = ''`，或扩展 `topic_subgraph` 同样过滤。

### [P1] `topic_subgraph` 边查询依赖 `coalesce`，而 store 文档声明 portable subset 不含此函数
- 溯源：`code/kb-app/src/kbapp/graph/queries.py:104-108` + `code/kb-app/src/kbapp/graph/ladybug_store.py:5-9`（docstring）
- 证据：边查询 4 次，每次均使用 `coalesce(a.entity_id, a.doc_id, a.section_id, a.name) IN […]` 与 `RETURN coalesce(…) AS src/dst`。`ladybug_store.py` 顶部声明 "portable Cypher subset (match / where / return / order / limit / merge / set)"——未列 `coalesce`。`topic_subgraph_collects_nodes` 测试种子图只有 3 类型节点各 1，路径形态单一，未触及实际 `coalesce` 与 LadybugDB 是否实现的边界。
- 维度：契约一致性 / RR-1；防御性 / RR-7。
- 建议：把"统一 ID 取值"放在 Python 层（在 `_seed` 时已经按 label 知道 PK，遍历节点时一次取齐）；或 4 次分别按 label 写专属 Cypher。

### [P1] `compare_cmd` 行为与 15 §5.1 "对照表" 语义不符
- 溯源：`code/kb-app/src/kbapp/cli/search.py:228-262`（`compare_cmd`）
- 证据：循环 `for d in doc_ids: graph_related(...hops=1...) → for r in r["related"] if r["type"] == "Entity": graph_compare(concept=r["id"], …)`，把每条 related 实体当 concept 单独调一次。注释自承 "MVP 阶段直接按 doc_id 关联的 entity 聚合"。结果是 N×E 次 Cypher + 拼接到 `row["concept"]/row["doc_id"]`，并未对"同一概念跨多文档"的 RELATES_TO 做对照。
- 维度：正确性；契约一致性 / RR-1。
- 建议：先聚合多 doc 共享 entity 集合，再以该集合为 concept 调一次 `graph_compare`，并把 `doc_ids` 真正下推到 `graph_compare`（与 P1-1 联动）。

### [P1] `stage_extract_graph` 吞掉 LLM/JSON 失败，status 仍为 ok

- 证据：

- 维度：正确性；契约一致性 / RR-1（skipped 与 ok 在 status 上不可区分）。
- 建议：`stage_extract_graph` 根据 `metrics["skipped"]` 决定 `StageResult("ok" | "skip" | "retry")`；或新增 `StageResult("partial", detail="json_decode_failed")`。

### [P1] Cypher 字符串拼接成 IN 子句，违反 store 的"parameter binding 强制"声明
- 溯源：`code/kb-app/src/kbapp/graph/queries.py:44,54,63,102-108` + `code/kb-app/src/kbapp/web/api.py:36-43`（`_aggregate_entities`）
- 证据：

  - store.py 顶部明确写 "Parameter binding is mandatory — callers never concatenate strings."
- 维度：契约一致性 / RR-1；防御性 / RR-7。
- 建议：走参数绑定（LadybugDB Binder 是否支持 IN-list 参数需验证）或迁到 Python 端批量查；至少把 store.py 顶部契约改写为现实口径。

### [P1] `topic_subgraph` 边查询在大图上 4 次全表扫描
- 溯源：`code/kb-app/src/kbapp/graph/queries.py:99-110`
- 证据：4 个 rel 标签分别发 4 次 Cypher，每次 WHERE 仅过滤可见节点集，端点端点扫描全图；RELATES_TO 在 600 entities 测试场景下变 4×N 边扫描。
- 维度：正确性（性能下的可用性）；契约一致性 / RR-1（与"500 节点裁剪"承诺冲突但用户感知是页面卡死）。
- 建议：4 个 rel UNION ALL 一次拉端点，再 Python 端去重；或按节点集做 `MATCH (a)-[*1..1]->(b)` 一次。
