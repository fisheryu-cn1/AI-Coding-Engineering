### [P1] `stage_index_graph` 会在墓碑 Document 上 `valid_to = ""` 复活（不可复活违例）

### [P1] `RELATES_TO` 边 MERGE 模式缺 `kind` 区分键，异 kind 关系互相覆盖
- 溯源：`code/kb-app/src/kbapp/graph/ladybug_store.py:117-141`（`upsert_edges`）+ `code/kb-app/src/kbapp/graph/schema.py:106-122`（`RelDef("RELATES_TO", …, props={kind, weight, evidence_section_id})`）
- 证据：
  ```python
  # upsert_edges：
  self._run(
      f"MATCH (a:Entity {{entity_id: $src}}) MATCH (b:Entity {{entity_id: $dst}}) "
      f"MERGE (a)-[r:RELATES_TO]->(b) SET {set_clause}", params,
  )
  ```
  MERGE 模式仅含 `(entity_id, entity_id)`，未含 `kind`；`set_clause = ", ".join(f"r.{k} = ${k}" for k in rel_def.props)` 把 r.kind 设为最新值。同一对实体 (RAG, Vector DB) 若先 upsert `kind="uses"` 再 upsert `kind="evaluates"`，第二次 MERGE 命中已存在边，`SET r.kind = "evaluates"` 把 "uses" 覆盖丢失。`kind` 是 REL_KINDS 受控词表的 9 个区分维度，是边类型的语义区分键。
- 维度：状态生命周期 / **RR-4 #3 合并键完整**；契约一致性 / RR-1（与 `extract.run_extract` 中 `rel_edges` 用 `(src_eid, dst_eid, kind)` 三键去重的口径冲突——extract 知道要 kind 三键，store 不知道）。
- 反例：测试 `test_run_extract_writes_entities_mentions_relations` 只 seed 同对同 kind 的两条 + 1 条未知 kind 丢弃，**未覆盖异 kind 冲突**；`test_graph_contract.py`/`test_graph_queries.py`/`test_extract.py` 均未触及异 kind 同对场景。属 RR-4 #3 反例信号 "MERGE 模式省略区分键"。
- 建议：改为 `MERGE (a)-[r:RELATES_TO {kind: $kind}]->(b) SET r.weight = $weight, r.evidence_section_id = $evi`；或在协议层用 key 字典 `{src, dst, kind}` 构造唯一性，新增 "REL-only key 含全部区分维度" 的契约断言。
- run1/run2 交叉：run1 未列；run2 P1-3（独立发现）；run3 复验一致。

### [P1] `topic_subgraph` 边查询 `coalesce` 把 Section PK 错配成 doc_id，边端点语义塌陷
- 溯源：`code/kb-app/src/kbapp/graph/queries.py:100-108`（topic_subgraph 边查询 4 次 for-loop）+ `code/kb-app/src/kbapp/graph/schema.py:71-86`（Section PK = section_id，doc_id 是 Section 节点的**普通属性**）+ `code/kb-app/src/kbapp/graph/sync.py:80-87`（Section 节点显式写入 `doc_id` 属性）+ `code/kb-app/src/kbapp/graph/ladybug_store.py:5-9`（"portable Cypher subset"声明未列 `coalesce`）
- 证据链：
  1. Section 节点 schema（schema.py:71-86）props 含 `doc_id: STRING`，sync 落地（sync.py:83）写 `doc_id=doc_id`——Section 节点**同时拥有** PK `section_id`（如 `"D1#1"`）和**非 PK 属性** `doc_id`（如 `"D1"`）。
  2. 边查询（queries.py:103-107）使用 `coalesce(a.entity_id, a.doc_id, a.section_id, a.name)`——对 Section 端点，`a.entity_id` 为 NULL，`a.doc_id` 已 set，返回 `doc_id`（**而非 PK section_id**）。
  3. 后果分级：
     - **CONTAINS_SECTION（Document→Section）**：a 是 Document（coalesce→doc_id="D1"），b 是 Section（coalesce→doc_id="D1"）→ 返回 `src="D1", dst="D1"`。`new_seen` 集合里有 `"D1"`（Document）但没有"Document→Document 自环"。`if r["src"] in new_seen and r["dst"] in new_seen` 看似通过，但 `r["src"] == r["dst"]` 在 UI 上渲染成自环边，与 `CONTAINS_SECTION` 语义不符。
     - **MENTIONS（Section→Entity）**：a 是 Section（coalesce→doc_id="D1"，**错的**），b 是 Entity（coalesce→entity_id="Method:rag"）→ 返回 `src="D1", dst="Method:rag"`。UI 把 MENTIONS 边画在 Document→Entity 上而非 Section→Entity 上，**章节级粒度丢失**。
     - **`new_seen` 集合 vs coalesce 结果的失配**：collection 中 Section 用 `"D1#1"`，边查询返回 `"D1"`——`r["src"] in new_seen` 对 Section 出发的边**按文档 id 通过**而非按章节 id 通过，MENTIONS 边被错误归到 Document 出发的边集合里。
- 维度：契约一致性 / **RR-1**（PK 身份契约 + 与 store 顶部 portable subset 声明冲突）；状态生命周期 / RR-7（防御性）。
- 反例：测试 `test_topic_subgraph_collects_nodes`（tests/unit/test_graph_queries.py:80-89）只断 `types in nodes`（Topic/Document/Entity 集合），**未断言边 src/dst 与 seen 集合的对应关系**——三类型小种子图掩盖了 Section PK 错配问题。
- 建议：(a) 在 Python 层维护 `{label: pk_field}` 表，遍历边时按端点 label 取 `entity_id`/`doc_id`/`section_id`/`name` 之一，不再依赖 `coalesce`；(b) 对每个 rel 写 4 条专属 Cypher（MATCH scope 限定 label）；(c) `topic_subgraph` 端到端断言 `edges[].src in {section_ids for Section}` 与 `edges[].dst in {entity_ids for Entity}`。
- run1/run2 交叉：run1 P1-4（同一 coalesce 处，但归因到 "portable subset 声明"，未点出 Section PK 错配这一更严重后果）；run2 P1-4 升级为 PK 身份错配——run3 复验一致并明确给出 CONTAINS_SECTION 自环化 + MENTIONS 错配 Document 的两个具体失效路径。
