# 规约-验证对：在 code-review skill 资产上的实例化（D2-S4，2026-08-19 第 14 场）

> 定位：方向二的 P2 收尾交付（规划 §3 #12）。把"规约-验证对"（specification–verification pair）作为面向大模型核心组件软件的工程方法**实例化**：知识资产充当规约，锚定真实缺陷的评估集充当验证，溯源标注提供两者的绑定。模板见 §5（已并入 `02-中间产物模板集` 作 v1 增量）。
> 实例化对象：`review-pi/.pi/skills/code-review/`（规约面：review-rules.md v5）× `review-pi/evals/cases.jsonl`（验证面：21 案例）× 规则溯源标注（先验 / 案例渗入）。

## 1. 概念与动机

传统软件中规约（接口契约、不变式）与验证（测试、形式化检查）成对出现且相互独立。大模型为核心组件的软件里，行为性知识沉淀为**文本资产**（规则集、清单、模板、样例指南）——它们同样需要"规约-验证"配对，但有三个新特征：

1. **规约是概率执行的**：规则经提示注入后由模型执行，验证测的是"规约被遵循后能否引导发现真实缺陷"，不是机械断言；
2. **验证锚定历史事实**：案例 = 真实评审发现 + 修复证实（或修复意图证实）的缺陷，而非合成输入——`cases.jsonl` 每条含锚点（review_base）、期望意见（expected_finding）、证实方式；
3. **绑定靠溯源标注**：每条规则标 `先验`（提炼自实践）或 `案例渗入`（由评估失败触发，注案例号）——拟合与泛化成绩由此可分离（留出验证的前提）。

## 2. 规约面：规则集 v5 的规约结构

| 结构要素 | 实现方式 | 作用 |

## 4. 验证结果的已知局限（诚实登记）

1. **答案可见效度注**：f62f287/e7c9aa9 锚点的历史命中数字（run1–3/6/7/8/9/10/12）在"标准答案（17/14 号评审报告）对评审 agent 合法可见"条件下取得，整组标注风险；F/NF 系列不受影响（2026-08-19 起隔离纪律已封堵，人工待办 12-1 选项 A）。
2. **规约-验证错位样例**：R-3 证明"验证失败未必指向规约缺失"——v5 后 run12 仍漏检，根因在检查方法未操作化（规约的执行程序层），由规则修订工作单的根因分类（R1 缺失 / R2 不可操作）区分——**规约-验证对需要分层诊断**，不是简单的"失败即改规则"。
3. **单语料拟合风险**：规则在 kb-app 上迭代、Vision-Sudoku 上静态验证（设计阶段覆盖仅 25%——文档链一致性由 D2 模板集承担，分工见 `experiments/03-VisionSudoku规则覆盖验证.md` §4）；泛化成绩留待 P3 冷启动。

## 5. 规约-验证对模板（v1，可复用于任意 LLM 知识资产）

```markdown
# <资产名> 的规约-验证对
1. 规约面：<资产文件、版本>——条文 / 适用域（前置谓词）/ 执行程序 / 元规约（未覆盖声明）/ 变更治理（工作单+CHANGELOG）
2. 验证面：<评估集文件>——案例 schema：锚点(review_base) + 期望意见(expected_finding) + 证实方式(fix_commit | 修复意图 | 人工核证) + 隔离声明（答案文档可见性！）
3. 绑定：每条规约标溯源（先验 | 案例渗入[案例号]）；每案例标验证规约编号；双向清点——规约无实例 / 案例无规约覆盖 两类缺口显式列出
4. 验证状态表：规则 × 最佳命中记录 × 已知局限（效度标注）
5. 诊断路由：验证失败 → 规则修订工作单（根因 R1 规约缺失 / R2 执行程序不可操作 / R3 谓词误排除 / R4 过宽 / R5 非规约问题）
6. 停止条件：机制验证完成后转入迁移验证（P3），不在源语料上持续微迭代（2026-08-19 裁定）
```

## 6. 与方向一/三的衔接

- D1：规约-验证对是 skill 资产的"出厂检验"配置——组件目录登记的 F-通用组件应附此对；
- D3：验证状态表即"工具对象"指标卡的数据源（召回三口径 + pass^k）；溯源标注支撑规则渗入比指标。
