# 问题类型判定指南（含已核定样例）

> 版本：v1.2（skill v5 新增；修订史见 `../CHANGELOG.md`）
> 用途：意见卡"类型"字段的判定依据——给出**判定程序**与**已核定样例**，支撑"自动判定 → 人工确认"循环：agent 按程序自判，人工抽检确认，确认与分歧结果回填本指南，逐步提高自判可信度。
> 样例来源：场景一评估案例（17/14 号评审报告，修复提交证实）与 run6 潜在新发现人工复核（`evals/新发现复核-2026-08-18.md`）；设计错误样例来自 Vision-Sudoku 设计方案评审（`../../03-VisionSudoku规则覆盖验证.md` §2，2026-08-19 研究者核定认可）。

## 1. 判定程序（按序执行，先到先归）

1. **测试缺陷优先判**：问题出在测试代码本身——弱断言（任一结果均可通过）/ 覆盖虚报 / 平台依赖未标记（skipif 缺失）→ **测试缺陷**。注意：测试缺陷可与被测代码缺陷**并存**（如"属性被清空"与"测试未断言属性保留"是两条意见），分别立项、各判各的。
2. **查设计文档**（含契约表、接口签名、规范章节、代码自订契约声明如 store 头注）：
   - a. **无对应条目/口径**（写代码前就没列入）→ **范围缺口**；证据须引用"设计文档查过而无此要求"（§ 级引用）。
   - b. **有条目，但条目方案本身错**（照设计实现也会出错）→ **设计错误**。
   - c. **有条目且方案对，实现与条目不一致**（含"设计有代码无"）→ **实现偏离**。
3. **设计参照缺位**：被评审文件无任何设计文档/契约可对照（临时脚本、vendor 页面等）→ 类型标**其他（设计参照缺位）**，不强行归入 2a/2c——区分"没设计"与"偏离设计"需要参照物存在。

判定顺序的意义：范围缺口与实现偏离的分叉点在"设计文档有无条目"——**先查文档再判**，避免把"设计未定口径"错判成"实现偏离"（对照样例 G1 与 E2）。

### 设计错误（5 例，已核定 2026-08-19——均通过反事实论证门槛：可论证『照设计文档实现也会出错』）

| # | 案例 | 判定依据（反事实论证） |
|---|---|---|
| D1 | CHECK 约束 5 值与流程写入 "Unknown" 冲突（Vision-Sudoku CS-01） | LLD §2.2 的约束与 §5.1/IxD §6.3 的流程两处设计照做即冲突——保存操作必触发约束违规 |

| D3 | 保存盘面 source 硬编码 'manual'（Vision-Sudoku MJ-03） | LLD §7.2 硬编码与 SRS 三来源需求冲突——按 LLD 实现则摄像头/剪贴板来源全部错标 |

> 判定纪律：设计错误的主张必须过**反事实论证门槛**——构造『若严格照设计实现会发生什么』的论证并给出冲突双方出处；只有『设计不佳/可改进』而无冲突论证的，归实现偏离或范围缺口。

## 3. 边界情形与易错点

- **G1 型摇摆（范围缺口 vs 实现偏离）**：自判最常见的系统性错向——run6 自判 20 条实现偏离、0 条范围缺口，人工抽检发现 #10 应为范围缺口。程序第 2 步"先查设计文档有无条目"即为此设。
- **反向摇摆（有条目却判成范围缺口）**：run9 意见卡把"6 处读路径无 valid_to 过滤"计入范围缺口统计，但设计 15:137 有"查询层过滤"显式条目——应判**实现偏离**；分歧记录见 `evals/待确认问题卡-2026-08-19.md` #1。G1 型是"无条目误判有偏离"，本型是"有条目误判缺口"，两向都须以文档条目为准。
- **E1 型对照（实现偏离 vs 设计错误）**：判设计错误须论证"照设计做也会错"——E1 的设计（path 高亮）本身可实现，是实现没做，故为实现偏离；若设计规定的方案本身达不到其宣称目标，才是设计错误。
- **"契约"不限于设计文档**：代码自订契约声明（如 store 头注 "parameter binding is mandatory"）同样构成第 2c 分支的参照——Cypher 字符串拼接违反 store 绑定契约（run6 新发现 #2）属**实现偏离**而非范围缺口。
- **测试缺陷与被测缺陷并存**（T3 与 R-1 属性清空并存）：同源两条意见，类型各判各的，不得合并消解。
