# 方向一专题 06：产出物格式契约——前置供给与历史适配

> 日期：2026-08-18
> 话题标签：[D1]（[D1+D2]：本质是契约指南"输入契约"的工具化落地）
> 状态：已有结论（原则确立，落地动作见 §3）
> 触发来源：评分器格式依赖讨论（score_review 全文匹配无格式依赖 / compare_runs 高度依赖意见卡结构——签名 v1 伪影）

## 1. 原始思考（2026-08-18）

实际使用中，若工具链对产出物格式有依赖：**把格式约定作为一个规则文档记录下来**。应用研究成果于实际项目时，在流程前置环节直接提供这一规则，使全流程产出物格式统一；若是**历史项目**（已有格式不同的存量资产），则采用**修改代码（适配器）**的方式来适应历史资产。

## 2. 评价：原则成立，且是既有框架的自然推论

1. **本质是"输入契约"的生产端前置**：契约指南 §2 中每个组件都有输入契约——评分器/一致性分析器作为意见卡的**消费方**，其输入契约此前是隐式的（compare_runs 猜测 markdown 结构，伪影即违约后果）。本原则把隐式契约显式化为规则文档（意见卡模板 v2 的机器可读字段规范），并**在生成端强制而非在消费端宽容**——生产端强制格式的成本（模板约束）远低于消费端鲁棒解析的复杂度与误判率。两因素模型表述：格式契约为下游消费者供给确定模式，是因素 2 工程。
2. **双路径的分工正确**：
   - **新项目（契约前置）**：格式规则随装配流程 ③（上下文与提示组装）作为必供内容进入 skill/模板——产出天然合规，工具链零适配；
   - **历史项目（适配器）**：不反向污染核心工具——代码修改集中在 legacy adapter 层（把历史格式转换为契约格式），核心评分器保持单一契约。与 kb-app GraphStore 薄适配层同构：核心面向契约，变化被隔离在适配层。
3. **两点补充（防隐性失效）**：
   - **契约版本化与双端同步义务**：格式规则文档自身迭代（如模板 v2.1 改溯源字段写法）时，消费端工具须同版本升级——挂到既有 CHANGELOG 机制即可（契约文档与工具各记一行，互相引用）；
   - **适配器覆盖率登记**：历史格式解析不了的条目必须如实报告（"N 条未能解析，原因"），不得静默丢弃——RR-3 登记真实性精神在工具层的自应用。

## 3. 落地动作（2026-08-18）

1. **规则文档即既有模板**：`review-pi/.pi/skills/code-review/assets/opinion-card-template.md`（v2）就是意见卡的格式契约文档——补一句显式声明（本模板同时是评分/一致性工具的输入契约）；
2. 装配流程 v2 ③ 增补"格式契约前置"检查项、⑥ 增补"历史资产走适配器"检查项；
3. 评分器 v2 需求方向确认：核心解析面向契约格式（与模板同步），历史格式经适配器进入——不再追求"对任意格式的鲁棒解析"。
