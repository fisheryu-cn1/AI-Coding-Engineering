## 1. 原始思考记录（2026-08-18 备忘整理）

**想法 1：RR 规则的通用性分级。** 当前 skill 中的 review rules 通用程度不同：RR-1/2/3/5/8 通用性很高，几乎任何项目都有对应情景；RR-4/6 则有些项目有、有些没有，或实际设计与评审规则不完全一样。

**想法 2：RR-7 按输入来源拆分。** RR-7 同时考虑了 LLM 输出、外部系统 API 输入、用户人工输入三类来源，但三类特点不同：LLM 可能幻觉但可通过后处理做约束防御；外部系统若已经过测试则输入边界通常明确；用户人工输入无法前置限制、边界不可控。人工测试会对三类来源设计不同用例——仿照人工处理，RR-7 应拆成三种输入来源的不同检查规则。

**想法 3：提升中的拟合成分与新项目规则确定方法。** 三次迭代使覆盖率和检查深度明显提升，但其中可能有相当程度来自评审规则对实验项目内容的**拟合加深**。其他项目可能也需要识别与定制化规则的过程——本项目成果的规则清单部分适用、部分需调整。需要结合迭代过程研究：**新项目中如何快速有效完成评审规则的确定？是否同样需要多次迭代？**

**想法 4：评审问题应做类型区分。** 很多发现是"需求未实际列入设计"而非"设计错误"——如 run5 首个问题（代码未做 Windows 平台识别与写锁处理），根因是对应代码块编写前未把此项需求列入设计范围。两类问题性质不同：**未列出设计**可通过细化设计文档、在设计逐步细化过程中做上下游一致性与覆盖比例检查来控制；**设计错误**则可能是基模能力问题，需针对基模能力弱点提供参考设计样例解决。评审后区分问题类型，可对可观测和迭代决策提供支持。

**想法 5：版本标签与可交付状态分离。** review-rules.md 规则名称处同时记录迭代版本标签，研究过程方便，但最终交付时是干扰项。若要追踪每轮修改，可把版本差异单独记录在独立文件，**保持产出成果物始终处于可交付状态**。

## 2. 逐条评估（结合既有框架与证据）

### 2.1 想法 1：采纳——规则的"适用条件"化，notes/04 三层分解的细化

与 notes/04 的框架层/领域先验层/项目实例层精确对应：RR-1/2/3/5 属**过程级通用层**（任何开发过程都有），RR-8 属**声明-实现层**（凡有 UI/接口声明处），RR-4/6 属**域条件层**（仅当系统含软删除/并发写时适用）。改进方向不止于"分组"，而是给每条规则标注**适用前置谓词**（applicability condition）——新项目接手第一问从"有什么规则"变为"哪些规则对我适用"，这本身就是填充方法的第一步（与场景画像问卷联动：画像答"无软删除"即自动排除 RR-4）。**已列入 v4 改组**。

### 2.2 想法 2：采纳——RR-7 拆分为 7a/7b/7c，且三类来源各有理论锚点

拆分与既有知识严丝合缝：

| 子规则 | 输入来源 | 特点 | 防御重心 | 证据锚点 |
|---|---|---|---|---|
| RR-7a | LLM 输出 | 幻觉、格式漂移、think 污染 | **后处理**：schema 校验、清洗、输入/输出预算 | F-2（150KB 致空响应）、F-3（think 吃预算）、run1 意见（`<think>` 混入） |
| RR-7b | 外部系统输入 | 契约相对明确（已经过测试） | **按契约校验 + 版本漂移警惕** | N-2/N-3b（平台语义差异）、13 号 D7 钉版本教训 |
| RR-7c | 用户人工输入 | 不可前置限制、边界不可控 | **上界 + 消毒 + 兜底**最重 | run2/3 的 `docs_csv` 无上限意见 |

三类来源恰对应契约指南 §1 知识供给的三种入口——拆分后 RR-7 与契约指南可互引。**已列入 v4**。

### 2.3 想法 3：质疑成立且已有拟合证据——需引入"留出验证"与"规则溯源"

- **拟合证据已在手**：N-3a 是唯一未参与任何规则迭代的案例，也是 v3 下唯一未命中的语义案例——这个对照支持"提升含显著拟合成分"的判断（单例不充分，但方向明确）；
- **方法论解法（采纳为研究设计）**：①**规则溯源标注**——每条 RR 记录"学自哪个案例/先验"（provenance），评估时区分"先验规则"与"测试集渗入规则"的成绩（与 ML 的数据污染/data contamination 思想同构）；②**留出验证（holdout）**——需要一个未参与规则迭代的项目/锚点做泛化测试（候选：本仓库 code/ 其他项目历史、或 P3 迁移实验的第二项目）；
- **"新项目规则确定是否需多轮迭代"** → 成为 P3 迁移实验的核心度量：**迭代收敛速度**（第 N 轮达到多少语义召回）。工作假设（依据 notes/04 填充方法）：新项目 = 通用层直接继承 + 域条件层按画像选择 + 实例层从该项目缺陷史冷启动（首轮评审 + 人工复核挖掘）——收敛速度取决于缺陷史可得性。**已列入规划 §8.3 与 P3 设计**。

### 2.4 想法 4：采纳且对接三方——问题类型 = 修复路由（[D1+D2]/[D1+D3]）

类型学在用户两类基础上补第三类（kb-app 案例已有实证）：

| 类型 | 定义 | 控制手段 | 对接 |
|---|---|---|---|
| **范围缺口** | 需求未列入设计 | 细化设计文档 + 上下游一致性/覆盖比例检查 | 模板集 R4/R5（FR↔场景、NFR↔验收覆盖矩阵）——检查机制已存在，缺的是评审侧的归类 |
| **设计错误** | 已列入但设计错 | 参考设计样例（针对基模能力弱点） | 两因素模型：样例 = 模式供给（few-shot）；样例库可成为组件目录 L2 新子类 |
| **实现偏离** | 设计对、实现走样 | 登记/回写机制 | 模板集 R9；kb-app"设计有代码无"10 项实证 |

价值判断同意且可强化：**问题类型分布 = 过程改进的仪表盘**——范围缺口多 → 需求/设计过程问题；设计错误多 → 基模能力/样例库问题；实现偏离多 → 流程纪律问题。这正是 D3-S3（迭代决策支持）需要的错误分析框架，与 MAST"失败分类决定干预"思想同构但在评审层。**落地**：意见卡模板增加"问题类型"字段（v4），轨迹报告质量实体增加类型分布（v4 模板 + 可观测清单补一行）。run5 Windows 案例的归属（范围缺口 vs 设计错误）按此框架回填核定。

### 2.5 想法 5：采纳——CHANGELOG 分离作为产物通用约定

工程惯例成熟（keep a changelog）：产物文件头只保留**当前版本号一行**，修订历史入独立 CHANGELOG.md。本仓库适用范围不止 review-rules：意见卡模板、组件目录、决策树、可观测清单等所有迭代型产物统一采用——**"迭代注记入 CHANGELOG，产物头只留当前版本"** 写入产物规范（模板集 v1 的头部约定候选）。收益正是用户所说：成果物始终处于可交付状态（always-shippable）。**已列入 v4 + 产物规范**。
