# 方向一专题 04：抽象模板与具象化填充

> 日期：2026-08-17
> 话题标签：[D1]（第 2 节含 [D1+D2]、[D1+D3] 交叉）
> 状态：讨论中（构建 code-review skill 后的思考备忘）
> 关联：notes/03（两因素模型——填充即因素 2 工程）、`experiments/02-装配实录.md`、`agent-software-design/experiments/02-中间产物模板集v0.md`、`../../装配流程v1.md`

## 1. 原始思考记录（2026-08-17 备忘整理）

**观察一：skill 的过拟合事实。** 本次构建的 code-review skill，其评审要点与 kb-app 的设计及开发过程中因各类偶发因素实际出现过的代码问题密切相关——可以说存在**针对特定案例的过拟合**。因此，其他项目所需的 code-review skill 在具体内容上需要根据该项目本身的特点与技术设计方案调整；本次构建的 skill **只在框架结构上具备参考价值**。

**观察二：方法论适用范围与抽象程度的关系。** 这恰是本研究中值得考虑的因素：**方法论本身的适用范围与其抽象程度高度相关**；但回到具体应用场景，又需要结合具象的实际场景、需求、设计等上下文信息，把"被抽象掉的部分填充回来"。这个**整理信息进行"填充"的方法**，可以说是作为本研究目标的软件工程方法的主要内容之一。

**核心判断：填充方法可能比模板更重要。** 抽象模板可能是研究的重要成果物；但在具体应用场景中，**如何结合抽象模板与实际情景上下文、基于抽象模板形成具象成果物——这个方法的重要性可能超出抽象模板本身**。

## 2. 结合既有框架的分析（2026-08-17）

### 2.1 对"过拟合"的细化：skill 实为三层复合体

逐条审视 `assets/review-rules.md` 的 RR 规则，其"过拟合"程度并不均匀——按可迁移性可分三层：

| 层 | 内容 | RR 例子 | 跨项目价值 |
|---|---|---|---|
| **框架层** | SOP 流程、checklist 骨架、意见卡格式、红线（溯源/证据/诚实性） | 五步流程、分级口径 | 完全可复用 |
| **领域先验层** | 某类系统共有的缺陷先验 | RR-4 状态生命周期四查（适用于**任何**含软删除/墓碑的系统）、RR-7 外部输入三件套（任何消费 LLM/外部输入的系统）、RR-5 幂等 | 按域选用子集 |
| **项目实例层** | 特定技术栈与项目史的检查项 | FTS5/LadybugDB 特性、kb-app 的锁口径与任务分派约定 | 不可迁移，须重建 |

**修正观察一**：skill 并非"只有框架结构可参考"——领域先验层是可按域复用的中间资产；真正必须为新项目重建的只是实例层。这个三层分解本身就是一个可复用的**skill 结构模板**。

### 2.2 "填充方法"已在项目中的雏形与命名

观察二所说的填充方法，在既有工件中已有雏形，本次备忘将其**提升为显式概念**：

- **装配流程 v1 就是填充方法的骨架**：②能力清单的"知识三段登记"（内蕴/外部知识/供给方式）界定了"要填什么"；①场景画像采集"从哪填"（项目特点/规范载体）；③–④组件选配与上下文组装执行填充。
- **两因素模型的对应**（notes/03）：抽象模板解决的是"模式匹配"的脚手架（因素 2 的结构侧）；填充供给的是"模式外信息"（因素 2 的内容侧）——填充质量直接决定输出质量。
- **知识来源的泛化——缺陷史挖掘**：本项目评估集的"自举"（评审报告 → 标注案例）可以泛化为填充的标准信息源：**新项目的实例层规则与评估语料，应从该项目自身的缺陷史（评审报告/issue/postmortem/修复提交）挖掘**——"每个项目的历史缺陷是其评审 agent 的最佳训练先验"。

### 2.3 对研究成果物观的修正（[D1+D2]）

核心判断对成果物框架的影响：模板类产出（中间产物模板集 v0、skill、组件目录、可观测清单）应统一附带**具象化过程记录**（模板 → 实例的映射方法与实际操作），且二者在评估中权重对调——

- 模板的价值 = 框架层 + 领域先验层（可分发部分）；
- **填充方法的价值 = 使模板在任意新场景落地的能力**（本研究的核心方法贡献候选）；
- 因此 P2 的装配实录不应只记"装了什么"，要记"**每个抽象件是如何被具象化的**：填了什么信息、从哪来、判断依据"——这是比清单更重要的数据。

### 2.4 与经典原理的呼应（[D1+D2]）

Brooks 的本质/偶然复杂度在此有精确对应：抽象消去的是偶然复杂度（重复的流程脚手架）；**填充处理的是本质复杂度（该场景不可化约的具体性）——这正是"没有银弹"在 agent 工程方法层的表述**。填充不可自动化消除，但可以被**方法化**（这正是研究目标）。
