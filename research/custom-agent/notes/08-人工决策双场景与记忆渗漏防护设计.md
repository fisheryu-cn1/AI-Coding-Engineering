# 人工决策交互的双场景设计与框架记忆渗漏防护（P3 前置，2026-08-19 第 16 场）

> 背景（自足）：P2 阶段结束、P3（在新项目上检验评审智能体的泛化能力）启动前，研究者提出两项改进：其一，研究过程中需要人工审核决策的环节存在两个问题——决策材料的文字预设读者了解全部前序上下文与自创术语（易造成审阅不完整），且所需比对的材料分散在多个文档的多个章节（人工比对极不便）；同时现有交互机制只覆盖"研究过程"的决策，没有区分"使用研究成果（评审 skill）过程中的决策"。其二，实验多次出现评审智能体读到前序评审结果影响独立性的问题，除提示词控制外，还需评估框架自带记忆系统是否构成渗漏通道，并利用开源框架（pi/DSH）的可定制性做针对性设计。本笔记给出两方面的设计并落地立即可用的部分。

## 1. 人工决策交互的双场景规范

### 1.1 两类决策的区分

| | 场景 A：研究过程决策 | 场景 B：使用成果过程决策 |
|---|---|---|
| 何时发生 | 研究推进中（口径裁定、结果核定、方向决策） | 使用者运行评审 skill 时（A-B 评审闭环内的介入点） |
| 决策者 | 研究者（了解研究目标） | skill 使用者（开发者/评审负责人，**没有研究上下文**） |
| 已有机制 | 人工待办事项清单（按研究步骤分文件、五字段结果记录） | 仅散见于闭环工作流文档，未成规范——**本笔记补齐** |
| 反馈方式 | 五字段（处理人/结论/依据/处置动作/下游影响） | 轻量：卡上勾选归类 + 一句话理由 |

场景 B 的介入点清单（使用 skill 时需要人的三个时刻）：①A 应答中被驳回且 B 复审仍持异议的意见（人工裁决，不得默认放行）；②评审产出与使用者已知事实矛盾（填待确认问题卡）；③复审结论中"部分修复/新发现"项的接受与再修复决策。

### 1.2 两条硬规范（对两种场景同时生效，源自 P2 教训）

1. **内联摘录原则**：决策文档必须把需要比对的内容**原文摘录内联**——双方判断、关键证据片段（代码行/文档原句）直接放进决策文档的表格或段落里；路径与章节引用只作溯源补充。**不得要求人工跳转到其他文档的其他章节才能完成比对。**机器可读靠引用，人工可读靠内联。
2. **自足表述原则**：每个待决策事项配一段自足背景叙述（约百字内）：做了什么、为何需要人来定、两个选项各意味着什么；内部速记（运行编号、案例编号、规则编号）首次出现必须附一句白话说明；不得使用未定义的自创术语（AGENTS.md §6 已有总则，此处为决策文档的具体化）。

对分散问题的产出侧优化：**复审卡必须逐条内联原意见标题、A 应答结论与修复核验结果**——单一文档内完成"意见-应答-修复"三方比对，不依赖回读前两张卡（此要求写入 review-recheck 提示模板）；闭环各卡统一命名 `<日期>-<对象>-<阶段>.md` 且同放 reviews/ 目录（已是现状，固化为约定）。

## 2. 框架记忆渗漏评估（pi）与定制设计

### 2.1 pi 的记忆/上下文通道清单（依据官方文档，非推测）

| 通道 | 机制 | 评估场景风险 | 官方开关 |
|---|---|---|---|
| 会话恢复 | `-c`/`-r`/`--session` 把历史分支全部重注入上下文 | **高**（误带即整段旧评审进上下文） | 不使用即可；`--no-session` 免落盘 |
| 压缩摘要 | 会话超长自动压缩，恢复时摘要+保留尾自动进上下文 | **高且隐蔽**（摘要为旧信息浓缩） | `compaction.enabled:false`；不复用会话即不触发 |
| 上下文文件注入 | 启动时自动加载 cwd 向上各层与全局的 AGENTS.md/CLAUDE.md | **中——本次评估新识别**：review-pi 向上命中 `research/AGENTS.md`（90 行研究约定与状态），历次评审运行均被静默注入（内容不含缺陷答案，属研究过程线索渗漏，原则应封堵）；注入链上无其他文件（仓库根与 kb-app 均无 AGENTS.md，被评审仓库无合法上下文损失） | `-nc`/`--no-context-files` |
| 技能元数据 | 各层 skills 目录的名称+描述常驻系统提示词 | 低（code-review 自身属合法；用户级其他技能仅描述可见） | `--no-skills`（评估时不用） |
| 全局层 | `~/.pi/agent/` 的全局 AGENTS.md/settings/extensions 跨项目生效 | 中（内容取决于本机配置） | `PI_CODING_AGENT_DIR` 重定向 |
| 扩展 | 可读全部会话（含跨项目）并注入消息/改系统提示 | 现装扩展仅写保护守卫，无记忆类扩展——未激活；属**潜伏面** | `--no-extensions` |
| 会话文件路径 | bash 工具经 `PI_SESSION_FILE` 可见当前会话 JSONL 路径 | 低（当前会话内无前序评审；恢复场景则高） | 规程禁止读 |
| 工作区文件 | 旧评审产物存于工作区，read/bash 可达 | **高——三次事故的实际通道** | 无框架级屏蔽 → 定制见 2.3 |

### 2.2 评估结论

P2 三次事故（run6 读旧意见卡、run11 读工作区内评审报告、答案文档在锚点内）全部经由"工作区文件"通道，提示词纪律已逐次强化；框架记忆通道（恢复/压缩/全局注入）从未在事故中激活——因为评估一直用 `pi -a -p` 每次新会话。但 **AGENTS.md 注入通道此前未识别且一直在发生**，本日核实后封堵。结论：提示词纪律只能约束"自觉"，框架级通道需要框架级手段——这正是选择 pi/DSH 开源框架（可定制）的动机所在。

### 2.3 定制设计（分层）

1. **规程层（立即生效）**：评估运行的批跑命令升级为 `pi -a -nc -p "<提示>"`（`-nc` 禁上下文文件注入——注入链上仅有 research/AGENTS.md，无合法损失）；维持"每次新会话、不复用、不 /compact"；禁止读取 `~/.pi/agent/sessions` 与 `PI_SESSION_FILE` 所指文件（写入隔离纪律）。会话 JSONL 仍正常落盘（它是轨迹观测数据源，保存是输出不是输入，不构成渗漏）。
2. **扩展层（P3 实施）**：新写 eval-hygiene 扩展，把提示词纪律变成硬约束——①tool_call 读保护：拦截对锚点后提交路径、reviews/archive、evals/、scripts/、sessions 目录的 read/bash 访问（现有 review-guard 只拦写，扩展为读写双拦）；②上下文卫生：before_agent_start 校验上下文文件来源仅限被评审仓库层（研究层文件存在即告警），需要时显式注入被评审仓库的说明作为首条消息（控制注入替代自动注入）；③运行头注入评估元信息（锚点、规则版本）到 custom entry（不进 LLM 上下文，供轨迹对账）。
3. **验证（扩展上线后）**：诱饵检验——工作区故意放置含唯一标记串的旧意见卡与伪造答案文档各一份，黑盒运行一次评审，确认读保护拦截且产出意见无标记串污染。
4. **DSH 等价**：迁移成本矩阵将登记"读保护守卫"与"上下文卫生"两项的 DSH 对应形态（其上下文/记忆机制的等价开关）——P3 组件登记时补。
