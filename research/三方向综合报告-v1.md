## 0. 摘要与核心主张

本研究探讨一个问题：**当软件的核心组件是大语言模型（LLM）时，软件工程的方法需要哪些变形？** 围绕一个真实场景——用可定制智能体框架组装"AI 代码评审智能体"并投入真实使用——展开了三个方向的工作：专用智能体的组装方法（工程视角）、面向大模型软件的软件工程原则（原理视角）、以及这类系统与开发过程的可观测性（度量视角）。

核心主张三条，均为经实验检验后仍成立的表述：

**主张一：LLM 为核心组件的软件工程可归结为"规约 × 验证 × 人在回路"的三元结构。** 行为性知识沉淀为可分发的文本资产（规则集、模板、清单）——它们扮演传统软件中"规约"的角色，但是**概率执行**的；因此每个资产必须配"验证面"——锚定真实缺陷的评估集，而非合成输入；而判定"发现是否成立、缺陷是否够严重、迭代是否该停止"这类**大尺度判断**，实验反复证明超出当前模型的自证能力，必须由人承担，且人的介入可以被规范化为可追溯的流程环节。三元中任何一元缺失都会在现场事故中暴露：无验证的规约虚标能力，无人工裁定的验证被代理初判污染（实测一次初判 7 项命中被人工终审推翻为 4 项），无规约的人在回路退化为不可复盘的闲谈。

**主张二：AI 生成代码的缺陷谱系决定工程重心上移。** 三个真实项目（kb-app、Vision-Sudoku、fundseeker）的证据一致表明：语法与引用类低级错误近乎绝迹（模型低错误率 + 强制单元测试双重过滤），缺陷集中于更大尺度——逻辑架构、功能完整性、文档与实现的一致性、异常边界、并发竞态。因此评审资源应系统性投向文档链一致性、架构契约与边界处理；单元测试全通过不再构成"功能达成"的证据（实测存在单测测不出的数据停摆类缺陷）；单轮评审只是对缺陷空间的一次采样（实测单轮召回 31–46%），多轮采样与归并成为必要组成。

**主张三："结构先于规则"的工程原则在新范式下依然主导。** 当问题的规则复杂度上升时，优先改变物理与格式结构让规则消失，而不是加更多规则：评审隔离靠目录分置与命令输出面控制（五条渗漏通道全部是结构封堵），而非叮嘱"不要作弊"；历史产物的格式差异靠适配器转换，而非让评分脚本学会宽容解析；产出可比靠生产端格式契约前置，而非消费端猜测。本项目中四次"多加一条禁令仍挡不住"的事故，最终都由结构改动终结。

第 2–4 章分别展开三个方向的成果，第 5 章汇总实验证据，第 6 章与 36 篇文献对话，第 7 章效度，第 8 章把主张二展开为后续研究议程。

## 1. 研究问题与方法

### 1.1 三个方向与相互关系

| 方向 | 研究问题 | 一句话结论 |
|---|---|---|
| 方向一：专用智能体组装方法 | 如何用可复用组件在可定制框架上快速形成做特定工作的智能体？ | 七步装配流程 + 五层组件目录 + 资产迭代闭环；交付形态为可打包的"评审工作包 V1.0" |
| 方向二：面向大模型软件的 SE 原则 | 传统软件工程概念（规约、验证、中间产物）在"行为由模型概率生成"的软件里如何变形？ | 三处变形 + 文档链模板 + 类型判定学 + 适配器原则 + 变更治理 |
| 方向三：可观测性 | 如何度量 LLM 软件系统的质量与 AI 辅助开发过程本身？ | 评估口径体系 + 污染通道分类学 + 人工环节可观测化 + 三对象指标与自观测 |

三者是同一项实验的三个切面：方向一提供实验载体（评审智能体及其装配过程），方向二提供产物的规范与原理（评审规则集正是"规约-验证对"的实例），方向三提供度量与过程证据（所有运行数字、污染事故、人工决策都按观测制度落盘）。这避免了三个方向各做各的实验。

### 1.2 研究方法：对话式研究 × 自观测

- **对话式研究**：研究以研究者与 AI 代理的多轮对话推进，工作约定（话题分类、归档规则、写作规范）成文于 `research/AGENTS.md` 并两次制度化修订。每轮对话结束必须落盘，不允许只存在于对话中的结论。
- **三层过程管理**：台账（任务状态，支持中断续跑）、规划（前瞻与成果物）、日志（事后方法记录，[方法]/[尝试]/[教训] 三类标注）——职责分离，使 26 个场次的工作可完整回放。
- **自观测**：过程数据（人工决策、AI 运行、文档演化）由既有制度零额外埋点采集，形成三对象基线与五个过程改进案例（第 4.5 节）。
- **人在回路的规范**：人工核定/裁定/决策事项进入"人工待办事项清单"（固定五字段：结论/依据/处置/下游影响/处理人），全周期登记 12 项、全部处理完毕——人工环节本身成为可追溯的研究数据。

### 1.3 实验载体与三个样例项目

- **框架**：pi（badlogic/pi-mono，"极简内核 + 扩展"路线的开源智能体框架）；DSH（DeepSeek Harness）作为跨范式迁移可能性的设计参照（登记等价形态与接入成本，未做运行级实迁）。
- **模型**：全部评审运行使用同一模型（MiniMax-M3，thinking=high）——跨模型比较不在本报告范围。
- **三个样例项目**（角色互斥，防止评估污染）：

| 项目 | 角色 | 用途 |
|---|---|---|
| kb-app（本仓库内知识库应用，含 17 份设计文档链与 5 轮评审历史） | 源项目 | 规则集的提炼与迭代场（P2）；其历史评审产物反向构成评估标注集（"自举式评估语料"） |
| Vision-Sudoku（数独应用，文档完备、无 git 历史） | 第二语料 | 规则集静态覆盖验证（无运行级评估） |
| fundseeker（基金数据采集分析系统，生产在用） | **留出项目** | P2 全程隔离，P3 冷启动检验泛化（从未参与规则集任何迭代） |

### 1.4 术语表

| 术语 | 定义 |
|---|---|
| 锚点 | 被评审代码的一个历史版本（git 提交号）——目标缺陷在该版本中存在、随后被修复提交证实 |
| 意见卡 | 评审智能体的输出文档，逐条列出发现的问题（级别、位置、证据、建议、分级依据），格式受模板约束 |
| 语义命中 | 人工逐条比对意见与考题后的严格判定：缺陷的机制被意见显式表达。区别于关键词匹配的机械判定（后者只作上界参考） |
| 评审污染 | 评审输入混入不该有的信息（如别次评审的旧输出、含答案的文档），导致命中数字虚高不可用 |
| 留出检验 | 用方法从未接触过的项目检验真实泛化能力（在源项目上测出的是"学过的内容回注"效果） |
| 适配器 | 把不符合约定格式的旧产出物转换成约定格式再送入评分工具的小程序——原则是转换旧产物，而非修改评分工具迁就格式 |
| 规约-验证对 | 知识资产（规约面）与锚定真实缺陷的评估集（验证面）的配对，两者以溯源标注绑定（第 3.1 节展开） |
| 单轮召回 | 单次评审运行命中的确认问题主题数占分母（全部确认主题）的比例 |

## 2. 专用智能体组装方法（方向一）

### 2.1 组件目录：五层结构与三档复用性

对 pi 与 DSH 两类"极简内核 + 插件/扩展"框架的定制机制做代码级调研后，形成组件目录 v1：**五层**（L1 行为干预 / L2 知识技能 / L3 工具 / L4 界面 / L5 观测验证），每层组件标注**三档复用性**——F-通用（纯文本/标准协议，跨框架直接迁移，如 Agent Skills 标准的 skill 文件）、F-配置（声明式配置可完成的组装，如 DSH 的 YAML 挂载）、F-绑定（依赖宿主 API，迁移需重写，如 pi 的扩展钩子）。

选配规则三条，经场景一装配与跨项目迁移两次验证：**L2 先行**（上下文构建组件成本最低、复用性最高，任何场景优先配）、**L5 必配**（观测与验证组件是必备件而非可选件）、**L1 慎用**（行为干预是重资产，仅在 L2/L3 不够时引入）。场景一实际装配 7 件组件中 F-通用 5 件（71%），唯一的 F-绑定自研件是写路径守卫。

### 2.2 装配流程：七步 checklist 与"填充方法优先"

装配流程 v1（七步法：场景画像→组件选配→上下文与提示组装→评估集与门禁→清洁运行→验证与评分→迭代闭环）经六场实践修订为 v2 的 checklist 形态，每条检查项括注其来源场次——流程本身按"发现→修订→复用"闭环演化。

一个重要的定位修正来自实践：模板与目录类成果物属**抽象层**（框架层 + 领域先验层），"结合场景上下文把抽象模板填充为具象成果物"的**填充方法**（填什么、从哪来、判断依据）重要性可能超过模板本身——因此装配实录被要求记录填充过程，填充方法在最终成果中列为核心方法贡献候选。典型例证：评审规则集的框架结构可泛化，但其内容必须从被评项目的缺陷史挖掘填充（第 2.3 节），"缺陷史挖掘"由此成为流程的正式步骤。

### 2.3 知识资产的迭代闭环：从缺陷史到规则集

评审 skill（规则集 v1→v5）的演化是本研究最完整的"资产迭代闭环"样例：

1. **提炼**：从源项目 5 轮历史评审报告（约 60+ 条带 file:line 标注的缺陷）提炼十条评审规则（RR-1~RR-8，部分按输入来源拆分）；
2. **迭代**：每轮运行后做错误分析，区分两类失败——"错误排除"（评审者看到了问题却主动判为无碍，须把检查程序机械化）与"盲区"（无规则覆盖，须增补规则）——修订后同锚点复测。三轮闭环使语义严格命中从初版约 9–18% 提升到 v4 的 ≥10/11 显式（11 个考题、f62f287 锚点、清洁运行；该锚点带"标准答案合法可见"效度注，见第 7 章）；
3. **治理**：每条规则标注溯源（提炼自通用实践，还是由某考题漏检触发增补）——v4 时 10 条规则中案例渗入 3 条；修订须走工作单（含泛化检验三问与留出保护）；版本史入 CHANGELOG；
4. **停止**：当修订开始针对单一案例的具体形态、复测通过率不再显著提升时，停止在源项目上微迭代，转入迁移验证——迭代停止条件成文为四信号判据（这是文献未覆盖的空白，见第 6 章）。

规则集的可分发性同时被检验：初版曾用项目内路径引用规则来源，破坏脱离项目环境的可用性——修订为规则摘录进自包含的 assets 文件，"引用完整性"由此成为可分发组件的默认红线。

### 2.4 规约-验证对：知识资产的"出厂检验"（与方向二共用）

每个知识资产交付时配一对：规约面（规则条文 + 适用域 + 执行程序 + 已知局限声明 + 变更治理）× 验证面（锚定真实缺陷的评估集，每案例含锚点、期望发现、证实方式）× 溯源绑定。双向清点使两类缺口显式化——无实例验证的规则（如外部系统输入防御 RR-7b，诚实登记为"无专属案例"）与无规则覆盖的案例。详见第 3.1 节。

### 2.5 交付形态：评审工作包 V1.0 与真实应用闭环

研究的可用交付打包为"评审工作包 V1.0"（2026-08-20）：评审方法总纲（人在回路全流程）、skill 全资产、三阶段提示模板、守卫扩展、决策与规约模板、评估工具，附安装说明、最小起步六步（第一步即"先跑裸模型基线"）、**效果与边界诚实声明**、跨框架迁移注记与源头声明。

交付前完成了真实应用闭环：评审发现的两项确认缺陷由编码智能体真实修复 → 评审智能体独立复审确认修复并抓出修复引入的一处回归 → 按处方修正 → 人工核实后合并入生产项目主干。修复者当日两次低级失误（代码块错位、真值守卫写反）分别被自身冒烟测试与独立复审拦截——"评审→修复→复审"三段缺一不可的现场实证。

## 3. 面向大模型软件的 SE 原则（方向二）

### 3.1 传统规约-验证概念的三处变形

传统软件中规约（接口契约、不变式）与验证（测试、形式化检查）成对出现。当行为性知识沉淀为文本资产（规则集、清单、模板）时，"规约-验证"配对依然成立，但有三处结构性变形：

1. **规约是概率执行的**：规则经提示注入后由模型执行，同一规则的执行质量随任务、措辞、模型状态波动——验证测的是"规约被遵循后能否引导发现真实缺陷"，不是机械断言。这决定了验证面必须是语义判定口径（人工终审），机械口径只能作上界。
2. **验证锚定历史事实**：考题不是合成输入，而是"真实评审发现 + 修复提交证实"的缺陷，锚定在缺陷仍存在的历史版本上。评估集由此不可跨项目复用，但**构造方法**（缺陷史挖掘 + 修复提交父态锚定）可复用。
3. **绑定靠溯源标注**：每条规则标注来源（先验提炼 / 案例渗入并注案例号）——拟合成绩与泛化成绩由此可分离，这是留出检验成立的前提。

一个重要的配套发现：**验证失败须分层诊断**。实测一条考题在规则升到 v5 后仍漏检，根因不是规则缺失而是规则的检查程序不可操作（检查者判不出问题）——"失败即改规则"是误区，诊断路由应区分规约缺失 / 执行程序不可操作 / 适用条件误排除 / 规则过宽 / 非规约问题五类根因。

### 3.2 文档链模板：产物内建一致性，替代评审注意力

对源项目完整文档链（需求→选型→概设→详设→数据规范→评审，17 份文档）的回溯分析发现：产物**之间**的覆盖核查有制度（设计评审核对需求落点），但产物**内部**的一致性没有任何内建机制，完全依赖下游评审的偶然注意力——手工检验仍从最成熟的需求文档中找出 5 类真实不一致（术语颗粒度错位、名词两种指称、清单两处硬编码、非功能需求无验收映射、功能需求无场景反向覆盖）。

对策是中间产物模板集：四类产物模板（需求/架构描述/接口规约/验收定义）+ 一致性规则最小子集 R1–R13，其中 8 条可脚本机检。规则全部标注案例实证来源；新增的第 13 条（带软删除状态的系统须查属性保留、读路径过滤、合并键完整、不可复活四项）来自评审主题统计中最高频的"状态生命周期缺陷"——该缺陷类在多智能体失败分类学（MAST）中没有对应类目，是本研究识别的新缺陷类候选。

模板集自身带抽象层声明：它替代不了评审（弱判定边界：规则只能证伪不一致，不能证明完备），其价值在"填表即自查"的机制，以及把外部知识（清单、术语表）单源化。

### 3.3 类型判定学：给缺陷分类，并配判定纪律

把评审发现分为四类——**范围缺口**（需求未进入设计）、**设计错误**（设计本身错）、**实现偏离**（实现走样）、**测试缺陷**——每类配不同修复路径（缺口→设计过程问题、错误→能力或样例库问题、偏离→流程纪律问题）。类型分布因此成为迭代决策仪表盘：实测两个语料分布迥异（实现密集的源项目以实现偏离主导；文档密集的第二语料设计错误与文档不同步合计近四成），指导评审资源先投设计评审还是代码评审。

"设计错误"的判定配有**反事实论证门槛**：判定"设计文档本身有错"必须构造"若严格照设计实现会发生什么"的论证，不允许凭实现现状反推设计有错。该纪律源于实测中的一类易错判定，配套已核定样例（初版 8 个，后补设计错误类 5 个，全部过反事实门槛）。

### 3.4 适配器原则：改结构还是改逻辑

评估管线遇到的典型问题：历史项目的产出物不符合新契约格式。两种解法——让评分脚本学会宽容解析（改逻辑），或写适配器把旧产物转换成契约格式（改结构）。本研究确立后者为原则：核心工具不写多格式宽容解析，未解析条目如实登记；适配器以代码资产为模板由智能体现场改写，约束是样例验证通过方可使用、最小改动只动解析不动判定、改写登记版本与验证结果。

该原则的普适性在评审协议设计中再次出现：隔离纪律的每次失效都不是"叮嘱不够"而是"结构有洞"——最终解法是枚举信息通道并逐一结构封堵（第 4.2 节），以及物理目录分置让并行互读在结构上不可能。

### 3.5 变更治理：权威转移、回写与受控修订

LLM 资产的变更治理复用并扩展了传统配置管理做法，全部在 26 个场次中实际执行：

- **权威转移而非覆盖**：文档链演化时，新文档声明"以本文档为准"并附回写清单，上游以加注同步——需求演化可追溯；
- **版本纪律**：文件头只留当前版本号，修订史入 CHANGELOG，产物始终可交付；
- **受控修订**：规则修订走工作单（根因分类 + 泛化检验三问 + 留出保护 + 溯源标注）；
- **登记真实性**：完成定义（DoD）条目未执行不得登记完成，须附执行证据与环境口径——源于实测"登记≠执行"（可机检机制可被虚报绕过，一次实测发现 12 项应答承诺未兑现）；
- **停止条件**：改进循环自身何时停止（第 2.3 节四信号）。

## 4. 可观测性（方向三）

### 4.1 评估口径体系：三口径与多次一致性

- **召回三口径**：启发式召回（关键词机械匹配，必然高估，只作上界）／语义严格召回（人工逐条核定，机制被显式表达）／语义宽松（半命中计 0.5）。任何召回数字必须标注（口径 × 规则版本 × 锚点 × 清洁/污染 × 模型），跨口径混算是本项目早期最大的一类数字误引风险。
- **多次一致性（pass^k 思想）**：单次通过不代表每次通过。实测同任务不同运行命中波动 4~11 个考题、意见条数差 2 倍、成本差 1.7 倍——方差本身列为独立观测量。一致性只在同资产版本内计算（跨版本意见集剧变，不可混算）；意见的跨运行配对须用稳定标识（命中规则编号 ∪ 关联对象文件），早期用"标题词+级别"作签名曾产生 0% 相似度的解析伪影。
- **量的指标不等于质的指标**：一次对照运行产出 30 条意见但严格命中仅 3 题——意见多不等于找得准（与 METR 随机对照试验的"产出类度量被写得冗长混淆"警示同向）。

### 4.2 污染通道分类学：五通道枚举与结构封堵

实验过程中先后发生四次评审污染/渗漏事件，每次都导致一批数字不可引用，也每次暴露一条此前未被想象到的信息通道：

| # | 通道 | 事件 | 封堵方式（均为结构封堵） |
|---|---|---|---|
| 1 | 既往评审产物 | 评审者读取了工作区中先前的意见卡 | 运行前归档旧产物 + 指令禁读 |
| 2 | 工作区当前文件 | 读取了工作区中后续版本的文档 | 一切内容经 `git show <锚点>:<路径>` 读取 |
| 3 | 锚点内既有评审报告（含考题答案） | 答案文档恰在被评版本中已合法入库 | 禁令追加 + 历史数字整组加效度注 |
| 4 | 提示词引用命令的完整输出面 | 定位命令 `git show <fix> --stat` 默认携带修复提交主题行，而主题行常直接陈述缺陷 | 改用 `git diff <fix>^ <fix> --stat`（无提交信息） |
| 5 | 对被隔离材料的越界断言 | 禁读某材料后，评审者仍对其内容下"未登记"类断言 | 禁令：只允许声明"未核查"，不得断言 |

方法论结论：**隔离审查必须枚举信息通道的完整输出面**——"不许看 X"不等于"看不到 X 的影子"；通道 4（提示词自身引用的命令携带答案）在文献中未见讨论，是本研究的新发现之一。主层载体裁定：以标准化提示词条款为主（约 20 次运行明示规则遵从率 100%，事故全为规则缺口而非违抗），辅以薄执行层工具（eval-hygiene，observe 检测/enforce 拦截双模式，诱饵检验与全流程零中断阳性对照通过）。

### 4.3 人工环节的可观测化

人工核定与裁定是这类研究流程的必要环节，但文献普遍缺少其记录规范。本项目的做法：人工事项进入版本化待办清单，每项要求"涉及文件完整路径 + 对该文件的具体工作 + 处理建议"，处理结果按五字段回填（处理人/结论/依据/处置动作/下游影响），结论须写成不依赖项目上下文的完整句。配套两条硬规范使人工处理可行：**内联摘录**（需比对的内容原文摘录进决策文档，禁止只给路径让人跳转）与**自足表述**（每个待决事项配自足背景段）。全周期 12 项人工事项全部可追溯。

人工终审的必要性有直接证据：一次代理语义初判（7 项命中）被研究者逐条复核推翻为 4 项——大模型裁判在根因级判定上的混淆高发，与 MAST 文献的自述一致（详见第 6 章 2-3）。

### 4.4 成本与方差

过程观测的另一组产出：同任务成本方差最高 1.7 倍（输入 118.9K–207.4K token、65–110 轮）、意见量方差 2 倍；方差来源（采样参数还是风格）未归因，列为开放课题。设计侧的呼应：缓存友好与防渗漏同向（禁上下文文件注入既堵渗漏通道又稳定缓存前缀）——工程约束之间的一致性偶然但可利用。

### 4.5 三对象指标与自观测基线

过程观测按三对象组织指标（对齐 DORA/SPACE/DevEx，另有三项自定义增量：成本方差、规则渗入比、实验→思考启发链密度），零额外埋点填卡 70%——数据全部来自既有过程文档与会话日志的副产品。全周期基线与五个"观测数据驱动流程改进"的归档案例（文档维护事故→制度化→零复发；术语漂移→执行点迁移；四次污染→五通道；人工结论不可复盘→清单机制；过拟合→停止条件）呈现同一环路：**事件被采集层捕获 → 制度化为机械可执行的规则 → 以零复发/可追溯验证**。改进的抓手几乎都不是"更努力"，而是改变结构——与主张三同构。

**四项不一致/幅度差异/待检验**：①增益幅度显著小于文献典型值（3→4 vs 文献的近三倍）——归因于基线不同（裸模型已有部分能力）与资产-任务匹配度，引用文献效应量必须带基线条件；②欠同模型多次运行投票对照——已在 P3 补齐（E3/E5，More Agents 基线在通用缺陷上很强）；③对大模型裁判的信任程度——坚持人工终审，裁判一致率数字须按任务粒度分层引用；④强制性纪律的冗余风险——首测未见意见膨胀，保持观察。

**五项文献未覆盖的新发现**：①评估输入状态内含答案文档的构造性污染（区别于参数记忆污染与可检索泄漏的第三种）；②迭代停止条件；③人工环节的过程规范化；④适配器原则；⑤设计错误判定的反事实论证门槛。

## 7. 局限与效度威胁

按影响从大到小排列，均有对应的处置或标注：

1. **答案可见（效度注，不可回溯修复）**：源项目两份历史评审报告（考题的标准答案）恰好在被评代码版本中已合法入库——无法回溯判断各次运行是否读过，该两锚点的历史命中数字整组带风险标注。处置：运行规程已明令禁止（2026-08-19 起）；关键结论改以留出项目（E4，无此风险）与信息盲复跑支撑。
2. **单模型**：全部评审运行使用同一模型。规则集增益、错判率、采样方差均未做跨模型稳健性检验——结论表述限定于该模型。
3. **小样本**：对照设计组内 n=2~3；85 条复核的组间错误率差异明确标注为方向性信号；35 主题分母是"被至少一轮发现"的并集（未知的未知不在分母）。
4. **单一研究者（n=1）**：过程观测的人对象与协同对象结论不可外推至团队；满意度类指标未采。
5. **术语漂移**：AI 长程工作中的翻译型生造词曾三次被读者点名不可解——已全量审查治理（64 处替换）并机制化（每 10 场次复扫），但该现象本身提示 AI 生成文档需要独立的语言质量观测项。
6. **评估即干预**：评估运行本身使用被研究的方法（评审智能体），方法缺陷会同时污染结果与研究对象——靠三层评审结构与人工终审部分缓解，不声称完全消除。

## 8. 展开项：AI 生成代码的缺陷谱系与新型架构设计方法

本章把主张二展开为独立议程（素材：研究者对生产项目 fundseeker 的观察 + 本研究全部实验证据，备忘 notes/10）。它是本研究通向"最终目标——基于大模型特点研究以大模型为核心的新型软件架构及架构设计方法"的桥。

### 8.1 三个基础观察（事实）

1. 生产在用的 AI 辅助开发项目"带着缺陷可用"是常态——评审发现的缺陷未阻断功能达成；
2. AI 代码工作流普遍严格执行自动化单元测试，进入评审前测试全通过；
3. 大模型的低级错误（语法/引用类）发生概率远低于人类；问题质量分布集中在更大尺度：逻辑架构、功能完整性、功能理解偏差、异常边界、并发竞态。

### 8.2 与本研究证据的互证

- 三个 AI 参与开发的项目中，缺陷类型分布以实现偏离与范围缺口（文档-实现缺口）主导，语法级缺陷近乎绝迹——与传统人写代码的评审重心不同；
- 错判成因的组间差异与之呼应：裸模型的硬错集中在"运行时行为臆测/逻辑极性反转"（恰是大尺度类别中的推理难点），带规则组的失真集中在"机制推演糙"（观察对、推演错）；
- 外部文献同向：AI 相关技术债中测试类占比从传统的 2.1% 升至 21%，设计类占 40.7%（GIST 技术债研究）——AI 改变了缺陷与技术债的分布。

### 8.3 研究含义（后续议程）

1. **评审资源配置上移**：低级错误已被"模型低错误率 + 强制单测"双重过滤，评审应系统性投向文档链一致性、架构与契约、边界与并发——这解释了本研究规则集增益的"条件性生效"（通用工程缺陷裸模型即中，领域契约类才有增量），也为"部署前先测裸模型基线、把规则预算投给盲区"的操作建议提供机理。
2. **验证层补全**：单测全通过 ≠ 功能达成（实测存在单测测不出的数据停摆类缺陷）——需要"规约-验证对"式的过程性验证与多轮采样归并（单轮召回 31–46%）作为单测之上的补充层，而非替代。
3. **人与模型的协同分工**：人负责大尺度判断（架构裁定、完整性裁定、跨轮归并终审——错判五类成因的复核清单已给出可操作形态），模型负责覆盖面遍历与多轮采样。该分工在评审场景已被完整实例化（评审工作方法总纲 V1.0），向架构设计场景的推广是下一步：设计文档的"缺陷谱系"（一致性缺口、契约缺口、状态生命周期缺口）是否有同构的单轮采样与归并结构——开放问题。
4. **新型架构的种子**：若缺陷谱系持续上移，"架构设计"的重心将从模块划分转向**规约资产的组织**（什么知识进规则集、什么进文档链、什么进测试断言）与**验证面的构造**（每个资产配什么口径的考题）——即第 0 章三元结构在架构层的投影。本研究的三件工具（规约-验证对模板、文档链一致性规则、类型判定学）是该投影的初步构件。
