> 基于 10 篇 2026 年 6–7 月 arXiv 论文全文分析  
> 目的：识别领域内的实质性争议、方法张力与开放问题  
> 日期：2026-07-12

## 一、GraphRAG 社区发现：k-core vs. Leiden/模块度

### 分歧双方

| 立场 | 代表论文 | 核心论断 |
|------|----------|----------|
| **k-core 更优** | Core-based Hierarchies for Efficient GraphRAG (arXiv:2603.05207v2) | 稀疏知识图上模块度优化存在指数级近似最优划分，Leiden 不稳定、不可复现；k-core 是确定性、线性时间、密度感知的替代方案 |
| **模块度社区是传统路径** | 原始 GraphRAG (Edge et al.) 及大量后续工作 | 模块度聚类能捕捉主题社区，适合全局 sensemaking |

### 分歧本质

- **优化目标不同**：Leiden 追求主题聚类；k-core 追求连接密度与关系 richness。
- **稳定性不同**：Leiden 在稀疏图上退化；k-core 完全确定。
- **可解释性不同**：模块度依赖零模型；k-core 直接对应最小度要求。

### 对本项目的启示

在 API 文档知识图谱、代码依赖图谱上，不能默认选 Leiden。应做 head-to-head ablation，比较：
- 社区稳定性（多次运行一致性）
- 检索/摘要质量（comprehensiveness, diversity）
- token 效率
- 人类开发者对生成结构的认知匹配度

## 二、LLM 是否应保留编排者角色

### 分歧双方

| 立场 | 代表论文 | 核心论断 |
|------|----------|----------|
| **LLM 不应是编排者** | LLM-as-Code (arXiv:2606.15874) | 把确定性控制流交给概率模型是类别错误；token 爆炸、控制流幻觉、不可靠完成都是架构性后果；程序应控制流程，LLM 只作为可调用的自适应组件 |
| **LLM 可保留元决策权** | HORMA (arXiv:2606.11680), VISTA (arXiv:2606.30005), ActPlane (arXiv:2606.25189) | 在可观测状态下，LLM 适合做记忆检索、上下文归档、策略生成等高层决策；关键在于提供正确接口或确定性执行层 |

### 调和思路

这不是非黑即白，而是**分层问题**：
- **必须确定保证的控制流**：循环次数、验证顺序、提交前检查、错误处理 → 写入程序。
- **可交给 LLM 的元决策**：在多个候选文件中选择下一步读取、决定归档哪个上下文块、生成具体策略 DSL → 在可观测、可回滚的接口下由 LLM 执行。

### 对本项目的启示

AI 编程 Agent 的架构应是“程序骨架 + LLM 节点”：
- 骨架保证流程正确；
- LLM 节点负责推理、生成、判断；
- 不允许 LLM 直接改变程序执行路径。

## 三、上下文管理：三种不同范式

### 分歧矩阵

| 论文 | 管理主体 | 核心机制 | 是否训练 | 关键假设 |
|------|----------|----------|----------|----------|
| **TokenMizer** (arXiv:2606.06337) | 系统/代理层 | 类型化知识图谱 + 确定性启发式提取 | 否（默认） | 会话历史是结构化知识工件 |
| **HORMA** (arXiv:2606.11680) | 解耦为两个 Agent | 文件系统式层次记忆 + RL 导航 Agent | 是（检索 Agent） | 记忆构建与检索应分别优化 |
| **VISTA** (arXiv:2606.30005) | Agent 自身 | 本体感知 dashboard + 无损归档/恢复 | 否 | LLM 有潜在管理能力，缺的是状态接口 |

### 具体争议点

1. **记忆构建是否该被学习？**
   - HORMA：应该，通过成功/失败轨迹对比进化记忆管理技能。
   - TokenMizer：默认应确定性、零 LLM 调用，保证成本和可解释性。

2. **上下文该"结构化"还是"可感知"？**
   - TokenMizer：重历史结构（图）。
   - VISTA：重运行时元数据（大小、年龄、访问历史、剩余预算）。

3. **归档是否必须无损？**
   - VISTA：强烈主张无损归档/恢复，并证明在预算压力下必要。
   - TokenMizer：允许图序列化压缩，但保留关键决策转换记录。

### 对本项目的启示

三层能力并不互斥，可融合设计：
- 底层：TokenMizer 式状态图，记录任务/决策/文件/错误/环境；
- 中层：HORMA 式层次记忆，支持导航式检索；
- 表层：VISTA 式 dashboard，让 Agent 感知上下文预算并自主归档。

但需明确默认路径是确定性还是学习式，以及归档是否允许有损。

## 四、视觉模态在代码理解中的角色边界

### 已知共识

- **SeeRepo** (arXiv:2606.14061) 明确：纯视觉输入不足，text + vision 作为补充模态有效。

### 仍存争议

1. **视觉收益的来源**：
   - 是图提供了文本无法表达的结构信息？
   - 还是视觉化减少了无效文本读取，间接降低 token？
   - SeeRepo 未严格区分这两者。

2. **视觉表示标准化**：
   - Graphviz、Mermaid、自定义渲染哪种最友好？
   - SeeRepo 只比较了 graph/nested/tabular 三种布局。

### 对本项目的启示

代码图谱可视化给 Agent 看是可行方向，但需要做更细粒度 ablation：
- 控制 Agent 能访问的文本量，看视觉是否仍有效；
- 比较不同渲染格式对同一模型的影响；
- 测量视觉在探索、定位、修复各阶段的边际收益。

## 五、评测目标分化

### 不同论文的评测焦点

| 论文 | 评测焦点 | 隐含优先级 |
|------|----------|------------|
| **SWE-Explore** (arXiv:2606.07297) | 仓库探索/定位质量 | 行级覆盖与排序效率 |
| **RepoRescue** (arXiv:2607.01213) | 兼容性救援与源级修复 | source-only 真实修复能力、禁止测试 shortcut |
| **TICoder** (arXiv:2606.08135) | 仓库级代码生成 | 测试驱动规划与实现感知复用 |
| **LLM-as-Code** (arXiv:2606.15874) | 长程视觉操作序列稳定性 | 控制流可靠性 |
| **ActPlane** (arXiv:2606.25189) | 策略合规率 | 安全/正确性约束 |

### 分歧

- SWE-Explore 主张把 exploration 从 end-to-end 中拆出来单独测。
- RepoRescue 认为真实场景验证（禁止编辑测试）才能暴露 shortcut 行为。
- LLM-as-Code 关注的上游控制流正确性，尚未被现有 benchmark 覆盖。

### 对本项目的启示

应采用多层评测体系：
1. 上游：控制流正确性（是否执行了规定步骤）；
2. 中游：探索质量（行级覆盖、排序效率）；
3. 下游：patch 正确性（source-only、runtime-blocked、scenario validation）；
4. 横向：策略合规率。

## 六、策略执行分层之争

### 分歧双方

| 立场 | 代表 | 核心观点 |
|------|------|----------|
| **OS/内核级执行** | ActPlane (arXiv:2606.25189) | 工具层拦截会漏掉间接执行路径；安全红线必须在 OS 层用 eBPF/IFC 强制执行 |
| **程序/工作流级保证** | LLM-as-Code (arXiv:2606.15874) | 只要程序控制流程，项目级规则可在工作流中确定保证 |

### 调和思路

两者是互补的不同粒度：
- **项目约定/开发流程规则**：在工作流层执行足够（如改 API 必须同步文档）。
- **安全/资源隔离规则**：必须 OS/容器级执行（如不删除 /data、不泄露 API key）。

### 对本项目的启示

策略执行应分层设计：
- 工作流引擎负责项目级规则；
- OS/容器/eBPF 负责安全红线；
- 两者都需语义化反馈，而不是 opaque denial。

## 七、Agent 是否需要"看见"自己的状态？

### 分歧双方

| 立场 | 代表 | 核心论断 |
|------|------|----------|
| **Agent 必须本体感知** | VISTA (arXiv:2606.30005) | frontier LLM 对自身上下文是盲的，必须外部提供 dashboard 才能做合理归档决策 |
| **Agent 不需要感知，程序已安排好** | LLM-as-Code (arXiv:2606.15874) | 控制流和上下文结构由程序构造，Agent 按调用接收上下文即可 |
| **系统代劳** | TokenMizer, HORMA | 上下文管理由代理层/记忆层负责，Agent 不直接参与 |

### 对本项目的启示

这取决于架构选择：
- Agentic Programming 范式下，上下文由程序构造，Agent 不需要感知；
- VISTA 范式下，Agent 有自我管理权，需要状态接口；
- 两种设计哲学可针对不同类型的 Agent 采用。

## 八、最值得关注的 4 组对立（总结表）

| 对立 | 甲方 | 乙方 | 调和/选择思路 |
|------|------|------|---------------|
| **控制流归属** | 程序完全控制（LLM-as-Code） | LLM 保留元决策权（HORMA/VISTA/ActPlane） | 确定性流程外化，元决策留给 Agent |
| **记忆构建方式** | 确定性图谱（TokenMizer） | RL 进化的层次记忆（HORMA） | 默认确定性，复杂场景引入学习 |
| **社区检测方法** | k-core（Core-based GraphRAG） | Leiden/模块度（传统 GraphRAG） | 在代码/API 图上做 ablation |
| **上下文管理主体** | 系统/代理层（TokenMizer/HORMA） | Agent 自身（VISTA） | 由任务类型决定，关键规则系统强制执行 |

## 九、结合项目既有 references 的分歧评价

将本期 10 篇论文与项目 `references/` 目录中的既有资料（AIOS、CodeGraph、ContextEngineering、KnowledgeEngineering、ontology 等）交叉对照后，可以更清晰地定位各分歧在学术-工业光谱上的位置。

### 9.1 LLM 角色：从工业实践到学术批判的光谱

| 位置 | 来源 | 立场 |
|------|------|------|
| 强确定性端 | **LLM-as-Code** (arXiv:2606.15874) | 程序完全控制控制流，LLM 仅作为可调用的推理组件 |
| 工程折中端 | **Databricks Agent Design Patterns** | 从 Deterministic Chain 开始，真正需要时再升级到 Single-Agent/Multi-Agent |
| 编排增强端 | **Symphony / Harness Engineering** | LLM 可以编排，但每个动作必须通过 CI/Review/Video 等 Agentic Proof of Work 验证 |
| 传统端 | ReAct / AutoGen / OpenHands | LLM 是 orchestrator，负责循环、分支、终止决策 |

**评价**：这不是对错问题，而是**自主性层级**的选择。本项目以代码生成/重构为主，属于高可靠、可重复任务，应优先靠近 LLM-as-Code / Databricks Level 1 的确定性链设计，但在探索阶段可保留 LLM 的局部决策权。

### 9.2 上下文管理：三派与工业三大流派的对应

| 本期论文 | 核心机制 | 工业对应 | 解决的问题 |
|----------|----------|----------|------------|
| **TokenMizer** | 类型化知识图谱 + 决策转换记录 | Anthropic 结构化笔记 / Claude Code NOTES.md | 长程会话中状态/决策历史不丢失 |
| **HORMA** | 文件系统式层次记忆 + RL 导航 | LangGraph checkpoint / Mem0 / Zep | 经验复用与跨会话记忆积累 |
| **VISTA** | 本体感知 dashboard + 无损归档 | Anthropic auto-compact / Cursor auto-context | 单会话内预算压力下的动态 keep/archive |

**评价**：三派分别对应上下文工程的三个层级（状态持久层、记忆组织层、运行时决策层），应融合而非互斥。本项目可采用"TokenMizer 作为真相源 + HORMA 用于历史经验 + VISTA 用于当前窗口管理"的三层架构。

### 9.3 代码理解：四种表示的互补关系

| 表示 | 代表 | 优势场景 | 局限性 |
|------|------|----------|--------|
| **视觉图** | SeeRepo | 快速定位、全局结构感知 | 纯视觉不足，收益来源待验证 |
| **代码中介** | CodeGraph | 精确结构/数值计算 | 需要外部解释器 |
| **统一属性图** | CPG / Agent-BOM | 安全审计、复杂依赖查询 | 构建成本高 |
| **中性文本规范** | Code–Text–Code | 跨语言迁移、语义保持 | 需要校验与损失估计 |

**评价**：未来系统应支持多表示切换。探索/定位阶段用视觉图，复杂依赖查询用 CPG/Agent-BOM，精确计算时生成代码执行，跨模块演化时维护中性规范层。

### 9.4 GraphRAG：稳定性 vs. 主题性的取舍

| 方法 | 代表 | 优势 | 风险 |
|------|------|------|------|
| **k-core** | Core-based GraphRAG | 确定性、线性时间、稀疏图理论保证 | 社区语义可能不如 Leiden 直观 |
| **Leiden/模块度** | Microsoft GraphRAG | 主题聚类直观 | 在稀疏知识图上不稳定、不可复现 |

**评价**：本项目涉及的 API 文档图、代码依赖图通常是稀疏的，且工程落地需要可复现索引，因此应优先尝试 k-core，同时保留与 Leiden 的对比实验。

### 9.5 策略执行：三层互补架构

| 层级 | 代表 | 适用规则 |
|------|------|----------|
| **工具护栏** | 现有 Agent 框架 | 简单、直接的动作拦截 |
| **工作流/程序级** | LLM-as-Code | 项目约定、开发流程规则 |
| **OS 内核级** | ActPlane | 安全红线、资源隔离、跨进程间接路径 |
| **图审计层** | Agent-BOM | 事后追溯、根因分析、影响评估 |

**评价**：本项目应设计"工作流引擎 + OS/容器级 enforcement + Agent-BOM 式审计"的分层策略栈。低风险规则由工作流保证，高风险操作由 OS 层兜底，所有操作写入可审计图。

### 9.6 评测：中间能力 vs. 端到端的融合

| 取向 | 代表 | 价值 |
|------|------|------|
| **中间能力评测** | SWE-Explore, Codebase-Memory | 定位瓶颈、指导模块优化 |
| **端到端真实验证** | RepoRescue, SWE-bench | 验证最终可用性、发现 shortcut |
| **接口层评测** | SWE-agent ACI | 验证人机/工具接口设计 |

**评价**：应采用"分层评测 + 相关性验证"：上游控制流合规、中游探索质量与上下文效率、下游 source-only/runtime-blocked/scenario validation，并用下游任务验证中游指标是否真正预测成功。

### 9.7 分歧总评：光谱而非对错

各分歧可映射到一条"理想确定性 ←→ 工业实用性"光谱：

| 维度 | 学术/理想端 | 工业/实用端 |
|------|-------------|-------------|
| 控制流 | LLM-as-Code | ReAct/AutoGen/Symphony |
| 上下文 | TokenMizer 结构化图 | VISTA Agent 自管理 |
| 代码理解 | CPG/Agent-BOM 统一属性图 | SeeRepo 视觉图辅助 |
| 策略执行 | ActPlane OS 内核 | LLM-as-Code 工作流级 |
| GraphRAG | k-core 确定性拓扑 | Leiden 主题聚类 |
| 评测 | SWE-Explore 分解 | RepoRescue 真实验证 |

**核心启示**：不要简单站队，而要在每一维度上设计一个可配置的分层架构——让确定性规则走确定层，让探索性决策在可观测接口下由 LLM 完成，让评测同时覆盖中间能力和端到端效果。

## 十、结论

这些分歧并不意味着领域混乱，反而说明 Agentic Coding 正在从"一个 ReAct 包打天下"走向**分层、专业化、可组合**的架构。对本项目而言，最有价值的是在这些张力中明确自己的分层策略：

- 哪些控制流必须确定保证？
- 哪些决策可以交给 LLM？
- 上下文默认是结构化还是可感知？
- 知识图谱用哪种拓扑构建？
- 策略在哪一层执行？
- 中间能力指标如何映射到最终成功率？

这些问题没有统一答案，但需要在本项目的设计文档中给出明确选择及理由。
