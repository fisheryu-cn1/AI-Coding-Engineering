## 1. 核心论点链（按推演顺序）

**命题一（可读性不等价与分离点）**：AI 软件工程的重要约束是对人可读性与对 AI 可读性不等价；应在"原始需求→最终代码"流程中设一个分离点——之前的文档面向人的可读/可编辑性优化，之后面向机器可读性优化。

- 学术证据：2606.31725（LLM 与人对混淆代码的理解困难模式**部分对齐但不等价**）；2504.10557（受控混淆测 LLM 理解）。
- 张力证据：2605.13280（LLM 生成代码可读性数值指标与人类基线平价）——**精读精确化**（见 SEforLLM/summaries/15）：总体 win rate 51.3%–64.7% 但 Wilcoxon 效应量仅 r=0.104（N=13,263），且**总分相近的表象下失败模式相反**——人类代码"欠生产"（缺注释 60/风格不一致 58），LLM 代码"过生产"（过度复杂 48/冗余注释 24）+三个 LLM 特有模式（Unknown API/Redundant Variables/Overblanking）；prompt 设计中仅 signature（重要性 0.40）与 constraints/style 显著。**合理解读：训练语料为人类代码，当前模型下"人可读≈分布内可读"成立，但等价只在分数层、不在失败模式层——人/机可读性分离更多是前瞻性主张，当下差距未测得。**
- 实践：spec-driven development 已把分离点产品化（GitHub Spec Kit / AWS Kiro 的 requirements→design→tasks 流；Martin Fowler 批判其规模适用性——多数日常修改小到不值得全流程）。

**命题二（上下文供给 > 修改规模控制）**：AI 使代码生成末端成本大降后，"通过文档为每轮 AI 调用供给高效上下文"对总成本的价值可能超过"控制每轮修改规模"。

- 反方关键证据：**2602.11988（ETH，Gloaguen et al.，被引 35）**——精读核实（见 ContextEngineering/summaries/45）：LLM 生成 context file 使成功率不升反微降（SWE-BENCH −0.5%、CTXBENCH −2%，均不显著），**成本 +20%/+23% 与步数增加显著**；开发者手写文件（DEV）则比 LLM 生成文件平均领先 7%（p=0.038）；失败模式为 agent 忠实执行文档指令**即使与代码库实际状态冲突**（uv 指令 1.6 vs <0.01 次/实例）。
- 命题修正：不是"文档供给上下文→总成本优化"，而是**上下文供给是双刃杠杆——准确/最小/不冲突的上下文正收益，过期/错误文档负收益（curation > provision）**。
- 规模控制的去向：不是消失而是**转移**——从"代码演进历史管理"转移到"人审接口管理"（GitHub 巨型 AI PR 切栈、PR 尺度 3.5× 后缺陷漏检上升、2601.17581 agent 修改模式实证）。**16 号精读注记**：24,014 个 Agentic PR vs 5,081 个人类 PR 的实测显示 agent PR 的差异**主要在变更结构而非行数规模**（commits 数大效应 Cliff's δ=0.54、files/deletions 中效应、additions 仅小效应；且描述-diff 语义对齐略优于人类 CodeBERT 0.9356 vs 0.9285）——即"碎片化"而非"巨型化"才是 agent PR 的结构特征，规模控制的对象应进一步精确为**提交粒度**而非 diff 行数。

**命题三（重构经济学反转，第一版）**：代码生成成本大降后，"为避免彻底重构而引入复杂设计"可能不再成本最优——复杂设计破坏 AI 可理解性，完全重构反而更便宜。

- 第一轮判定：**证据最弱**。支持侧仅 legacy modernization 叙事；反方三层（工程主流坚持渐进+质量门；AI 代码自身成为新债——Cursor 复杂度 +40.7%/304K 提交审计；验证成本未同比例下降）。

**命题三（修正版，第二轮）**：若存在合理的人机分离点，使分离点**之后**的环节机器执行可靠性高**且存在自动化验证**，则重构（重新生成）成本低于迭代+复杂设计即可成立。极端锚点：分离点=经过严格验证的伪代码，此后生成与审核均自动化且远优于人类。研究方向=从此极端点探索**把分离点往上游推**（依赖更好模型/程序化工具，或在现有工具上重构方法论）。

- 修正版的本质：**重构经济学的可行域 = 自动验证的覆盖域**。"分离点上游推"在形式化方法中的严格形式 = correctness by construction / refinement 阶梯（B 方法/Event-B 学派 40 年）。
- 已有研究三层（详见 §3）：refinement 阶梯（Event-B Agent 已做"需求分配到各 refinement 层级"的自动化决策——即分离点上游推的论文级实现）；LLM 闭环验证（Clover 验证 docstring/代码/形式注解三态一致性=验证文档层）；spec-as-source 工程化（Tessl 代码盖 GENERATED 章可再生；其自认"stable regeneration is hard"是重构经济学的最后一公里）。

## 2. 三个研究空位（两轮讨论的产出）

1. **分离点位置的经济学建模**：所有已有工作各自固定了一个分离点（Event-B Agent=形式规格、Clover=契约注解、Tessl=自然语言 spec），无人把"分离点位置"本身作为研究变量——每上推一层，收益是更深代码层变为可再生派生物，成本是该层验证语义密度要求上升+人审负担全部上移到 spec 层（2602.11988 的教训在规格层会重现）。最优点在哪、随模型能力如何移动，**可实验化，且与新项目首选实验方向（E 实测+任务结构化调度）严丝合缝：分离点=调度边界=E 的人机接口**。
2. **验证语义谱系中间档空白**：Event-B Agent 只覆盖最重档（全 refinement），Tessl 只覆盖最轻档（自然语言+测试），property-based testing→契约→部分形式化→全 refinement 之间的成本-覆盖曲线无人画过。
3. **稳定再生的等价性验证**：经典 regression verification（程序等价性证明、CEGAR）与 2026-08 刚出现的 2608.09919（基础模型 oracle 检测重构行为变化）是两条现成线，无人接入 spec-as-source 再生成循环作为收敛机制——工具依赖路径上的低成本组合创新。

入场姿势建议：避开"又一个闭环"（Clover/Event-B Agent/DafnyBench 一线已拥挤），主攻空位 1（与既有实验设计衔接）或空位 3（现成线组合）。

## 3. 已有研究地图（三层）

- **Refinement 阶梯（分离点上游推的严格形式）**：B 方法/Event-B（correctness by construction）；**Event-B Agent（FSE 2026，2605.17475）**——NL 需求→LLM 规划 refinement 策略（需求分配到各层级）→模型检查+定理证明反馈闭环；Refine4LLM（TOSEM 2025，DOI 10.1145/3704905，被引 57）——验证反馈引导 LLM 代码精化；Ferrari et al. 2025（Formal RE×LLM 路线图，被引 71）——上游推到需求层的学科级规划。
- **LLM 闭环验证（"严格验证的伪代码"锚点）**：**Clover（CAV 2024，2310.17807，被引 130+）**——正确性检查降维为人可读 docstring/代码/形式注解三态一致性检查（Dafny）；2601.12845（LLM+测试 oracle 自动生成 Dafny 验证注解）；2604.10392（Intent-aligned Formal Spec Synthesis via Traceable Refinement——标题即暴露真难题：规格是否对齐意图）；DafnyBench 等。
- **Spec-as-source（重构经济学产品化）**：**2602.00180**（学术正式化：spec 是人唯一直接编辑的工件、代码完全从 spec 生成）；Tessl（`// GENERATED` 可再生代码）；InfoQ/Augment 等业界叙事；Tessl 自认 stable regeneration is hard。

## 4. 风险与边界条件

- **意图对齐是真正的墙**：LLM 把"写形式规格"成本打下来，但"验证规格正确表达人的意图"仍开放（2604.10392 核心难题）；分离点越上游，单点人审杠杆与单点错误代价同增。
- **规模适用性**：Fowler 对 SDD 的批判同样适用——多数日常修改不值得全流程；分离点上游推可能只在"高变更密度/长寿命"子系统回本，经济学建模必须计入任务分布。
- **与本项已有框架的关系**：该方向本质是"验证边界最大化"研究，落在三元结构"规约×验证"边上；它是命题三的严格化而非复活。**等价关系本身（重构经济学可行域=自动验证覆盖域）值得作为新项目一节的命题。**
- Naur《Programming as Theory Building》（1985）思想线：Naur 明确反对"spec 盲译成代码"——恰是 LLM 使能的工作流；理论与 spec-as-source 之间有真张力，精读时需对照（原文公开 PDF：pages.cs.wisc.edu/~remzi/Naur.pdf）。

## 8. 第三轮扩展（2026-08-26）：需求→代码可靠性的判定基础

> 当日讨论链：LSP×主流 agent → Qoder/CodeBuddy/Trae 纳入（trae-agent 入库）→ 五级建模是否保证 AI 上下文 → 需求完整性确定性检查三件套 → SAT/SMT 开源栈 → SAT×OWL 关联 → LLM+OWL+HermiT 循环精化 → 信息论统一。核心产出：**分离点的信息论定义（§8.4）**。

### 8.1 协作范式与反馈通道补充（含一个重大结论修正）

- **LSP×agent 三形态**：①诊断回流型（最普遍：Cline 只喂新增错误+3.5s 等待、VS Code Copilot agent mode、Cursor IDE 版）；②工具化消费型（OpenCode 一等 LSP 工具、Copilot CLI 官方 LSP、VS find_symbol）；③中间件型（agent-lsp/lsp-mcp）。反例：Zed（LSP 最重的编辑器，agent 却不消费诊断， issue #58535）、CC/Aider 零 LSP（确定性验证放 test 层——与 Cherny 弃 RAG 立场同族）。中国阵营补齐：CodeBuddy 插件体系 LSP 即时诊断、Qoder NEXT 模型 Error Refactoring（模型层消费 LSP 错误）、Trae 官方薄弱靠社区 mcp-diagnostics-trae 补。
- **三家纳入**（设计轴）：Qoder=Quest Mode 自动生成 Spec+Repo Wiki 持续同步（spec-first/黑板思想产品化又一证）；CodeBuddy=Craft 计划驱动+2.0 CLI 驱动向 CC 靠拢+文档化上下文管理+InfoQ 99.9% 吃狗粮实验；Trae=SOLO 双 agent（Builder 0→1/Coder 1→100 可调子代理防上下文污染）。谱系：业界实际三条路——CC 极简单循环｜大厂结构化流水线（文档中间产物，比 CC 更近 MetaGPT 但组织形态换壳）｜**Trae ensemble 第三条路（不分工而采样，靠归并出质量）**，Trae 唯一双脚踩两条路线。
- **【重大修正】"重复采样全线缺位"已被推翻**：字节 trae-agent（论文 arXiv 2507.23370 已入库 `references/AgentParadigms/31` 并精读）实现首个 agent 化 ensemble——coder agent 高温 N 次独立采样（Mixture 轮换三 LLM）→分层剪枝（unidiff 规范化去重+回归测试）→selector agent 类人程序理解（静态+动态）并行多数票。SWE-bench Verified **75.20% 第一**（2025-07）、超 prompting 式基线 5.83–14.60%、N=1→10 持续提升（基线退化）、剪枝组件可移植（+3.91%/+4.72%）。**总纲差异化空间从"无人做"移向归并机制（结构化归并 vs 投票）与剪枝语义**。精读要点：剪枝"宁留错杀少"（FN 仅 3.69%/FP 33.04%，全败保守保留全集）；N 扩展失败归因=上下限发散+上下文稀释，分层剪枝同时治两者（ensemble space 缩 27.8–39.2%，与 Pass@1 强负相关 Spearman 0.80–1.00）；selector 动态验证=生成执行单测看各 patch 行为（与 FM05 构成"执行行为作为选择证据"两种实现）。

### 8.2 需求完整性的确定性检查：三件套与工具栈（验证语义谱系"模型检测档"的确立）

- **三件套皆有可判定解**：①规则矛盾→SAT/SMT（UNSAT+unsat core 定位冲突；SAT 的模型=具体冲突场景反例）；②数据引用完整→类型检查/依赖图/Datalog（多项式）；③流程完整性→WF-net soundness 三性质（van der Aalst：可完成/正常终止/无死任务，BPMN→Petri 网标准映射）。前移价值：**在代码存在之前即可执行验证**——模型检测的"模型"是需求模型而非代码。
- **开源栈**：SMT 双雄 Z3（MIT，`pip install z3-solver`）/cvc5（Apache-2.0，Yices2 注意 GPLv3）；SAT：Kissat/CaDiCaL/MiniSat/PySAT；规则原生范式：Clingo（ASP，answer set=冲突场景）/Soufflé（Datalog）；流程：LoLA 2/WoPeD/ProM；综合反例：Alloy Analyzer（MIT）。全部 SMT-LIB 互换，零锁定。
- **SAT×OWL 关联三层**：理论同源（OWL=SROIQ 描述逻辑，命题 SAT 是 ALC 可满足性特例=DL 内含 SAT 核）；算法同族（tableau 与 DPLL 同源）；工程归约（Konclude 显式 DL→SAT；OWL 2 RL→Datalog：Jena/RDFox/Nemo；EL→ELK）。profile（EL/QL/RL）设计意图=把 DL 压到 SAT/DB/Datalog 三类基础设施引擎区间。
- **LLM+人工澄清→OWL→HermiT 循环精化方案**（与 FM02/FM04 同构，FM03 数字支撑方向可行）：**"完整"拆三层**——一致性（HermiT 判定、循环单调收敛）／结构完备（**OWA 盲区**：开放世界对缺失沉默，需 closed-world 手段——disjointness+nominals 或转 RL→Datalog）／语义完备（不可判定，对策=**预期实例测试**：假想业务场景过 realization，推不出=约束不足，推出反预期=过强——对抗"空泛一致"的核心武器，KAOS obstacle/Alloy 反例同思想）。循环内两个人工环节风险：**翻译审计点必须前移**（HermiT 查 OWL 自洽不查"OWL 说了 NL 想说的"，漏译/弱译下游不可见——意图对齐之墙）；**AI 懒惰修复**（削公理消矛盾，同 Cline cast-to-Any）——对策：justification（OWL 界 unsat core）直达人工、修改方向限定"澄清意图"。
- **OWL 不能直接驱动代码生成**：结构/术语（是什么）vs 行为（做什么：状态迁移/前置后置/流程）结构性错配+无数值。正确形态：**三元输入**（OWL 结构+BPMN/契约行为+测试验证锚）或 **context+oracle 双角色**（OWL 作高保真领域上下文喂 LLM+RL 规则编译为输出校验器）；FM01 Clover 三态一致性是"多工件互检"样板。

### 8.3 五级建模的边界（IBM EA 方法→AI 上下文充足性）

- **不能"保证"**——四处断裂：①本体不完备（模型是业务 lossy 快照，隐性知识/例外路径不可全捕获，Naur：理论在人脑不在文档）；②充足性是**调度问题非存量问题**（2602.11988 实证：量大了超窗/稀释/过期指令仍被忠实执行；五级模型数千节点"完整注入"恰造三害——全库≠工作集，E≪W）；③粒度错配（L5=人的操作粒度≠软件行为规格粒度，隔意图对齐最后一公里）；④无 enforcement 必腐烂（advisory vs enforced，EA 三十年教训+AI 加速漂移）。
- 三命题替代："保证"→①上界命题（建模提高初始质量与分解稳定性，真实价值）；②调度命题（任务时刻充足性取决于 L3–L5 切片到工作集的调度机制——实验对象）；③正确性命题（取决于 L5→行为规格翻译+可机检 enforcement）。
- 判断：本质是**用 LLM 重演 Big Design Up Front 赌注**——上游完全规格化假设未被 LLM 改变（LLM 只降下游翻译成本）；Simulink 先例成立的真正前提=模型级验证+认证生成（8.2 三件套正是补该缺口的可行路径）。
- 可实验化：同粒度任务下注入 L4 切片 vs 全模型 vs 无模型对照（复用 2602.11988 协议）。

### 8.4 信息论统一（本轮核心理论产出）

- **文档链信息操作分解**：每步=保持+决策注入（消除未决=新增信息）+丢弃；H(代码)=H(需求)+H(决策集 Z)−H(丢弃)。信息从不守恒；"信息一致+纯呈现转换"的严格含义=存在规范逆（refinement 的 abstraction 单射）。
- **Z 分解**：Z=Z_伪（被共识知识唯一确定：框架语义全集、"jpeg"→ISO 10918+行业默认参数——激活公共知识不注新信息）∪ Z_真（连上下文加尽仍留自由度）。**确定性条件：Z_真=∅ 且丢弃与可观察行为无关**——信息完整不要求信息量大，只要求**决策闭合**。
- **分离点的信息论定义：Z_真 开始为空的最早链上位置**。统一解释既有证据：MetaGPT 流水线失败=在 Z_真 非空处强行自动化（伪确定性）；CC 单循环+人审=承认 Z_真 弥散、交互逐个消解；Event-B/Simulink 成功=受限域先清零 Z_真 再自动化；Trae ensemble=Z_真 残存时采样+归并买保险。
- **可判定三层阶梯**：绝对层（Kolmogorov K(Y|X) 不可计算，NCD 压缩近似）；形式层（蕴含+解空间单点性——Event-B proof obligation 为工程最成熟实现）；**统计层（可计算近似，最有操作价值）**：同一上游 N 次独立生成下游×语义等价类计数=Z_真 规模度量。现成成果：语义熵（Farquhar et al., Nature 630, 2024-06，幻觉检测）、self-consistency/pass^k（库内 23/19 号）、**Trae Agent patch 去重=解空间等价类计数的现成实现**（31 号，用于剪枝；反向用于诊断即是需求信息缺口检测器）。
- **丢弃集不可逆（DPI）**：即使 Z_真=∅，动机/叙事不出现在代码——"完整"只能对**约定投影**（可观察行为/需求谓词）判定→外部 oracle 不可消除→三元结构"规约×验证"在信息论侧再出现。
- **E 实验扩展方向**：沿真实项目文档链各阶段边界做分歧度采样（同上游产物×N 独立生成×语义等价类计数），画 **Z_真 沿链分布曲线**——归零点=该项目分离点实测位置，随模型能力可复测；全部实现件在 31 号论文中现成。

### 8.5 产品空位

- 行业最成熟形态=需求追溯矩阵（DOORS/Jama/Sparx，DO-178 强制）——只查**链接存在性**（拓扑代理），不查语义蕴含（信息代理）。
- **无产品把"分歧度=信息缺口度量"做成需求签收门禁**——SDD 工具（Kiro/Spec Kit）的逐层人审是 Z_真 人工消解的制度化，但无量化判定。**该空位与 8.4 的 E 实验共享全部实现件。**

## 9. 第四轮扩展（2026-08-26 下午）：中间表示选型与转换质量检验机制

> 当日讨论链：伪代码有无行业标准 → BDD×OWL 双通道互检方案 → UML 三角架构。核心产出：**两个可直接进 R1/R3 的机制设计**（BDD 场景作为 OWL 转换的检验用例；UML 作为确定性映射缓冲）。

### 9.1 中间表示的标准地图（"行业标准的伪代码"不存在的原因）

- **结论**：介于业务需求与代码之间无单一伪代码标准——该地带被**分层标准群**占领：业务规则层 SBVR（OMG）、需求条目 EARS（约定）、规格层 **Z（ISO/IEC 13568）**/**VDM-SL（ISO/IEC 13817-1）**/**OCL（ISO/IEC 19507）**、流程层 **BPMN 2.0（ISO/IEC 19510）**、状态机 **SCXML（W3C）**、动作语言 ALF（OMG）、接口层 OpenAPI（事实标准）、并发行为 TLA+/Event-B（事实标准）、性质 PSL（IEEE 1850）、系统工程 SysML。
- **结构性张力**：伪代码的价值在无严格语法，标准的本质是严格语法——PDL（IBM 1975）工业化失败即此；**标准化了的"伪代码"必然分化为各层规格语言，松散部分留作教科书风格约定**（CLRS/LaTeX algorithmic）。唯一真正标准化的伪代码规范出现在教育界（AP CS / Cambridge IGCSE 的考试句式规范）——小共识域内轻量句法可标准化。
- **选型含义**：S3 不自创伪代码方言，按层拼标准件（规则→SBVR/OCL、数据→OCL/Z、流程→BPMN/SCXML），每件自带层内确定性检查器。

### 9.2 机制一：BDD×OWL 双通道互检（预期实例测试的 BDD 化）

- **组合创新定位**：= 预期实例测试（BDD 场景库替代人工临时编场景）+ Clover 三态一致性（NL↔OWL↔BDD 结构同源互检）+ 分歧度度量（双通道不一致率=转换质量信号）的焊接。
- **机制**：Given/Then 编译为 ABox 断言——检验方向一（一致性/过强）：Given+TBox 不一致则公理过强，justification 定位；检验方向二（蕴含/过弱）：Then 作 DL query，推不出则过弱/漏翻。
- **两个语义陷阱**：① **When 动态性**——OWL 无动作语义，Then 须二分标注：状态约束类（进 OWL 蕴含检验）vs 动作效果类（归流程模型/SWRL，否则大量误报）；② **oracle 独立性**——BDD 与 OWL 必须从需求文本**独立双通道**生成（防同源 tautology；Clover 零假阳性的机制基础）。
- **四个增强**：公理覆盖率（未触达公理→定向补场景提示，把补全从盲劳变引导）；负例场景（变异 Given 构造应拒非法状态，对抗空泛一致）；数值断言路由 Z3；裁决协议（justification 直达+修改类型标注，反懒惰红线）。
- **质量指标**：公理覆盖率/交叉一致率/负例排斥率——可接 S5 分歧度门禁；双通道不一致率沿澄清轮次的收敛=Z_真 可计算代理（R4 新观测量）。

### 9.3 机制二：UML 三角架构（把 LLM 从最难翻译步撤出）

- **核心洞察**：NL→OWL 的脆弱翻译拆为两段——**NL→UML（LLM+人审图形）→OWL（确定性映射，无需 LLM）**。OMG **ODM（Ontology Definition Metamodel）**规范正式定义 UML 类模型↔OWL 双向映射；实用管线：LLM 生成 PlantUML/Mermaid（结构化文本生成稳定）→XMI→ODM→OWL。LLM 翻译面从"描述逻辑公理"压缩为"类图/状态机"（Text2UML 可靠度显著高于 Text2OWL），翻译审计点前移为**人审图形**（成本低于人审公理一个量级）。
- **UML 三角色**：①渐进形式化缓冲（NL→UML→OWL 表达力梯度，UML=分离点上"人可读的形式化"现成载体）；②行为层载体（状态机/活动图补 When 陷阱——BDD 场景=状态机测试轨迹，配 SCXML（W3C）/fUML 可自动回放验证）；③双侧可测中枢（BDD 同时测 UML 侧（OCL 快照一致性，USE 类工具）与 OWL 侧（ABox）——四态互检 NL↔UML↔OWL↔BDD）。
- **语义差异风险表**（映射器必须显式标注转换假设）：UML 封闭世界 vs OWA；泛化默认不隐含兄弟不相交（映射默认补 {disjoint} 是常见错误，应为显式决策项）；多重性局部约束 vs 类上限定；关联双向性 vs inverseOf；**映射是"UML 类图子集→OWL"的有损通道**（匿名类/属性链/逆属性等高级构造仍需直接写 OWL/OCL——UML 是引导格式非完整载体）；行为图与 OWL 无对应（走 SCXML/Petri 线，三件套分工不变）。
- **边界判断**：增益集中在结构/静态层与状态层；不解决数值约束（仍 Z3）与跨文档语义一致性（仍裁决协议）——是工程化强化（翻译面收窄+人审降本+行为补全），非语义完备性突破。R4 再增观测量：NL→UML→OWL 与 NL→OWL 直译的**双路径交叉一致率**。

### 9.4 项目落点

- method/13（翻译规范）+method/14（检查套件）草案新增两机制为 S3-S4 衔接的候选实现；R1 案例可直接试 BDD×OWL 双通道（成本最低）；工具选型增补：ODM 兼容链（PlantUML→XMI→OWL）、USE/Dresden OCL（快照检验）、SCXML 引擎（轨迹回放）。

## §10 第五轮扩展：双通道方法的行业先例检索与历史归因（2026-08-28）

> 背景：method/18 完成方法机制的系统表述后，用户提出两项追问——行业是否有类似先例；人工开发时代为何未大规模使用这类检查。四轮联网检索+分析完成，详细报告见 `requirement-to-spec/notes/双通道方法先例检索与历史归因.md`，本节为备忘主线记录。

### 10.1 先例地图（四条线）

1. **UML→OWL**：OMG ODM 标准（2006-2009）+Djurić 2005 奠基+ATL/EA 工具生态——二十年标准史，但主流用法是**本体工程**（UML 建本体服务语义网），作需求验证管线用是边缘形态（本项目重写转换器时已实测其工具链的私有格式断裂）。
2. **SAT/SMT 需求检查**：学术线持续（SMT 配置一致性/有界模型检查场景矛盾），2025-26 出现 **LLM+SMT 检查自然语言需求**的新趋势（arXiv 2506.16639，已入库 07 号）。
3. **BDD×形式化**：三支线（Gherkin→转移系统/Event-B×Cucumber 铁路/UML 化 Gherkin）；**最强邻居=PICKLES（ECMFA 2026，arXiv 2604.26572，已入库 06 号）**——场景↔形式模型双向翻译+master model 做基于模型的测试。与本项目 BDD 分路编排高度同构；差异=我们叠加场景独立性纪律（先例普遍允许模型侧派生）、两维标注路由、需求锚定绑定闭包。
4. **工业采用**：AWS TLA+（Newcombe 2014——设计期模型检查抓 S3/DynamoDB 并发缺陷，"写规格比代码找错便宜"）=**设计文档层形式化检查 ROI 成立的铁证**；航空 DO-178C/铁路 EN 50128 强制。采用分布与单次故障代价高度正相关。

### 10.2 本方法的诚实定位

全部引擎是旧轮子（HermiT/Z3/ODM/BDD 皆成熟多年）；组合层贡献四项：**双通道独立性作为设计约束**（防 tautology）、**需求锚定的三级绑定闭包**（需求↔模型↔层间缺失检查——先例中普遍缺位）、**LLM 只起草不判定的人机红线**、**文档链层间可运维化**（E-V-G 界面/执行队列/活文档治理）。

### 10.3 人工时代未普及的六归因（按重要性）

①**翻译墙成本结构（核心）**——NL→形式化只能专家手工，写规格比写代码更难抽象；引擎等了二十年，等的是便宜的翻译层，LLM 改变的正是翻译成本的数量级而非验证技术本身；②反馈周期错配（天/周 vs 小时）；③需求变更维护税（规格腐化，仅需求冻结领域可持续——R4/R5 待实测，regen 单点证据不足）；④组织错位（形式化被当验收步骤而非设计工具）；⑤锚点基础设施缺失（编号纪律与工具集成管道）；⑥技能门槛（轻量形式化吃掉动机）。

### 10.4 理论呼应

§8 的分离点定义在行业史上得到一个经济侧注脚：**翻译墙的成本决定了分离点的实际位置**——高代价领域能付形式化分离点前推的成本（AWS/铁路），普通软件的分离点被成本压在代码层。LLM 降低翻译成本=允许分离点前推的经济学条件变化——这正是本项目工程化命题（§8.4）的时代性依据。

## §11 第六轮扩展：BDD 生命周期定案——检验、覆盖与测试源三段式（2026-08-29）

> 背景：§9.2 提出 BDD×OWL 双通道机制；第 32-33 场两次实跑（kb-app 首练 / loan-system Run-14，后者 BDD 抓到枚举约束防线缺口并驱动转换器增强）后，用户提出两段递进设计，本节为定案记录。

### 11.1 方案一（保守段）：环节内验证 + 下游专用输入

BDD 在**生成文档的环节内**承担完整性验证（独立场景对账模型与裁决库，发现问题→当前环节完善文档至验证通过）；**不进入** PRD/设计等后续生成环节的上下文；作为**验证计划（测试用例）生成环节的主要输入**。

- **实跑锚点**：loan-system Run-14 即此循环（SC5N 抓缺口→修 puml2owl 增 sh:in→全链回归全绿）；收敛条件=签收门（全过或分歧全有裁决）。

### 11.2 方案二（激进段）：反向覆盖检查 + 纯 BDD 测试源

文档完善后**反向**用文档检查 BDD 完整性（每个需求条目/模型公理至少被一个场景覆盖——§9.2 "公理覆盖率"的机制化，实现为绑定闭包第三族：需求↔场景映射，确定性可查）；确认覆盖完整后，验证计划生成**只输入设计文档的背景描述部分+全部 BDD，不输入详细设计**。

- **依据（oracle 独立性）**：验收测试照需求行为规格写、不照实现写——从详设生成测试将继承详设的假设与盲区，形成详设-实现-测试三层共谋（对照 arXiv 2506.16639 的"输出与检查器同错但一致"失效模式：依赖链每多一份独立即少一层共谋）；
- **先例**：PICKLES（FormalMethodsLLM/06，ECMFA 2026）——测试从场景规格生成、全程不依赖实现，覆盖 30%→100%，证明该路线非妥协而是增益；
- **前提逻辑**：双向闭合（正向验证+反向覆盖）后，BDD 成为需求的**行为完备投影**——详设中对测试有用的行为若无场景覆盖，反向检查已暴露（补场景或判定设计越权），故详设对验收测试的信息增量理论上为零。

### 11.3 三边界（成立条件）

1. 适用域=**验收/系统级（黑盒）测试**：白盒用例（分支/路径覆盖）仍需详设与代码（AST 通道另路）；
2. "背景描述 vs 详细设计"的切分标准需显式定义（按 design.md 章节结构划线：需求上下文/系统定位/约束入背景，内部结构/模块划分/数据细节算详设）；
3. NFR 类测试（性能/压力）在场景库属"统计/实现域"，验证计划需补充输入源（NFR 文档或扩展场景库形态）。

### 11.4 完整闭环与方法定位

```
① BDD 从需求独立生成（保独立性）
② 正向：验证文档 → 完善 → 通过
③ 反向：文档条目/公理 → 场景覆盖检查 → 补场景至完整
④ 验收测试 = 背景描述 + 完整 BDD（不输入详设）
⑤ 白盒测试另路：详设 + 代码（AST 通道）
```

BDD 由"一个检查手段"升格为**行为规格的唯一权威源**：完备性由文档链双向保证，独立性在测试链变现。与 §9.2 原机制的衔接：分路编排（状态约束/动作效果/统计）仍是验证执行层的结构，本节定的是 BDD 的**生命周期位置**。

### 11.5 验证状态（诚实标注）

设计定案、**未经对照实验验证**。已排实验位（R3）：同一对象（loan-system 原交付，有完整实现代码）上对照"验证计划从 PRD 验收标准生成 vs 从背景+BDD 生成"，测量用例场景覆盖率与可测性——实现代码可作检出能力的终审对照。method/19 作业流的正式修订待该实验后进行。
