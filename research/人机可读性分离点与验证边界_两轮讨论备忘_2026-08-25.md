## 1. 核心论点链（按推演顺序）

**命题一（可读性不等价与分离点）**：AI 软件工程的重要约束是对人可读性与对 AI 可读性不等价；应在"原始需求→最终代码"流程中设一个分离点——之前的文档面向人的可读/可编辑性优化，之后面向机器可读性优化。

- 学术证据：2606.31725（LLM 与人对混淆代码的理解困难模式**部分对齐但不等价**）；2504.10557（受控混淆测 LLM 理解）。
- 张力证据：2605.13280（LLM 生成代码可读性数值指标与人类基线平价）——**精读精确化**（见 SEforLLM/summaries/15）：总体 win rate 51.3%–64.7% 但 Wilcoxon 效应量仅 r=0.104（N=13,263），且**总分相近的表象下失败模式相反**——人类代码"欠生产"（缺注释 60/风格不一致 58），LLM 代码"过生产"（过度复杂 48/冗余注释 24）+三个 LLM 特有模式（Unknown API/Redundant Variables/Overblanking）；prompt 设计中仅 signature（重要性 0.40）与 constraints/style 显著。**合理解读：训练语料为人类代码，当前模型下"人可读≈分布内可读"成立，但等价只在分数层、不在失败模式层——人/机可读性分离更多是前瞻性主张，当下差距未测得。**
- 实践：spec-driven development 已把分离点产品化（GitHub Spec Kit / AWS Kiro 的 requirements→design→tasks 流；Martin Fowler 批判其规模适用性——多数日常修改小到不值得全流程）。

**命题二（上下文供给 > 修改规模控制）**：AI 使代码生成末端成本大降后，"通过文档为每轮 AI 调用供给高效上下文"对总成本的价值可能超过"控制每轮修改规模"。

- 反方关键证据：**2602.11988（ETH，Gloaguen et al.，被引 35）**——精读核实（见 ContextEngineering/summaries/45）：LLM 生成 context file 使成功率不升反微降（SWE-BENCH −0.5%、CTXBENCH −2%，均不显著），**成本 +20%/+23% 与步数增加显著**；开发者手写文件（DEV）则比 LLM 生成文件平均领先 7%（p=0.038）；失败模式为 agent 忠实执行文档指令**即使与代码库实际状态冲突**（uv 指令 1.6 vs <0.01 次/实例）。
- 命题修正：不是"文档供给上下文→总成本优化"，而是**上下文供给是双刃杠杆——准确/最小/不冲突的上下文正收益，过期/错误文档负收益（curation > provision）**。
- 规模控制的去向：不是消失而是**转移**——从"代码演进历史管理"转移到"人审接口管理"（GitHub 巨型 AI PR 切栈、PR 尺度 3.5× 后缺陷漏检上升、2601.17581 agent 修改模式实证）。**16 号精读注记**：24,014 个 Agentic PR vs 5,081 个人类 PR 的实测显示 agent PR 的差异**主要在变更结构而非行数规模**（commits 数大效应 Cliff's δ=0.54、files/deletions 中效应、additions 仅小效应；且描述-diff 语义对齐略优于人类 CodeBERT 0.9356 vs 0.9285）——即"碎片化"而非"巨型化"才是 agent PR 的结构特征，规模控制的对象应进一步精确为**提交粒度**而非 diff 行数。

**命题三（重构经济学反转，第一版）**：代码生成成本大降后，"为避免彻底重构而引入复杂设计"可能不再成本最优——复杂设计破坏 AI 可理解性，完全重构反而更便宜。

- 第一轮判定：**证据最弱**。支持侧仅 legacy modernization 叙事；反方三层（工程主流坚持渐进+质量门；AI 代码自身成为新债——Cursor 复杂度 +40.7%/304K 提交审计；验证成本未同比例下降）。

**命题三（修正版，第二轮）**：若存在合理的人机分离点，使分离点**之后**的环节机器执行可靠性高**且存在自动化验证**，则重构（重新生成）成本低于迭代+复杂设计即可成立。极端锚点：分离点=经过严格验证的伪代码，此后生成与审核均自动化且远优于人类。研究方向=从此极端点探索**把分离点往上游推**（依赖更好模型/程序化工具，或在现有工具上重构方法论）。

- 修正版的本质：**重构经济学的可行域 = 自动验证的覆盖域**。"分离点上游推"在形式化方法中的严格形式 = correctness by construction / refinement 阶梯（B 方法/Event-B 学派 40 年）。
- 已有研究三层（详见 §3）：refinement 阶梯（Event-B Agent 已做"需求分配到各 refinement 层级"的自动化决策——即分离点上游推的论文级实现）；LLM 闭环验证（Clover 验证 docstring/代码/形式注解三态一致性=验证文档层）；spec-as-source 工程化（Tessl 代码盖 GENERATED 章可再生；其自认"stable regeneration is hard"是重构经济学的最后一公里）。

## 2. 三个研究空位（两轮讨论的产出）

1. **分离点位置的经济学建模**：所有已有工作各自固定了一个分离点（Event-B Agent=形式规格、Clover=契约注解、Tessl=自然语言 spec），无人把"分离点位置"本身作为研究变量——每上推一层，收益是更深代码层变为可再生派生物，成本是该层验证语义密度要求上升+人审负担全部上移到 spec 层（2602.11988 的教训在规格层会重现）。最优点在哪、随模型能力如何移动，**可实验化，且与新项目首选实验方向（E 实测+任务结构化调度）严丝合缝：分离点=调度边界=E 的人机接口**。
2. **验证语义谱系中间档空白**：Event-B Agent 只覆盖最重档（全 refinement），Tessl 只覆盖最轻档（自然语言+测试），property-based testing→契约→部分形式化→全 refinement 之间的成本-覆盖曲线无人画过。
3. **稳定再生的等价性验证**：经典 regression verification（程序等价性证明、CEGAR）与 2026-08 刚出现的 2608.09919（基础模型 oracle 检测重构行为变化）是两条现成线，无人接入 spec-as-source 再生成循环作为收敛机制——工具依赖路径上的低成本组合创新。

入场姿势建议：避开"又一个闭环"（Clover/Event-B Agent/DafnyBench 一线已拥挤），主攻空位 1（与既有实验设计衔接）或空位 3（现成线组合）。

## 3. 已有研究地图（三层）

- **Refinement 阶梯（分离点上游推的严格形式）**：B 方法/Event-B（correctness by construction）；**Event-B Agent（FSE 2026，2605.17475）**——NL 需求→LLM 规划 refinement 策略（需求分配到各层级）→模型检查+定理证明反馈闭环；Refine4LLM（TOSEM 2025，DOI 10.1145/3704905，被引 57）——验证反馈引导 LLM 代码精化；Ferrari et al. 2025（Formal RE×LLM 路线图，被引 71）——上游推到需求层的学科级规划。
- **LLM 闭环验证（"严格验证的伪代码"锚点）**：**Clover（CAV 2024，2310.17807，被引 130+）**——正确性检查降维为人可读 docstring/代码/形式注解三态一致性检查（Dafny）；2601.12845（LLM+测试 oracle 自动生成 Dafny 验证注解）；2604.10392（Intent-aligned Formal Spec Synthesis via Traceable Refinement——标题即暴露真难题：规格是否对齐意图）；DafnyBench 等。
- **Spec-as-source（重构经济学产品化）**：**2602.00180**（学术正式化：spec 是人唯一直接编辑的工件、代码完全从 spec 生成）；Tessl（`// GENERATED` 可再生代码）；InfoQ/Augment 等业界叙事；Tessl 自认 stable regeneration is hard。

## 4. 风险与边界条件

- **意图对齐是真正的墙**：LLM 把"写形式规格"成本打下来，但"验证规格正确表达人的意图"仍开放（2604.10392 核心难题）；分离点越上游，单点人审杠杆与单点错误代价同增。
- **规模适用性**：Fowler 对 SDD 的批判同样适用——多数日常修改不值得全流程；分离点上游推可能只在"高变更密度/长寿命"子系统回本，经济学建模必须计入任务分布。
- **与本项已有框架的关系**：该方向本质是"验证边界最大化"研究，落在三元结构"规约×验证"边上；它是命题三的严格化而非复活。**等价关系本身（重构经济学可行域=自动验证覆盖域）值得作为新项目一节的命题。**
- Naur《Programming as Theory Building》（1985）思想线：Naur 明确反对"spec 盲译成代码"——恰是 LLM 使能的工作流；理论与 spec-as-source 之间有真张力，精读时需对照（原文公开 PDF：pages.cs.wisc.edu/~remzi/Naur.pdf）。
