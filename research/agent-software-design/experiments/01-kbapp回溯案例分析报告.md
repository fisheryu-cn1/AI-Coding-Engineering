## 1. 案例与方法

kb-app（GraphIt-KB）是本仓库内一条**完整的"需求→设计→实现→评审"文档链**（17 份文档、6 个里程碑、5 轮代码评审 + 1 轮设计评审，2026-08-11 至 08-16），且实现与文档高度可能由 AI 辅助完成——因此它同时是"LLM 核心软件的设计过程"与"AI 辅助开发过程"的双料样本。本报告回放该链条，检验方向二理论框架的解释力，并为中间产物模板集 v0（见 `02-中间产物模板集v0.md`）提供实证输入。

## 2. 文档链全景与四个方法学模式

链上角色：01 需求 → 02 选型决策（D1–D13）→ 03 概要设计 → 04 交互设计 → 05 详细设计 → 06 数据规范 → 07 设计评审 →（M1）→ 09/10 M2 补充设计+代码评审 → 11/12 M3 → 13/14 M4 → 15/16/17 M5M6（设计+开发计划+评审终审）。提取稿识别出四个可复用模式：

1. **权威转移而非覆盖**：每份补充设计声明"本里程碑以本文档为准"并附**回写清单**（09 §14、11 §12、13 §8、15 §9），上游文档以加注/改写同步——形成权威链。需求演化（FR-3.1/FR-5.1a 的 MVP 裁决括注回写 01）正是靠该机制实现，**直接回应了 Liu 综述 §4.1.4"无需求演化支持"的挑战**。
2. **评审三层结构**：评审→修复记录→独立复核（file:line 取证 + 实机复现）；17 号更进一步出现"复核推翻评审结论"（v1 通过 → 复核发现 R-1~R-9 → 终审通过）。
3. **DoD 即契约**：每里程碑的完成定义被下游评审逐项核查（登记 vs 实测双列），未执行项阻塞关闭（14 P0-1）。
4. **回写核验闭环**：13/15 的回写清单在 14 §6/17 §6 被逐行核对并附行号证据。

## 3. 透镜一：两维范式框架定位

kb-app 在"控制流归属 × 状态管理"两维上的定位清晰：

| 维度 | kb-app 的选择 | 证据 |
|---|---|---|
| 控制流 | **开发者显式编排（workflow 形态）**：五段流水线为确定性管道，LLM 仅在分类仲裁、摘要、实体抽取三个节点内决策；MCP 服务是工具集而非自主循环；自动收集配人在回路（Inbox 审核） | 03 §1/§4；01 §4.1；FR-6.3 |
| 状态 | **全外部化**：SQLite（files/tasks）+ LadybugDB（图）+ FTS 索引三存储承载全部状态；任务表 + 幂等重放达最终一致；软删除墓碑保留历史 | 03 §6.2；09 §2 |

**对框架的印证与细化**：该定位与任务画像匹配（数据密集、流程确定、错误成本中低、单用户本地）——支持"架构复杂度与任务匹配"原则与"显式编排回归"趋势（工业对比材料 C.1）。**细化点**：kb-app 展示了 workflow 形态内部的一个子型——**"流水线节点内的受限 LLM 决策 + 节点间零 LLM 衔接"**（任务分派全靠 tasks 表 kind 枚举与串行 runner，15 §4.1 刻意"不新增 kind、无 DDL 变更"）——这可补充进两维框架的"控制流"轴作为刻度（LLM 决策密度：节点内 / 衔接处 / 全局）。

## 4. 透镜二：中间产物命题检验

命题（notes/02 §4）：中间产物以"可机检 + 可验证"承担传统"代码+评审"的正确性职能。

**支持证据（命题成立的部分）**：
- **可机检机制真实承担了正确性职能**：`SUMMARY_MANIFEST_MISMATCH` 实现"摘要↔台账↔源文件三方机检"（06 §4.4 → 09 §5 → 10 P1-2 修复落地）；15 个跨文档一致性锚点（提取稿统计 B）从 FR 一路追到测试断言（如 entity_id 消歧：15 D15-13 → 03/05 回写 → 16 Task 9 `test_norm_collides`）；契约测试集（15 §3.3）、`test_no_removed_edges` 断言被砍边不存在——**产物规范直接变成可执行断言**。
- **DoD 核查阻塞了带病关闭**：14 P0-1（三项实机验收未执行）使 M4 不能关闭；12 的 DoD-7 执行揪出 D-1~D-5 五个 P0（80/203 篇 PDF 零 chunk 等）。

**边界证据（命题需要修正/补充的部分）**：
- **登记 ≠ 执行**：评审主题 Top2"验收与登记真实性"约 13 项——DoD 未执行、milestone-log 失真、留档空心、v1 评审对未实测功能虚报"正常"（17 R-11）。**可机检机制本身可以被虚报绕过**——"外置门禁的门禁"只能靠观测层兜底：评审人亲测、环境对照实验（14 复核的双 Python/SQLite 版本）、浏览器截图留档。这为 D3 提供了最直接的动机证据：[D2+D3] **产物验证体系必须配套过程观测（执行真实性观测），否则正确性职能名存实亡**。
- **验证不是免费的**：拦截 13 项生命周期缺陷 + 11 项契约一致性缺陷，代价是三层评审 + 复核推翻 + 终审的人力/时间成本——印证 MAST 干预结论"战术修补不够，须结构级设计"，同时提示**验证深度应按错误成本分级**（kb-app 的 P0~P3 分级是良好实践）。

**与 MAST 的映射**：评审主题 Top1"生命周期/状态机闭环"（13 项）在 MAST 中无对应失败类——它既非规范缺失（设计有定义）也非验证缺位（评审发现了），而是**"设计定义 → 实现落库"之间的工程性漂移**（墓碑清空属性、MERGE 键坍缩）。这提示 MAST 分类在"单 agent + workflow"场景下的盲区，也构成**新的缺陷类候选：状态生命周期缺陷**（可并入 D2-S3 模板集的机检规则）。

## 5. 透镜三：需求多视角一致性检验（01 号文档手工执行）

按 notes/03 的方法对 01 做四视角检验（场景 S1–S6 / 术语表 / 功能点 FR+NFR / 验收标准）：

**先说结论：01 是一份较强的需求产物**——多视角基本齐备（场景故事、数据字典雏形、33 条 FR、8 条 NFR、7 条验收），且每条需求带溯源引用（FR-1.5 引 manifest 字段规范、FR-1.8 引 05 §2.6、FR-2.7 引外部笔记），为下游供给了高质量上下文。**但手工检验仍发现 5 类真实不一致/缺口**（全部为一阶可机检规则的反例）：

| # | 类型 | 实例 | 对应规则（模板集 v0） |
|---|---|---|---|
| 1 | 颗粒度错位 | 术语表定义 Chunk 为检索单位，FR-5.3 承诺"最小定位单位为章节"——FTS 实际命中单位是 chunk，需 chunk→section 归属弥合（05 §2.1 fts_chunks + 11 §2.2 聚合） | R1 颗粒度一致 |
| 2 | 名词漂移 | 术语"锚点"= 文件路径+章节+页码；FR-3.5 说"文档 ID + 章节路径 + 页码"——路径 vs ID 两种指称未裁决 | R2 名词单源 |
| 3 | 清单不一致 | §1.1 称"六大主题"，FR-1.2 列出 10 个目录（混列 references 与 research 两套体系）——会漂移的清单硬编码在两处 | R3 参照物单源 |
| 4 | NFR 无验收映射 | NFR-4（性能数字）与 NFR-7（可观测）在 §7 验收标准中无对应项（性能直到 12 号 DoD-8 才被实测） | R5 NFR↔验收覆盖 |
| 5 | FR 无场景反向覆盖 | FR-1.6（原文跳转）、FR-4.6（维护）、FR-6.6/6.7（评分配置）无对应场景故事——属可接受的功能性缺口，但应显式标注"无场景（配置/运维类）" | R4 双向覆盖矩阵 |

**关键观察**：这 5 类问题没有任何一类被 07 号设计评审的"覆盖核查清单"拦截（07 核查的是 FR→05 落点，即"设计是否覆盖需求"，而非"需求内部是否一致"）——**印证 notes/03 的判断：完整性/一致性检验在现流程中无内建机制，完全依赖下游人工评审的偶然注意力**。同时，07 自己发现了 17 项"设计层覆盖缺口"，说明"产物间"覆盖有核查制度而"产物内"一致性没有——这正是模板集 v0 要补的空位。

## 6. 透镜四：两因素模型视角（上下文构建复盘）

把文档链视为"为下游实现者（含 agentic workers）供给因素 2 上下文"的工程：

**优秀实践（可入装配流程模板）**：
- **溯源引用网**：01/02 的每条需求/决策带来源（外部文档+章节），02 的 D-x 含"备选/拒绝理由/风险对策"成对结构——下游可独立校验决策而不必信任结论；
- **16 号开发计划的上下文构造**：每任务带 file:line 锚点 + Interfaces（Produces/Consumes）显式声明依赖方向 + Global Constraints（DDL 冻结、依赖禁入）——是"给 agentic worker 的单窗口上下文"的范本；
- **DoD 可执行化**：验收条件写成可执行项（`--help` 逐字一致、success@10 口径精确定义），使验收成为上下文的一部分。

**因素 2 失败实例（印证"外围校验层"必要性）**：
- **上下文未被消费**："设计有、代码无"静默缺失 10 项（stale 检测、MISMATCH 不报）——上游上下文存在但实现跳过，且 milestone-log 未登记；
- **上下文内部不一致**：09 §9 重试语义文本自相矛盾（1s→2s→4s vs …8s）、03 §3.2 图 Schema 三处自相矛盾（07 S3）；
- **变更未回写**：PDF 三级判定塌缩为两级未登记（10 P1-3）、依赖变更未回写（P3-7）；
- **LLM 调用的输入构造缺陷**（流水线节点的因素 2 工程）：F-1 api_key 未传、F-2 抽取输入无上界（150KB 致空响应）、F-3 max_tokens 被 think 吃光——且这些**只有"真实 LLM 端到端验收"才暴露**（17 §5；复核人总结："真实 LLM 验收覆盖不到、单测又各自自证"）——这是 self-conditioning/门禁命题在工程层的直接实证。

## 7. 发现汇总

**对方向二命题的支持**：
1. 中间产物的"可机检+可验证"确实承担了正确性职能（三方机检、锚点链、DoD 阻塞）——命题成立；
2. "权威转移 + 回写核验"是需求/设计演化的可行机制（回应 Liu §4.1.4）；
3. 溯源引用 + Produces/Consumes + DoD 可执行化构成"面向 AI 实现者的上下文构造"实践集，可直接进 D1-S3 装配流程模板。

**对命题的修正/补充**：
1. **登记≠执行**：可机检机制可被虚报绕过，产物验证必须配套执行真实性观测（[D2+D3] → D3-S1/S4 的观测点设计输入）；
2. **产物内一致性无内建机制**（§5 五类实例）——模板集 v0 应把一致性规则做进产物模板而非依赖评审注意力；
3. **状态生命周期缺陷**是 MAST 之外的稳定缺陷类（13 项），应有机检规则（墓碑过滤/属性保留/键序）；
4. 两维框架可增加"LLM 决策密度"刻度（节点内/衔接处/全局）。
