> 状态：讨论中。v0.2（2026-08-17）回填工业框架实证（台账 #5，见 3.4 节）与经典 SE 对照（台账 #6，见第 4 节），台账调研线全部完成。

## 1. 出发点：核心论点的精确化

动机讨论确立的论点：**Agent 系统中一部分决策逻辑不再以形式符号化代码表达，代码退居为人类/外部系统与 LLM 之间的衔接层。**

学术梳理为该论点提供了三个支撑点：

1. **"衔接层"有实证对应物**：SWE-bench 的演进证明"一次性生成"在真实 SE 任务上完全失效，agentic 循环（定位—编辑—运行测试—迭代）是必要条件——循环控制、状态持久化、工具适配这些"衔接代码"正是围绕 LLM 决策构建的工程实体，而非附属品。
2. **非形式化决策的失败有结构**：MAST 分类法（v3：专家 GT 150 条轨迹 + LLM judge 扩展至 1642 条）显示多 agent 系统近七成失败源于系统设计问题（FC1, 44.2%）与验证缺位（FC3, 23.5%）——即"非形式化的决策逻辑"若没有显式规约与验证机制兜底，失败是组织性的而非模型能力性的。这直接支持子问题 B 的核心关切：中间产物规范不是文档习惯问题，而是系统正确性的主要来源。
3. **可靠性是独立维度**：pass^k 腰斩现象（τ-bench）与 self-conditioning 效应（长程错误自我强化）表明"单次能力 ≠ 稳定成功"。决策逻辑非形式化的代价必须用工程机制偿还：外部化状态、分段验证、确定性护栏、人类检查点。

## 2. 三层分析框架（文献骨架）

学术梳理给出三个互补的分析层，可作为本方向文献与案例的组织骨架：

| 层 | 代表文献 | 回答的问题 | 对应本子方向 |
|---|---|---|---|
| 组件架构层 | Wang et al. 2308.11432（profile/memory/planning/action 四模块） | 单个 agent 内部由什么构成 | 子问题 A 的"LLM 侧组件清单" |
| 领域任务层 | Liu et al. 2409.02977（SE 任务 × agent 组件矩阵） | 不同任务需要哪些组件组合 | 子问题 A 的"划界依据" |
| 工程过程层 | Hassan et al. 2509.06216（Actors/Processes/Tools/Artifacts 四支柱 + agency/autonomy 两轴自治分级） | agent 系统作为工程产物如何被构建与治理 | 子问题 B 的框架宿主 |

**初步综合**：三个层合起来暗示一个设计顺序——先定自治级别（L2/L3，任务需要 agency 还是 autonomy），再按任务类型选组件组合，最后落实到工件与过程的规范。这与经典 SE 的"需求 → 架构 → 过程"顺序同构，可作为"重走经典过程"的对照映射。

## 3. 子问题 A 的理论框架：范式作为两个正交维度的组合

学术梳理的关键结论：**范式差异本质是"控制流结构 × 状态管理策略"两个正交维度的组合选择**。这正好回答了 00 文档中"分类轴混合"的疑虑——正交化后的框架：

### 3.1 维度一：控制流归属（决策权在哪）

| 控制流形态 | 范式代表 | LLM 的决策职责 | 代码的职责 |
|---|---|---|---|
| 反应式循环 | ReAct | 每步行动选择 | 循环骨架、工具执行、结果回传 |
| 静态计划+执行 | Plan-and-Solve / plan-and-execute | 计划生成 + 节点内执行 | 计划的分步调度与状态跟踪 |
| DAG/并行计划 | LLMCompiler | 计划生成 | 依赖解析、并行派发、重规划触发 |
| 搜索树 | ToT | 分支生成与状态评估 | 搜索策略（BFS/DFS）、剪枝 |
| 固化流程 | workflow 编排（LangGraph 式） | 节点内局部决策 | 全部控制流 |

**"划界"的判别依据（从文献提炼）**：任务分型四问——是否需要外部交互？是否有可验证反馈可重试（→ Reflexion 外循环）？是否组合搜索且中间状态可自评（→ ToT）？可否预先静态分解（→ plan 类，动态环境必须 replan）？

### 3.2 维度二：状态管理（记忆在哪、如何维护）

- 无状态 / 上下文窗口内 → 短任务、无连续性需求
- 外部化状态 + 分段检查点 → 长程任务（self-conditioning 的对抗手段）
- 记忆流 + 加权检索 + 周期反思 → 长时程连续性需求（Generative Agents 消融证据）
- **架构复杂度应与任务的时间跨度与状态性匹配**——这是文献给出的最明确的"复杂度预算"原则。

### 3.3 多智能体的位置：例外而非常态

- MAS 三原语对应经典 SE 关切：角色分工（CAMEL）、过程模型/SOP（MetaGPT）、通信中间件（AutoGen）。
- 实证约束：MAS 收益随基座模型增强而收窄，协调开销确定存在；任何 MAS 须以"单 agent + best-of-N"为 baseline；SE 任务上单 agent + 强反思是当前更优默认。
- 上 MAS 的前置条件：任务/角色/终止规范显式化 + 独立验证器。

### 3.4 工业框架如何落这些维度（2026-08-17 回填，依据台账 #5 `materials/agent框架-工业设计对比.md`）

7 个框架按 3.1 的控制流谱系与 3.2 的状态管理定位（详表见材料 A 部分横向小结）：

| 框架 | 控制流归属 | 状态管理重心 |
|---|---|---|
| LangGraph | 开发者显式（图 + 条件边，模型在受限点分支） | 共享 State（reducer 合并）+ checkpoint 持久化/HITL |
| AutoGen v0.4 | 去中心化，消息涌现（actor 模型） | agent 本地状态，无全局共享 |
| CrewAI | hierarchical 时交 LLM 管理者；Flow 层显式编排 | crew memory + 任务级 replay |
| OpenAI Agents SDK | 单 agent 模型循环 + 模型决策 handoff | Session 持久化抽象 |
| Google ADK | 图 / 模板 / LLM 编排三态并存 | Session 服务为中心（压缩、缓存、rewind） |
| AgentScope | v1 显式 pipeline；v2 收敛到 ReAct 循环 + 中间件 | 消息历史 + 记忆中间件 |
| smolagents | 模型写代码即行动（code action） | 代码变量 + 对话日志，无持久层 |

**对 3.1–3.3 的验证结论**：
1. 两维框架解释力得到确认——各框架差异确实可分解为"控制流归属 × 状态管理"的组合，且材料给出一个学术梳理未预见的共性趋势：**"第二代"框架普遍从"框架替你编排"退回到"开发者显式编排 + 模型在受限决策点自主"**（LangGraph、AutoGen v0.4、CrewAI Flow、AgentScope v2 一致），与 3.1 表中"固化流程"一行的权重上升相互印证。
2. **状态管理成为新分水岭**（LangGraph checkpoint、ADK/Agents SDK 的 Session 服务、AgentScope v2 中间件）——印证 3.2"架构复杂度与任务状态性匹配"原则已内化为框架设计的一等考量。
3. 多 agent 边界收敛（材料 C.3）：Cognition（写密集反多 agent）与 Anthropic（读密集可并行挺多 agent）主张实际兼容——共识为"上下文一致性是多 agent 第一风险，并行只适合无副作用子任务"，与 3.3 的"例外而非常态"结论一致且给出更精确的划界（读/写比）。

## 4. 子问题 B 的理论框架：中间产物作为正确性基础设施

文献证据链：

1. **规范缺失是主要失败源**（MAST v3 FC1 系统设计 44.2%）：任务规范、角色规范、终止条件——这些正是"需求描述文档"在多 agent 语境下的形态。
2. **结构化中间产物可抑制幻觉级联**（MetaGPT）：agent 间以文档/接口规约为契约并校验中间产物，有效性已被基准实验支持。
3. **工件一等公民化**（Hassan 四支柱）：人机协作的交互应由结构化、版本化工件承载（BriefingScript 等概念），人类角色转为 Agent Coach。
4. **评估口径即规约质量**（SWE-bench → Verified 的教训）：模糊需求的任务是残留失败集中区——需求描述的歧义直接转化为系统失败。

**初步命题**：在 Agent 软件中，中间产物（需求描述、任务/角色规范、接口规约、验收条件）承担传统软件中"代码 + 评审"承担的正确性职能，因为被它们规约的决策逻辑不再有形式化载体。因此中间产物规范的设计标准是**可机检性 + 可验证性**，而非可读性。

库内同类工作（2026-08-17，详见 `materials/README.md`"references 库内相关论文"）：`references/ContextEngineering/10`（Formal Architecture Descriptors——架构描述符作为可机检导航原语）与 `08`（Codified Context——形式化上下文基础设施）是该命题在架构描述与上下文两个切面上的已有实例；`references/CodeGraph/12`（TraceDev）提供需求→代码工件链在多 agent 系统中的契约化案例。

### 经典 SE 对照（2026-08-17 回填，依据台账 #6 `materials/软件工程原理与LLM系统.md`）

结论：第 4 节命题是**经典原理的延续而非范式断裂，但经典原理内部发生了分工转移**——

1. **形式化规约史是关键类比**：形式化方法"技术上成功、商业上未成主流"（INRIA 2020 Expert Survey）的原因是规约成本 > 收益（除航天/密码学/硬件等高失败代价域）。prompt 正处于"比自然语言 SRS 更弱、比代码更强"的中间态；历史提出的问题是：LLM 系统会否重蹈"规约成本 > 收益"，还是 **evals + 统计抽样 + 蜕变测试（MT）提供了历史上缺失的廉价检查手段**——这是子问题 B 的核心研究空间。
2. **DbC 的概率化变形**：LLM 组件的前置/后置条件概率性满足、"不变式"随模型版本静默漂移（六维差异对照表见材料 3.1）。已有工作显式借用 DbC 建模多智能体协作（arXiv:2510.12120），说明契约思想可迁移但需要新形态。
3. **"prompt 即规约"的三方观点**：乐观派（prompt + eval suite 即新型规约-验证对，工业界为主）/ 审慎派（自然语言规约自身有歧义、满足是概率性的，操作性规约应下放到 evals 与 MT 蜕变关系）/ 混合架构派（不给 LLM 写完整契约，用确定性外壳——schema 校验、符号验证器、guardrails——限制非确定内核的失败面，即 CBSE 在概率组件上的复兴）。本方向的"中间产物规范"命题与审慎派 + 混合架构派的组合最兼容。
4. **Brooks 检验**：LLM 压缩的是偶然复杂度（样板代码），本质复杂度（需求澄清、概念一致性、变更管理）转移到 spec/eval 工程——即本方向研究的"需求描述与中间产物规范"恰是经典需求工程的领地回归，论证了研究对象的稳定性。

## 5. 对方向一的输出（[D1+D2] 交叉引用）

学术梳理对方向一组件模型的直接输入：

- **组件粒度建议**：Wang 四模块（profile/memory/planning/action）可作为专用 agent 组件的顶层分类——skill 对应 profile+action 知识，上下文源对应 memory，工具对应 action。
- **必备组件**：评估/验证组件（对应 FC3）与状态外部化组件（对应长程可靠性）应作为组件库的常备类别，而非场景可选件。
- **评估指标锚点**：方向一的"任务成功率"指标应区分 pass@1 与 pass^k 口径；构建耗时之外，"超出模型时间地平线的任务需人类检查点"（METR）应写入场景分析框架。
