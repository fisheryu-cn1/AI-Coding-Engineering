# 方向二专题 03：需求阶段的人机协作边界与完整性检验

> 日期：2026-08-17
> 话题标签：[D2]（第 2.3/2.4 节含 [D2+D3]、[D1+D2] 交叉）
> 状态：讨论中（原始思考来自阅读 `references/AgentParadigms/02`（Liu et al. TOSEM 综述）§4.1 Requirements Engineering 触发）
> 关联：notes/02 §4（中间产物命题）、notes/00 §3（子问题 A 划界）

## 1. 原始思考记录（2026-08-17 讨论整理）

**观察一：现状缺口——形式约束 ≠ 内容控制。** 当前 AI 辅助需求分析着重对 AI 文档**输出形式**的约束：提示词通常只做身份定义与输出模板约定；但对"如何确定需求发现的**完整性**""如何梳理需求**内部逻辑规则的完整性与一致性**"缺少指引——这两项基本依赖大模型自身能力。

**观察二：人类参照——理想过程与实际偏差。** 理想的人类需求分析近似面向对象建模过程：从用例、流程、业务实体对象等方面逐一梳理，以**功能点、关键数据、业务场景故事中的执行流程**为参照物，对各角度建模结果做交叉检验（一致性与完整性）。实际执行中，由于对需求分析职责理解与人员技能背景的差异，标准不一；典型偏差是**偏重软件交互方式的沟通，对内部逻辑与数据模型的描述完整性控制不足**。

**核心论点：能力/知识边界识别是需求阶段人机协作的关键。** 从基础训练看，大模型应已具备 UML 建模知识（内蕴能力）；但**如何使用**——按怎样的流程、规范、标准应用这些知识，尤其是涉及**实际业务规则与用户使用系统的方式**这类外部知识——需要人类输出。因此，识别"模型已具备能力"与"需人工提供的外部知识"的边界，可能是需求阶段找到人与大模型协作较优方式的关键点。

## 2. 结合已收集资料的评价与补充

### 2.1 综述证据对观察一的印证（支持）

- Liu 综述 §4.1 显示现有 RE agent 的两条策略**都未解决**观察一指出的缺口：多 agent 角色扮演（Elicitron 多 persona 模拟用户采访、MARE 五角色团队）覆盖面广，但"协同质量保证是难点"（§4.1.3）——其 checker 角色本质上是又一次 LLM 自检，无外部锚点；工具增强单 agent（SpecGen 用 OpenJML 迭代精化并变异验证）只适用于可形式化为 JML 类规约的子域。§4.1.4 列出的挑战（生成需求含糊/不相关、人机交互被"角色替换"弱化、无需求演化支持）与观察一同源。
- **该区域学术证据也薄弱**：综述 §7.2 威胁效度指出 RE 多 agent 策略 3 篇中 2 篇未经同行评审——观察一指出的缺口同时是文献薄弱区，具备研究价值。
- **与 MAST 证据链衔接**：多 agent 系统 44.2% 失败源于系统/规范设计问题（FC1）——需求产物的不完整与不一致正是下游"任务规范"缺陷的上游源头；本思考等于把方向二 v0.2 的中间产物命题（"可机检 + 可验证"承担正确性职能）在需求阶段具体化：**输出模板只覆盖了"可机检"的形式面，完整性与一致性属于尚未规约化的"可验证"面**。

### 2.2 对"交叉检验"的补充：一致性关系可以规约化，但它是弱 oracle

- 多视角交叉检验可以规约为**可机检的一致性规则集**（UML 模型间一致性研究的经典方向）：用例步骤引用的业务对象必须出现在实体模型中；顺序图消息与类操作签名匹配；状态机事件与外部消息覆盖；场景故事的执行流程与用例前置/后置条件不矛盾。这是把"理想人类过程"规约化的具体路径，即 D2-S4"操作性规约"的需求侧实例——**检验标准不寄望于模型能力，而是外置为规则**。
- 与蜕变测试的类比划定了能力上限：一致性关系是**弱 oracle**——只能证伪不一致，不能证明完备（需求完整性无金标准）。因此评价体系应按"不一致检出率 + 参照物覆盖率"设计，而非虚构一个"完整率"。
- 参照物（功能点清单/数据字典/场景故事）本质上是需求阶段的**观测锚点**，其覆盖检查可像测试覆盖率一样量化——[D2+D3] 需求产物的覆盖/一致性指标应纳入观测体系（RQ-A2 数据模型的一类产物），作为规范资产迭代的效果信号。

### 2.3 对"能力边界识别"论点的补充：边界是三段的，且会漂移

- **同构印证**：D2-S2 的划界判据（可验证性、错误成本）在需求阶段获得第三个具体判据——**知识内蕴性**（UML 建模知识 in 预训练 vs 业务规则/用户行为 exogenous）。三者可并列写入契约指南的需求节。
- **边界不止二分，而是三段**：①模型内蕴知识（建模方法）；②须人工供给的外部知识（业务规则、用户使用方式）；③**外部知识的供给方式设计**——静态文档、动态澄清、参照物清单。第三段最关键也最被忽视：τ²-bench 的核心发现（协调与沟通是独立于推理的能力短板，no-user→dual-control 显著掉点）说明模型缺的往往不是建模知识而是**引导用户澄清的能力**；ClarifyGPT（主动识别歧义并提问，综述 §5.3）是该方向的早期实例。人机协作设计点应聚焦"缺口发现→澄清问题生成→人工补齐"的循环协议，而非单纯的知识注入。
- **人类基线不稳的警示**：观察二自陈人类执行标准不一（重交互、轻数据模型）。若 AI 辅助只做形式约束，等于复制并放大既有偏差（DORA"AI 是组织能力的镜子"）。因此目标不应是"模仿人类分析师过程"，而是"**把理想过程规约化后由人机分工执行**"——与综述 §6(6) 的结论同向：SE 专业知识约束的简单工作流（Agentless 式）胜过复杂自主 agent。
- **边界随模型代际漂移**：形式化规约史的类比在此同样成立——今天须人工供给的（如某些业务常识）明天可能内蕴。边界识别应是持续观测任务而非一次性划分（[D2+D3]：能力边界漂移本身列为观测对象）。

### 2.4 可操作机制候选（缺口 → 机制 → 库内依据）

| 缺口 | 机制候选 | 依据 |
|---|---|---|
| 完整性发现 | 参照物覆盖检查：功能点/数据字典/场景故事做成 checklist，逐项核对面 | 测试覆盖率类比；观察二的参照物 |
| 内部一致性 | 多视角模型间一致性规则集（可机检） | UML 一致性研究方向；D2-S4 操作性规约 |
| 生成可靠性 | 多次生成的需求一致性（self-consistency 作稳定性信号）+ pass^k 口径 | τ-bench（23 号）；Reflexion 消融 |
| 外部知识缺口 | 澄清循环：缺口检测→澄清问题→人工补齐 | ClarifyGPT；τ² dual-control；Reflexion 外循环 |
| 过程规范沉淀 | 需求分析 skill：把 OO 建模流程 + 检验规则封装为 SKILL.md | Agent Skills 知识激活（ContextEngineering/09）；skills 生态六主题（30 号）中并无"完整性/一致性检验"类——恰是空位 |
| 可形式化子域 | 需求→形式规约→工具验证（SpecGen 路线） | 综述 §4.1.2 |

### 2.5 两点风险提示（对原始想法的修正）

1. **"完整性"没有绝对判据**：交叉检验只能逼近（覆盖 + 证伪不一致），宣传"确保完整"的机制声明应降格为"检出 N 类不一致 + 参照物覆盖 M%"。
2. **多视角建模有成本**：全维度 OO 建模对小需求过重，需按场景裁剪——需求阶段的建模深度本身应成为 D1-S2 场景画像的一个问项（[D1+D2]）。
