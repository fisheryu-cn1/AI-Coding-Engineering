## 2. 三方一致的结论（强共识，9 条）

1. **四步实为两体系拼接、brainstorm↔4p12s 结构性断裂**——P 给出四维断裂表（路径/产物语义/下游终态/ID 体系），K 称"第 0 步名实不符"，Z 列为缺陷 D1。
2. **4p12s 子集内部拓扑约束体系完备且质量高**（ID 分型与所有权/双向覆盖/写边界/澄清 ID 隔离/UI 防降级链）。
3. **一致性检查（SAT/soundness/引用）与确定性检查器全部缺失**——门禁全是 LLM 自检/人工核表（"同源验证"Z、advisory 自查 K、单层检查器 P 三种表述同义）。
4. **翻译审计缺失**——"保留业务含义"是要求不是机制，漏译/弱译/改义下游不可见。
5. **"可观察可测试"无操作化判据**；spec-reviewer 为宽松校准的软门/可选件。
6. **覆盖规则无机器执行器**——ID 引用闭包恰是最易脚本化的检查，三方均未在其 skill 中发现任何工具化。
7. **动态拓扑执行近乎完美**：零悬挂引用、US/AC/SC/DE/TC 全闭环、状态账本合法、诚实 blocked。
8. **RULE-003 全链静默丢失穿透多道门禁**——三方各自独立发现（Z 用脚本、P 列 D-1、K 列 D-3 并进一步查实代码）。
9. **正面机制得到验证**：澄清问答回写、待决项（阈值/费率）全链传递、终点纪律（release_trigger 不伪造）。

## 4. 各方独有发现（及其方法论根源）

**K 独有（4 项，语义层最深）**：
- **PRD 验收标准无 ID→名义映射脆弱**（缺口 2 + D-6 实证："M1 删除"→"M1 删除（级联）"名称漂移已发生；N-2：不是风险是既发事实）——比 Z 的 C3"覆盖无执行器"更根本：覆盖的**键**本身就不是 ID。
- **DEL-001/002 私造前缀**（D-2）：九类分型闭集外的自造，下游全盘继承——**Z 与 P 的核验正则都被产物污染**（两者均在清单中默认纳入 DEL，漏判此违规；Z 尤其在静态评估明列九类后仍被产物带偏）。
- **FLOW-001 无溯源注入 + Q-001 错标**（D-7）：登记的结构化表述新增三项源摘录不存在的约束（draft 起点/rejected 终态/级联删除）且澄清记录未覆盖，PRD 还把状态口径来源错标为 Q-001——"Z_真 被伪装成 Z_伪"（K 原话）。
- **代码↔文档逆向断裂**（N-1）：RULE-003 文档链消失但代码真实实现（types.ts/BorrowerForm.vue 枚举）——追溯矩阵**双向失真**的实证。

**P 独有（4 项，结构/工程层）**：
- **brainstorm 在动态产物中完全缺席**（D-8）：无任何 superpowers/specs 产物、raw_input 直接喂考题文本——"平行而非串联是生产常态"，把 Z/K 的静态断裂判断推进为动态事实。
- **大项目分解机制断点**（1.1.4）：brainstorm 有 decompose 能力但 4p12s 不消费。
- **DE-01 设计-实施偏离无记录机制**（D-4）：设计 mysql2 连接池、实际 store.ts 内存层，无偏差记录字段。
- **基础设施件"借用覆盖"灰区**（D-3）：DE-10/11 靠 E2E 间接触发满足映射，规则未覆盖此形态。

**Z 独有（2 项，框架层）**：
- **门禁判定基准错位的归因**：覆盖规则写"需求 ID"为源、执行按"PRD 验收标准"为源——RULE-003 丢失的直接机制解释（P/K 均发现丢失但未给出此归因）。
- **"上半场拓扑/下半场语义"定性框架**与同源验证天花板的机制表述（P/K 结论同向但无此框架化表述）。

## 6. 元观察（对比本身的方法论发现）

1. **评估深度与"离语义层的距离"成反比**：P 的核验体系最系统（对照表 20 条、规则正则 12 项），但恰好漏掉两个最重的语义缺陷（操作员矛盾/TC-005）——结构化脚本天然不做跨文档语义比对；K 补齐的关键动作是**代码抽查+溯源审计**两个非常规步骤。结论：结构核验系统性与语义发现能力**不可互相替代**，需显式分层。
2. **"评估者被产物污染"是真实风险**：Z 与 P 均在核验清单/正则中默认接受了产物私造的 DEL 前缀（Z 甚至在静态评估明读九类分型后仍被带偏）——检查器的基线必须来自**规范文本**而非产物现状，此教训直接写入本项目 tools/scripts 的设计约束。
3. **严重度排序反映评估者的层别立场**：P 将 ID 未引用列为最严重（结构层违规），Z/K 将操作员语义矛盾列为最重要（语义层失真）——同一缺陷集在不同质量观下排序不同，报告合并时应双层并列而非折中。
4. **修复方向三方独立收敛**：脚本化引用闭包（K 实测"50 行"即可）、PRD 验收标准 ID 化、翻译审计/溯源字段、分歧度度量——三个外部视角独立指向本项目计划 R2/R4，构成对研究计划的三角验证。

## 7. 对本项目的综合启示

- **R1 对照基线升级**：kimi 的四项独有发现（尤其验收标准无 ID、溯源失真）应纳入 method/10–13 的规范设计输入——"PRD 验收标准分配稳定 ID""登记表增加决策溯源字段"两条规则直接来自交叉验证的缺陷。
- **检查器设计红线新增**：核验基线锚定规范文本而非产物（DEL 教训）；结构核验与语义核验分层显式化（P 漏检教训）；增加"声明层级 vs 实际执行方式"比对项（TC-005 教训）。
- **评估协议沉淀**：本次"同任务+隔离+独立文件名+禁读清单"的三方交叉评估模式可作为本项目可复用的评估协议（分歧本身就是信息：判定分歧暴露规范两可处，漏检暴露方法边界）。
