# 01-工具选型（分阶段）

> 原则：**方法优先于工具；部署成本低（pip 一行/桌面绿色软件/Git 内置）；可定制拓展（开源+脚本化）；确定性判定不依赖 LLM**。许可红线：避开 GPLv3 组件进入集成层（独立脚本使用无碍）。

## 0. 人工方法替代映射（研究初期的关键决策）

检查器类工具**从 R1 起即直接使用**（桌面级、零代码、无可行人工替代——人不做描述逻辑推理与状态空间分析）；**人工先行**适用于以下五环节（它们是方法验证期的研究对象本体，也都有成熟人工做法）：

| 环节 | 软件工具（后期） | 初期人工方法 |
|---|---|---|
| S1 需求解析 | 解析 skill | 人工标注（表格逐句过：实体/规则/流程/数据项/歧义/缺口六列） |
| S3 形式化翻译 | 翻译 skill | 人工在 Protégé 建模+手写约束（Z3 Python 表达）/WoPeD 画流程 |
| S3 翻译审计 | 对照表辅助工具 | 人工逐条对照（模板强制 NL 原文↔形式化条目双列） |
| S4 预期场景设计 | 场景生成建议 | 人工编写业务场景（领域专家职责，不可外包） |
| S5 分歧度评估 | 自动采样+等价类计数 | 人工多轮独立评审（2–3 人背靠背写下游设计再比对差异点=人工 Z_真 度量） |

## 2. 明确不引入（现阶段）

- 重型 EA/BPM 套件（Camunda/Signavio 商用栈）——部署与维护成本违背原则，WoPeD+PNML 已覆盖 soundness 需求；
- 纯 Java OWL API 工程链——owlready2 足以覆盖脚本化需求，需要时再上；
- LLM 判定位——设计原则红线（LLM 不做判定，只做翻译/建议/回译）；
- 自建 Web 平台——R5 前全部文件型工作流（Git+Markdown+桌面工具+脚本）。

## 3. 演进触发器

- 本体规模 > 数百公理或分类耗时长 → ELK/Konclude；
- 规则以传递/分类为主且量增 → Clingo 替代 Z3 表达；
- 分歧度采样成为日常 → 将 trae-agent 的去重-归并组件抽为独立工具；
- 多人协作 → 引入轻量评审流（Git MR+检查报告随附）。
