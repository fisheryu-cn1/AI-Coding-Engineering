# 00-研究计划：从开放式需求到确定性规范的整体工作方法

> 版本 v0.1（2026-08-26 立项）。上游理论：`../../人机可读性分离点与验证边界_两轮讨论备忘_2026-08-25.md` §8。

## 1. 问题定义

从原始需求到代码的传统文档链上，每步转换注入决策 Z = Z_伪（共识可推导）∪ Z_真（真自由度）。本研究的工程化命题：**设计一套人机结合的工作方法，在需求设计文档层把 Z_真 消解（人工澄清）或显式化（标记为待决项），使下游转换的确定性在信息论意义上成立**（备忘 §8.4：确定性 ⟺ Z_真=∅ 且丢弃与可观察行为无关）。

质量目标采用备忘 §8.2 的三层"完整"定义：
- **一致性**（可判定）：无矛盾规则、本体无 unsatisfiable class；
- **结构完备**（可判定，需 closed-world 手段）：无未定义引用、流程无死端（soundness）；
- **语义完备**（不可判定，测试兜底）：预期业务场景全部被蕴含，分歧度（Z_真 规模）收敛到阈值内。

## 2. 成果物目标（四件，即立项任务书）

1. `plan/01-工具选型.md`——分阶段、低部署成本、可定制；
2. `method/`——整体工作流程与规范（含人机分工、受控语言、翻译审计、检查套件、门禁）；
3. `templates/`——六类标准产出物模板；
4. `tools/`——衔接用的程序/Skill/Agent（后期）。

## 3. 阶段计划

| 阶段 | 目标 | 主要活动 | 产出 | 评估 |
|---|---|---|---|---|
| **R0 方法设计**（1–2 周） | 工作方法 v1 | 七阶段流程细化；受控语言子集选型（EARS vs SBVR-SE）；人工执行方法逐环节定义；模板 v1 | method/10–15 规范草案、templates 六件 | 方法走查（桌面推演一个纸面案例） | ✅ 2026-08-27 完成（走查以 loan-system 实练为超集证据） |
| **R1 案例试点**（2–3 周） | 人工全流程验证 | 选 1–2 个中等复杂度真实需求（含审批流+数值规则+多角色，候选见 cases/README）；人工按方法走 S0–S6，桌面工具跑检查 | 案例全套产出物+痛点/耗时记录 | 检查器捕获缺陷数；人工环节耗时分布；空泛一致案例数 | 前半 ✅（loan-system 收官，Run-1~12） |

| **R2 检查器最小集成**（1–2 周） | 重复劳动脚本化 | Z3 检查脚本、引用完整性脚本（Datalog/Python）、分歧度抽样脚本（多次生成+unidiff 规范化去重，借鉴 trae-agent 件） | tools/scripts 三件（按 p2s-kit v1 标准 pip 包化） | 脚本与人工结果一致率 |
| **R3 LLM 辅助位试点**（2 周） | 翻译/回译/建议位接入 | **具体化为 pi 适配器实验（plan/02 §4）**：steering 注入+三 skill（S1 解析/S3 翻译/S4 回译）；翻译审计成本实测 | pi 衔接层+审计数据 | 新使用者在 pi 内闭环一轮且红线零违例 |
| **R4 Z_真 曲线实测**（2–3 周） | 分歧度门禁实证 | 沿 S2/S3/S4/S5 各边界做 N 次独立生成下游设计×语义等价类计数；画 Z_真 沿流程的收敛曲线；对比"澄清前 vs 澄清后" | 曲线数据+门禁阈值建议 | 归零点是否随阶段单调前移（方法有效性证据） |
| **R5 工程化与门禁**（2 周） | enforcement 落地 | Git pre-commit 钩子串检查套件；**pi hooks 双形态（plan/02 §4.1，视 R3 结论取舍）**；产出物模板绑定 | CI 门禁+完整工具链 | 变更-检查-修复闭环时延 |

总周期约 10–14 周（弹性：R2/R3 可并行，R4 依赖 R3 的生成件）。

## 4. 核心实验设计（R4，衔接既有 E 实验方向）

- **自变量**：流程阶段边界（S2 术语表定稿后 / S3 形式化后 / S4 检查通过后 / S5 澄清后）；澄清操作（有/无）。
- **因变量**：N 次独立生成（固定模型与提示）产出的语义等价类数（Z_真 规模代理）；等价判定用"unidiff 规范化去重 + LLM 语义判等 + 人工抽检"三层（trae-agent 31 号的现成模式）。
- **假设**：①等价类数沿 S2→S5 单调下降；②S4 检查通过前后的下降主要来自一致性问题消解，S5 后残留者多为真业务自由度（可标为待决项交付）。
- **对照**：同一需求不走方法直接生成（基线分歧度）。

## 5. 风险与对策

| 风险 | 对策 |
|---|---|
| 翻译墙（NL→形式化不忠实）成为主要成本 | R3 专门实测审计成本；受控语言收窄表达面；翻译件逐条对照（模板强制） |
| 空泛一致（本体什么都不敢约束） | 预期实例测试强制入 S4；场景覆盖率作为单独指标 |
| 懒惰修复（AI/人削公理消信号） | 修改必须引用 justification+类型标注（方法规范红线） |
| 案例选择偏差（单案例过拟合方法） | R1 双案例异构（流程重 vs 规则重）；R4 复用第二案例验证 |
| 方法过重（比直接写代码还贵） | 每阶段记录耗时；若 Z_真 曲线不收敛则如实报告负结果——方法适用边界本身是研究成果 |
| 产出物腐烂 | R5 门禁；无门禁环境下明确标注 advisory 状态 |

## 6. 立项决策记录

- 目录名 `requirement-to-spec`：研究重心在"需求→规范"段（分离点前推），代码生成侧仅作 R4 的下游探针，不是本项成果物。
- 桌面级检查工具（Protégé+HermiT、WoPeD、Z3 脚本）从 R1 起即使用——部署成本近零且无可行人工替代（人不做 DL 推理）；"人工先行"适用于解析、翻译、审计、场景设计、分歧评估五环节（详见 01-工具选型的映射表）。
- LLM 选型暂不定死：R3/R4 需要多模型对照（Mixture 经验：31 号论文轮换三 LLM 增多样性）。
