# 02-交付物与部署设计（v1）

> 2026-08-27 立案。触发：loan-system 收官后、第二案例前的交付形态决策（用户提出）——当前方法在研究过程中"长成"，存在三重使用门槛；若不在扩案前固化交付形态，每多一个案例就多一份不可传播的隐性知识。
> 本文档定义最终研究成果的交付架构，并给出各研究阶段与交付层的整合关系。

## 1. 问题定义：三重门槛

| 门槛 | 现状证据 | 后果 |
|---|---|---|
| **部署门槛** | 环境搭建跨多次踩坑（镜像/坐标/XMI 废弃，tools/env/README 记录全程），手工步骤无脚本化 | 新使用者复制环境需半天且必踩同坑 |
| **认知门槛** | 方法逻辑与术语（Z_真/行 ID/决策节/绑定闭包/签收门）在研究日志与七件规范中逐步形成，无操作视角入口 | 新使用者需读完 30+ 文件才能动手 |
| **衔接门槛** | 操作循环（起草→审计→检查→决策→执行）靠研究者手工衔接 AI 与检查器 | 方法无法嵌入主流 AI 工具的日常工作流 |

## 2. 交付架构（三层，规约与实现分离）

```
┌─ 认知层：使用指南（GETTING-STARTED）────── 操作视角文档+术语表+walkthrough
├─ 部署层：p2s-kit ──────────────────────── requirements+环境自检+案例骨架模板
└─ 衔接层：适配器（首个实验对象=pi）────────── steering/skills/hooks
        ↑ 单一事实源：method/ 七件规范 + templates/ T1–T6
```

**核心原则：规约与适配器分离**。method/ 与 templates/ 是工具无关的单一事实源；衔接层只是"把规约翻译成某种 AI 工具能消费的形态"的适配器。pi 是首个实验对象（选型理由：实现简单纯净、扩展面开放——Skill/插件/钩子俱全），验证适配器模式后可平移 Claude Code（CLAUDE.md+hooks）/Cursor（rules）等。

## 3. 部署层设计（p2s-kit）

### 3.1 最小依赖面（实测盘点，Run-1~12 验证）

| 依赖 | 用途 | 必要性 |
|---|---|---|
| Python ≥3.10 | 五个自研脚本 | 必需 |
| owlready2（pip，**内置 HermiT.jar**） | OWL 构建+一致性推理 | 必需 |
| pyshacl + rdflib（pip） | 闭包/约束校验 | 必需 |
| z3-solver（pip） | 规则集检查 | 必需 |
| Java 运行时 ≥17 | HermiT 的 JVM | 必需（owlready2 调用） |
| PlantUML jar | SVG 图形渲染（人审辅助） | **可选**（不装则纯文本链可跑） |
| model2owl + Saxon | 规则参考（B 方案已不依赖） | 不需要 |

pip 四件均为纯安装（唯一踩坑=网络镜像，脚本内置清华源备选参数）；Java 为唯一系统级依赖。

### 3.2 一键化路径（渐进三步）

1. **v0（随本设计落地）**：`requirements.txt` + `tools/scripts/check_env.py`（环境检测 + `--smoke` 全组件冒烟——把当初手工冒烟的五次验证变成一条命令）+ `templates/case-template/`（`cp -r` 即建新案例的骨架）。
2. **v1（R2 产出形态标准）**：install 脚本（pip 镜像参数化）+ 自研五脚本 pip 包化（`pip install p2s` 后获得 `p2s-convert/p2s-check/...` 命令行入口）。
3. **v2（视需求）**：Dev Container（Java+Python 双运行时的容器化；Windows 环境优先级后置）。

### 3.3 案例骨架模板

`templates/case-template/`：raw/（T1 登记表空表）→ review/（V00 索引+E30/E41 空表，16 号规约结构）→ formal/（puml 头注解模板+bindings 空表+rules_z3 骨架）→ reports/（T5 台账头部）→ regression/（baseline 机制说明）。复制即得合法目录，检查器开箱可跑（空绑定+空模型的 PASS 是合法初始态）。

## 4. 衔接层设计（pi 适配器，实验位=R3）

### 4.1 方法环节 → pi 机制映射

| 方法环节 | pi 机制 | 形态 | 阶段 |
|---|---|---|---|
| 方法纪律（六条设计原则/红线/词表，README+method/11/13） | **steering 注入**（常驻上下文） | steering 文件=规范摘要+指向 method 原文（避免全文注入膨胀） | R3 |
| S1 解析（NL→登记表起草） | **skill** | SKILL.md：操作步骤+T1 模板+术语纪律引用 | R3 |
| S3 翻译（登记→puml/Z3 起草+审计表预填） | **skill** | SKILL.md：注解词表约束+T3 预填规则（只进机器区） | R3 |
| S4 回译（台账→工作台） | **skill** | SKILL.md：三纪律+完整性守恒声明生成 | R3 |
| 检查链触发（.puml 保存→转换+七项检查；review/ 变更→队列重生成） | **hooks** | 文件变更钩子串检查脚本——R5 门禁的 pi 形态（pre-commit 等价物） | R5 |
| 人工评审填写 | **不映射**（人在 review/ 目录直接编辑，红线：判定不依赖 LLM） | — | — |

### 4.2 设计约束（从 method/11 直接推导）

1. skill 产物只进预填位与 .puml（LLM 边界不因载体改变）；
2. hooks 只串确定性脚本（判定不依赖 LLM）；
3. steering 注入的是规范摘要而非全文（上下文预算纪律）；
4. pi 机制依据为源码阅读结论（steering 注入/技能加载五层/钩子面），实现时以 pi 当期文档校验——适配器版本随 pi 版本锁定。

### 4.3 实验成功判据

新使用者在 pi 内完成"起草→审计表预填→检查→工作台"一轮，全程不直接接触 method/ 原文（规范经 steering/skill 到位）且红线零违例（抽查产物边界）。

## 5. 认知层设计（使用指南）

1. **GETTING-STARTED.md**（使用者视角，区别于研究视角的日志/报告）：方法一句话（把需求变成可机器检查的规范文档）→ 五个角色动作（登记/翻译/审计/决策/执行各自做什么）→ 一条链命令 → check_env → 常见问题（镜像/Java 路径）。
2. **术语表**（操作术语优先）：行 ID/决策节/Z-x/绑定清单/执行队列/签收门/机器区人工区——每条一句话+规范节指向。理论术语（Z_真/分离点）后置到"原理"节（可先不懂原理即能用）。
3. **walkthrough**：loan-system 作为教学案例——跟 Run-1~12 台账走一遍（台账的"只追加+归因"结构天然适合回放）。
4. 分层原则：研究者视角（日志/报告/价值实证）与使用者视角（指南/模板）物理分离，互不污染。

产出排期：v0.5 于 R1.5（第二案例前，与 p2s-kit v0 同批）；第二案例全程按新指南操作=部署设计的首次真实测试（吃自己狗粮）。

## 6. 与研究阶段的整合

| 阶段 | 原计划 | 交付层整合 |
|---|---|---|
| R1.5（新增，2–3 天） | — | p2s-kit v0 + 使用指南 v0.5 + 案例骨架 |
| R1 后半 | 第二案例 | 按新骨架+新指南跑（部署设计首测） |
| R2 | 检查器集成 | 产出形态直接按 p2s-kit v1 标准（pip 包化） |
| R3 | LLM 辅助位试点 | **具体化为 pi 适配器实验**（steering+三 skill） |
| R5 | 门禁工程化 | pi hooks 与 pre-commit 双形态（视 R3 结论取舍） |

## 7. 决策记录

- 交付架构=三层（部署/认知/衔接）+规约适配器分离——2026-08-27 用户提出方向，本设计定形；
- pi 选型理由（简单纯净/开放/Skill-插件-钩子俱全）——用户提供；机制映射实现时校验；
- 容器化后置——Windows 主环境+研究阶段优先级判断，v2 视需求重议。

## 8. 交付物自包含原则（2026-08-27 用户纠正确立）

**分发集**（最终交付物）＝ p2s-kit + GETTING-STARTED + method/ + templates/。**不含**实验材料（cases/）与研究过程记录（notes/、reports/）——分发对象不了解也不应被要求了解实验内容。

推论与执行：

1. **分发件内禁止依赖性引用**：不得引用 cases/ 路径、Run 台账编号、"首例实践"文件等实验材料；示例一律内联自包含（如 GETTING-STARTED §4 微演示——虚构迷你需求+真实运行输出）。
2. **templates/**：模板文件中"首例实践"行剔除；templates/README 的实练状态表转为开发仓库注记（分发打包时剔除该节）。
3. **method/**：规范正文中的实证锚点（Run 编号/案例文件引用）是**研究版**特征，服务规范的可信度溯源；**分发打包时执行清洗**——锚点剥离或转写为内联说明（"此规则的依据"改述为一般化理由），清洗由 R5 打包步骤统一执行并校验（打包后 grep 无 cases/ 引用）。
4. **开发仓库与分发版的双面性是显式设计**：研究期保留锚点（证据文化不损失），分发期机械清洗（原则 3 的校验可脚本化）。两者不混装。
