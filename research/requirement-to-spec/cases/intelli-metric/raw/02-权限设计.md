# 需求梳理 —— 权限设计 v0.1

> 状态：初稿，待评审。本文是 `01-需求总览与功能分解.md` 第 3.5 节的细化，编号 F-SEC-*。

## 1. 模型总览

权限模型由三层构成，三层相互独立、通过关联规则衔接：

```
┌─────────────────────────────────────────────────────────┐
│ 全局功能权限（RBAC）                                       │
│ 角色 = 功能权限集合，用户被授予角色                          │
│ 如：创建数据源、创建指标、创建用户、查看全局监控/审计          │
└───────────────────┬─────────────────────────────────────┘
                    │ 获得"创建资格"后，创建行为产生资源
                    ▼
┌─────────────────────────────────────────────────────────┐
│ 资源级权限（ACL，按资源实例授权）                            │
│ 数据源：所有人(owner) / 可读(reader) / 无权限(none)          │
│ 指标：  可修改(manager) / 可读(reader) / 无权限(none)        │
└───────────────────┬─────────────────────────────────────┘
                    │ 授权主体可抽象化
                    ▼
┌─────────────────────────────────────────────────────────┐
│ 授权主体（Principal）抽象 —— 组织架构预留                    │
│ subject = 用户 ｜ 组织节点（预留）                           │
│ 后期：用户自动继承其所属组织节点（及祖先节点）的授权            │
└─────────────────────────────────────────────────────────┘
```

## 2. 数据源角度（F-SEC-DS）

**F-SEC-DS-01 权限级别**

| 级别 | 能力 |
|---|---|
| 所有人（owner） | 修改数据源配置（含连接参数）、执行/配置元数据采集、查看依赖该数据源的指标列表（影响分析）、为其他用户配置本数据源的权限（owner / reader / none）、删除数据源 |
| 可读（reader） | 查看数据源信息与元数据（连接凭据永不可见）、在构建指标时选用该数据源的表/字段 |
| 无权限（none） | 数据源对该用户不可见（列表、检索、指标构建器中均不出现） |

**关联规则：**

- **R-DS-1 创建即所有**：数据源首次接入时，操作用户自动成为该数据源的所有人（前置：该用户拥有"创建数据源"全局功能权限）。
- **R-DS-2 所有人可授权**：所有人可将其他用户指定为所有人或可读，也可降级/移除（包括把其他 owner 降级）。
- **R-DS-3 至少一名所有人**：任何时刻每个数据源至少保留一名所有人。最后一名所有人不可被降级或移除；数据源不可删除至"零所有人"状态。
- **R-DS-4 凭据隔离**：连接凭据加密存储，仅服务端采集/计算使用，任何级别权限的用户（含所有人）均不可经 API 读取明文。

## 3. 指标角度（F-SEC-M）

**F-SEC-M-01 权限级别**

| 级别 | 能力 |
|---|---|
| 可修改（manager） | 修改指标定义与元信息、执行测试、发布/暂停/下架等生命周期操作、为其他用户配置本指标权限、创建新版本 |
| 可读（reader） | 查看指标定义、口径说明、测试结果，通过指标服务查询结果 |
| 无权限（none） | 指标对该用户不可见 |

**关联规则：**

- **R-M-1 创建资格与创建即管理**：创建指标是全局功能权限；创建者自动成为该指标的可修改者（manager）。
- **R-M-2 管理者可授权**：manager 可为其他用户配置 manager / reader / none；每个指标至少保留一名 manager（同 R-DS-3 逻辑）。
- **R-M-3 版本继承**：指标口径变更产生新版本时，权限配置随指标实体继承，不按版本割裂。

## 4. 全局功能权限（F-SEC-G）

**F-SEC-G-01 功能权限清单（首版）**

| 权限点 | 说明 |
|---|---|
| datasource:create | 创建数据源 |
| metric:create | 创建指标 |
| user:manage | 用户管理：创建、停用/启用、重置密码、分配角色 |
| role:manage | 管理角色与功能权限分配 |
| api-consumer:manage | API 调用方管理：创建/停用调用方、颁发/吊销 token |
| knowledge:manage | 知识库管理：创建/导入/导出知识条目（条目编辑另受创建人规则约束，见 PRD-04） |
| monitor:view | 查看指标服务监控（范围见 `03-指标服务与监控.md`） |
| audit:view | 查看调用日志与审计记录 |

**F-SEC-G-02 内置角色（可被 role:manage 调整）**

| 角色 | 功能权限 |
|---|---|
| 系统管理员 | 全部功能权限；对所有资源相当于兜底 owner（用于无人认领资源的接管，操作留审计） |
| 指标开发者 | datasource:create、metric:create、api-consumer:manage、knowledge:manage、monitor:view（限自身范围） |
| 业务查看者 | 无全局创建权限；可读取被授权的指标并调用服务 |

## 5. 三个角度的关联规则（F-SEC-AR）

- **AR-1 开发态从严**：构建、修改、试算指标时，用户必须对指标依赖的每个数据源均有 reader 及以上权限；构建器中无权限数据源的元数据不可见、不可选。
- **AR-2 消费态以指标为授权边界**：指标发布后，查询指标结果只需对该指标有 reader 权限，**不**回溯校验底层数据源权限。指标即数据对外暴露的受控出口，由指标 manager 承担口径与数据暴露责任。（设计意图：业务消费者不应被要求理解底层数据源授权；如需更严策略，预留"消费态联动校验"开关，默认关闭。）
- **AR-3 权限回收不影响已发布服务**：用户对数据源权限被回收后，已发布指标的服务不受其个人权限影响（服务端以系统身份执行计算），但该用户后续不能再基于该数据源构建/修改指标。
- **AR-4 数据源所有人的影响知情权**：数据源 owner 可查看依赖本数据源的指标清单（用于结构变更的影响分析与下架联动，见 F-LC-05），但查看指标明细/修改指标仍需相应指标权限。
- **AR-5 无越权放大**：任何授权操作只能由资源 owner/manager 发起，且不得通过指标授权向用户暴露其在开发态无权访问的数据源明细（指标 reader 只能看到口径说明与结果，不能看到构成 SQL/字段清单——除非其对依赖数据源有 reader 权限）。
- **AR-6 调用方鉴权独立**：API 调用方（consumer）的 token 调用只校验 token 有效性、指标授权范围与指标发布状态，不涉及内部用户权限体系；consumer 的授权范围调整由指标 manager 发起，纳入审计。

## 6. 系统初始化与超级管理员（F-SEC-BOOT）

- **R-BOOT-1 空实例初始化**：系统首次启动且无任何用户时，通过初始化向导（Web 页面）或 CLI 命令创建首个超级管理员（设置用户名/密码）；首个超管创建成功后初始化入口永久关闭。
- **R-BOOT-2 超级管理员角色**：内置角色，拥有全部功能权限，并对所有资源具备兜底接管能力（操作留审计）。职责是创建第一批用户、分配角色；后续资源的授权由各资源 owner/manager 自管理，不依赖超管。
- **R-BOOT-3 至少一名超管**：系统始终保留至少一名启用状态的超级管理员；最后一名超管不可被停用或降级。
- **R-BOOT-4 用户生命周期**：用户支持创建、停用/启用、重置密码、角色调整。停用用户前，若其是某些资源的唯一 owner/manager，须先完成移交（移交向导批量转授）或由管理员强制接管，避免出现无主资源。

## 7. API 调用方与访问 token（F-SEC-API）

- **F-SEC-API-01 调用方模型**：API 调用方（consumer）是外部消费者账户，不是内部用户。属性：名称、唯一标识、负责对接的内部用户、状态（启用/停用）、授权的指标范围（指标集合）。
- **F-SEC-API-02 token 生命周期**：一个 consumer 可持有多个 token（区分用途/环境）；支持颁发（设置有效期与备注）、吊销、到期自动失效；token 明文仅在创建时展示一次，服务端只存哈希。
- **F-SEC-API-03 鉴权规则**：指标服务 API 调用需携带有效 token；校验顺序：token 有效 → consumer 启用 → 目标指标在其授权范围内 → 指标处于发布状态。token 吊销/范围回收即时生效（鉴权缓存短 TTL，秒级）。
- **F-SEC-API-04 管理权限**：创建/停用 consumer、颁发/吊销 token 需要 `api-consumer:manage` 功能权限；调整某 consumer 的指标授权范围，还需操作人对相关指标具备 manager 权限（或为管理员）。
- **F-SEC-API-05 留痕**：consumer 的创建、token 颁发/吊销、授权范围变更全部记入审计；consumer 的调用日志按调用方维度进入监控统计（见 `03-指标服务与监控.md`）。

## 8. 组织架构扩展预留（F-SEC-ORG，后一期实现）

**目标**：权限授权与组织架构关联，用户自动继承其所在组织节点（及祖先节点）被授予的数据源/指标可见范围，减少逐人授权成本。

**当前版本的设计预留（避免后期架构大改）：**

1. **授权主体抽象**：授权记录的主体为 `(subject_type, subject_id)`，`subject_type ∈ {user, org_node}`。首版只启用 `user`，表结构与 API 均已按两类主体设计。
2. **权限判定接口统一**：所有权限判定走 `resolve_effective_subjects(user) -> [principal...]` 入口，首版返回用户自身；接入组织架构后扩展为"用户 + 所属节点 + 祖先节点"集合，判定逻辑不变。
3. **继承语义预定义**：组织节点授权沿组织树向下继承（节点授权 → 其子树内所有用户）；资源级权限冲突时取最高级别（owner > reader > none）。
4. **不预留的部分**：组织节点自身的维护（对接 HR/LDAP 或平台自建）留到扩展期设计，本期仅保证授权与判定链路支持非用户主体。

## 9. 权限判定流程（概要）

```
请求 → 1. 认证（内部用户会话 / API 调用方 token）
     → 2. 功能权限校验（角色 → 权限点，如 metric:create；token 调用跳过，走 AR-6）
     → 3. 资源权限校验（ACL：subject ∈ resolve_effective_subjects(user)，级别足够？）
     → 4. 数据范围过滤（列表/检索/监控数据按可见范围裁剪）
```
