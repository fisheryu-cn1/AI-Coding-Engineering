# 设计文档与代码的 UML 提取比对实验报告（loan-system）

> **这份报告检验什么**：此前所有的检验都停留在文档层——需求登记表、PRD、设计文档之间互相比对，从未接触过最终的代码。本实验把检验链延伸到最后一环：设计文档里描述的结构和代码里实际实现的结构，到底是不是一回事？如果设计说订单有六个状态、审批由独立服务完成，代码里真的是这样吗？
> **用什么方法**：让 pi（一个 AI 编程助手，本次实验中扮演"提取员"角色）做两次提取——第一次从设计文档（design.md，175 行）里读出它描述的类、方法、状态机，画成 UML 图；第二次从实际代码（后端 TypeScript 13 个源文件 + 前端 Vue 五个页面）里读出同样的东西。然后由本报告的作者（GLM，扮演"比对员"角色）把两张图逐项对照，再往上与 PRD 层的既有模型对照，形成"PRD → 设计 → 代码"三段比对。
> **怎么读**：第 1 节是两次提取各自拿到了什么；第 2、3 节是两段两两比对的结果；第 4 节是四个预先立案的疑问在本实验中得到的最终答案（这是最值得关注的部分）；第 5 节是对"让 AI 从文档提取方法设计"这件事本身的评估。不需要预先了解之前的实验细节，涉及的概念会在出现处解释。

## 1. 两次提取各自拿到了什么

### 1.1 从设计文档提取（pi 第一次任务）

输入是原交付的设计文档 design.md。pi 产出了两张图：

- **类图**（design-concept.puml）：11 个类、2 个枚举、14 条关联，以及 **42 个方法**——这一项是本实验的特殊之处：以往从需求提取的类图只有属性没有方法，这次明确要求把方法连同逻辑描述一起提取（每个方法附一行"@logic"注释，说明它做什么、依据设计文档哪一节）。例如设计的 LoanOrder 有 submit、sign、complete 这些操作，每个操作的触发条件和效果都记录在注释里。
- **状态机**（design-flow.puml）：订单的六个状态（draft/pending/approved/rejected/active/closed）和它们之间的迁移，与 PRD 层一致。

**一个计划外的重要收获**：pi 在提取时主动列出了一份"设计文档含糊、无法决定怎么建模"的清单，共 11 条。例如：贷款用途字段在设计文档里只写了 `purpose : string`，没有说合法取值是哪些（而 PRD 里明明定义了四类枚举）；删除借款人时是否级联删除其订单，文档没有说明。这份清单相当于**把设计文档里所有"没说清楚的地方"一次性暴露了出来**——这正是形式化提取的价值之一：模糊之处在画图时无法回避，必须表态。

### 1.2 从代码提取（pi 第二次任务）

输入是原交付的实际代码（排除测试文件和构建产物）。pi 产出：

- **类图**（code-concept.puml）：27 个类、3 个枚举、33 条关联、**80 个方法**（方法签名直接取自代码真实定义，每个附实现摘要）。比设计层多出的类主要是前端页面、API 客户端、数据存取层——这些是实现层自然生长的结构。
- **状态机**（code-flow.puml）：同样六个状态，迁移上还标注了守卫函数（如 `canTransition` 校验）和触发路由。

pi 同样主动列出了一份代码层的"与常规模型不符"清单，共 8 条，全是实现层的真实问题——例如：状态机校验只写在服务层，数据存取层不拦截，服务漏写就能绕过；提交订单的函数先写 pending 状态再调自动审批，如果审批函数抛异常，会留下一个永远停在 pending 的脏数据（没有 try/catch 兜底）。

两张概念图和两个状态机都通过了本仓库管线的语法验证（转换器可解析、状态机五项结构性质成立）。

## 2. 第一段比对：PRD → 设计

比对工具是 diff_models（本项目的模型比对脚本，逐项比类、属性、枚举、关联、方法名的增减），输出差异清单后由人工做语义甄别。主要发现：

**枚举改了名但语义还在**。PRD 层的订单状态枚举叫 OrderStatus，设计文档改叫 LoanStatus；审批结果 PRD 叫 CreditDecision，设计叫 Decision。名字漂移，但六态/两值的取值范围经人工核对一致。这类改名没有语义损失，但值得注意：每一层都自作主张换名字，到代码层累积的漂移会更明显（见第 3 节）。

**贷款用途枚举在设计层断了**。PRD 明确定义用途为四值枚举（装修/教育/旅游/医疗），设计文档里这个字段退化成了自由字符串——pi 的含糊清单第 1 条如实报告了这一点。这是此前基于文档链推断的"RULE-003 断链"在设计层的直接确认（RULE-003 是需求条目编号，指"贷款用途固定枚举"这条规则）。

**大量新增属于设计阶段的正常细化**。设计层比 PRD 多出 8 个类（审批配置、评分规则、操作日志、四个服务类）——这些是详细设计本来该做的事，多数能在设计文档里找到依据，归为合法新增。

## 3. 第二段比对：设计 → 代码

**审批服务的结构重组**。设计文档定义了一个独立的 CreditService（审批服务），代码里没有这个类——审批逻辑被并入了 LoanOrderService（订单服务）的 submit 方法内部，作为一个名为 autoApprove 的内部步骤。审批的语义还在（评分、过线通过、不过线拒绝，一样不少），但设计划定的服务边界没有传导到实现。这是"结构变了、语义没丢"的典型。

**审批配置的能力收窄——这是真实的弱化**。设计文档把审批配置建模为泛化结构：阈值、权重、还有一个"指标数组"（metrics——意味着将来可以配置任意多个评分指标）。代码里的配置是三个写死的字段：通过阈值、收入权重、负债率上限。设计承诺的"指标可扩展"（这直接关联需求 RULE-001"评分规则参数化配置"）在实现中收窄成了固定两项。这不是风格差异，是能力的减损。

**命名风格整体漂移**。费率字段在设计里是 annual_rate（下划线风格），代码里是 annualRate（驼峰风格）。无语义损失，属于实现层的习惯性适配。

**一个设计未言明的行为变异**。设计文档里 pending（待处理）是一个可以停留的状态——订单提交后停在 pending，等待自动审批。代码的实现是提交函数一口气做完三件事：置 pending、跑审批、立刻覆盖为 approved 或 rejected——pending 在代码里是一个外部看不见的瞬态中间值，调用方只能观察到最终结果。状态机的**结构**（六态六迁移）与设计完全一致，但状态的**驻留语义**变了。结合 pi 发现的"审批抛错留脏 pending"问题，这个变异并非无害：它恰恰是那个脏数据缺陷的成因。

## 4. 四个预先立案的疑问，最终答案（本实验核心产出）

此前的检验（全部在文档层进行）留下了四个只有看代码才能回答的疑问。本实验给出终态裁决：

**疑问一：RULE-003（用途枚举）最终在代码里是什么状态？**
答案比之前推断的更精确，也更出乎意料。此前基于文档链的推断是"全链丢失"（PRD 有、设计没有、推测实现也没有）。实际链条是三段三种形态：PRD 是四值枚举 → 设计是自由字符串 → **代码的 TypeScript 类型定义里枚举回来了**（types.ts 里 `purpose: LoanPurpose`，四个中文值齐全）——但是，**运行时的接口校验里没有它**：校验中间件只检查必填和格式，外部调用者向 API 提交任意用途字符串不会被拒绝。也就是说：写代码的人自己补上了设计丢掉的枚举（以类型声明的形式），但只补在编译期，没有补到运行时防线。**代码比对修正了文档链推断**——真实情况不是"丢失"，是"半程恢复、防线缺位"。

**疑问二：操作员角色的矛盾最终如何落地？**
PRD 有六处"操作人员执行通过/驳回"的表述，而设计 UML 和代码 UML 里都没有任何操作员方法——订单状态完全由自动审批驱动。矛盾精确地断在 PRD → 设计这一段。这与此前的人工裁决（D-A：确认为原始需求歧义，采纳"自动审批即生效"一侧）一致，但这次是机械呈现，不再依赖人工通读五份文档。

**疑问三：六态状态机是否贯穿三层？**
贯穿。PRD、设计、代码三层的状态集合与迁移完全一致（包括 rejected 终态不可回流）。唯一变异是上文说的 pending 驻留语义。

**疑问四：让 AI 从文档提取"方法设计"靠不靠谱？（此前讨论的假设首次实测）**
基本靠谱，但有一个重要限定。靠谱的部分：42 个方法提取顺畅，逻辑描述（@logic 注释）抽查 5 条与文档语义一致，足以支撑与代码的比对。限定的部分：设计 42 个方法与代码 80 个方法的对照中，机器报出 38 项差异，其中**大部分是实现层的合法适配**（重组、改名、前端新增），真正的语义问题（审批配置收窄）只占少数——如果不做逐项归因，原始差异清单的噪声会淹没信号。结论：AI 提取的方法设计可以直接用于比对和参考，但**必须配归因步骤**（本项目的"三分法"：纯实现细节 / 合法适配 / 语义漂移，逐项归类后信号才浮现）。

## 5. 对实验本身的评估

1. **文档链检验延伸到代码层是可行且值得的**。整个实验（两次 AI 提取加人工比对）一个下午完成，产出了四个终态裁决加两个新发现（pending 变异、配置收窄），其中"RULE-003 半程恢复"直接修正了此前的推断——这类"代码现实纠正文档推断"的能力，是纯文档检验永远给不了的。
2. **AI 提取的"被迫表态"效应值得机制化**。pi 两次主动产出的清单（设计含糊 11 条、代码问题 8 条）是免费副产品——相当于自动生成的"翻译审计预填"。建议固定进提取流程：每次提取必须附"无法决定的点"清单。
3. **方法逻辑描述（@logic）开辟了新的检查面**。以往模型只有结构，这次每个方法带了一两句逻辑描述，使得"设计的 submit 应该做什么"与"代码的 submit 实际做什么"可以逐条对照——本报告第 3、4 节的多项发现（原子执行、审批并轨）正是从 @logic 描述读出来的。
4. **对原交付的最终评价因此被修正**：它的语义保真度好于此前静态评估的认知（六态贯穿、审批语义完整、实现者甚至主动补了设计缺失的枚举），核心缺陷 RULE-003 的真实形态是防线缺位而非全链蒸发。

## 6. 局限

单案例、单次提取（AI 提取的随机性未测量，属 R4 实验范畴）；方法逻辑描述只抽查了 5 条非全量核验；前端只提取了页面级结构，组件内部未建模。
