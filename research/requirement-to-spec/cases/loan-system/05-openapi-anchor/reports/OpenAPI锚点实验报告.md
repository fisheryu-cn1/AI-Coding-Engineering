# OpenAPI 锚点实验报告（loan-system，第 05 轮）

> 日期：2026-08-30。**这份报告写给三类读者**：未参与前几轮的读者只需知道——loan-system 是一份真实的 AI 生成交付（《个人消费贷款管理系统》，含需求/PRD/设计/代码全链产物），本案例群已对它做过四轮实验（构造全链 / PRD 评审 / 再生成对照 / 设计↔代码 UML 比对）；知道备忘 §12 讨论的读者可直接看第 4-5 节（本实验是 §12.5-① 工作项的首个实验）；只想看结论的读者看本段下一句。**一句话结论：OpenAPI 作为继 UML-OWL、BDD 之后的第三个机器可读规格锚点，主张成立——一次 34KB 零依赖脚本全自动生成 20 个端点的合规规格，与设计文档比对后一次性显形 15 条偏差与 2 条未声明接口，其中没有任何一条能被前四轮的 UML 通道发现。**
>
> 角色分工（用户指定）：pi 执行（写提取脚本、生成 OpenAPI、做文档比对），GLM 评审（独立对账复核，不使用 pi 的任何中间产物作输入）。

## 1. 实验设计

**实验从哪来**：备忘 §12.4 分析了 AI 生成项目普遍缺失 API 接口文档（OpenAPI）、时序图、泳道图的三层归因，其中"验证回路缺席"归因推出一个可检验主张——若 OpenAPI 能从代码确定性反向生成（永不漂移），并作为规格锚点接入文档一致性检查，它就具备成为第三个机器可读规格锚点（继需求侧 UML-OWL、行为侧 BDD 之后，接口侧）的条件。本实验用 loan-system 原交付验证该主张的两个半链：**主张 A**（代码→OpenAPI 确定性生成可行）与**主张 B**（OpenAPI 锚点使文档↔代码一致性比对可行）。

**双通道设计**：GLM 在 pi 动手前先用 grep 对 backend 源码独立完成路由对账（20 个 operation 的基准清单 + design.md 22 条声明的逐条判定），形成评审基准；pi 的产出评审时才与基准比对。这与 04 轮"AST 通道 vs LLM 通道"的双通道思想同构，但角色换位：本轮 pi 负责程序化通道，GLM 的独立 grep 充当第二通道。

**输入**：`raw/design.md`（175 行原交付设计文档，API 契约为"REST 接口（前缀 `/api`）"小节的 4 组共 22 条 method+path 声明）；代码为 `giencoder-exam-P0151020/backend/src`（TypeScript/Express，路由集中在 `routes/index.ts` 与 `routes/health.ts`）。

**任务书约束**（`prompts/task-openapi.md`）：提取必须纯程序化（脚本可复跑、零 LLM 参与、同输入必同输出）；schema 能从 `types.ts` 确定性推导的才写，推不出的标 `x-uncertain: true`，**红线=不得编造字段**；比对表逐行可复核（每行带代码证据 file:line）。

## 2. pi 执行结果（三件产物，均在 `gen/`）

**`extract_routes.cjs`（35KB）**——提取脚本。pi 自主选择了纯正则而非 AST/TypeScript Compiler API，三条理由记录于脚本头部：路由声明风格统一（`router.<METHOD>('path', ...)` 无装饰器无注解，AST 无增量收益）；giencoder 工程内 typescript@7 是 5.x→7.x 断代版（Compiler API 失效，正则方案零依赖跨工程隔离）；`types.ts` 的 interface 语法面窄且稳定。确定性措施：输出按 path/method 排序、不读环境不连网、声称并实测 byte-identical。局限诚实列出：不支持跨行类型/条件类型/泛型实例化（本工程未用到）。

**`openapi.yaml`（31KB / 948 行）**——脚本直接产物：12 条 path、20 个 operation、10 个 schema 组件（含从 `handle()` 包封 `res.json({code:0,data})` 提取的 `SuccessEnvelope`/`ErrorResponse`）。`x-uncertain` 定义 3 处，语义上覆盖全部 20 个 200 响应的 `data` 字段（经 `SuccessEnvelope` 的 `$ref` 复用）——脚本明确不静态推导 service 返回类型（"避免编造"），宁可标注。

**`api-doc-code-diff.md`**——design.md 22 条声明逐条拆分到 method+path 粒度的对照表（24 行判定），五类判定+统计校验（22=7+11+4；20=7+11+2 自洽），附 7 条与偏差表正交的可疑点观察。

**产物迭代记录（评审观察）**：pi 交付过程中脚本有一版迭代（语义指标前后不变：20 ops/12 paths/10 schemas/x-uncertain 定义 3 处），重跑后 openapi.yaml 行号排布变化，比对表行号引用随之同步重写——GLM 以中途快照对照新版 yaml 时一度误判"引用未同步"，以最终产物核验后确认**终态自洽**（全部行号引用精确命中当前 yaml 的 operation 行）。教训有二：评审必须锚定产物终态（中途快照可能作废）；产物间行号引用在"上游重跑"时确实存在脆断风险，本次靠 pi 手工同步修复，工程化后应改语义定位（method+path 检索）或引用自动重算。

## 4. 实验发现（内容层）

### 4.1 API 层文档↔代码漂移全景：一致率 32%

design.md 的 22 条接口声明中，与代码完全一致的仅 **7 条**（Borrower 全组 5 条 + `/config/approval` 2 条）；**11 条形近变体**——路径段命名漂移覆盖三组：`/loans`↔`/orders`（整组 8 条，含 sign/complete/submit 动作端点）、`/config/rates`↔`/config/rate`（复数↔单数，2 条）、`/credit-results`↔`/credits`（1 条）；**4 条设计未实现**——CreditResult 的全部写操作（POST 创建、GET/PUT/DELETE 按 ID）代码完全缺失，仅存 `GET /credits?order_id=N` 过滤列表；反向**2 条代码超出设计**——`GET /api/orders/{id}/contract`（签约页合同详情，design.md 接口清单未列，但"数据流"小节的叙述隐含了它）与 `GET /api/health`（运维惯例接口）。

**与 04 轮的对照是本实验最重要的方法层发现**：04 轮 UML 双提取比对（类图 27 类+80 方法）没有抓到上述任何一条——类图与状态机根本不携带路由信息（资源命名、HTTP 方法、路径参数、CRUD 覆盖）。API 层的漂移密度（15/22=68% 有偏差）远高于 UML 结构层。**第三锚点的增量价值不是理论推演，是被 04 轮的盲区直接证实的。**

### 4.2 形近变体的第三种载体

本项目形近变体缺陷已跨三轮出现，载体各不相同：03 轮 regen 实验（LLM 再生成引入 **ID 变体** FULC/FOW，被 A2 检测抓出）→ 05 轮（**路径变体** loans/orders、rates/rate、credit-results/credits）。值得注意：本轮的路径变体出自**人写（或人机协写）的设计文档与代码两端**，不是 LLM 再生成的产物——命名漂移是跨主体的系统性一致性问题，不是 LLM 特有缺陷。这为"形近变体检测"从 check_doc_closure 的 ID 正则+编辑距离推广到 API 路径空间（exact 匹配→路径段对齐→编辑距离分级）提供了直接动机，且完全可规则化。

### 4.3 CreditResult 半实现：一个典型的"待裁决"发现

设计声明 CreditResult 具备全套 CRUD（5 端点），代码只实现只读列表（1 端点），创建动作内化到 `submit→autoApprove` 流程。两头都有道理：派生数据（审批结果由系统生成）暴露人工 POST 本就语义可疑——代码方向可能更合理；但 PUT/DELETE 缺失意味着**审批结果不可修正、不可删除**，若业务要求纠错能力（如误判复核）则是实现缺口。这正是评审方法要产出的一类知识：不是"代码错了"，而是**暴露一个设计未表态的分歧点，需要需求方裁决后回写文档或补实现**——与 01 轮 D-B 裁决（需求两状态体系混淆）同性质：方法价值在于让分歧显形，不在于预设哪边正确。

### 4.4 行为级发现：文本检查不可达的四条

伪成功 200（缺 404 语义）、PUT 半 PATCH（方法语义与实现行为不符+status 强制重置副作用）、错误响应双格式（客户端需两套解析）、模块漂移（design 的 `creditService` 在代码中不存在，逻辑并入 `rules/scoring.ts`）。这四条的共同点：**全部处于"运行时行为/模块内部组织"层，任何基于文档文本的检查（无论人工还是 LLM）都不可达**，只有把代码翻译成规格（openapi.yaml）并与设计声明并置后才显形。

## 5. 方法层结论

**主张 A（确定性反向生成）成立，且有成本数据**：34KB 一次性脚本投入，20 端点+10 schema 全自动，重跑零成本、byte-identical；校验生态即装即用（openapi-spec-validator 一条 pip 命令）。"永不漂移"的含义在本实验中具体化为：代码变更后重跑脚本，规格与代码的偏差恒为零——这与 UML-OWL 通道（LLM 提取、需人工裁决审计）形成鲜明对比，OpenAPI 通道是三条锚点中唯一**反向全自动**的。

**主张 B（锚点比对）半自动成立，规则化空间明确**：本轮比对表由 pi（LLM）生成、GLM 独立复核零分歧——LLM 比对在 22 条规模上可靠。但比对的主体逻辑（method+path 精确匹配→判定一致；不匹配→路径段对齐+编辑距离→判定形近变体；剩余→未实现/超出）完全可规则化为确定性脚本，即 check_doc_closure 的 A2 检测从 ID 空间推广到 API 路径空间。LLM 的不可替代部分收敛到"语义存疑"类判定（如 PUT 半 PATCH 这种行为级观察）。

**对备忘 §12.4 工程推论的第一份数据支撑**：API 文档在 AI 生成流程中的合理角色确实是"反向生成+锚点校验"而非"人工先写"——本实验中它已经产出了 04 轮 UML 通道全部产不出的 17 条偏差级发现（15 偏差+2 超出）。§12.5-① 工作项可标记为完成。

## 6. 局限与后续

- **单案例、单框架风格**：正则方案的适用前提是"路由声明风格统一、无装饰器/注解"（Express+手工 router 满足）；Spring/NestJS（装饰器）需换 AST 或注解读取方案——脚本头部已诚实标注此边界。
- **响应 schema 静态不可推导**：`SuccessEnvelope.data` 标 x-uncertain 是当前上限；消解路径有二——静态推导 service 返回类型（工程量可控）或运行时录制（schemathesis 方向，属低频审计档）。
- **design.md 的"接口清单 vs 数据流叙述"双源问题**：contract 端点在清单未列、叙述隐含。设计文档的接口声明若存在两个来源，清单级比对会漏隐含项——未来模板应强制"接口只在清单声明、叙述引用清单"。
- **工具收编候选**：`extract_routes.cjs` 具备进 `tools/scripts/` 的条件（零依赖、确定性、CLI 接口规范），但收编前需按工具包规范补充：多工程自测、README 条目、check_env 冒烟位——**待用户决定，本轮不收编**。
- **后续实验位**：形近变体路径检测的规则化（check_doc_closure 扩展）；schemathesis 运行时契约测试首试（需起服务，属重链）。

## 7. 发现的组织化：API 检查位接入工作流（2026-08-30 同日增补，用户指出缺口驱动）

**缺口**：本报告 §4 的 17+7 条发现最初只存在于 gen/ 生成物与实验报告中——不在 method/16 评审界面体系内（无 E 前缀评审表、无行 ID 锚点、无决策节、不进执行队列），发现不可被人裁决、不可追踪。用户提问"发现的不一致问题在哪个文档中体现+如何组织结果输出/人工评审/后续改进"后，同日完成接入设计并试点：

**方法层三处增补**（设计定案，工具规则化留 R2）：
1. **method/16 §3.1**：新表型 E50-API 对齐评审表（机器区六列+人工区三列防覆盖；判定五类词表；条目锚两级规则——新项目 EP 编号锚/存量位置锚；**组级决策聚合**——同一偏差成因多行聚为一个 DA-x 节；裁决出口三分支=回写设计/改代码/豁免登记；回归签收=重生比对+偏差全有裁决）；决策 ID 词表增 `DA-x`。
2. **method/14 检查项 8**：API 对齐（反向生成全自动+比对半自动+裁决纯人工；签收标准=无未裁决偏差行且队列清零；触发=代码产出/变更、设计接口章节变更、里程碑审计）+ 命令链增补 + 由来注记（05 实验锚）。
3. **method/19 v1.1**：三线七位→**三线八位**（新增接口线；⑧独占路由信息维、唯一反向全自动锚）；三节奏挂点——首次建模 S6 后首跑⑧、常规变更代码变更时⑧轻链（extract 重跑秒级+差异行对账）、里程碑 API 全对齐+行为级复查。

**试点**（本案例 review/）：[E50-API对齐评审表.md](../review/E50-API对齐评审表.md)——AA1-01~24 行（一致 7 免评/偏差 17 待评）+ DA1~DA10 决策节（机器区预填按质量红线：选项自足、证据就地、原交付不可改的出口降级说明）；[V00-INDEX.md](../review/V00-INDEX.md) 评审入口（本次待办=17 行+10 决策）。

**组织化设计的要点回顾**（为什么这样组织）：发现分两层入界面——规则可判的进表格行（L1）、行为级可疑点直进决策节（L2，规则化不可达）；行级发现按成因聚合成组级决策（24 行→10 决策，避免逐行裁决的碎屑化）；裁决出口三分支覆盖"文档错/代码错/两者都对但属惯例"三种真实情况；裁决执行后反向生成+比对重生即回归闭环（重跑零成本使"改到绿"可行）。
