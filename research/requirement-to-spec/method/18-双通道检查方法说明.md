# 18-双通道检查方法说明：需求文档—UML—OWL 线与需求文档—BDD—OWL 线

> 版本 v1（2026-08-28）。本文档解释方法的核心检查机制：两条检查线各自怎么工作、为什么这样设计、每一步用什么软件组件、信息在转换中发生了什么、哪些检查在转换过程中发生、哪些依赖转换结果、两条线结合后在哪里交叉互证、在哪里互补。操作规程（怎么跑命令）见 method/14，翻译与审计规范见 method/13。
> 写作约定：术语首次出现时给出定义；示例取自 loan-system 与 kb-app 两个实际案例（可在 cases/ 下找到全部原始材料）；不要求读者熟悉实验过程细节。

## 1. 要解决的问题

从需求文档到设计再到实现，每一次转换都会注入新的决策：把"贷款用途包括装修、教育等"写成程序里的枚举是一个决策，把"自动审批"实现为评分阈值判断是另一个决策。这些决策里有些是人人皆知的常识推导（写成什么样都行），有些是真正的自由选择（写错方向整个系统就错了）。传统做法靠人工评审把关，但人工评审有三个结构性弱点：注意力有限（长文档读后半忘前半）、标准漂移（同一个问题这次查下次不查）、无法做穷举推理（人不会在脑中推演"这三十条规则放一起有没有矛盾"）。

用大模型做评审同样有天花板：它检查自己（或同类）生成的内容属于"同源验证"——同一套偏见既生成了错误也审查不出错误。

本方法的核心思路：**把需求文档中机器可以判定的部分提取成形式化表示，交给确定性计算引擎检查；机器判不了的部分（真歧义、真自由度）显式标记出来留给人决策**。确定性引擎不会疲劳、不会漂移、对同样的输入永远给同样的答案——这个性质让"检查通过"成为可以信赖的结论而不是又一次猜测。

由此形成两条检查线，它们的分工源于一个根本事实：**描述"系统是什么样子"和描述"系统应该怎么表现"是两种信息**，前者走模型线（UML→OWL），后者走场景线（BDD→分路检验）。

## 2. 线路一：需求文档 → UML → OWL（模型线）

### 2.1 全流程与信息形态变化

```
需求登记表            UML 模型                OWL 本体               检查结论
(自然语言,结构化表格)  (PlantUML 文本)         (RDF/XML 图)           (一致/矛盾/违规)
      │                    │                      │                    │
   人工确认            LLM 起草+人工审计        确定性转换            推理与求解
   (S1)               (S3 翻译位)             (puml2owl)          (HermiT/Z3/pySHACL)
```

每一步的信息形态和损耗如下：

**第一步：需求登记（自然语言条目化）**。原始需求被整理成登记表，每条有唯一编号（如 RULE-003"贷款用途为固定枚举：装修、教育、旅游、医疗"）。这一步不损失自然语言，只是加了编号和分类。

**第二步：翻译成 UML（信息从"文本"变为"结构"）**。翻译位（大模型起草、人审计）把每条需求表达成 PlantUML 图形语言：RULE-003 变成一个枚举 `LoanPurpose` 加四个互斥字面量。这一步是**翻译墙**所在——翻译可能漏（需求有、模型没有）、可能弱化（枚举写成了自由文本）、可能错译。所以方法的铁律是**翻译审计点前移**：人审计的是翻译件本身（逐行对照原文和模型），而不是只看最终的检查结果——漏译到了下游就不可见了。

**第三步：UML 转换成 OWL（信息从"结构"变为"逻辑图"，零人为干预）**。转换器 puml2owl 把 PlantUML 文本变成 OWL 本体文件：类变成 OWL 类，枚举变成一组带互斥约束的子类加个体，`@required` 注解变成 SHACL 约束。这一步是纯机械的——**同一份输入永远产出字节相同的输出**（这个性质本身被当作一个检查项，见 2.3）。机械性是关键：如果这步有大模型参与，检查失败时就分不清是需求错了还是转换抖动——无法归因。

**第四步：引擎检查（逻辑图上做推理）**。三个引擎各自回答一类问题（引擎是并列的，各管一段）：

- **HermiT**（OWL 推理器，描述逻辑）：回答"是什么"类问题——分类体系有没有矛盾（本体一致性）、某个体是否属于某类（蕴含）。例：一个贷款用途个体同时被断言为"装修"和"医疗"，而这两个枚举值声明了互斥，HermiT 立即报告本体不一致。
- **Z3**（SMT 求解器）：回答"数值与规则"类问题——一组约束放在一起有没有解、矛盾出在哪几条。例：把"操作人员基于审批结果执行通过"和"自动审批即生效无操作员环节"两条语义同时编码，Z3 报告不可满足并给出最小冲突集（点名这两条规则），人立刻知道矛盾在哪。
- **pySHACL**（形状校验器）：回答"数据合不合规格"——一个实例缺了必填字段、格式不对，它报违规。例：缺少金额字段的贷款订单实例被 MinCount 约束拦截。

### 2.2 各环节的软件组件与作用

| 环节 | 组件 | 性质 | 发挥的作用 |
|---|---|---|---|
| 翻译 | 大模型（LLM） | 辅助位 | 起草 UML 草稿和审计表预填——**只起草，不判定**（红线：一切通过与失败由确定性引擎或人判定） |
| 审计 | 人（评审者） | 决策位 | 逐行核对翻译忠实度（E30 审计表：原文、模型落点、结论三栏对照）；决策歧义（E41 决策记录） |
| 转换 | puml2owl | 确定性程序 | UML 文本→OWL/SHACL 文件；保证同输入同输出，使检查失败必可归因 |
| 构建 | owlready2 | Python 库 | 在程序中构建和加载 OWL 本体、调用推理器的桥梁 |
| 推理 | HermiT（经 owlready2） | 计算引擎 | 本体一致性、类蕴含、互斥约束检查 |
| 求解 | Z3（z3-solver） | 计算引擎 | 数值/逻辑约束可满足性、最小冲突集、反例构造 |
| 校验 | pySHACL | 计算引擎 | 实例数据对结构约束（必填/格式）的符合性 |
| 状态机 | fsm_check | 确定性程序 | UML 状态图的五项结构性质（可达性、终态封闭、禁回等）——**注意：状态图不经过 OWL**（OWL 表达不了迁移语义），直接做图遍历 |
| 溯源 | check_model_bindings | 确定性程序 | 需求编号与模型元素的对照清单（绑定闭包）：每个需求有落点、每个落点真实存在、没有凭空的编号 |
| 层间 | diff_models | 确定性程序 | 相邻两层同类模型的元素级比对（类/属性/枚举/关联/方法名五维），查层间漂移 |

### 2.3 转换过程中直接发生的检查（不需要等转换结果）

有一类检查藏在转换动作本身，容易忽略但价值很高：

1. **翻译被迫表态**：把"贷款用途包括装修、教育、旅游、医疗**等**"写成枚举时，语法要求把值列全——"等"字处的开放性立刻暴露，要么声明可扩展（治理规则），要么被登记为待澄清事项。自然语言里模棱两可的地方，形式化语法会强迫翻译者做出选择并留下记录。
2. **语法面检验**：PlantUML 子集有明确语法约定，违反（如类定义不带花括号）转换直接失败——非法表达进不了模型。
3. **决定性验证**：同一输入转换两次比对输出哈希，相同才算通过——转换器自身被当作被检对象。
4. **绑定闭包**：转换前后对照需求编号与模型元素，需求有而模型没有（承接缺失）、模型有而需求没有（凭空发明）、落点失效（元素被改后对照悬空）都被点名。这一检查不需要推理引擎，纯文本对照，但它回答的是"翻译墙"上最重要的问题：**漏了吗**。

### 2.4 转换之后依靠结果才能做的检查

- 本体一致性（HermiT）：矛盾类层次、互斥违例；
- 蕴含检验（HermiT）：从断言推出预期分类（BDD 状态约束走这条通道，见第 3 节）；
- 约束求解（Z3）：规则组自洽、参数组合效应（如降权系数乘接收线后的落档行为）、两套判据的等价性反例；
- 实例校验（pySHACL）：给定数据样例，必填/格式约束的违规报告；
- 层间比对（diff_models）：相邻层模型的结构漂移。

### 2.5 本线检查不了什么（诚实边界）

方法的前置后置条件（调用前须满足什么、之后保证什么）与算法逻辑不在覆盖内——OWL 的描述逻辑表达不了"做什么"；它们的现状是：状态效果由状态机查、数值约束由 Z3 查、其余靠人工审计加验收测试（详见 method/13 §8 覆盖面边界声明）。

## 3. 线路二：需求文档 → BDD → 分路检验（场景线）

### 3.1 设计原理：第二个独立的信息源

模型线检验的是"翻译对不对"，但**翻译全对也不够**——模型可能什么都没说错、可是什么有用的都没说（一条空模型在 HermiT 里也是一致的，这叫**空泛一致**）。要发现"模型够不够用"，需要拿真实的业务预期去试：给定一个具体情形，模型的约束组合能不能产生预期结论。业务预期最自然的载体是 BDD 场景（Given 给定前提 / When 发生动作 / Then 预期结果）。

BDD 线的独立性是它的命门：如果场景由同一个大模型从同一份模型反推，那是自己证自己。所以场景必须从**需求原文**（而不是从模型）生成，且严格形态是人工撰写（独立性谱系：同源生成 < 异模型生成 < 人工撰写；人工场景在边界情况和异常情况两类上尤其不可替代——哪里是业务敏感区是领域知识，机器从文本看不出来）。

### 3.2 转换过程与分路

```
需求文档（场景/验收标准）
      │  生成（LLM 自动 + 人工提供），并做两维标注
      ▼
BDD 场景库（Given/When/Then）
      │  按 Then 类型分路（编排层，不是新引擎）
      ├─ 状态约束类 Then（"处理完成的文档应有主题分类"）
      │      → 翻译成 ABox 实例断言 → HermiT 蕴含检验        ← 这里用了 OWL 推理
      ├─ 动作效果类 Then（"接受候选后进入处理流水线"）
      │      → 迁移序列 → fsm_check 路径走查                  ← 用状态机，不经 OWL
      ├─ 数值边界类 Then（"0.72 分的候选降权后落在哪一档"）
      │      → 实例化 → Z3 求解                                ← 预留通道
      └─ 统计/实现类 Then（"解析成功率 ≥95%"）
             → 如实标注归验收测试域                            ← 形式化检不了统计比率
```

两个技术细节说明为什么这样分路。其一，**开放世界假设**（OWA）：OWL 推理假设"没说的可能是真的"，所以"删除的文档**不会**出现在检索结果"这种否定式结论它判不了——只能断言墓碑标记存在，过滤行为归查询层。这条边界如实记录在场景库里。其二，**动作语义**：OWL 没有动态语义（"做什么"表达不了），动作只能走状态机的迁移路径。

### 3.3 转换过程中直接发生的检查

- **验收可测性检验**：一条验收标准如果写不出 Given/When/Then，它就是不可测的——生成场景的过程本身在体检验收标准的质量（某次实练中两条验收标准因此被标注为"统计/实现域"，这还导致检查分类从两分扩展为三分）；
- **场景独立性审计**：确认场景来自需求侧而非模型反推；
- **两维标注**：每条场景标注"怎么验"（状态约束/动作效果/统计实现）和"验什么"（主线/边界/异常）加来源（自动/人工）——标注后的分布即覆盖健康度（如某次实练 6 条场景全部是主线、边界与异常为零，失衡立现）。

### 3.4 分路之后的检查

各通道把 Then 变成对应引擎的输入：断言一致性（HermiT，负例：互斥违例应被抓获）、路径存在性（fsm_check）、边界实例求解（Z3）。场景**走不通**说明模型缺了业务要求的行为；场景**不该走得通却走得通**说明模型多了可疑的自由度——两个方向都有发现能力。

## 4. 两条线结合：哪里交叉互证，哪里互补

### 4.1 交叉检验（同一对象、两条独立路径到达，结论应当一致）

| 对象 | 模型线路径 | 场景线路径 | 交叉的意义 |
|---|---|---|---|
| 实例符合性 | pySHACL 闭包校验（数据满足形状约束） | BDD 状态约束断言（数据蕴含预期） | 两路都过=强证据；一路过一路不过=**某条线的转换或生成有错**，差异本身是发现 |
| 状态行为 | fsm_check 结构性质（每条边存在、可达、终态封闭） | BDD 动作路径走查（具体业务链路走得通） | 结构合法是路径存在的必要非充分条件——结构全绿而场景走不通=模型缺行为；场景能走而结构报错=场景侥幸（如借道了不该有的边） |
| 蕴含正确性 | HermiT 从模型公理推 | 人/独立生成器从需求预期 | 推理结果与业务预期对账=翻译墙的两侧对照 |

交叉检验的价值在于：**两条线的错误来源不同**（模型线的错在翻译，场景线的错在生成），同一对象两路结论一致时，各自的错误大概率也相互抵消不了——一致即强证据。

### 4.2 互补（各自覆盖对方的盲区，不可互替）

| 盲区 | 只有一条线能查 | 原因 |
|---|---|---|
| **空泛一致**（模型什么都不约束，模型线全绿） | 只有场景线能查 | 业务预期拿不到蕴含结论时暴露 |
| **模型元素从未被使用**（公理覆盖率缺口：某条约束没有任何场景触达） | 只有模型线能查（反向统计） | 场景生成方不知道模型里有什么（独立性的代价），覆盖率要由模型侧统计 |
| **层间漂移**（相邻两层模型的结构差异） | 只有模型线能查 | BDD 场景不跨层生成 |
| **否定式行为**（"不该出现"） | 只有场景线（封闭快照） | OWL 开放世界判不了否定 |
| **数值边界行为**（恰好压线的落档） | 场景线为主（Z3 实例化）、模型线给规则组自洽 | 自洽是全局性质，落档是具体行为——两层证明 |
| **翻译漏译** | 只有模型线的绑定闭包 | 场景只试得到的部分，漏掉且没被场景覆盖的需求不可见 |

### 4.3 结合的整体审查流程（合流点）

日常运转时两条线在三个点合流：（1）**翻译审计**——场景库里状态约束类的断言失败，回溯时先查翻译（模型线责任）再查场景本身（场景线责任），决策记录（E41）承载决策；（2）**签收门**——模型线七项检查全绿**加**场景线覆盖健康度达标（三性质分布均衡、无走不通场景）才过 S5 签收；（3）**证据台账**——两条线的运行输出进同一本只追加台账（Run-N），任何结论可回溯到机器原始输出。

## 5. 已知限制

- 翻译墙无法根除，只能前移审计点并要求逐行对照；
- 场景独立性在当前实践中是半独立的（异模型生成与人工撰写是升级路径）；
- 统计/实现域（性能、成功率、LLM 输出质量）不在形式化检查内，由验收测试兜底；
- 前置/后置条件与算法逻辑不在覆盖内（见 method/13 §8）；
- 一切检查的前提是需求编号体系本身被遵守——绑定闭包依赖它做锚。
