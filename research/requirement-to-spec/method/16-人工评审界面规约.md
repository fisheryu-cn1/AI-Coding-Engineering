# 16-人工评审界面与文档规约

> 版本 v1（2026-08-27）。设计输入：评审实践暴露的三个痛点——①评审文件分散多目录需按说明分别寻找；②评审结果就地记录会覆盖机器原始输出，被迫另存 done 快照（已实际造成活表/快照状态分裂）；③下游 LLM 自动化步骤需要"评审后待机器处理的上下文"集中可寻址，避免单次调用读入无关信息。
> 适用范围：S4 机器检查全绿之后、S5 签收之前的人工环节（翻译审计签注、人工决策点、需求人员回应），及后续消费评审结果的自动化步骤。

## 1. 目录组织：物理归并填写件，逻辑归并只读件

案例目录下设 `review/`，**人工需要动手填写的文件全部物理归并于此**；评审动线中的只读材料（证据台账、模型大纲、SVG 图形）**不复制不迁移**，由 `00-INDEX.md` 统一链接（一次点击可达）。理由：复制只读件会制造双份漂移面——正是 done 快照教训的推广。

```
review/
  00-INDEX.md            # 评审入口：任务清单 + 文件地图 + 只读材料链接
  30-翻译审计-S3.md       # 填写件（模板见 §3）
  40-需求人员工作台-S4.md  # 填写件（LLM 回译产物，见 §5）
  41-人工决策记录-S4.md    # 填写件（决策事实源，见 §4）
  90-执行队列.md          # 生成物（脚本聚合，非人工维护，见 §6）
```

## 2. 文件命名规约

**文件名 = 两位十进制编号 + 稳定名称 + 归属阶段**，编号即排序即动线：

| 编号段 | 含义 |
|---|---|
| `00` | 入口导航（唯一例外） |
| `1x`–`6x` | 十位数 = 流水线阶段 S1–S6，个位数 = 同阶段内序号（如 `30-`=`S3`、`40-/41-`=`S4`） |
| `90` | 跨阶段机器汇聚物（执行队列） |

**版本不进文件名**：文件版本由 git 承担（本仓库即版本库），文件名级版本号会制造 `-done`、`-v2` 类分裂副本——被本规约明令禁止。轮次与演进语义由两个机制承载：①文件头"版本与变更"节（追加式，记录何时何因重生成/重构）；②表格**行级 ID**（见 §3）。仅当一轮评审整表作废重来时，才允许旧表归档为 `-R<n>-归档` 后缀并重建同名新表（归档例外须在 00-INDEX 记录原因）。

## 3. 评审表通用格式（模板）

所有"逐条对照、逐条裁决"类评审（翻译审计、场景审计、术语审计等）使用统一表格。以翻译审计为例：

```markdown
| ID | 条目ID | NL 原文(摘录) | 模型元素/落点 | 机器预填 │ 评审结论 | 执行标记 | 签注 |
```

**列分区（防覆盖的核心）**：

- `ID` + `│` 左侧五列 = **机器区**：由翻译/检查位生成，评审者只读，自动化步骤重生成时原样覆盖；
- `│` 右侧三列 = **人工区**：`评审结论`、`执行标记`、`签注`，仅评审者可写，**任何机器重生成必须按行 ID 对齐保留人工区**（v1 为手工纪律；表格重生的脚本化合并列 R2 落地）。

**行 ID 锚点规则**：`<表码><轮次>-<序号>`，如 `TA1-05`（翻译审计第 1 轮第 5 行）、`TA2-03`。行 ID 全局唯一、终身不复用（行删除后其 ID 不得再分配）。Markdown 表格行没有原生 URL 锚，**锚点 = 行 ID 字符串检索**（脚本与 LLM 均按行 ID 定位拉取该行，不整读文件）。

**合法值词表**：

| 列 | 合法值 |
|---|---|
| 评审结论 | `忠实` / `弱化(<原因>)` / `待澄清(<问题>)` / `确认` / `驳回(<原因>)`（留空=未评审） |
| 执行标记 | `[待执行:<动作说明>]` / `[仅记录]` / `[裁决后执行:<动作说明>]` / `[驳回执行:<原因>]`（留空=无动作） |
| 签注 | `<人名缩写> <YYYY-MM-DD>`（可加来源注记，如"迁移自 done-v1"） |

## 4. 人工决策记录（41-）

散落在表格行内的"待澄清/待裁决"事项，必须在 `41-人工决策记录` 开独立决策节（表格行只做指向）。每节固定六行、**前三机器区后三人工区**（与 §3 表格分区同一哲学：决策说明永不挤占结果位，人工结论与机器输出位置分离互不覆盖）：

```markdown
## D-B <决策名>（<关联行ID/需求ID>）
- 决策要求: <该事项需要人做什么、有哪些选项>          ← 机器区（预填，人工只读）
- 机器执行: [待执行:<动作>] | [裁决后执行:<动作>] | 无   ← 机器区
- 证据依据: <Run 编号或文件锚点>                        ← 机器区
- 状态: 待裁决 | 待输入 | 暂缓                          ← 人工区（初始值机器预填；裁决时人改为 已裁决(YYYY-MM-DD) / 已消解）
- 结论: <裁决结果；未裁决必须留空>                      ← 人工区
- 签注: <人名缩写> <YYYY-MM-DD>                         ← 人工区
```

**一望即知规则**：`结论` 为空 = 待办；非空 = 已完成。待办事项的说明只存在于机器区 `决策要求` 行。

决策 ID 体系：`D-x` 人工裁决点、`Z-x` Z_真 显式化项（含待输入数值类）、`Q-x` 澄清问题（沿用登记表）。ID 终身不复用；已消解事项并入他节时保留壳节指向（如 Z3→D-A），不删除。

**状态与执行解锁**：`机器执行: [裁决后执行:…]` 的动作在状态行变为 `已裁决`/`已消解` 后自动转入执行队列"待执行"组（collect 脚本按此分组，见 §6）——人工完成裁决的瞬间，机器侧动作在队列层面可见地解锁。

## 5. 工作台（40-）：回译视图，不是事实源

工作台是 LLM 从台账**整 理 转写**给需求人员的行动清单（回译位产物），**每轮重新生成**——因此它自身不可承载持久回应（人工填写会被下轮生成覆盖，这是 done 陷阱的变体）。它的每个行动项必须指向一个持久事实源的锚点（41- 的决策节或 30- 的行 ID），需求人员的实际回应记录在那些锚点处。工作台头部须带三纪律与完整性守恒声明（首件已立：见 2026-08-27 版）。

## 6. 执行队列（90-）与下游 LLM 调用模式

`tools/scripts/collect_review_actions.py`（确定性脚本，零 LLM）扫描 `review/` 全部填写件：

- 评审表人工区的 `[待执行…]` / `[裁决后执行…]` 标记；
- 41- 各决策节的 `机器执行:` 行（按节标题带出决策 ID 与状态）。

聚合输出 `90-执行队列.md`：每条 = 行 ID/决策 ID + 动作 + 来源文件锚点（+ `--expand` 时嵌入该行/该节文本，供单次调用直接消费）。

**下游 LLM 调用纪律**：自动化步骤的调用上下文 = 执行队列（或其过滤子集），按锚点拉取最小行级上下文；**禁止**为单项任务整读填写件全表——无关行既耗上下文又构成干扰（本规约设计痛点③的机制化解答）。

## 7. 评审者动线（三步）

1. 打开 `review/00-INDEX.md` → 看"本次待办"（未评审行数 + 待裁决决策数）；
2. 点进对应填写件，**就地**在人工区三列填写（看到即记录，无跳转）；
3. 保存即完成（git diff 即评审记录）。需要证据时按 INDEX 链接只读材料，不动它们。

## 8. 本规约与既有文档的关系

- `method/14`（检查规程与人工决策指南）：14 管"检查怎么跑、判定标准是什么"；16 管"评审界面长什么样、放哪里、结果怎么回传"。14 中人工决策点的记录方法自 v1 起指向本规约的 41- 文件。
- 首例迁移：loan-system 案例（2026-08-27，迁移记录见其 review/00-INDEX 与检查台账 Run-10）。

## 9. 演进位

- R2：表格重生的脚本化合并（机器区覆盖、人工区按行 ID 保留）；队列生成的 pre-commit 挂接；
- R3：LLM 回译位（工作台生成）的"完整性守恒"脚本校验（finding 数与台账守恒）；
- 待实践反馈后修订：七列表格在条目数 >100 时的可用性（分表策略）。
