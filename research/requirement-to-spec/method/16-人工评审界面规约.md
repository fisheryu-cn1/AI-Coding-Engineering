# 16-人工评审界面与文档规约

> 版本 v1（2026-08-27）。设计输入：评审实践暴露的三个痛点——①评审文件分散多目录需按说明分别寻找；②评审结果就地记录会覆盖机器原始输出，被迫另存 done 快照（已实际造成活表/快照状态分裂）；③下游 LLM 自动化步骤需要"评审后待机器处理的上下文"集中可寻址，避免单次调用读入无关信息。
> 适用范围：S4 机器检查全绿之后、S5 签收之前的人工环节（翻译审计签注、人工决策点、需求人员回应），及后续消费评审结果的自动化步骤。

## 1. 目录组织：物理归并填写件，逻辑归并只读件

案例目录下设 `review/`，**人工需要动手填写的文件全部物理归并于此**；评审动线中的只读材料（证据台账、模型大纲、SVG 图形）**不复制不迁移**，由 `V00-INDEX.md` 统一链接（一次点击可达）。理由：复制只读件会制造双份漂移面——正是 done 快照教训的推广。

```
review/
  V00-INDEX.md             # 入口：任务清单 + 文件地图 + 只读材料链接（V=只读）
  E30-翻译审计-S3.md        # 填写件（E=人工编辑，模板见 §3）
  V40-需求人员工作台-S4.md   # 只读回译视图（V，LLM 每轮再生成，见 §5）
  E41-人工决策记录-S4.md     # 填写件，决策事实源（含轮次沿革，见 §4）
  G90-执行队列.md           # 生成物（G=脚本聚合，非人工维护，见 §6）
```

## 2. 文件命名规约

**文件名 = 编辑性前缀字母 + 两位编号 + 稳定名称 + 归属阶段**，编号即排序即动线：

| 前缀 | 含义 | 谁可写 | 本案例现例 |
|---|---|---|---|
| `E` | **Edit——人工填写件**（评审动作发生地） | 人工区人工写；机器区机器写 | `E30-翻译审计-S3.md`、`E41-人工决策记录-S4.md` |
| `V` | **View——只读参考件**（导航/回译视图，**禁止在其上填写**） | 生成方（INDEX 人手或脚本维护；工作台=LLM 回译每轮再生成）；**V00-INDEX 须随每轮内容同步更新**——入口陈旧=内容不可见（2026-08-28 kbapp 教训） | `V00-INDEX.md`、`V40-需求人员工作台-S4.md` |
| `G` | **Generated——机器生成物**（勿手改，重生成覆盖） | 脚本 | `G90-执行队列.md` |

| 编号段 | 含义 |
|---|---|
| `00` | 入口导航 |
| `1x`–`6x` | 十位数 = 流水线阶段 S1–S6，个位数 = 同阶段内序号（如 `30-`=`S3`、`40-/41-`=`S4`） |
| `90` | 跨阶段机器汇聚物 |

**参考件与填写件的内容关联**不在文件名层（那是锚点机制的职责，见 §3/§4），而在两处显式声明：①V 件文件头"本文件是 Exx 的××视图/导航"行；②`V00-INDEX` 文件地图的"关联"列（如：V40 工作台 → 各行动项锚定 E41 决策节 / E30 行 ID）。

**版本不进文件名**：文件版本由 git 承担（本仓库即版本库），文件名级版本号会制造 `-done`、`-v2` 类分裂副本——被本规约明令禁止。轮次与演进语义由两个机制承载：①文件头"版本与变更"节（追加式）；②表格**行级 ID**（§3）与决策**节内轮次+沿革**（§4——含人工决策被自动评审退回后重议的场景）。仅当一轮评审整表作废重来时，才允许旧表归档为 `-R<n>-归档` 后缀并重建同名新表（归档例外须在 V00-INDEX 记录原因）。

## 3. 评审表通用格式（模板）

所有"逐条对照、逐条裁决"类评审（翻译审计、场景审计、术语审计等）使用统一表格。以翻译审计为例：

```markdown
| ID | 条目ID | NL 原文(摘录) | 模型元素/落点 | 机器预填 | ✍评审结论 | ✍执行标记 | ✍签注 |
```

**列分区（防覆盖的核心）**：

- 前五列（`ID`/`条目ID`/`NL 原文`/`模型元素`/`机器预填`）= **机器区**：由翻译/检查位生成，评审者只读，自动化步骤重生成时原样覆盖；
- `✍` 前缀三列（`评审结论`/`执行标记`/`签注`）= **人工区**，仅评审者可写，**任何机器重生成必须按行 ID 对齐保留人工区**（v1 为手工纪律；表格重生的脚本化合并列 R2 落地）。
- 表格分隔符一律 ASCII `|`，**禁止在表格行内使用 `│` 等 Unicode 制表符**（曾致表头列数与分隔行不匹配、整表渲染失败，2026-08-27 修复留训）；分区标识靠列名 `✍` 前缀，不靠特殊分隔符。

**行 ID 锚点规则**：`<表码><轮次>-<序号>`，如 `TA1-05`（翻译审计第 1 轮第 5 行）、`TA2-03`。行 ID 全局唯一、终身不复用（行删除后其 ID 不得再分配）。Markdown 表格行没有原生 URL 锚，**锚点 = 行 ID 字符串检索**（脚本与 LLM 均按行 ID 定位拉取该行，不整读文件）。

**合法值词表**：

| 列 | 合法值 |
|---|---|
| 评审结论 | `忠实` / `弱化(<原因>)` / `待澄清(<问题>)` / `确认` / `驳回(<原因>)` / `修正(<内容>)` / `补充(<内容>)`（留空=未评审） |
| 执行标记 | `[待执行:<动作说明>]` / `[仅记录]` / `[裁决后执行:<动作说明>]` / `[驳回执行:<原因>]`（留空=无动作） |
| 签注 | `<人名缩写> <YYYY-MM-DD>`（可加来源注记，如"迁移自 done-v1"） |

`修正(<内容>)`/`补充(<内容>)`（2026-08-27 首例 TA2-04 增补）：评审中给出**超出原条目语义的需求修正或补充**时使用（例："保存草稿前也应触发表单检验规则"）。内容涉及模型/规则变更时，执行标记必须联动指向对应决策节或直接 `[待执行:…]`；该值是对"确认/驳回"二值的补充——评审不止是接受/拒绝机器产出，也是需求精化的一等入口。

**预填文字质量要求**（机器区一切说明文字——决策要求/证据依据/机器预填列——的红线，2026-08-27 依用户反馈增补）：

1. **上下文自足**：决策者不读登记表/台账原文也能理解该条目在问什么——涉及的需求条目须就地给出原始语义（而非只写编号），涉及的证据须就地给出结论性一句话（而非只写 Run 编号；Run 编号作为溯源锚保留）。
2. **不自造词**：使用登记表与本项目术语表的原始表述；内部缩写（如 D-B、TA1-03）首现时以"缩写（一句话解释）"形式就地展开；禁止无定义的工程黑话。
3. 目标 = 把决策者的记忆负担降为零：所有理解所需的信息都在条目眼前，记忆只用于判断而非检索。

### 3.1 API 对齐评审表（E50-，2026-08-30 增补）

API 契约（设计文档接口声明）↔ 代码实现（OpenAPI 反向生成物）的对照评审使用专用表型（首例：loan-system 05-openapi-anchor，源自第 35 场实验）：

```markdown
| 行ID | design 声明(原文摘录) | OpenAPI method+path | 判定 | 证据锚 | 关联决策 | ✍评审结论 | ✍执行标记 | ✍签注 |
```

与 §3 通用表的差异及专项规则：

1. **机器区六列**（行ID/design 声明/OpenAPI/判定/证据锚/关联决策）+ 人工区三列，分区与防覆盖纪律同 §3；
2. **判定词表**（五类）：`一致` / `形近变体(<差异说明>)` / `设计未实现` / `代码超出设计` / `等价但语义存疑`；
3. **条目锚的两级规则**：新项目设计文档的接口声明**必须先编号**（`EP-xx`，method/12 ID 纪律向设计接口声明的延伸——比对表行锚定 EP 编号，design 变更后行稳定）；存量无编号文档（如外部交付）允许位置锚（原文摘录+行号），须在表头注明其脆性（design 变更后按原文摘录重对齐）；
4. **组级决策聚合**：同一偏差成因的多行（如同一资源命名分歧产生的 8 条形近变体）不开多节，聚合为一个决策节（`DA-x`）——"关联决策"列填 DA 编号，行内评审结论随组裁决批量落；
5. **裁决出口三分支**（机器执行列展开）：回写设计文档 / 修改代码 / 豁免登记（如运维惯例接口）；原交付不可改时降级为"登记为已裁决偏差"；
6. **回归签收**：裁决执行后重跑反向生成（确定性，G 产物覆盖）+ 比对重生成——已裁决偏差的判定应转为 `一致` 或附裁决锚；签收标准 = 无未裁决偏差行且队列清零（G 门思想移植）；
7. **发现的分层**：比对表行承载规则可判的发现（L1）；行为级可疑点（伪成功/语义变异等，超出 method/13 覆盖四维的运行时行为层）直接进 `DA-x` 决策节（L2），不强行入表。

**决策 ID 体系增补**：`DA-x` = API 对齐决策点（与 §4 的 D-x/Z-x/Q-x 并列，全局唯一、终身不复用）。

## 4. 人工决策记录（E41-）

散落在表格行内的"待澄清/待裁决"事项，必须在 `E41-人工决策记录` 开独立决策节（表格行只做指向）。每节固定八行、**前三机器区后五人工区**（与 §3 表格分区同一哲学：决策说明永不挤占结果位，人工结论与机器输出位置分离互不覆盖）：

```markdown
## D-B <决策名>（<关联行ID/需求ID>）
- 决策要求: <该事项需要人做什么、有哪些选项>          ← 机器区（预填，人工只读；质量要求见 §3）
- 机器执行: [待执行:<动作>] | [裁决后执行:<动作>] | 无   ← 机器区（裁决后由执行位按结论+附记展开为具体清单）
- 证据依据: <结论性一句话 + Run 编号/文件锚点>          ← 机器区
- 状态: <词表见下>                                      ← 人工区（初始值机器预填）
- 结论: <当前轮裁决结果一句话主句；未裁决必须留空>       ← 人工区
- 附记: <裁决的完整陈述：论证、对原始需求的修正说明、     ← 人工区（可选；结论只是一句话主句，
        实现意图等长文本。裁决含论证时必填>                  附记承载全部展开——下游执行位读此行展开动作>
- 签注: <人名缩写> <YYYY-MM-DD>                         ← 人工区
- 沿革: <各轮记录，只追加>                              ← 人工区尾（见下）
```

**结论与附记的分工**（2026-08-27 首例 D-B 增补）：结论 = 一望即知的裁决主句（扫描用）；附记 = 完整裁决陈述（执行与复核用）。裁决含论证、含对原始需求文档的修正、或超出决策要求预设选项时，附记必填——这正是人工裁决产出新知识的载体（见案例报告"评审方法价值实证"）。

**状态词表**：`待裁决(第N轮)` | `待输入(第N轮)` | `暂缓` | `已裁决(YYYY-MM-DD, 第N轮)` | `已消解` | `退回重议(第N轮)`。

**一望即知规则**：`结论` 为空 = 待办；非空 = 已完成（当前轮生效中）。待办事项的说明只存在于机器区 `决策要求` 行。

决策 ID 体系：`D-x` 人工裁决点、`Z-x` Z_真 显式化项（含待输入数值类）、`Q-x` 澄清问题（沿用登记表）。ID 终身不复用；已消解事项并入他节时保留壳节指向（如 Z3→D-A），不删除。

### 4.1 退回重议（人工决策被自动评审否决或要求细化）

人工裁决**不是终局**：裁决生效后，机器侧仍可能证明其有问题或依据不足。三类触发源：

| 触发源 | 典型情形 |
|---|---|
| 执行链检查 FAIL | 裁决回写模型后全链重跑，HermiT 不一致 / Z3 unsat core 指向该裁决 / 新 sha256 基线漂移无法归因 |
| 自动评审位（R3/R4） | LLM 审计或分歧度门禁判定决策依据不足、与登记表其他条目语义冲突 |
| 新证据到达 | 需求变更 / 新 Run 证据推翻裁决前提 |

**退回操作规程**（自动化步骤执行，这是机器写人工区的**唯一豁免情形**）：

1. 将当前轮"结论+签注"**原文移入沿革**（不删不改）：`- R1 2099-01-01 FY "接线" → 退回(Run-11): <原因>（<证据锚点>）`；
2. 清空结论/签注，状态改 `退回重议(第N轮)`；
3. 在机器区证据依据行追加退回证据锚点；队列中该节动作归回"裁决后执行"组（等待状态=退回重议）；
4. 需求人员重议时按常规流程填写（新一轮次），历史轮永远留在沿革——**这就是决策记录的"版本标记"：轮次在节内，不在文件名**（文件级版本仍由 git 承担，理由见 §2）。

**状态与执行解锁**：`机器执行: [裁决后执行:…]` 在状态为 `已裁决`/`已消解` 时自动转入执行队列"待执行"组；被退回（`退回重议`）则留在"裁决后执行"组直到新一轮裁决（collect 脚本按此分组，见 §6）。

## 5. 工作台（V40-）：回译视图，不是事实源

工作台是 LLM 从台账**整 理 转写**给需求人员的行动清单（回译位产物），**每轮重新生成**——因此它自身不可承载持久回应（人工填写会被下轮生成覆盖，这是 done 陷阱的变体）。它的每个行动项必须指向一个持久事实源的锚点（E41- 的决策节或 E30- 的行 ID），需求人员的实际回应记录在那些锚点处。工作台头部须带三纪律与完整性守恒声明（首件已立：见 2026-08-27 版）。

## 6. 执行队列（G90-）与下游 LLM 调用模式

`tools/scripts/collect_review_actions.py`（确定性脚本，零 LLM）扫描 `review/` 全部 E 前缀填写件：

- 评审表人工区的 `[待执行…]` / `[裁决后执行…]` 标记；
- E41- 各决策节的 `机器执行:` 行（按节标题带出决策 ID 与状态）。

聚合输出 `G90-执行队列.md`：每条 = 行 ID/决策 ID + 动作 + 来源文件锚点（+ `--expand` 时嵌入该行/该节文本，供单次调用直接消费）。

**下游 LLM 调用纪律**：自动化步骤的调用上下文 = 执行队列（或其过滤子集），按锚点拉取最小行级上下文；**禁止**为单项任务整读填写件全表——无关行既耗上下文又构成干扰（本规约设计痛点③的机制化解答）。

## 7. 评审者动线（三步）

1. 打开 `review/V00-INDEX.md` → 看"本次待办"（未评审行数 + 待裁决决策数）；
2. 点进对应填写件，**就地**在人工区三列填写（看到即记录，无跳转）；
3. 保存即完成（git diff 即评审记录）。需要证据时按 INDEX 链接只读材料，不动它们。

## 8. 本规约与既有文档的关系

- `method/14`（检查规程与人工决策指南）：14 管"检查怎么跑、判定标准是什么"；16 管"评审界面长什么样、放哪里、结果怎么回传"。14 中人工决策点的记录方法自 v1 起指向本规约的 E41- 文件。
- 首例迁移：loan-system 案例（2026-08-27，迁移记录见其 review/V00-INDEX 与检查台账 Run-10）。
