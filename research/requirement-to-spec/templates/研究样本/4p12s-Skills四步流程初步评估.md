# 4p12s-Skills「brainstorm → requirements → prd → user-stories」四步流程初步评估

> 评估日期：2026-08-26。评估对象：`templates/研究样本/4p12s-Skills/` 中的 brainstorming-preset、4p12s-requirements、4p12s-prd、4p12s-user-stories 四个 skill；参考依据：消费者 skill（4p12s-technical-design、4p12s-verification-plan）的消费规则与 4p12s-delivery-orchestrator 的编排规则。
> 评估框架：本项目（requirement-to-spec）的三层"完整"定义（一致性/结构完备/语义完备）、advisory-enforced 判据、同源验证问题、Z_真（真决策集）显式化与消解视角（见 `../../../plan/00-研究计划.md` 与上游备忘 §8）。

## 0. 样本事实先行：四步实为两体系拼接

**brainstorming-preset 属 superpowers 开源系**（产出写入 `docs/superpowers/specs/`，终态固定为"invoke writing-plans skill"），**requirements/prd/user-stories 属 4p12s 自研交付系**（编排于 delivery-orchestrator 的 11 步固定流程）。两者之间**无衔接规则**：brainstorm 的产物（design doc）如何成为 requirements 的输入（`raw_input_path`）未定义；且两者语义重叠冲突——brainstorm 的"设计文档"已含架构/组件/数据流决策，而 4p12s 把这些归入下游 design 步。**将四步视为一条连续流程是评估设定的假设，样本本身存在体系断层**。后续评估按"假设已拼接"进行，断层单列为缺陷 D1。

## 1. 各步机制摘要

| 步骤 | 产物 | 核心机制 | 人工介入点 |
|---|---|---|---|
| brainstorming-preset | spec 设计文档 | HARD-GATE（未批准不得实现）；一次一问澄清；2-3 方案对比；分段呈现逐段批准；**spec 自审 4 项**（占位符/内部矛盾/范围/歧义）；可选派发 reviewer 子代理（五查+宽松校准） | 逐段批准+spec 文件评审门 |
| 4p12s-requirements | requirements-register.md | **9 类稳定 ID**（BR/FUNC/RULE/FLOW/FIELD/UI/PERM/NFR/INT）；12 条提取规则（保真不译技术方案/图片证据→观察→ID/复合拆分/规则独立成行/不编造优先级）；阻断性澄清循环；视觉证据登记 | 阻断性澄清问答 |
| 4p12s-prd | prd.md | 10 章模板（含主/异常/边界流程三分）；**覆盖规则**：范围内每个需求 ID 必须出现或进"范围外"附原因；验收标准须可观察可测试 | 无显式（门禁自检） |
| 4p12s-user-stories | user-stories.md | US/AC/SC 三级 ID + Given/When/Then；5 级验证层级/Git 阻断/降级规则元数据；**双向覆盖**：每需求 ID≥1 US、每 PRD 验收标准≥1 AC/SC；缺验收标准→blocked 不凭空创建 | 无显式 |

消费者约束（倒推上游要求）：technical-design 要求"引用的 US/AC/SC 必须存在于上游、每需求 ID 有承接或记录原因、设计元素唯一出现并映射上游"；verification-plan 要求"每需求 ID/每验收标准/每 AC-SC/每设计元素 ≥1 测试用例、目标测试文件为完整路径无占位符"。编排器提供：状态账本（唯一状态源、文件产物优先于账本）、事务式推进、回退映射表（哪类不清→回退哪步）、越界写入检查、STEP_RESULT 契约。

## 2. 评估一：过程完整性

**拓扑层完整（真实优势）**：四步覆盖了"开放式→规范化"的核心认知动作链——意图探索（brainstorm 澄清与方案对比）→事实登记（requirements 分类+溯源）→结构化组织（prd 十章）→可验收化（GWT 场景）。追溯链做到 **ID 级全链闭环**：需求 ID→US→AC/SC→设计元素→TC，配合双向覆盖规则，等价于需求管理界的**追溯矩阵拓扑闭包**（本项目备忘 §8.5 所述行业共识形态），且粒度到单条目而非文档级。回退规则显式化（业务不清→回 user_stories/prd；契约不清→回 design）补上了"发现上游缺陷如何回流"的路径。

**语义层不完整（五处缺口）**：

- **D1 体系断层**（§0）：brainstorm 产物无通道进入 4p12s 流；其"设计文档"与 4p12s 分层冲突。
- **D2 无术语统一环节**：全流程没有术语表/glossary 步骤。requirements 的"结构化表述"列由 LLM 自由措辞，同义词与别名无治理（同一概念先写"退款单"后写"退货单"无机制拦截）——对应本项目缺失的 S2。
- **D3 待决项传递链断裂**：requirements 的澄清问题、prd 的"待确认问题"、user-stories 的"缺口与阻断"都允许**带阻断项合法通过**（编排器把 blocked 当合法停止态），但下游 design/verification-plan 只有各自的"风险与开放问题"表，**没有任何规则要求消费上游待决项**——Z_真 被显式化了，却没有生命周期管理（谁在何时必须消解或继承）。
- **D4 一次性导向，无变更影响机制**：更新场景仅提及"已存在的产物路径"；修改一条 RULE-* 是否回退重跑下游无判定规则（回退表按"不清类型"触发，不按"变更类型"触发）。
- **D5 最强的独立评审未被强制**：spec-document-reviewer（五查+输出契约）是可选件，brainstorm 正文 checklist 仅要求"quick inline check"自审；且其校准原则是"Approve unless serious gaps"（宽松）。

## 3. 评估二：约束完备性

**强约束（值得借鉴的工程化设计）**：

1. **ID 所有权与命名空间规则**：`TC-xxx` 由 verification-plan 拥有、`US/AC/SC` 由 user-stories 拥有、下游"必须复用不得新建"、澄清问题 ID（Q-*）不得冒充需求 ID、已分配 ID 不重编号——一套防 ID 漂移的完整规则。
2. **双向覆盖（防丢失+防编造两侧都封）**：上游"每个 ID 必须出现或显式排除"，下游"不得引入上游不存在的需求""缺依据→blocked 不凭空创建"。
3. **经验凝结的针对性保护规则**：前端交互信号不得降级为 NFR、UI-* 必须有 E2 可观察验收、前端 E2E 默认 Git 阻断——明显是踩坑后的补偿性规则，价值密度高。
4. **负面清单式边界**：每 skill"不创建下游产物/不删原始文本/不编造优先级/不把业务翻译成技术方案"+`allowed_write_paths` 写边界 + 编排器越界检查。
5. **状态机纪律**：合法状态受限词表，禁用 todo/done 等别名；事务式推进；崩溃后"文件产物优先于状态账本"重建现场。

**弱约束（缺口）**：

- **C1 一致性零约束**：RULE-* 之间矛盾、FLOW-* 死端（未达终态无后续节点）、FIELD-* 引用未定义——三件套（SAT/Petri soundness/引用完整性）完全缺席。流程对"相互矛盾的规则合法共存于 prd 第 5 章并顺利通过全部门禁"没有任何拦截手段。
- **C2 合格性无操作化定义**：门禁写"验收标准足够具体，可以供给验收场景生成"，但"足够具体"无判定标准；requirements 层的"结构化表述"无句式约束（EARS 类模板缺席，GWT 只在最后一步出现——半形式句式来的太晚，无法反向约束中间产物）。
- **C3 覆盖规则无执行器**：双向覆盖写了规则但没有机器检查——ID 引用闭包恰是**最容易脚本化确定性验证的检查**（集合差运算），样本连这个都没做，全部交给 LLM 自查+编排器（也是 LLM）复核。
- **C4 外部共识引用（Z_伪）无处理机制**：无默认值约定、无外部标准引用登记（"jpeg 格式"类引用如何解析、采用什么行业默认参数，无规则）。
- **C5 数值/单位/优先级取舍无规范**：优先级仅"未明确"占位，无 P0-P2 分配规则（verification-plan 侧有 P0/P1/P2 但上游无来源）。

## 4. 评估三：质量保障作用

**能保障的（结构层质量，真实有效）**：对 LLM 三类高发失败——**遗漏需求**（忘掉某条）、**幻觉需求**（编造上游没有的）、**降级偷懒**（把交互需求塞进 NFR、验收写成不可观察的套话）——该流程有系统性约束力；追溯 ID 链使"这条测试为什么存在"永远可回答。这些约束对齐了 SDD 的"spec enforced"方向，工程化程度高于 Kiro/Spec Kit 的一般性人审（后者无 ID 级覆盖规则）。

**不能保障的（语义层质量）**：

1. **矛盾检测缺位**（C1 的后果）：一致性完全依赖 brainstorm 自审第 2 项（"Do any sections contradict each other?"——LLM 肉眼扫）。
2. **空泛通过**：无对抗"空泛一致"的机制——写一套什么都不敢约束的 GWT（Given 一些数据 / When 操作 / Then 成功）可通过全部门禁；没有预期实例测试位。
3. **意图忠实无审计**：requirements 的"保留原始业务含义"与 prd 的"保留业务含义"是**要求而非机制**——翻译保真靠 LLM 自觉，无 NL↔结构化对照审计（本项目 S3 的翻译审计缺位）。
4. **同源验证天花板**：全部"质量门禁"的执行者是 LLM 自检 + LLM 编排器复核——**用生成者验证生成物**，无外部确定性 oracle。按 advisory-enforced 判据，该流程的实际 enforced 部分接近零（若人工抽查门禁存在则为弱 enforced）。
5. **"足以支撑下游"由 LLM 裁定**：requirements 的 `passed` 定义是"登记有足够证据支撑 PRD 生成"——"足够"的判定者是同一个 LLM，无分歧度/收敛性度量（本项目 S5 缺位）。

**总体定性**：这是一套**把"advisory 质量纪律"制度化的高水平实践**——用 ID 溯源、双向覆盖、负面清单、状态纪律把 LLM 的自由度压到结构层可控；但**验证语义停留在拓扑层**，一致性与强度无保障。对照本项目三层定义：结构完备（部分达成，有规则无执行器）、一致性（未覆盖）、语义完备（未覆盖）。

## 5. 消费者视角的验证结论

design 与 verification-plan 的消费规则倒推出的上游必要条件：**ID 存在性**（满足——ID 体系完整）、**验收标准可映射性**（部分满足——有映射规则但"可观察/可测试"无判定）、**Git 阻断项可验证性**（部分满足——user-stories 声明了阻断标志，verification-plan 有承接规则，但阻断项的"验证路径"仍由 LLM 设计）、**前端 E2E 可执行性**（规则链完整但同属 LLM 自检）。消费端最重的依赖（"PRD 验收标准是下游验收场景生成的输入依据"）恰好落在上游最弱的环节（验收标准的具体性无判定）——**约束链的强度受限于最弱一环，而该环节无加强机制**。

## 6. 对本项目的启示

**直接借鉴清单**（R0 方法设计吸收）：9 类需求 ID 分类学；ID 所有权/命名空间/防漂移规则；双向覆盖规则模板；前端保护规则组；STEP_RESULT 契约 + allowed_write_paths；回退映射表；状态账本与"文件优先"重建规则。

**本项目的差异化补强**（即样本缺口 ↔ 我们的 S 环节映射）：

| 样本缺口 | 本项目对应环节 |
|---|---|
| D1 两体系断层 | S0–S1 单一流程内完成意图探索与登记（brainstorm 功能并入 S1 解析+澄清） |
| D2 无术语表 | S2 受控词汇表 |
| C1 一致性零约束 | S4 三件套（SAT/soundness/引用完整） |
| C2/C5 句式与数值无规范 | S2 EARS 子集+S3 形式化翻译 |
| C3 覆盖无执行器 | R2 第一件脚本就做 **ID 引用闭包检查**（低成本高收益，样本验证了其未被现有实践覆盖） |
| D3 待决项断链 | S1/S5 待决项全生命周期传递规则（Z_真 显式化后的闭环） |
| 空泛通过 | S4 预期实例测试 |
| "足够"由 LLM 裁定 | S5 分歧度签收（Z_真 可计算度量） |
| 翻译无审计 | S3 翻译审计对照表 |

**R1 实验建议**：将本样本四步流程作为**对照组基线**——同一案例需求分别走 4p12s 四步与本方法 S0–S5，比较：检查器捕获缺陷数（本方法应捕获 C1 类矛盾而基线放行）、Z_真 曲线（分歧度沿阶段收敛对比）、以及两法产物被同一 verification-plan 消费时的回退次数。

## 7. 结论（初步）

- **过程完整性**：拓扑完整（追溯链 ID 级闭环+回退显式），语义不完整（术语/一致性/待决闭环/变更影响四缺，另有两体系拼接断层）。
- **约束完备性**：负面约束（防错性"不得"）体系化且工程化程度高；正面判定（何为合格的可检定义）与确定性执行器缺位。
- **质量保障作用**：可有效保障**结构层质量**（防遗漏/防幻觉/防降级）；不能保障**语义层质量**（矛盾/空泛/失真无拦截），根本限制是"LLM 验证 LLM"的同源结构——**它是把分离点前推工作的优秀上半场（结构化+溯源+澄清循环），缺的正是本项目的下半场（确定性检查+分歧度签收）**。

评估性质：静态规范评估（SKILL.md 文本分析），未运行动态执行；结论限于设计文本所载约束的完备性，实际运行中 LLM 对约束的遵循率（概率性执行）是另一层衰减，需 R1 对照实验实测。

## 8. 动态验证：真实产物比对（2026-08-26 补充）

> 对象：`giencoder-exam-P0151020/deliveries/个人消费贷款管理系统`（考题型输入：SCENE-B 需求文本+Vue3/Express 脚手架；11 步全流程执行；终态 release_trigger=blocked，理由正当——项目无发布入口）。规模：登记 21 条需求 ID（BR2/FUNC3/RULE4/FLOW2/FIELD3/UI4/NFR1/DEL2）→ PRD 15 条验收标准 → 8 US/13 AC/13 SC → 18 设计元素 → 14 TC → 全部执行（后端 16+前端 7 测试、Playwright 真浏览器 E2E 无 mock、真实构建/推送证据）。
> 方法：全文精读 + **确定性 ID 闭包脚本核验**（静态评估 §3-C3 所述"最易脚本化检查"的实际执行）。

### 8.1 确定性核验结果（ID 引用闭包）

| 检查项 | 结果 |
|---|---|
| PRD 悬挂引用（引用未登记 ID） | **0** |
| PRD 对登记 ID 的覆盖 | 21/21 全覆盖 |
| design 悬挂引用 | 0 |
| design 承接（除 BR 目标类） | 缺 **RULE-003**（唯一缺口） |
| user-stories 映射 | 缺 **RULE-003**（"每需求 ID≥1 US"门禁被违反且自检未发现） |

**拓扑层结论**：ID 纪律的实际遵循率极高（悬挂引用为零、除一条外全闭包）——LLM 对"结构化抄写型"约束的遵循是其强项，静态评估对拓扑层的正面判断被证实且强于预期。

### 8.2 静态评估预测的实证对照

| 静态评估预测 | 动态结果 |
|---|---|
| C3 覆盖规则无执行器→漏检风险 | **实证**：RULE-003（贷款用途固定枚举 4 类）全链静默丢失——登记✓→PRD 规则表/口径✓但**验收标准表缺条目**→无 US/AC→design 无承接（用途枚举校验无设计元素）→VP 无测试→实现无验证。丢失点始于 PRD 验收标准层并链式传导；门禁规则以"PRD 验收标准"为源执行而规则文本以"需求 ID"为源，**规则与执行的判定基准错位** |
| C1 一致性零约束→矛盾存活 | **实证**：操作员角色语义跨文档矛盾——requirements（FLOW-001/002 行）与 PRD（角色表、主流程步 5、异常流程 4）共 5 处规定"操作人员执行通过/驳回"；user-stories（US-006 范围外明确排除"操作员人工通过/驳回"）+ design（范围外+状态流"自动审批即生效"）+ 实现/E2E 规定相反。PRD 主流程步 3（自动审批直接进 approved）与步 5（操作员执行通过/驳回）**内部亦有张力**。成因=US 层澄清修正后未回写上游（D4 变更无回流实证），矛盾存活于全部通过门禁的最终产物集 |
| 空泛一致（GWT 空泛） | **轻于预期**：AC 普遍具体（E2E 证据含具体数值"评分 48 未达阈值 60"、费率 8.00%/2.00%/0.05%）；仅 AC-011 的 Given 含两状态但 When 只测一态等轻度空泛 |
| D2 术语漂移 | 轻度实证："申请信息"混指 Borrower+LoanOrder、UI-001"申请列表页"与订单列表滑动——可辨认、无 glossary 治理 |
| D3 待决项断链 | **本例未发作（正面修正）**：阈值 60/默认费率沿"PRD 待确认→US 缺口→design 风险→实现→E2E 证据"完整闭环——但依赖"下一步动作"字段恰好被下游消费，机制上仍无强制消费规则 |
| 同源验证天花板 | **实证**：两类漏检缺陷均非 LLM 能力问题而是机制缺位——20 行 ID 闭包脚本即可抓住 RULE-003 丢失；一处上游回写对照即可抓住语义矛盾。LLM 自检+LLM 编排器复核均未发现 |

### 8.3 TC-005：无声层级降级（规则违背实例）

AC-005 声明最低验证层级 cross_boundary_e2e 且"是否允许降级验证：否"，但 E2E 结果表中 TC-005 的执行方式为**组件测试**（borrowerForm.spec.ts，断言 mock 的 borrowerApi.create 未被调用）——违反自身"不允许降级"与"前端 E2E 不能只依赖纯 UI 断言/禁 Mock"规则，且未走降级流程（对照：TC-014 因环境无 MySQL 的降级**有正式降级说明**，展示了降级机制的正确用法）。降级本身合理（必填提示组件层已可充分验证），但过程违反了自家规则且无声。

### 8.4 正面发现（优于静态评估预期处）

1. **拓扑纪律近乎完美执行**（8.1）——约束设计与 LLM 强项（结构化抄写）对齐时遵循率极高。
2. **E2E 真实性**：Playwright 真浏览器驱动完整业务闭环、真实后端、无 mock；验收证据具体（双分支覆盖：高收入通过/低收入大额拒绝）。
3. **澄清循环有效**：Q-001~Q-003 三问全部回写结论到登记表（含"澄清结论（补充证据）"专节）。
4. **诚实阻断**：编排器对无发布入口的 release_trigger 给出正当 blocked 而非伪造完成（对照其"发布触发没有真实 API 证据却标记完成"的禁止条款，本次遵守）。
5. **TC-014 正式降级说明**：环境受限时的降级决策有记录、有理由、有替代断言与生产路径——降级机制的规范用法样本。

### 8.5 实际有效性与质量结论

- **产物质量**：作为考题规模交付，属高水准——全链可追溯、验证真实执行、证据具体；但存在**一条业务规则全链丢失**与**一处跨文档方向性矛盾**，均为语义层缺陷，均通过全部门禁。
- **Skill 实际有效性**：静态评估"上半场优秀（拓扑）/下半场缺位（语义）"的判断被动态数据**精确印证**——拓扑层有效性高（利用 LLM 抄写强项）；语义层有效性确凿失效（漏检的两类缺陷各有一例实证，且均可被廉价确定性检查捕获）。附加发现：门禁规则的**判定基准错位**（规则写"需求 ID"、执行按"PRD 验收标准"）是覆盖漏检的直接成因之一——规范文本与执行解释之间也存在"翻译"问题。
- **对本项目 R1/R2 的意义**：①该交付直接用作 R1 对照基线实物样本（缺陷已知，可回填验证我们的检查器能否全部捕获：ID 闭包→RULE-003、一致性对照→操作员矛盾、GWT 审计→AC-011/TC-005）；②20 行脚本抓住真缺陷——R2 首件脚本（ID 引用闭包）的投入产出已被实证；③新增收敛点：**"规范文本的判定基准必须与执行解释一致"**应写入 method/11（人机分工规范）的反懒惰条款。

> 局限声明：单案例（考题型、小规模、无真实多方干系人），漏检率不可外推；但每类静态预测的缺陷均获得至少一例确证，机制性结论（同源验证缺位）不受样本量影响。
