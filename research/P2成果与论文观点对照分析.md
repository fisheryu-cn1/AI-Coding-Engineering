# P2 阶段实验结果与论文观点对照分析（阶段性报告）

> 用途：本研究的 P2 阶段（2026-08-17 至 08-19）已结束，进入 P3 阶段之前，把这一阶段的实验结果与项目初期收集的 36 篇学术论文的观点做一次系统对照——哪些结果与文献一致（印证）、哪些不一致或存在幅度差异（需解释）、哪些是文献没有讨论过的新发现。本文件也服务于最终综合报告的文献对话章节。
> 读者约定：本文件自足——不需要读者预先了解本研究的任何细节。第 0 节提供全部背景；文中出现的研究术语在第 0.3 节的术语表中定义；论文观点转述自本仓库 `references/` 目录下的精读摘要（每条附摘要文件路径，可复查），未回读论文原文。

## 0. 背景：本研究在做什么、P2 阶段做了什么

### 0.1 研究项目

本研究是一个关于"如何工程化地构建以大语言模型为核心组件的软件"的对话式研究项目，分三个方向：一是**专用智能体的组装方法**（如何用可复用组件拼装出一个做特定工作的 AI 助手，而不是每次从零开发）；二是**面向大模型软件的软件工程原则**（传统软件工程的概念——规约、验证、中间产物——在"程序行为由模型概率生成"的软件里如何变形）；三是**可观测性**（如何度量和评估这类软件与其开发过程）。

### 0.2 P2 阶段的实验（在方向一的框架下进行，同时为方向二、三提供数据）

研究对象是一个真实的小型知识库软件项目（下称"源项目"，位于本仓库 `design/kb-app/`）。它有一段完整的开发历史：设计文档链、五轮人工加 AI 的代码评审报告、以及修复每次评审发现问题的提交记录。P2 阶段围绕这段历史做了五块工作：

1. **组装一个代码评审智能体**：在开源智能体框架 pi 之上，装配件包括——一份**评审规则包**（skill：十条评审规则及配套的检查程序、反例信号，随智能体分发的文本知识资产）、评审任务提示模板、输出格式模板（"意见卡"）、防止智能体越界写文件的守卫扩展、以及一个自动评分脚本。整个工作区在 `research/custom-agent/experiments/review-pi/`。
2. **建立评估集并迭代规则包**：从源项目历史评审报告中整理出 **21 个已证实的真实缺陷**作为"考题"（每个考题锚定一个缺陷还存在的代码历史版本），让评审智能体去审那个版本的代码，看它能否独立发现这些缺陷。规则包经三轮"分析漏检原因 → 修订规则 → 重新测试"的迭代（v1→v4）。
3. **对照实验**：同一个模型，分别在"加载规则包"与"不加载规则包"两种条件下评审同一批缺陷，度量规则包这份知识资产的增量价值。
4. **评审闭环**：模拟真实开发中的做法——一个模型写代码（A 角色），另一个评审（B 角色），A 对评审意见逐条应答（接受/驳回需给反证），修复后 B 再复审。用历史材料完整走了一遍并做成可复用的流程工件。
5. **第二个语料的静态验证**：另取一个文档完备但没有 git 历史的项目（Vision-Sudoku，一个数独应用），把它文档链中记录的 27 个已证实缺陷逐条对照规则包，统计哪些类型的缺陷能被现有规则引导发现。

### 0.3 术语表（本文所有研究术语在此定义）

| 术语 | 含义 |
|---|---|
| 锚点 | 被评审代码的一个历史版本（git 提交号）——缺陷在该版本中存在、随后被修复 |
| 意见卡 | 评审智能体的输出文档：逐条列出发现的问题（级别、代码位置、证据、建议） |
| 命中 / 语义命中 | 一个考题缺陷被评审发现称为"命中"；"语义命中"指人工逐条比对意见与考题后的严格判定（区别于关键词匹配的宽松机械判定——后者只作上界参考） |
| 试跑（run） | 一次完整的评审运行（本文共 12 次，编号 run1–run12；不同 run 用的规则包版本不同） |
| 评审污染 | 评审输入中混入了不该有的信息（如别次评审的旧输出、或含考题答案的文档），导致命中数字虚高不可用 |
| 适配器 | 把不符合约定格式的旧产出物转换成约定格式、再送入评分脚本的小程序——原则是转换旧产物而不是修改评分脚本去迁就格式 |
| 留出检验 | 用规则包从未接触过的项目来检验规则的真实泛化能力（源项目上测出的是"学过的内容回注"效果，不能代表泛化） |

**已知局限（诚实登记）**：源项目的两份历史评审报告（也就是考题的"标准答案"）恰好在被评审的代码版本中就已经提交入库——评审智能体读设计文档目录时合法可见。无法回溯判断各次试跑是否实际读过它们，因此该锚点上的历史命中数字整组带此风险标注（2026-08-19 起的运行规程已明令禁止读取锚点内的评审报告）。

## 1. 与论文观点一致的实验结果（十组）

每组按"实验与发现（自足描述）→ 对应论文观点 → 一致点"陈述。

**1-1 迭代改进闭环有效。** 实验与发现：规则包经三轮"分析漏检原因→修订→重测"迭代，在同一批 11 个考题上，严格口径的命中从初版的约 1–2 个（9–18%）提升到第四版的 10 个以上显式命中（≥10/11）；该迭代机制本身重复验证了三次。论文观点：Reflexion（`references/AgentParadigms/summaries/06-Reflexion语言化反思.md`：把成败反馈转成语言化反思存入记忆、下次注入，不更新模型权重即实现自我改进）；MetaGPT（`12-MetaGPT多智能体装配线.md`：执行+单元测试+调试记忆的迭代使通过率 +4.2~5.4 个百分点）；SE 智能体综述（`02-面向软件工程的LLM智能体综述.md`：每轮自然语言反馈增益 2–17%）；Agent 框架实证（`18-Agent框架代码任务实证.md`：轨迹反思修订使修复率 47.3%→53.7%）。一致点：方向与量级（两位数百分点）同向。

**1-2 反馈质量是瓶颈。** 实验与发现：迭代并非总能修复漏检——有一个考题（关系数据表的合并键缺少一个区分维度）连续两个规则版本都没发现，复盘确认根因是规则的检查程序写得不够具体（检查者判不出问题），而不是规则缺失——即"错误定位"失败比"没有规则"更常见。论文观点：SE 智能体综述（同上：Self-Refine 的失败 33% 源于错误定位、61% 源于不当修复建议）。一致点：我们把失败按五个根因分类（规则缺失/检查程序不可操作/适用条件误排除/规则过宽/非规则问题）正是这一警示的操作化。

**1-3 规则包注入的增益是条件性的。** 实验与发现：严格对照（同一模型、同一批 11 个考题、唯一差异是是否加载规则包）显示命中 3 个 → 4 个——增益存在但幅度有限，且规则包版本相同的不同试跑之间方差很大（4 到 11 个命中）。论文观点：τ-bench（`23-TAU基准工具策略.md`：把领域政策从系统提示中移除，某场景掉 22.4 个百分点而另一场景只掉 4.4——规则只有强模型真正在用）；τ²-bench（`24-TAU2双控协调基准.md`：政策形式有条件生效，场景不匹配反而造成混淆）；Plan-and-Solve（`08-计划与求解提示范式.md`：提示指令越详尽推理质量越高）。一致点：与 τ 系列的"条件性生效"一致；与另一些文献的大幅效应的表面不一致见第 2-1 节的解释。

**1-4 规则需要分层、溯源和版本管理。** 实验与发现：规则包按"恒适用/满足条件才适用"分两层并配适用条件表；每条规则标注来源（提炼自通用实践，还是由某个考题的漏检触发增补）；修订史单独记录在版本日志中，规则修订须走受控流程（含防止规则死记硬背源项目的检查）。论文观点：SASE 路线图（`03-Agentic软件工程支柱与路线图.md`：领域规则应做成版本化的一等工件、规则自身要过质量门）；LLM 构件分类学（`references/SEforLLM/summaries/01-LLM作为软件构件分类学.md`：提示拆为静态指令/动态状态/任务三部件且来源可溯源）；Promptware 工程（`SEforLLM/summaries/02-提示使能系统的软件工程.md`：提示演化需要变更日志、语义化版本与影响检查）。一致点：分层+溯源+版本化三项实践与四篇论文主张同构。

**1-5 评估要锚定真实缺陷、看多次一致性、防污染。** 实验与发现：考题全部来自真实评审历史而非合成；一致性只在同一规则版本内计算（相当于文献的 pass^k 口径）；实验过程中**发生了三次评审污染**（智能体读了旧意见卡 / 读了工作区里后续版本的文档 / 答案文档在锚点内合法可见——见第 0.3 节局限），每次都导致数字不可引用，最终把隔离规程改为逐类枚举信息通道。论文观点：τ-bench（提出 pass^k：平均能过不等于每次能过——我们不同试跑 4~11 个命中的大方差正是其实证）；SWE-Bench 错觉（`21-SWE基准错觉与记忆污染.md`：模型对热门基准的问题分布过拟合，引用榜单须注明污染口径）；GAIA（`25-GAIA通用助手基准.md`：答案不应出现在语料明文中）；蜕变测试综述（`references/SEforLLM/summaries/04-蜕变测试与LLM双向赋能综述.md`：从抽象模式动态生成测试以防泄漏）。一致点：我们的三次污染事故是该组文献警示的现场重演。

**1-6 独立复核能抓住实现方的疏漏。** 实验与发现：评审闭环首次完整运行中，评审方（B）复审"修复提交"后发现历史修复实际只落实了承诺的三分之一（12 项应答承诺未兑现）；应答环节（A）还自己检出评审卡的"未发现问题"清单里有 5 条实为缺陷。论文观点：AutoGen（`13-AutoGen可编程会话.md`：对抗式检查者使不安全代码识别 F1 提升 8~35 个百分点）；MAS-for-SE 综述（`04-面向SE的LLM多智能体系统综述.md`：多角色辩论与交叉审查带来鲁棒性收益）；ToT（`07-思维树ToT审慎搜索.md`：生成与评审可异构混搭）。一致点：独立角色复核抓出承诺未兑现，是多评审者鲁棒性主张在代码评审场景的实证。

**1-7 输出格式需要显式契约。** 实验与发现：意见卡模板同时是评分脚本的输入契约（标题格式、单行字段、溯源写法）；不加载规则包的对照运行产出了自创格式，评分脚本解析结果为零，经适配器转换后才可评分——"转换旧产物、不改评分脚本"成为明确原则。论文观点：AgentScope（`14-AgentScope消息中心平台.md`：规则可解的错误用规则修正而不重调大模型——分层容错）；CAMEL（`11-CAMEL角色扮演协作.md`：统一输出格式防止空转与格式抖动）；Promptware（类型化输出契约）；LLMCompiler（`09-LLM编译器并行任务图.md`：用语法约束让代码直接解析模型输出）。一致点：五篇同向；适配器做法是分层容错思想在评估管线的对应物。

**1-8 缺陷分类指导流程资源配置。** 实验与发现：把缺陷分为四类（需求未进入设计/设计本身错/实现走样/测试自身缺陷）并给每类配修复路径；两个语料的类型分布差异明显——源项目（实现密集）以实现走样为主，第二个语料（文档密集、有独立设计评审）中设计错误与文档不同步合计近四成——说明类型分布可刻画项目特征、决定先投设计评审还是代码评审。论文观点：MAST（`15-MAST多智能体失败分类.md`：14 种失败模式分三大类，按类干预提升 15.6 个百分点）；Plan-and-Solve（错误类型学驱动提示设计）；GIST 技术债（`references/SEforLLM/summaries/10-生成式AI自认技术债.md`：AI 相关技术债中测试类占比从传统的 2.1% 升到 21%）。一致点："分类→干预"同构；测试类债升高同向。

**1-9 过程度量揭示方差与"量不等于质"。** 实验与发现：同一任务不同试跑的成本差 1.7 倍、意见条数差 2 倍；对照运行产出了 30 条意见但严格命中只有 3 个考题——意见多不等于找得准。论文观点：MAS-for-SE 综述（ChatDev 实测输出方差大：同任务第 2 次达标、第 10 次仍缺核心功能）；ToT（token 消耗 5–100 倍须权衡）；METR 随机对照试验（`references/SEforLLM/summaries/09-METR随机对照试验.md`：产出类度量会被"写得冗长"混淆）。一致点：方差与"量≠质"同向（幅度远小于多智能体文献值，因我们全程单智能体）。

**1-10 用大模型做裁判须分层设防。** 实验与发现：我们设计了三层结构——机械规则配对（确定性、可复算）→ 大模型在小组内判定并给理由 → 人工终审并把确认结果回流校准。坚持人工终审的理由被事实支持：第 9 次试跑的语义初判（7 个命中）被研究者逐条复核推翻为 4 个。论文观点：MAST（大模型裁判与专家一致率 94%/κ=0.77，但症状相似的不同根因可能混淆）；Promptware（裁判可能放大共同偏见，需混合评判机制）；CAMEL（先汇总再评，防止凭格式识别）。一致点：三层结构即"混合评判"的实例化；初判被推翻 3 条正是根因混淆警示的实例。

## 2. 不一致、幅度差异与待检验（四项）

**2-1 增益幅度显著小于文献典型值。** 文献：SE 智能体综述报告注入人类计划片段使通过率 26.9%→74.5%（近三倍）；τ-bench 的政策移除在某场景掉 22.4 个百分点。我们的结果：严格对照仅 3 个→4 个（11 个考题）。分歧点解释：文献的大效应建立在"裸模型面对全新任务"的基线上，而我们的对照组（不加载规则包的裸模型）本身已能答对 3 个——模型自身能力已覆盖部分模式；且规则包提炼自被评项目本身，测的是"蒸馏出的知识回注"而非跨领域迁移。这与 τ-bench 中弱生效场景（仅 4.4 个百分点）同型。**结论**：引用文献效应量必须带基线与资产-任务匹配度条件；真正的跨域检验留给 P3 的留出设计。

**2-2 欠缺"同模型多次运行投票"的对照组。** 文献：More Agents（`16-更多智能体采样投票.md`：不加角色分工的采样+多数投票即超过多种复杂多智能体方案——任何多角色增益主张应先赢过这个基线）。我们的情况：A-B 双角色闭环的增益主张尚未与"同一模型多次运行投票"的基线比较。这是实验设计缺口而非结果矛盾；已列为 P3 必补对照组。

**2-3 对大模型裁判的信任程度不同。** 文献：MAST 报告裁判与专家一致率 94%。我们的情况：坚持人工终审（初判被推翻的实例见 1-10）。分歧点解释：MAST 的高一致来自症状级标注任务；我们的语义命中判定要求根因级区分，恰是 MAST 自述的混淆高发区——不是矛盾，但提示**裁判一致率数字须按任务粒度分层引用**。

**2-4 强制性纪律的冗余风险（观察项）。** 文献：τ²-bench 观察到政策在场景不匹配时反致混淆。我们的情况：为堵"发现了问题却不立项"的漏检，我们给规则包加了强制立项纪律；首测未观察到意见冗余膨胀，但样本仅一次运行——列入 P3 观察项。

## 3. 文献未覆盖的新发现（五项，综合报告素材）

1. **评估输入状态内含答案文档的构造性污染**：区别于"模型参数里的记忆污染"（SWE-Bench 错觉所论）与"答案可被检索到"（GAIA 所防），我们发现第三种——考题的标准答案（历史评审报告）恰好在被评审的代码版本中就已合法入库，评审者读设计文档目录即可看到。已通过修订运行规程封堵（第 0.3 节局限）。
2. **迭代停止条件**：文献的自我改进循环普遍不讨论何时停止；我们因"继续在源项目上打磨规则已属过拟合、偏离研究主目标"而明确停止微迭代并转入迁移检验（P3）——把"机制验证完成后转入迁移验证"作为显式判据写入模板。
3. **人工环节的过程规范化**：人工核定/裁定是这类研究流程的必要环节但文献普遍缺其记录规范；我们建立了带固定字段（结论/依据/处置/下游影响）的人工待办清单机制，使人工处理本身可追溯、可复盘。
