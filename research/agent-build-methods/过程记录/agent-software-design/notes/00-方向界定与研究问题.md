# 方向二：界定与研究问题（讨论稿）

> 状态：草稿，作为多轮讨论的基线。带 ❓ 的条目是待讨论/待决策点。

## 0. 研究动机（2026-08-16 讨论确认）

来自实际工作：承接 Agent 开发类项目。实践观察：

- Agent 开发范式多样且持续演变，工作中常用框架为 **LangChain/LangGraph 生态**与**阿里 AgentScope**，但范式/框架如何与实际需求适配，缺少基础理论支撑。
- **核心论点（本方向的出发点）**：传统软件是把人类处理问题的流程、规则以形式化的代码逻辑表达；Agent 以 LLM 为核心组件，**一部分决策逻辑不再以形式符号化的代码表达，代码退居为"人类使用者/外部系统与大模型之间的衔接层"**。因此 Agent 作为一种软件的基本逻辑范式需要重新理解，并据此重新梳理从需求到架构设计的过程中该做什么、如何做。

## 1. 问题陈述

现有 Agent 构建讨论多停留在"范式选型"（用 ReAct 还是 plan-and-execute？用不用多 agent？）层面，缺乏从软件工程基本原理出发的系统性设计方法。本方向把 Agent 系统当作**一类"核心决策逻辑部分非形式化"的软件系统**来审视——这区别于普通概率性组件（如缓存命中、模糊匹配）：LLM 承担的是原本由规则代码承担的**决策职责**。由此重新走一遍经典软件设计的前端过程：需求梳理 → 需求描述 → 架构设计，看哪些经典方法仍然成立、哪些必须改造、改造的中间产物规范是什么。

## 2. 设计范式对比清单（初拟，❓ 待补充修正）

> 对比需落到实际工作框架上：LangChain/LangGraph 生态、阿里 AgentScope（2026-08-16 动机讨论确认）。每个范式应能回答"在 LangGraph / AgentScope 中如何表达"。

| 范式 | 核心思想 | 确定性来源 | 典型形态 |
|---|---|---|---|
| ReAct / 反应式 | 思考-行动-观察循环，模型自主决策 | 仅系统提示与工具约束 | 单 agent + 工具集 |
| Plan-and-Execute | 先规划后执行，规划与执行分离 | 计划作为中间锚点 | planner + executor |
| Workflow / 编排式 | 流程由代码固化，LLM 只做节点内决策 | 传统控制流 | DAG/状态机 + LLM 节点 |
| 多 Agent 协作 | 角色分工、消息传递 | 角色规约 + 协议 | supervisor / swarm 等 |
| SDD 式规范锚定 | 规范文档是一等公民，生成锚定 spec | 规约文本 | OpenSpec / Speckit / Superpowers |
| Harness + 插件（pi/DSH 路线） | 极简内核，能力由扩展组装 | 扩展代码 + skill 规范 | 与方向一衔接 |

❓ 这个清单的分类轴是否合适？目前的分类轴混合了"控制流归属"与"确定性来源"两个维度，可能需要先正交化。

## 3. 子问题 A：系统构成视角

**核心问题：LLM 与传统组件（代码逻辑、向量库、知识图谱、规则引擎）在一个系统中如何划界与结合？**

候选分析框架（从经典软件原理借用的视角）：

- **关注点分离**：哪些职责必须交给确定性代码（权限、资金、状态一致性），哪些适合 LLM（语义理解、非结构化转换、开放域推理）？划界依据是什么——可验证性？错误成本？
- **接口与契约**：LLM 组件的"接口"是自然语言/结构化输出，契约如何表达与校验（schema、guardrails、测试集）？与传统 API 契约的本质差异在哪？
- **不确定性管理**：传统软件通过测试与形式化方法控制行为；LLM 组件通过什么——评估集、兜底逻辑、人在环、多路校验？
- **知识组件的角色**：向量库（相似性检索）与知识图谱（结构化关系）作为 LLM 的"外存"，三者分工的架构模式有哪些（RAG、GraphRAG、agentic 检索）？与本仓库 `context-engineering/` 成果直接衔接。

## 4. 子问题 B：设计过程视角

**核心问题：为了让 LLM 有效参与设计/构建过程（AI 辅助设计、AI 生成代码），中间产物的规范需要怎样调整？**

- **需求描述文档**：传统需求文档面向人类读者；面向 LLM 消费的需求文档需要什么——更严格的术语表？显式化的验收条件？机器可检查的结构？（衔接 `sdd/` 成果：规范作为人机共同事实来源）
- **架构描述的显式化**：`architecture/Spring架构与AI自动化演进策略分析.md` 已发现隐式架构（注解、DI）对 LLM 构成理解障碍——Agent 系统的架构描述如何避免同类问题？
- **设计过程的中间产物链**：需求 → 能力清单 → 组件划分 → 接口规约 → 提示/工具实现，每一环的产物格式如何设计才能被 LLM 可靠地生成和消费？
- **验证闭环的前移**：传统设计评审靠人；LLM 参与时，中间产物如何自带可验证性（可执行的验收条件、可机检的一致性约束）？
