# 方向一：界定与研究问题（讨论稿）

> 状态：草稿，作为多轮讨论的基线。带 ❓ 的条目是待讨论/待决策点。

## 0. 研究动机（2026-08-16 讨论确认）

来自实际工作：推动团队组织级的 AI 辅助编码应用。实践观察：

- 现有 AI 编码工具（Claude Code、Qoder、Codebuddy 等）主要面向**个人开发**；团队协作层面的规范落地、知识同步、岗位衔接仍靠人工管理，缺少适合的工具和标准化方法。
- 具体项目差异很大，**机械套用统一方法论效果不好**。更可行的路径：项目启动前先梳理项目特点，针对性确定 AI 辅助的方法、规范、流程，甚至对工具做一定程度定制，再开始执行。
- 单一工具未必最优，**组合各工具的关键亮点**可能更有效——因此基于高灵活性开源框架沉淀组件、按项目快速定制，是值得尝试的路线。

由此本方向实际涉及三个研究面：**设计方法**（项目特点如何映射到 AI 应用方案）、**团队工程管理方法**（规范/知识同步/岗位衔接如何借助 agent 工具化）、**工具**（基于 pi/DSH 的组件沉淀与快速定制）。本目录的实验以工具面为切入点，但组件模型与场景分析框架的设计需为前两个面预留位置。

## 1. 问题陈述

**要研究的不是"如何用 pi/DSH 搭一个 agent"，而是"针对任意一个给定项目/场景，能否形成一套可复用的方法，使得专用 agent 的构建时间从'重新发明'降到'选配组装'"。**

类比：pi/DSH 提供了"底盘和发动机接口"，我们研究的是"车型设计规范 + 选配目录 + 装配流程"。

## 2. 载体框架的初步对比认知

| 维度 | pi（pi-mono, badlogic） | DSH（DeepSeek Harness） |
|---|---|---|
| 定位 | minimal terminal coding harness，"adapt pi to your workflows" | 可插拔 AI agent harness，官方 Web UI + headless 模式 |
| 定制机制 | extensions（生命周期事件、工具、命令、UI、provider）、skills、prompt templates、SDK（`createAgentSession()` 编程式组装） | 插件体系（cordis.patch.yml 挂载）、skill、Web 客户端插件、profile |
| 生态 | examples/ 目录含 git 集成、subagent、MCP 等扩展示例 | 插件生态活跃（dshfind、awesome-dsh-plugin、插件超市，数百个第三方插件） |
| 语言 | TypeScript | TypeScript / JavaScript 为主 |
| 倾向 | 编程式深度定制（SDK 优先） | 配置式/插件式组装（插件挂载优先） |

❓ 两个框架的定制机制差异（SDK 编程式 vs 插件配置式）本身就是研究方向的一部分：方法论是否需要对两类机制分别设计，还是可以抽象出共同层？

## 3. 核心研究问题

- **RQ1 组件模型**：可复用组件应切在什么粒度？候选抽象层：工具（tool）、扩展/插件（extension/plugin）、技能（skill，含领域知识+操作规范）、提示模板、子 agent 角色、上下文源（MCP 服务）。各层的复用性与耦合关系如何？
- **RQ2 场景分析框架**：拿到一个新场景，问哪些问题就能决定组件选配？候选维度：任务确定性强弱、工具环境（CLI/Web/API）、人机交互密度、上下文来源类型、验证闭环的可自动化程度。
- **RQ3 工作流程**：从场景描述到可用 agent 的流程如何设计？候选骨架：场景画像 → 能力清单 → 组件选配/补缺开发 → 系统提示与约束组装 → 评估集构建 → 迭代。
- **RQ4 验证与度量**：专用 agent 的"可用"如何判定？任务成功率、人工接管率、组件复用率、构建耗时（方法本身的效果指标）。
- **RQ5 方法的可迁移性**：在 pi 上沉淀的方法/组件，多大程度能迁移到 DSH 或其他 harness（如 Kimi Code、Claude Code）？方法论的框架无关部分是什么？

## 4. 与既有研究的衔接

- `research/sdd/`：SDD 框架对比中的 Superpowers（多智能体 skill 体系）就是"可复用组件"的一种形态，可作参照。
- `research/context-engineering/`：专用 agent 的上下文来源（知识图谱、API 卡片、MCP 服务）已有积累，可作为组件库中的"上下文组件"类别。
- `research/ai-coding/`：三种范式（终端原生 / IDE 集成 / 自主多 agent）对场景分析框架有参考价值。
- `research/llm-observability/`【D1+D3 交叉】：本方向动机中的"团队工程管理方法"研究面已在方向三主题 B 展开（AI 辅助开发过程的观测与量化）；专用 agent 的评估口径（RQ4）与方向三的质量观测面共享指标体系。

## 5. 候选实验场景（❓ 待选）

挑选原则：场景间差异足够大以检验方法的通用性；至少一个场景与既有研究（知识图谱/SDD）衔接以复用已有组件。**动机更新（2026-08-16）**：候选场景不限于下表，也可直接取自团队实际项目——"项目特点梳理 → 定制方案"本身就是待验证的工作流程。

1. **代码评审 agent**——输入 PR/提交，按项目规范输出评审意见（与 design/kb-app 的评审报告工作衔接）
2. **API 文档问答 agent**——基于已研究的 API 知识图谱提取成果（context-engineering 衔接）
3. **会议纪要整理 agent**——结构化信息抽取类场景（非代码场景，检验方法是否限于编码领域）
4. **文献调研 agent**——arXiv 检索 + 摘要归档（与本仓库 research 流程衔接）
5. **遗留 Spring 项目改造辅助 agent**——与 architecture 方向衔接，上下文要求最高的硬场景
6. **团队知识同步/规范落地 agent**——直接对应动机中的团队协作痛点（如 onboarding 问答、规范检查、跨岗位交付物衔接）
