## 1. 框架路线的理论定位

pi 与 DSH 代表同一条路线——**"极简内核 + 可组合扩展"的 harness 路线**，与学术框架的对照：

- 对照方向二的范式框架：pi/DSH 本身**不预设控制流范式**（ReAct 循环是内核默认，但 extensions/插件可改写循环行为），其价值恰在于把范式选择权留给定制者。这与 Hassan 的 agency/autonomy 两轴吻合：harness 提供 agency 底盘，autonomy 程度由定制决定。
- 对照 MAST 教训：harness 路线把"规范与验证"的责任交给扩展/skill 作者——这意味着**用 pi/DSH 做专用 agent 时，规范类与验证类组件不是可选项**（详见方向二 02 文档第 5 节的交叉输出）。

## 2. 组件模型的初步假设

综合 pi 的定制机制（extensions / skills / prompt templates / 自定义工具 / provider）与 DSH 的定制机制（cordis 插件 / skill / profile / Web 客户端插件），两类机制可归入统一的分层组件模型：

| 层 | pi 中的形态 | DSH 中的形态 | 复用性假设 |
|---|---|---|---|
| 行为干预层 | extensions：约 25 类事件钩子 + ExtensionAPI（注册工具/命令/快捷键/provider/UI），TypeScript 编程式（#1） | cordis 插件：服务/事件/可逆副作用三贡献 + 能力接缝（ctx.llm/ctx.tools/ctx.shell/ctx.fs/ctx.sandbox…），YAML patch 挂载（#2） | 框架 API 绑定，迁移成本高 |
| 知识/技能层 | skills（Agent Skills 标准 SKILL.md，`/skill:name` 或模型按需加载）、prompt templates（`{{var}}` Markdown） | skills（同样 `.agents/skills/SKILL.md` 标准） | 纯文本为主，天然可迁移 |
| 工具层 | 自定义工具（pi.registerTool）、MCP 需扩展自建 | 工具类插件（ctx.tools 注册，schema 自动入 prompt） | 逻辑可迁移，注册方式需适配 |
| 界面层 | TUI 定制（widgets/footer/overlay）、themes | Web 客户端插件（ConversationNodeDefinition + renderer） | 场景相关，复用性低 |
| 会话/状态层 | JSONL 会话树（id/parentId 单文件原位分支 /fork /tree），压缩可被扩展接管（#1） | 只追加 SessionEvent 日志 + "model-visible means logged" 不变量；session fork 经 ctx.sessions.fork()（#2） | ✅ 已确认（2026-08-17）：两框架均把"模型可见内容全量落盘"作为会话层不变量，分支/回放是一等操作 |

**假设 H1**：知识/技能层与工具逻辑层是跨框架可迁移的"框架无关组件"，行为干预层是"框架绑定组件"——快速定制方法的组件库应按此二分组织。待台账 #1/#2 验证。

**H1 验证结论（2026-08-17，依据 #1/#2）**：基本成立，需两点修订——
1. 知识/技能层的可迁移性得到直接证据：pi 与 DSH 采用**同一 Agent Skills 标准**（SKILL.md、`.agents/skills/` 目录），且 DSH 生态有 claude-bridge/claude-move 类插件专门做跨工具迁移——"框架无关组件"已是生态事实而非假设；
2. 行为干预层的绑定程度出现**梯度**而非二分：pi 扩展是全功能 TypeScript 编程面；DSH 插件虽同为代码，但普通用户可经 cordis.patch.yml/settings.yaml 的声明式配置完成"组装级"定制而无须写代码。组件库宜增加中间档"配置式组装组件"（profile/bundle/patch 模板）。

库内论文佐证（2026-08-17，详见 `materials/README.md`"references 库内相关论文"）：知识/技能层有 `references/ContextEngineering/09`（AI Skills 作为知识激活原语）与 `30`（Agent Skills 注册表→仓库实证）；行为干预层的变更风险有 `references/AIOS/10`（harness 高风险组件 = Provider + Context Management 层）。

## 3. 场景分析框架的初步输入

从方向二学术梳理借用的场景分型问题（映射为场景画像的检查项）：

1. 任务是否需要外部交互、反馈信号是否可验证可重试？（决定是否需要 Reflexion 式迭代组件与验证组件）
2. 任务时间跨度与状态性？（决定记忆组件的复杂度：无状态 → 外部化状态 → 记忆流）
3. 流程确定性高低？（决定控制流定制：确定 → SOP 式编排组件；不确定 → 保留 ReAct 循环 + 强工具）
4. 是否超出模型可靠自主窗口（小时级）？（决定人类检查点组件的必要性）
5. 单一 agent 是否足够？（默认是；多 agent 需显式理由 + 独立验证器）

这 5 问与"项目特点梳理"（团队、规范、岗位衔接维度）的合并（2026-08-17，依据台账 #3）——新增团队协作维度的 4 个检查项：

6. **交付稳定性约束**：团队是否用吞吐/稳定性指标（DORA 型）考核？若是，专用 agent 必须内置评审/治理组件——实证显示 AI 采纳与交付稳定性 -7.2% 相关、PR 评审耗时暴涨（[DORA 2025]）。
7. **代码库熟悉度与资历结构**：METR RCT 显示"资深开发者 + 熟悉代码库"场景下 AI 反而慢 19%，且自感知严重失真（自认快 24%）——面向此类团队的 agent 应强调验证与解释组件，而非速度。
8. **规范载体成熟度**：团队是否已有 spec-driven 流程（Spec Kit/Kiro）与仓库级 AGENTS.md 约定（6 万+项目的事实标准）？已有规范载体的团队，专用 agent 应消费而非另造规范产物。
9. **多工具分层现实**：主流实践是"Copilot 规模化兜底 + Claude Code/Cursor 高自主工作"分层组合，专用 agent 需明确自己在分层中的位置与互操作面（AGENTS.md 是当前最小公分母）。

上述实证/轶事证据强度区分见 `materials/团队级AI编码实践调研.md` 第五节：采纳率、信任剪刀差、DORA 相关性、METR RCT 为实证；工具优劣对比基本仍属观点层。

## 5. 本版本的局限

- pi/DSH 信息已完成代码级/官方文档级核实（v0.2），但 DSH 处于 developer preview，API 面仍在变动。
- 组件模型分层可能仍遗漏"上下文源"维度：pi 明确"No MCP"（以 skills 替代），DSH 则兼容 MCP——两者对上下文源的态度相反，该维度需要在组件模型中显式处理（留待讨论）。
- 团队实践证据中，工具优劣与"最佳实践"多为观点/轶事级，引用时需保持强度标注。
