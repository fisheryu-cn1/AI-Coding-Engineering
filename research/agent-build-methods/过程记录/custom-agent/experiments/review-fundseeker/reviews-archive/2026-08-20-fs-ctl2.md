### [P1] robots.txt 拉取绕过 timeout，首次访问新 host 可能无限阻塞
类型：可靠性/超时
溯源 file:line: src/fundseeker/utils/http.py:91-104（`_can_fetch`）
证据：`RobotFileParser.read()` 走 urllib 默认 opener（`URLopener`），既不读取 `self._session` 的 socket 复用，也不应用 `self.timeout`；当目标站 robots.txt 慢响应/挂起时，首次访问新 host 的整次 `get()` 会在 `_enforce_delay` 之前就阻塞住。
维度：健壮性 / 网络超时
建议：robots 拉取也走 `self._session.get(robots_url, timeout=self.timeout)`，或显式 `socket.setdefaulttimeout(self.timeout)` 再 `urlopen`；对失败用缓存占位（deny by default 或 allow by default 但记录日志）以免再次触发。

### [P1] 单次 HTTP 重试循环无总耗时预算，慢站点会导致脚本长时间挂起
类型：可靠性/超时
溯源 file:line: src/fundseeker/utils/http.py:118-150（`get`），152-179（`post`）
证据：`for attempt in range(self.max_retries + 1)` 内每次都先 `_enforce_delay` 再 `time.sleep(backoff)`，`backoff = 2**attempt + random.uniform(0,1)` 无上限；以 Eastmoney 配置（min/max_delay 0.5/1.5、timeout=30、max_retries=3）估算，单次失败请求最坏耗时 ≈ (1.5 + 30) + (1.5 + 1-2 + 30) + (1.5 + 2-3 + 30) + (1.5 + 4-5 + 30) ≈ 136s。`run_holdings` 对每个产品逐年调用，N 个产品 × M 年 × 136s 在网络抖动下会让脚本小时级挂起。
维度：超时 / 资源预算
建议：引入 `total_deadline`（请求级截止时间），超出即放弃；或对 retries 累加 jitter cap；并显式提供 4xx 不重试分支（见 P2-1）。

### [P1] `_enforce_delay` 在重试循环内反复执行，放大失败请求的等待时间
类型：行为/缺陷
溯源 file:line: src/fundseeker/utils/http.py:118-150（`get` 内循环），152-179（`post` 内循环）
证据：节流延迟本意是"礼貌抓取"间隔，但 `get()` 把 `_enforce_delay()` 放在每次重试 attempt 的开头，对一个持续失败的请求会产生 (max_delay) × attempts 的纯等待开销——`max_retries=3`、max_delay=10s 时，仅节流就累积 40s。结合 P1-2 的 backoff，单次失败请求多花近一倍时间。
维度：性能 / 设计
建议：重试分支不应再次施加基础节流延迟；建议把 `_enforce_delay()` 移到"首次成功路径"或作为外部调度器的责任，与 `backoff` 互斥。

### [P1] 缺少 socket 保活与陈旧连接回收，长跑 collect 容易卡在"半开 socket"
类型：可靠性/网络
溯源 file:line: src/fundseeker/utils/http.py:33-79（`PoliteHttpClient.__init__`，默认 `_session.mount(...)` 未带任何 socket_options）
证据：`requests.Session` 默认装载 `HTTPAdapter`，未设置 `(SOL_SOCKET, SO_KEEPALIVE)` / `(IPPROTO_TCP, TCP_KEEPIDLE|TCP_KEEPINTVL|TCP_KEEPCNT)`，未限定 `pool_maxsize`、未设 `block=True`。在 run_holdings 长跑场景下，连接池里的 socket 可能被中间 NAT/防火墙静默关闭，下次复用时表现为"握手成功但读不到响应"——`requests` 的 `timeout` 仅覆盖当前 read，无法识别对端已 RST 的半开连接，导致脚本挂起直到进程级超时。
维度：网络 / 超时
建议：自定义 `HTTPAdapter` 装载 socket_options 启用 TCP keepalive；显式设置 `pool_connections`/`pool_maxsize`；对 urllib3 增加 `retries(Retry(...))` 配置使陈旧连接自动重建。

### [P1] `run_holdings` 无全局超时/中断机制，慢产品会阻塞整个 collect --holdings
类型：可靠性/中断
溯源 file:line: src/fundseeker/runner.py:`run_holdings`（约 380-525 行；含 `for product in products:` 串行循环与 `collector.collect_holdings(...)` 调用）
证据：循环仅靠 `try/except Exception` 跳过失败产品，但 socket 级别的 hang 不会抛异常——它会在 `requests` 内部阻塞直到超时；上层又没有 SIGALRM、线程化包装或 `future.result(timeout=...)` 给单产品设硬上限。一旦 Eastmoney 或其 CDN 在某次 collect 时响应异常缓慢（即便最终不超时），整个 `fundseeker_cli.py collect --holdings` 会从分钟级放大到小时级，cron 任务相互阻塞。
维度：超时 / 可中断性
建议：用 `concurrent.futures.ThreadPoolExecutor` 分片 products（每 task 用 `future.result(timeout=per_product_deadline)`）；或在主循环外加 SIGALRM 级 deadline；并对慢产品记录到 `collection_log`（status=timeout）便于 `build_summary` 推荐。

### [P2] 4xx HTTP 错误被 `requests.RequestException` 一并捕获并触发重试
类型：行为/缺陷
溯源 file:line: src/fundseeker/utils/http.py:125-138（`get` 异常分支），159-172（`post` 异常分支）
证据：`raise_for_status()` 抛 `HTTPError`（`requests.RequestException` 子类），被外层 except 捕获后走 retry 循环；对 401/403/404 等客户端错误反复重试毫无意义，反而把"被风控/被限流"的请求反复发出，触发服务端进一步限流甚至 IP 封禁，间接造成后续请求更慢甚至挂起。
维度：健壮性 / 礼仪
建议：分离 retryable（5xx、ConnectionError、Timeout）和 non-retryable（4xx，含 HTTPError 且 status<500）异常路径，4xx 直接抛出；该问题在 `b3a0342` 提交信息中似乎已部分处理，但当前 c5ee3e3 代码仍用宽口径 `RequestException`。

### [P2] Session 与 SQLAlchemy engine 在 CLI 结束路径未显式 dispose，长跑场景连接池残留
类型：资源/缺陷
溯源 file:line: src/fundseeker/runner.py:多处 `finally: session.close()`；src/fundseeker/utils/http.py:36（`_session = requests.Session()`）
证据：`fundseeker_cli.py` 串行调用多个 task，每个 task finally 仅关闭 ORM session，但 `get_engine()` 返回的是模块级单例 engine，`requests.Session` 也常驻在 collector 实例里。OpenClaw 类调度器持续触发多次 collect 时，urllib3 pool / SQLAlchemy pool 的 FD 可能未及时回收，间接导致长跑后 socket 资源耗尽。
维度：资源泄漏
建议：在 `fundseeker_cli.main()` 退出前调用 `engine.dispose()`；为 `PoliteHttpClient` 增加 `close()`，并在 collector `__del__` 或 CLI 末尾调用。

### [P2] `run_holdings` 串行处理，未并发/分片
类型：效率/缺陷
溯源 file:line: src/fundseeker/runner.py:`run_holdings` `for product in products:`（约 400-510 行）
证据：每个产品 × N 年的 HTTP 都顺序执行，单个慢站点会阻塞其余产品。即便 Eastmoney 节流已下调到 0.5-1.5s，数百至上千基金规模下整体 wall-clock 仍可达小时级，与 P1-5 共同放大"挂起"观感。
维度：性能
建议：按 institution_code 分组后用 `ThreadPoolExecutor(max_workers=N)` 并发；每个 worker 持有独立 Session（避免共享 session 的并发问题）；与 P1-5 的 per-task timeout 配套使用。

### [P2] `run_holdings` 每个产品双 commit，且 `_ensure_security` 按行 upsert
类型：效率/缺陷
溯源 file:line: src/fundseeker/runner.py:约 430-510 行（`session.commit()` × 2 + `for row in holdings: _ensure_security(session, row)`）
证据：每个产品先 commit HoldingReport 再 SELECT id，再循环每个 holding 调一次 upsert HoldingSecurityInfo，最后再 commit。N 个产品 × 数十 holding 的情况下，DB 往返开销线性放大 collect 总耗时；DB 慢时还会让 P1-5 的"挂起"更容易显现。
维度：性能
建议：`_ensure_security` 改为 collect 一次 `(asset_code, market, ...)` 的批量 `insert(...).values([...]).on_conflict_do_nothing()`；HoldingReport insert 使用 `RETURNING id` 拿 id，省掉一次 commit + SELECT；holdings/allocations/summary 合并到一次 commit。

### [P2] `run_holdings` 异常吞掉，失败产品无诊断信息
类型：可观测性/缺陷
溯源 file:line: src/fundseeker/runner.py:`for product in products: try: ... except Exception: skipped_products += 1; continue`
证据：异常被裸 `except Exception` 吞掉，仅累加 skipped_products；`build_summary` 也没有专门的 timeout/skipped 区分，运行结束后用户无法定位"为何 holdings 报告少了几条"，不利于事后排查"挂起"是否因部分产品异常导致。
维度：可观测性
建议：用 `logging.getLogger(__name__).warning("holdings failed for %s: %s", product.product_code, exc)` 或写一条 status=skipped 的 `collection_log`；`build_summary.recommendations` 增加"超时/失败产品清单"段落。

### [P3] 子类在 `__init__` 之后直接覆盖 `self.http.min_delay/max_delay`，绕过原构造时的 max>=min 校验
类型：代码健壮性
溯源 file:line: src/fundseeker/collectors/eastmoney_holding.py:39-41；src/fundseeker/utils/http.py:42-44
证据：`HoldingCollector.__init__` 已经做了 `self.max_delay = max(self.min_delay, float(max_delay))`；但 Eastmoney 覆盖时直接赋值 `self.http.min_delay = 0.5; self.http.max_delay = 1.5`，若调用方传入 `min_delay=2.0, max_delay=0.5` 这种非法组合，`_enforce_delay` 里 `required = random.uniform(min_delay, max_delay)` 仍能运行但语义反向。
维度：设计
建议：在 `PoliteHttpClient` 增加 `set_delay(min, max)` 集中校验并触发 `max = max(min, max)`；或在 `_enforce_delay` 内部把 `min/max` 缓存为 `min_delay, max(min_delay, max_delay)`。

### [P3] `_parse_market_date` 使用本地 `date.today()`，与可能跨时区的 quote_date 不一致
类型：边界一致性
溯源 file:line: src/fundseeker/runner.py:`_parse_market_date`（约 530 行）与 `run_market_quotes` 的 skip-existing 分支
证据：`date.today()` 返回本地日期，而 `MarketQuoteCollector._parse_eastmoney_kline` 解析的 `quote_date` 来自服务器响应字符串；跨时区或服务器使用 UTC 时，"近 2 天有行情品种数" 的 skip 判定可能漏掉/多算近 24h 的有效数据，影响 `build_summary` 的 market_quote_symbol_count 推荐。
维度：边界
建议：明确时区来源（UTC 或本机 TZ）并在 `_parse_market_date` 文档中固化；MarketQuoteCollector 暴露 `quote_date` 字段时同时携带 tz 信息或在比较前统一归一。
