### [P2] src/fundseeker/utils/http.py::_request_with_retries — 重试循环不再重复礼貌延迟
- 类型：实现偏离（设计正确、实现走样）→ 已纠正
- 溯源：
  - 883e8ce `src/fundseeker/utils/http.py:214-219`（修复点）
  - 883e8ce^ `src/fundseeker/utils/http.py:214-215`（修复前形态）
  - 同文件 `src/fundseeker/utils/http.py:158-165`（`_enforce_delay` 实现，验证其副作用契约）
- 原意见（内联）：「重试循环内每次重试都重复执行节流延迟 _enforce_delay，与指数退避叠加，失败请求等待时间被放大」。
- 证据（修复后）：
  ```python
  for attempt in range(self.max_retries + 1):
      # Polite delay only before the first attempt: retries already pay
      # exponential backoff below, so delaying here too would double the
      # wait on every failed request (P2, review 2026-08-20 fs 分析 §2.1).
      if attempt == 0:
          self._enforce_delay()
      ...
  ```
  - `attempt == 0` 才调用 `_enforce_delay()`；其余 `attempt ∈ {1, 2, 3}` 直接进入 try 块，失败后只走 `time.sleep(2 ** attempt + random.uniform(0, 1))`（http.py:236 / 245 / 251）。
- 维度：正确性 / RR-7c（外部系统交互时序）
- 边界回归核对：
  - 首次成功（attempt=0 命中 → return）：`_enforce_delay` 调用一次，更新 `_last_request_time`。✓ 与 883e8ce^ 行为一致。
  - 首次失败 → 退避 → 重试成功：仅在 attempt=0 触发礼貌延迟（设 `_last_request_time`），后续 attempt 直接 backoff。✓ 失败等待时间不再叠加。
  - 全部失败（所有 attempt 重试后 raise）：仅 attempt=0 调用 `_enforce_delay`；最后一次 backoff 后无额外 `_enforce_delay`。✓
  - 跨调用（同一客户端的不同 URL 之间）：下次 `_request_with_retries` 入口的 `_enforce_delay` 仍按 `_last_request_time` 衡量间隔——与 883e8ce^ 同形。✓
- 复审结论：**已修复**。条 1 缺陷本体（每次重试都执行 `_enforce_delay` 与退避叠加）已消除；首次尝试礼貌延迟语义保留；`_enforce_delay` 的 `_last_request_time` 更新副作用在 attempt=0 仍触发，不破坏跨调用间隔。
- 备注（行为变化，非缺陷）：修复后，若一轮 `_request_with_retries` 经历多次重试后失败，下一次调用入口的 `_enforce_delay` 看到的 elapsed 自 attempt=0 起算（含多次 backoff），通常已 ≥ min_delay，可能不再补睡——这是修复消除「重试内重复延迟」的预期下游效应，与「失败请求等待时间被放大」的原始诉求方向一致，不视为新缺陷。

### [P3] scripts/fundseeker_cli.py::main — `--holding-years 0` 因 `if getattr(...)` 真值判断漏过钳制
- 类型：实现偏离（钳制代码已写但守卫条件将其短路）
- 溯源：
  - 883e8ce `scripts/fundseeker_cli.py:221`（`if getattr(args, "holding_years", None):` 真值判断）
  - 883e8ce `scripts/fundseeker_cli.py:222`（被跳过的钳制赋值）
  - 883e8ce `scripts/fundseeker_cli.py:113`（`--holding-years` 仅 `collect` 子解析器持有，`init-db`/`report` 子解析器无该属性）
  - 消费链 `scripts/fundseeker_cli.py:170 / 195`（`cmd_collect` 直接透传 `args.holding_years` 给 `run_holdings(years=...)`）
- 原意见（非本次评审意见，系复审回归检查中发现）：本次评审条目之外的回归/新发现。
- 证据：
  ```python
  # scripts/fundseeker_cli.py:221
  if getattr(args, "holding_years", None):
      args.holding_years = max(1, min(int(args.holding_years), 10))
  ```
  - argparse `type=int, default=1` 接受 `--holding-years 0`，解析后 `args.holding_years == 0`。
  - Python 真值语义：`bool(0) is False`；`getattr(args, "holding_years", None)` 返回 `0`（非 None，但 falsy），`if 0:` 不进入分支，钳制语句被跳过。
  - 子命令分发意图：`getattr(..., None)` 用于在 `init-db` / `report`（无 `holding_years` 属性）下避免 `AttributeError`，并跳过钳制——但这与「值是否为 0」是独立维度，守卫把两件事耦合在一起。
  - 后果：`--holding-years 0` 在 `collect` 子命令下，`args.holding_years` 保持 `0`，原值透传至 `run_holdings(years=0)`；下游 `range(current_year - 0 + 1, current_year + 1)` 为空，不发任何 HTTP 请求（无放大危害），但实现自陈的 `max(1, ...)` 下限在该路径上不生效。
- 维度：防御性 / RR-7c（用户输入防御的「下界」与子命令派发的「属性存在性」不应共用同一真值表达式）
- 建议：将守卫改为属性存在性语义，避免与下界冲突。最小修正之一：
  ```python
  if hasattr(args, "holding_years"):
      args.holding_years = max(1, min(int(args.holding_years), 10))
  ```
  或等价：
  ```python
  years = getattr(args, "holding_years", None)
  if years is not None:
      args.holding_years = max(1, min(int(years), 10))
  ```
- 复审结论：**驳回不适用**（原 P2 上限钳制已修复），但**复审回归发现新缺陷**，单独立项。级别按错误成本定（P3：当前未造成 HTTP 放大，但实现自陈的下限在该路径上失效，与代码意图不一致；防御性缺陷而非功能性故障）。
- 备注：此条目仅在 `fundseeker_cli.py` 入口存在；`run_holding_collection.py:66` 不带 `getattr` 守卫，`--years 0` 经 `max(1, min(0, 10))=1` 正确收敛——边界行为一致。
