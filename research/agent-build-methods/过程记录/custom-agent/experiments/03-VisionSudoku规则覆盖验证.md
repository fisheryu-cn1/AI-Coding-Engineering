# Vision-Sudoku 静态规则覆盖验证（P2 深化·批次 5，2026-08-19 第 13 场）

> 定位（决策清单 §D）：Vision-Sudoku 作为**静态规则覆盖验证语料**——把该项目文档链中已记录的缺陷逐条映射到 code-review skill 规则集（v5），分"已覆盖 / 规则缺口"两类，并按问题类型判定程序归类；**不做运行级评估**（该项目无 git 历史，无法构造"缺陷尚在"的评审输入状态）。
> 方向约束（2026-08-19 研究者裁定）：发现的规则缺口**只登记、不修订**——规则泛化检验统一交 P3 冷启动，不在源项目或本语料上继续微迭代。
> 语料：v0.2 三份评审报告共 27 条结构化缺陷——12 号设计方案评审（CS×2/MJ×5/MN×5）、13 号代码审查（CR×9）、15 号变更评审（R×6）。v0.1 存档报告与 capture01 问题分析未计入（历史版本，口径另定）。

## 1. 映射口径

- **RR 覆盖判定**：该缺陷若出现在代码评审输入中，v5 规则集（含评审维度表）能否引导发现——能（指出规则/维度）＝已覆盖；不能＝规则缺口（登记归并模式）。
- **问题类型**：按 `issue-type-guide.md` 判定程序（先判测试缺陷 → 查设计文档条目三分支 → 设计参照缺位标其他）；设计错误须过**反事实论证门槛**（论证"照设计文档实现也会出错"）。

**规则缺口归并模式**（P3 输入登记，不修订）：
1. **文档链一致性类（8 条，全部来自设计评审）**：跨文档值域/命名一致性、文档内部矛盾、引用-定义完备性、需求→设计覆盖、跨层接口传递；
2. **状态与来源管理类（5 条）**：数据来源追踪（3）、状态重置完备性（1）、状态-可用性矩阵（1）——后两条是 RR-4/RR-8 的泛化方向实证；
3. **交互细节类（2 条）**：唯一触发路径、UI 状态显示一致性；
4. **其他（2 条）**：单一权威定义、新功能测试覆盖。

**问题类型分布（初判）**：实现偏离 12 / **设计错误 5**（CS-01、CS-02、MJ-03、MN-02、MN-03——均过反事实论证门槛，2026-08-19 研究者核定认可）/ **其他 5（文档同步 3[MN-01/MN-04/MN-05] + 设计未定 UI 1[CR-06] + 风格/维护 1[CR-08]）** / 范围缺口 4 / 测试缺陷 1。

## 4. 发现

1. **分层覆盖率差异显著**：代码/变更阶段缺陷 67%（10/15）可被 v5 规则引导发现，设计阶段缺陷仅 25%（3/12）——RR 规则集定位是"代码 vs 设计"审查，**设计文档自身质量检查基本不在覆盖面**。这不是 skill 的缺陷而是边界发现：设计评审规则恰好由 D2 的文档链模板承担（模板集 R4/R5 的需求覆盖矩阵、跨文档一致性检查）——**D1 skill 与 D2 模板集的分工在第二语料上获得实证**（与 kb-app 回溯案例的结论互证）。
2. **类型分布的项目间差异**（类型学作为"迭代决策仪表盘"的实证）：kb-app（实现密集）以实现偏离为主；Vision-Sudoku（文档密集 + 设计评审前置）设计错误 5 条、文档同步 5 条占比近四成——**类型分布刻画项目特征，指导评审资源配置**（文档链重的项目先跑设计评审再跑代码评审）。
3. **设计错误样例补齐**：类型指南 §2 的"设计错误 0 例"完备性声明可解除——本语料提供 5 个过反事实论证门槛的候选样例（待人工核定后回填指南，见人工待办 13-1）。
4. **RR-4/RR-8 泛化方向获得独立语料印证**（墓碑→状态重置完备；UI 声明→状态-可用性矩阵），按裁定仅登记、P3 处理。
5. 语义配对裁判校准小实验本场未执行（映射工作量占满），独立排期为下一小节。
